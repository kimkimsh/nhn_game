## 1. 무엇을 만드는가

「환도(還刀)」 — 플레이어가 공격 수단을 갖지 않고, 적 탄환을 패리로 튕겨낸 반사탄만이 유일한 데미지원인 종스크롤 탄막 액션. 5스테이지 · 보스 5기 · 업그레이드 카드 31종 · 총 플레이 타임 450초.

기능 요구사항은 전부 `docs/spec/기능_명세서.md`에 있고 **이 기획안은 그것을 하나도 바꾸지 않는다.** 이 기획안이 정하는 것은 스펙이 의도적으로 비워 둔 영역 — 기술 스택, 파일 구조, 시스템 경계, 연출 수치, 사운드 합성, 검증 방법 — 뿐이다(스펙 §0.2가 그 영역을 명시적으로 배제했다).

## 2. 확정 결정

### D-01. 소스 언어 — TypeScript (strict)

**결정.** `strict: true`. 밸런스 데이터는 `as const satisfies <Type>` 형태의 평범한 숫자 테이블로 두고, ID는 전부 union type으로 좁힌다.

**이유.** 스펙이 교차 참조하는 식별자가 63개다 — 탄환 P1~P12, 잡몹 E-A~E-I, 보스 B1~B5, 카드 N01~N14 · R01~R10 · E01~E07, 진입 형태 F-1~F-6. 구현을 여러 에이전트가 병렬로 나눠 가지면 `bullet: 'P2'`를 `'P02'`로 적는 실수가 예외 없이 조용한 런타임 버그가 된다. union type이면 그 오타가 편집 시점에 죽는다. 리서치도 같은 이유를 댄다 — "여러 AI 에이전트가 동시에 작업할 때 계약과 상태 오류를 줄인다"(`docs/research/codex_research/03_7일_제작_및_AI_에이전트_전략.md:5-16`), 그리고 스택 확정 블록이 `TypeScript (strict)`를 못 박았다(`docs/research/claude_research/00_제약_조건표_종합.md:367`).

**이 결정이 나빠지는 조건.** 밸런스 파일을 편집하는 사람이 타입 에러 메시지를 읽고 겁을 먹어 편집을 멈추면. 그때는 `config/` 아래만 타입 강제를 풀지 말고 — 강제가 이 결정의 전부다 — 대신 `config/types.ts`의 타입 이름과 필드 주석을 더 평범한 말로 고친다.

### D-02. 렌더링 — Canvas 2D, 게임 프레임워크 없음

**결정.** `CanvasRenderingContext2D` 직접 사용. Phaser · PixiJS · Three.js 전부 배제.

**이유.** 세 가지가 겹친다.

1. 리서치 최상위 판정이 그렇다. `00_제약_조건표_종합.md:195` — "바닐라 TypeScript + Canvas 2D 단일 추천. Phaser는 배제." 이 문서는 8개 리포트를 대조해 모순을 정리한 상위 판정 문서이고, `05_기술_스택_선정.md:13-17`이 남겼던 "동시 스프라이트 200개 이상이면 Phaser" 탈출구를 명시적으로 폐기했다.
2. **비주얼 계약이 이미 Canvas 2D로 쓰여 있다.** `docs/sample_image/_shared/engine.js`의 2,047줄 중 약 1,500줄이 `draw*` 함수군이고, 이것이 승인된 아트 디렉션 그 자체다. 프레임워크로 옮기면 이 코드를 전부 다시 써야 하고, 다시 쓰는 순간 승인된 그림이 아니게 된다.
3. Phaser 4는 능동적 위험이다. `05_기술_스택_선정.md:101` — v4에서 `Math.TAU`가 `PI/2`에서 `PI*2`로 바뀌었는데 **이름은 그대로다.** `:105` — "예외도 안 나고 콘솔 에러도 없고 화면 각도만 조용히 틀어진다."

**이 결정이 나빠지는 조건.** S5 W5(잡몹 20기 + 적 탄환 280 + 반사탄 240)에서 [02_아키텍처.md](02_아키텍처.md) §5의 최적화를 전부 적용하고도 60fps가 안 나올 때. 그때의 대응은 프레임워크 교체가 아니라 스펙 §14.3 T-07 — **동시 적 탄환 상한을 먼저 내린다.**

### D-03. 실행 — Vite dev server + 단일 파일 빌드

**결정.** 개발은 `npm run dev`(Vite, ES modules). 산출은 `npm run build` → `dist/index.html` 한 개 파일. JS·CSS inline, **웹폰트는 번들하지 않는다**([12_통합_계약.md](12_통합_계약.md) §3.1). 더블클릭으로 오프라인 실행.

**이유.** 요구가 둘인데 서로 반대다. "밸런스 파일 열어서 숫자 고치면 바로 보이게"는 dev server가 아니면 안 되고, "웹에 안 올리고 로컬로만"은 `file://`에서 열려야 편하다. 그런데 `file://`에서는 ES module import가 CORS로 차단된다(origin이 `null`이라 브라우저가 module fetch를 거부한다). 컨셉 이미지 목업이 `<script src>` 클래식 방식을 쓴 이유가 이것이다(`docs/sample_image/00_title/index.html:15-16`).

파일 60개 규모에서 클래식 script 방식은 전역 네임스페이스 + 태그 순서 의존이 되고, 순서가 틀리면 `undefined`가 난다. 그래서 개발과 산출을 분리한다. dev server는 로컬이므로 "웹에 안 올린다"를 위반하지 않는다.

**폰트는 처음부터 시스템 폰트 fallback이다.** 서브셋하지 않은 한글 웹폰트 2종을 base64로 인라인하면 수 MB이고, 이 프로젝트의 의존성 제한(vite·vitest·typescript·eslint 외 0개)에 서브셋 도구가 없다. 그래서 `config/ui.ts`의 폰트 스택은 목업 `tokens.css:44-46`의 목록을 값으로만 옮겨 적고(파일 자체는 이식하지 않는다 — [12_통합_계약.md](12_통합_계약.md) §3.2), 첫 항목인 웹폰트가 기기에 설치돼 있지 않으면 자동으로 다음 항목으로 내려간다. display / body / data 세 스택의 실제 목록은 [12_통합_계약.md](12_통합_계약.md) §3.1에 있다.

**그리고 그것이 되는지는 확인 항목이지 가정이 아니다.** 목업 README가 "오프라인이면 시스템 폰트로 대체되고 레이아웃은 유지된다"고 적었지만(`docs/sample_image/README.md:58`) 그 문장은 측정된 적이 없다. 웹폰트 없이 목업 15화면이 레이아웃을 유지하는지를 [09_검증_전략.md](09_검증_전략.md)의 환경 검사 항목으로 승격해 실제로 확인한다([12_통합_계약.md](12_통합_계약.md) §3.1).

**이 결정이 나빠지는 조건.** 단일 파일 빌드 결과가 16MB를 넘을 때. 이 항목이 원래 함께 적었던 "inline base64 폰트 때문에 초기 파싱이 느려질 때"는 위에서 닫혔다 — 인라인할 폰트가 없다. 폰트를 다시 넣고 싶어지면 서브셋 도구를 의존성에 추가하는 것이 먼저다.

### D-04. 시뮬레이션 — 고정 스텝 1/120초 + 스윕 충돌

**결정.** 게임 로직은 `dt = 1/120`초 고정 스텝으로 돌리고, 렌더는 `requestAnimationFrame`에서 보간해 그린다. 빠른 물체의 충돌은 스윕(이동 선분 대 원) 판정을 쓴다.

**이유.** 60Hz로는 등급 판정이 뭉개진다. 스펙 §5.3의 밴드는 GREAT `d ≤ 28` / GOOD `28 < d ≤ 48` / NOT BAD `48 < d ≤ 70`이고, GOOD 밴드의 폭은 20u밖에 안 된다. S5의 조총탄은 `760 × 1.34 = 1018 u/s`이므로 60Hz에서는 한 스텝에 **17u**를 움직인다 — GOOD 밴드 폭의 85%다. 즉 60Hz에서는 특정 등급이 표본 사이로 통째로 빠져나가 "제대로 눌렀는데 등급이 안 나온다"가 구조적으로 발생한다. 120Hz면 8.5u로 절반이 된다.

스윕 충돌은 별개 이유다. 반사탄 속도 상한은 2400 u/s이고, 120Hz에서 한 스텝 20u를 움직인다. 플레이어 코어 10u + 편전 5u = 15u이므로 **20u > 15u**, 점 표본 방식으로는 그냥 뚫고 지나간다. 스윕은 2차 방정식 한 줄이고, 리서치가 이것을 손맛의 절반이라고 부른다 — "손맛의 절반은 '절대 안 뚫린다'는 신뢰다"(`docs/research/claude_research_3/03_손맛_최상급_사례.md:239`).

**이 결정이 나빠지는 조건.** 저사양 기기에서 sim 스텝이 프레임 예산을 먹어 렌더가 밀릴 때. 프레임당 sim 스텝 상한을 5로 두고 초과분은 버린다(spiral of death 방지). 그래도 안 되면 dt를 1/90으로 올리기 전에 [02_아키텍처.md](02_아키텍처.md) §5의 렌더 최적화부터 검산한다.

### D-05. 결정론 — 시드 난수 주입, `Math.random()`·`Date.now()` 금지

**결정.** `sim/` 아래 어떤 함수도 `Math.random()`이나 `Date.now()`를 직접 부르지 않는다. 난수는 시드 RNG 인스턴스를, 시각은 누적 sim 시간을 인자로 받는다.

**이유.** 세 가지가 이것 하나에 달려 있다. ① 스펙 §14.3의 튜닝 규칙 T-01~T-07은 전부 실측을 요구하는데, 실측은 재현 가능해야 근거가 된다. ② 헤드리스 밸런스 시뮬([09_검증_전략.md](09_검증_전략.md))이 성립하려면 같은 시드가 같은 결과를 내야 한다. ③ 제출 영상 촬영 시 같은 장면을 다시 뽑을 수 있어야 한다 — 리서치가 "입력 기록/재생을 구현하라"고 명시했다(`docs/research/claude_research/03_30초_영상_전달력.md:280`).

리서치는 이 규칙을 어겼을 때의 실제 비용도 기록했다 — 상태 변경 경로가 갈라진 프로젝트에서 도메인 로직 200줄에 동기화 계층 800줄, 3일 밤 디버깅(`docs/research/claude_research/06_7일_스코프와_AI_에이전트_프로세스.md:190-210`).

**이 결정이 나빠지는 조건.** 없다. 이건 트레이드오프가 아니라 위 세 기능의 전제 조건이다. 포기하면 T-01~T-07이 측정 불가가 되고 스펙 §14의 수치가 영원히 미검증으로 남는다.

### D-06. 계층 — `config → sim → render` 단방향

**결정.** 세 계층으로 나누고 의존 방향을 한쪽으로 고정한다.

| 계층 | 담당 | 금지 |
|---|---|---|
| `config/` | 숫자와 표. 스펙의 모든 수치가 여기 산다 | 로직, 계산식, 다른 계층 import |
| `sim/` | 규칙. 판정·상태 전이·상한 | `canvas`, `document`, `window`, 색상값, 좌표 리터럴 |
| `render/` | 픽셀. sim 상태를 읽어 그린다 | sim 상태 변경 |

ESLint `no-restricted-imports`로 역방향 import를 빌드 에러로 만든다.

**이유.** 리서치가 같은 구조를 독립적으로 두 번 요구했다 — "판정 시스템은 한 책임으로 두고, 적은 판정 코드를 복제하지 않고 속성 데이터만 제공한다. **연출은 판정 결과를 구독하며 규칙을 바꾸지 않는다**"(`docs/research/codex_research_3/05_최종5개_스코어카드_CEO리뷰.md:148-150`). 그리고 이 게임에서 그 경계가 특히 중요한 이유는 스펙 §5.1의 판정 순서 규칙 때문이다 — "같은 프레임에서 패리 판정을 피격 판정보다 먼저 처리한다." 이 순서가 연출 코드 어딘가로 새어 들어가면 스펙 §5.3의 대형 탄환 GREAT가 조용히 깨진다.

**이 결정이 나빠지는 조건.** 렌더가 sim에 없는 정보를 필요로 해서 sim에 렌더 전용 필드가 늘어나기 시작할 때. 그 신호가 보이면 그 정보를 sim state가 아니라 [02_아키텍처.md](02_아키텍처.md) §6의 피드백 이벤트로 옮긴다.

### D-07. 자료 구조 — 평범한 배열 + 객체 풀. ECS 없음

**결정.** 엔티티는 평범한 객체의 배열이고, 탄환·파티클은 사전 할당 풀에서 꺼내 쓴다. Entity-Component-System 도입하지 않는다.

**이유.** 동시 엔티티 최대치가 잡몹 20 + 적 탄환 280 + 반사탄 240 = 540개다. 이 규모는 ECS의 캐시 지역성 이득이 나타나기 한참 전이고, ECS를 넣으면 스펙 §8.1의 표 한 줄이 코드 어디에 대응하는지가 흐려진다 — **이 프로젝트에서 스펙과 코드의 1:1 대응은 성능보다 비싼 자산이다.**

풀은 별개 문제로 필요하다. 초당 수백 개의 탄환 객체 생성·폐기는 GC 정지를 만들고, 정지 한 번이 프레임을 건너뛰면 그건 패리 실패로 나타난다.

**이 결정이 나빠지는 조건.** 프로파일러가 엔티티 순회 자체를 병목으로 지목할 때. 지금 예상 병목은 순회가 아니라 fill-rate이므로([02_아키텍처.md](02_아키텍처.md) §5), 그 반전이 실측으로 확인되기 전에는 손대지 않는다.

### D-08. 오디오 — Web Audio 절차 합성. 오디오 파일 0개, 라이브러리 0개

**결정.** 모든 효과음을 oscillator·noise buffer·filter·envelope로 런타임 합성한다. ZzFX·jsfxr·Tone.js 전부 쓰지 않는다.

**이유.** 스펙 §17이 사운드를 필수로 잡았고, 외부 음원은 라이선스 고지 의무를 만든다(`docs/research/codex_research/01_NAN2026_공식_요구사항.md:86-87`). 라이브러리도 마찬가지다 — MIT는 저작권 고지 유지를 요구한다(`docs/research/claude_research/09_코드만으로_만드는_비주얼과_오디오.md:801`). 그리고 필요한 분량이 작다. 같은 문서 `:802` — "함수 6개면 100줄 이하다."

**이 결정이 나빠지는 조건.** 절차적 BGM이 D5 시점에 안 끝날 때. 리서치의 중단 규칙을 그대로 쓴다 — "SFX 6종이 안 끝나면 BGM 포기"(`09:1175`). 효과음이 BGM보다 우선이다.

### D-09. 머니샷 — "한 번의 패리가 반경 70u 안의 탄을 전부 동시에 반사한다"

**결정.** 30초 영상과 게임 연출이 겨냥하는 단일 시각 사건은 **한 번의 패리가 반경 70u 안의 적 탄환 전부를 동시에 반사하는 순간**이다. 원본 컨셉이 노렸던 "한 발을 완벽하게 되받아치는 순간"은 반경 안에 탄이 하나뿐인 특수한 경우로 흡수한다.

**이유.** 스펙이 이미 공짜로 준다. §5.3 — "동일 활성 구간에 여러 탄환이 패리되면 **각 탄환이 자기 거리로 개별 등급을 받는다.**" 즉 패리 한 번이 반경 70u(§5.1) 안의 탄을 전부 반사한다. 카드 0장에서도 상시 성립하고, S5 W5의 동시 적 탄환 280발(§14.1) 밀도에서는 오히려 흔하다.

**승인된 목업이 처음부터 이것을 그리고 있었다.** 12번 화면의 제목이 「패리 성립 순간 — 5발 동시 반사」다(`docs/sample_image/README.md:51`). 비주얼 계약이 맞았고 이 결정의 이전 판이 틀렸다.

**이전 판을 죽인 것은 산수다.** 이전 정의는 "반사탄 **한 발**이 잡몹 여러 기를 차례로 지운다"였는데, 카드 없는 런에서 이 사건의 발생 횟수는 정확히 0이다 — §7.1이 "관통 | 기본 없음. **적 1기 명중 시 소멸**"이라고 못 박아서, 반사탄 한 발이 잡는 적은 정확히 1기다. 관통 카드 R02가 런에 도착할 확률도 35.9%뿐이다(레어 가중치 27/33/38/42%, 레어 10종, 슬롯 3개, 획득 4회. 같은 화면 중복 금지로 슬롯이 독립이 아니라 한 화면 제시 확률이 `3r/10`이므로 `1 − 0.919 × 0.901 × 0.886 × 0.874`, [12_통합_계약.md](12_통합_계약.md) §6). 스펙 §17이 "다수 동시 처치 | 반사탄 한 발이 여러 기를 정리한 사건이 한 번에 읽혀야 한다"고 요구한 것은 사실이지만, §7.1과 겹쳐 읽으면 그건 기본 런의 사건이 아니라 **카드가 붙었을 때의 사건**이다. 기본 런에서 매번 성립하는 것만 머니샷이 될 수 있다.

**순차 연쇄 요구는 그대로 남는다.** 리서치가 가장 많이 확산되는 시각 사건 1위로 "쌓인 것이 연쇄로 무너짐"(28건 중 9건)을 꼽으면서, **"고르다/맞추다/피하다" 계열 동사는 이것을 자동으로 얻지 못한다**고 적었다(`docs/research/claude_research_4/04_머니샷_사람들이_캡처하는_단일_시각사건.md:441`). 패리는 그 계열이다. 그리고 같은 문서 `:439`가 결정적 단서를 준다 — **"동시에 사라지면 그냥 삭제고, 순차적이어야 연쇄다."** 그래서 동시 반사와 그 처치 연출을 **약 0.04초씩 어긋나게** 낸다([06_렌더링과_게임필.md](06_렌더링과_게임필.md) §6). 0.04초 스태거는 이전 판에서 그대로 살아남는다.

R02(관통)·R01/E01(분열)·R08(파편)은 이 머니샷의 **증폭 카드**로 남는다. 없어도 성립하고, 있으면 커진다.

**이 결정이 나빠지는 조건.** 실플레이에서 한 번의 패리가 반사하는 탄이 평균 1~2발에 머물 때. 그때는 연출을 키우는 게 아니라 [09_검증_전략.md](09_검증_전략.md)의 헤드리스 리포트로 패리당 동시 반사 발수를 먼저 재고, 스펙 §14.1의 동시 적 탄환 도달치를 앞 스테이지에서 올리는 쪽을 검토한다.

### D-10. 치트 모드는 1일차부터 만든다

**결정.** 스펙 §18의 치트 모드를 후반 편의 기능이 아니라 **초기 인프라**로 취급하고, 스테이지·보스 페이즈 자유 입장을 게임 루프가 도는 즉시 붙인다.

**이유.** 스펙 §18.1이 이미 근거를 적었다 — "정상 진행으로 스테이지 5 보스에 도달하려면 약 6분이 걸리고 ... 검증 1회에 수십 분이 드는 구조를 그대로 두면 §14의 수치는 실측되지 않은 채로 남는다." 이건 개발 편의가 아니라 **밸런싱의 전제 조건**이고, 밸런싱은 앞당길 수 없는 유일한 long pole이다(`docs/research/claude_research/06_7일_스코프와_AI_에이전트_프로세스.md:112`, `:130` — "밸런싱을 앞당길 수는 없다. 대신 측정 비용을 0에 가깝게 만든다").

**이 결정이 나빠지는 조건.** 없다. 늦게 만들수록 손해가 커지는 종류의 항목이다.

## 4. 열려 있는 위험

닫지 않았고, 실측이 필요한 것들이다. 여기 없는 것은 닫혔다는 뜻이다.

### R-01. 스코프가 리서치의 7일 상한을 초과한다

리서치의 강제 스코프 상한은 "적 2종 이하, 보스 없음"이다(`codex_research/03_7일_제작_및_AI_에이전트_전략.md:83`). 현재 스펙은 잡몹 9종 + 보스 5기다.

**판단.** 의도적 초과로 간주하고 진행한다. 근거는 두 가지다. ① 그 상한은 1인 디렉터가 순차로 만드는 56시간 예산에서 나온 값인데, 이 프로젝트는 병렬 에이전트 구현을 전제로 한다. ② 잡몹 9종은 서로 다른 9개의 AI가 아니라 **`serve()` 한 함수에 파라미터가 다른 9줄**이다 — 목업 `engine.js:1814-1827`이 이미 그 구조를 증명했다. 보스도 마찬가지로 패턴 프리미티브의 조합이다.

**그래도 남는 위험.** 잡몹 종수가 아니라 **보스 5기 × 페이즈 2~4 = 총 15페이즈 × 패턴 2~3개 = 약 38개 패턴**이 실제 분량이다. [11_구현_계획.md](11_구현_계획.md)가 이것을 단계로 쪼개고, 각 단계 끝에서 잘라낼 수 있게 배치한다.

### R-02. 동시 탄환 수 대 프레임률의 실측 데이터가 없었다 — **닫혔다**

리서치 코퍼스 전체에 "탄환 N개 @ 60fps" 수치가 없었다(`claude_research/05:466`이 벤치마크 링크만 남기고 수치를 인용하지 않았다). [12_통합_계약.md](12_통합_계약.md) §10 E-18이 지시한 `probe.html`을 실제로 돌려 닫았다 — 전문은 [13_프로브_측정결과.md](13_프로브_측정결과.md).

| 측정 (n=30) | 값 |
|---|---:|
| `drawImage` lighter 85px — 중앙값 | 7.14 µs |
| — **p95** | **8.28 µs** |
| — 변동계수 | 9.8% |
| **프레임당 드로우 콜 상한 (p95 기준)** | **2,013** |
| fill-rate | 5,386 ~ 6,380 Mpx/s — 필요치 630의 **8.5~10배** |
| 1×1 스프라이트 | 4.6~5.0 µs — **비용의 70~76%가 픽셀과 무관** |

**D-02(Canvas 2D)는 유지된다.** `t = 7.33µs`가 E-18의 세 판정 구간 중 가운데에 떨어졌다 — GPU 경로가 살아 있고(ANGLE / Intel Iris Xe, 소프트웨어 래스터라이저 아님) 상한이 게임 규모와 같은 자릿수다.

**대신 두 가지가 바뀌었다.** ① 비용의 **70%가 픽셀과 무관한 호출 고정비**(1×1 스프라이트도 4.96µs)라서, fill을 줄이는 최적화는 이 게임에서 값을 하지 않는다 — [06_렌더링과_게임필.md](06_렌더링과_게임필.md) §3.6이 "호출 수보다 fill이 위험하다"고 적었던 전제가 뒤집혔다. ② 기획안 예산 **2,668**이 실측 상한을 **33% 초과한다**(잠정 — [13](13_프로브_측정결과.md) §1-B). **굽기 둘을 다 넣어야 1,990으로 겨우 1.1% 아래**다 — 잡몹 굽기가 −480이 아니라 −392이기 때문이다(글로우와 HP 바는 못 굽는다). **−1.1%는 변동계수 9.8% 안이라 통과 선언이 안 되므로 N-스윕으로 상한을 확정하는 것이 먼저다.** 이 숫자는 네 번 바뀌었다 — 단일 실행 2,274 → n=30의 2,013 → 예산 누락과 굽기 과대평가 보정 → §7.5-정정의 수렴선 제거. **n=1로 판단하면 안 되는 이유가 그만큼 나왔다.**

### R-03. B3·B5의 추정 DPS 여유가 과도하다

스펙 §14.4 검산표에서 B3는 +169%, B5는 +117%다. 스펙 자신이 "실제로는 반사 각도가 맞지 않아 빗나가는 비율이 크므로 명중률 축을 실측한 뒤 HP를 재산정한다"고 적었다(`기능_명세서.md:1141`).

**대응.** 헤드리스 시뮬이 반사탄 명중률을 측정 항목으로 뽑는다([09_검증_전략.md](09_검증_전략.md)). 추정치로 HP를 건드리지 않는다.

### R-05. 탄환 P3 편전은 스펙 안에 사용처가 없다

§6.1의 표에 한 줄(반경 5u, 속도 880 u/s, BRP 12, "최고속. 발사 예비동작이 가장 짧다")이 있고 §7.4가 "고속탄(P2·P3)을 반사 — 사실상 불가"라고 예시로 언급할 뿐, **§8.1의 어느 잡몹 `사용 탄` 열에도, §10의 어느 보스 패턴에도 배정된 적이 없다.** 목업 15화면에서 한 번도 스폰되지 않은 것은 목업의 누락이 아니라 스펙에 발사원이 없기 때문이다.

**대응.** 스펙을 바꾸지 않으므로 `config/bullets.ts`에는 정의를 그대로 남기고, 발사원 없이 둔다. 정의가 있고 사용처가 없는 것은 비용이 0이다. 다만 이건 스펙의 빈칸이므로 결정이 필요하면 알려 달라 — S5의 어느 웨이브에 넣거나 B5 페이즈 1에 붙이는 것이 자연스럽다.

### R-04. 심사 배점표가 비공개다

NAN 2026의 공식 배점표·심사위원 명단·축별 가중치는 어느 문서에서도 확인되지 않았고, 약관이 "세부 평가 내용을 공개하지 않을 수 있다"고 규정한다(`codex_research_3/01_공식요건과_선정전략.md:46`). 리서치가 "재미 40점, AI 30점" 같은 역산 전략을 근거 없음으로 기각했다(`:48`).

**대응.** 이 기획안은 배점을 역산하지 않는다. 대신 확인된 사실만 제약으로 쓴다 — 제출물 5종, 영상 30~60초, 실제 플레이 화면, AI 활용 문서 필수.

## 4-C. 규칙끼리 부딪히는 자리 1건 — S-04

§4-B의 셋은 스펙이 **같은 값을 두 번 다르게 적은** 경우다. 아래는 종류가 다르다. 값은 전부 맞는데 **두 규칙이 동시에 성립할 수 없는 좌표가 실재한다.** 실측이 아니라 산수로 나오므로 여기 적는다.

### S-04. HR-09 억제 거리가 보스전에서 플레이어 영역의 30%를 무발사 구역으로 만든다

**세 값이 부딪힌다.** 전부 §3.1과 HR-09에서 그대로 읽은 것이다.

```
플레이어 이동 영역   y ∈ [620, 1830]        §3.1
보스 정위치 영역     y ∈ [180,  520]        §3.1  (HR-08이 상단 고정을 요구한다)
최소 중심간 거리     620 − 520 = 100u
억제 거리            실제 탄속 × 0.45초      HR-09 · §6.2
```

**100u는 보스가 쓰는 어떤 탄종의 억제 거리보다도 작다.** 가장 느린 축까지 내려가도 그렇다.

| 보스·탄종 | 실제 탄속 | 억제 거리 | 100u와 비교 |
|---|---:|---:|---|
| B4 대통 폭탄 P7 (S4 ×1.24) | 322 u/s | **145u** | 억제된다 |
| B3 함포탄 P6 (S3 ×1.16) | 348 u/s | 157u | 억제된다 |
| B2 참격파 P5 (S2 ×1.08) | 454 u/s | 204u | 억제된다 |
| B1 조총탄 P2 (S1 ×1.00) | 760 u/s | 342u | 억제된다 |
| **B5 조총탄 P2 (S5 ×1.34)** | 1018 u/s | **458u** | 억제된다 |

가장 넓은 B5 기준으로 보면, 보스가 발사하려면 플레이어가 `520 + 458 = y ≥ 978`에 있어야 한다. 플레이어 영역이 620에서 시작하므로 **`y ∈ [620, 978]`의 358u 띠가 무발사 구역**이고, 이는 세로 이동 폭 1,210u의 **29.6%**다. 보스 바로 아래, 즉 반사탄을 가장 짧은 거리로 되돌릴 수 있는 자리가 통째로 여기 들어간다.

**발사원이 퍼진 패턴은 덜 걸리고, 한 점에서 나오는 패턴은 통째로 걸린다.** HR-09는 발사 하나하나에 걸리므로 발사원이 여러 개면 가까운 것만 억제되고 먼 것은 나간다. B1 일제사격은 `sourceSpread: 560`이라 바깥 발사원까지 `√(280² + 100²) = 297u`인데 S1 억제 거리가 342u여서 **그것도 억제되지만**, 스테이지·패턴에 따라서는 일부만 막힌다. 반면 **`sourceSpread: 0`이거나 `origin: 'boss'`인 패턴은 전부 한 점에서 나오므로 예외 없이 전멸한다** — B1 페이즈 1의 엄폐 전진, B1 페이즈 2의 난사, B5 페이즈 1의 난사 강화가 그렇다. 아래 세 결과는 그 「전멸하는 패턴이 현재 페이즈의 전부일 때」 성립한다.

**결과가 셋이고 셋 다 나쁘다.**

| # | 무슨 일이 나나 |
|---|---|
| 1 | 보스가 아무것도 안 쏜다. 그런데 HR-01상 플레이어의 유일한 데미지원이 반사탄이므로 **탄이 없으면 플레이어도 보스를 못 깎는다.** 이득을 보는 악용이 아니라 양쪽 다 멈추는 교착이다 |
| 2 | **HR-03(적 탄환 0인 상태 2.0초 초과 금지)이 정상 플레이 중에 깨진다.** [02](02_아키텍처.md) §8과 [05](05_시스템_설계.md) §13의 `sim/guards.ts`가 dev 빌드에서 오류를 던지고, [09](09_검증_전략.md) §4의 헤드리스는 런을 `guard-violation`으로 중단한다 |
| 3 | 2번이 밸런싱을 막는다. T-01·T-02의 보스 격파 시간은 헤드리스가 재는데([11](11_구현_계획.md) P7-2), 시뮬의 플레이어 정책이 저 띠에 들어가는 순간 측정이 숫자 대신 중단으로 끝난다 |

**스펙의 자체 답이 이 자리를 안 덮는다.** §6.2가 "근접 위협은 이 규칙에 걸리지 않는 수단(E-C·E-D의 본체 접촉, 보스 돌진)이 담당한다"고 적었지만, **B1 페이즈 1(일제사격 · 엄폐 전진)과 B5 페이즈 1(총력 일제사격 · 난사 강화)은 전부 P2 직선탄이고 돌진 패턴이 없다.** 그 두 페이즈에는 근접 답이 아예 없다.

**진짜 고침은 스펙 개정이고, 셋 중 하나다** — ① §3.1의 플레이어 상단 경계를 620에서 980 근처로 내린다, ② 보스 정위치 영역을 위로 올린다, ③ 모든 보스 페이즈에 근접 답(돌진 또는 접촉)을 하나씩 넣는다. **셋 다 스펙 §3.1 또는 §10을 고치는 일이라 이 기획안이 할 수 없다**([01](01_설계_결정.md) §1 — 기획안은 스펙을 바꾸지 않는다).

**그때까지의 구현 규칙 — 이것이 덮는 것과 안 덮는 것을 명시한다.**

| 항목 | 규칙 |
|---|---|
| 발사 | HR-09를 그대로 적용한다. 억제된 보스 발사는 [05](05_시스템_설계.md) §8.2대로 그 패턴 안에서 건너뛴다 |
| HR-03 가드 | **살아 있는 모든 발사원이 HR-09로 억제된 상태**인 동안은 `world.emptyBulletSec` 누산을 멈춘다. 소강 3초·보스 격파 연출과 같은 면제 처리이고, 면제가 걸린 사실을 리포트에 남긴다([09](09_검증_전략.md) §2.4의 면제 구간 표에 행을 추가한다) |
| 헤드리스 정책 | 시뮬의 플레이어 정책은 보스전에서 `y ≥ 1000`을 유지한다. **이 제약을 리포트 머리에 찍는다** — 측정이 플레이어 영역의 30%를 안 밟고 나온 숫자라는 사실이 숫자와 같이 다녀야 한다 |
| 덮지 못하는 것 | **사람이 저 띠에 들어가 만드는 교착은 그대로 남는다.** 가드가 안 던질 뿐 게임은 여전히 멈춘다. 이건 스펙 개정 전에는 못 고친다 |

**이 항목은 닫힌 것이 아니라 소유자 판단 대기다.** §4의 열린 위험 목록과 같은 지위이며, 판정이 나오면 위 구현 규칙을 지운다.

| AI 활용 문서 | 도구 / 구조 / 프롬프트 / 활용 내역 / 외부 에셋 출처 | 외부 에셋 0개가 이 문서를 짧게 만든다(D-08, 그리고 폰트는 D-03) |
| 별도 유료 라이선스 없이 실행 | — | 의존성은 Vite · TypeScript · Vitest · ESLint 넷뿐 (D-03 · [11](11_구현_계획.md) §2) |
