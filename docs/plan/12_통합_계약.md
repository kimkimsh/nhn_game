# 12. 통합 계약

문서 01~11은 병렬로 쓰였고, 그 결과 **서로 반대 방향을 지시하는 자리가 생겼다.** 이 문서가 그것들을 한쪽으로 확정한다.

**이 문서가 다른 모든 문서를 이긴다.** 아래 판정과 어긋나는 서술이 01~11 어딘가에 남아 있으면 그것은 오류이고, 이 문서가 정답이다. 각 판정은 해당 문서에도 반영했다.

판정 근거의 우선순위는 셋뿐이다.

1. `docs/spec/기능_명세서.md` — 규칙과 수치
2. `docs/sample_image/` — 외형
3. 둘 다 침묵하면, 그 자리에서 가장 적은 것을 잃는 쪽

## 1. 문서간 상충 — 확정

### C-01. 탭 포커스 상실 시 자동 일시정지 — **한다**

| 문서 | 주장 |
|---|---|
| 08 §10.5 | 자동 일시정지하지 않는다. "§14.3 실측 중에 예상치 못한 정지를 끼워 넣어 측정을 흐린다" |
| 09 §6 E-02 | 탭을 벗어나면 즉시 자동 일시정지, 복귀 시 카운트다운 후 재개 — **합격 기준** |

**확정: 09가 이긴다. 자동 일시정지한다.**

08의 거부 근거가 성립하지 않는다. §14.3의 실측은 헤드리스([09](09_검증_전략.md) §4)에서 도는데 거기엔 `requestAnimationFrame`도 탭도 없다. 브라우저 플레이의 자동 일시정지가 헤드리스 측정을 흐릴 경로가 없다.

그리고 09 §6은 09 §7.3의 완료 게이트 4단계다. 08대로 만들면 **게이트가 영구 빨간불이 된다.**

동작 사양:

```
document.visibilityState === 'hidden'  →  즉시 일시정지 (§13.4와 같은 정지)
복귀                                    →  3 · 2 · 1 카운트다운 후 재개
```

카운트다운 중에는 입력을 받지 않는다. 탭을 벗어난 동안 흐른 실시간은 sim에 전달되지 않는다 — `loop.ts`의 `realDt` 상한 0.25초([02](02_아키텍처.md) §1)가 이미 이것을 막지만, 일시정지가 그보다 먼저 걸린다.

### C-02. 카드 선택·결과·일시정지 화면의 배경 — **전투 프레임을 그린다**

| 문서 | 주장 |
|---|---|
| 06 §1.9 | `BG.void`(engine.js:1651-1654)를 세 화면 배경으로 그대로 이식 |
| 08 §1 | 세 화면 모두 전투 프레임을 배경으로 그리고 딤을 얹는다 (카드 0.86 / 결과 0.78 / 일시정지 0.9) |

**확정: 08이 이긴다. 전투 프레임 + 딤.**

승인된 목업이 그렇게 그렸고(`11_card_select/scene.js:183`), 08이 이유까지 적었다 — 런이 이어지고 있다는 사실 자체가 화면의 정보다. `BG.void`는 목업에서 **어느 화면도 쓰지 않는 폴백**이다([10](10_스펙_목업_불일치.md) D군 참조).

`BG.void`는 이식하지 않는다. 그 자리는 스테이지 배경 함수가 없을 때의 방어용이었고, 실게임에는 언제나 현재 스테이지가 있다.

### C-03. 타이틀 어트랙트 루프 — **자동 패리가 아니라 입력 재생**

| 문서 | 주장 |
|---|---|
| 06 §1.10 | `autoParry()` 폐기. "이 함수가 남으면 '자동 패리'라는 규칙 밖 경로가 코드에 상주하게 된다" |
| 08 §6 | 타이틀은 `play.ts`와 같은 `sim/` 스텝을 돌리고, 입력만 차단하고 **패리를 자동 정책으로 대신 넣는다** |

**확정: 둘 다 아니다. 기록된 입력을 재생한다.**

두 문서가 각각 옳은 것을 지키려다 충돌했다. 06은 규칙 밖 경로를 막으려 하고, 08은 타이틀에서 실제 게임이 도는 것을 보여 주려 한다. 셋째 답이 둘 다 만족시킨다.

```
dev/capture.ts 가 이미 입력 기록·재생을 소유한다 ([03] §1, [09] §4)
D-05 의 결정론이 같은 시드 + 같은 입력 → 같은 결과를 보장한다 ([01] D-05)
   ↓
타이틀 어트랙트 = 미리 녹화한 30초 입력 + 고정 시드의 재생
```

얻는 것이 셋이다. ① 자동 패리라는 규칙 밖 경로가 코드에 없다. ② 타이틀에서 도는 것이 진짜 플레이라서 §17의 어떤 신호도 가짜가 아니다. ③ **그 녹화가 곧 제출 영상의 소스다** — 따로 만들 것이 하나 줄어든다.

녹화 파일은 `src/screens/title-attract.ts`에 입력 배열 리터럴로 박아 둔다. 외부 파일을 읽지 않으므로 D-03의 단일 파일 빌드를 깨지 않는다.

**소유자: P6-2.** 녹화 자체는 P7에서 만든다 — 그전까지 타이틀은 정적 화면이다.

### C-04. 구울 탄환 스프라이트 — **30장**

| 문서 | 주장 |
|---|---|
| 02 §5.2 · 11 P1 | 12종 × 소유자 2 = 24장 |
| 06 §3.1 | 패리 가능 10종 × 3상태 = 30장 |

**확정: 30장.**

06의 유도가 맞다. P9 화염 장판과 P12 관통 대창은 `drawBullet`의 shape 분기에 case가 없고(engine.js:202-269) §6.1상 반사탄이 되지도 않으므로 탄환 스프라이트가 아니다 → 12 − 2 = 10종. 그리고 반사탄은 자해 유예 0.15초 동안 **적색 rim이 없다**(§17이 요구한 유예 구분, [06](06_렌더링과_게임필.md) §5.3) → 상태가 2가 아니라 3이다.

`10 × 3 = 30`.

여기에 글로우 스프라이트 13색이 별도로 붙는다([06](06_렌더링과_게임필.md) §3.1). **P1 게이트의 산출물은 탄환 30장 + 글로우 13색이다.**

### P1이 P2보다 먼저인 문제

11 §1의 단계 순서는 P1(성능 스파이크) → P2(설정 데이터)인데, P1의 소유 파일이 P2의 산출물을 필요로 한다 — 탄환 `shape`·`radiusU`(P2-3), 글로우 색 목록(P2-12a), 폰트 리터럴(P2-12b), 플레이필드 좌표(P2-1).

**확정: P2-0 · P2-1 · P2-3 · P2-12a · P2-12b를 P1 앞으로 옮긴다.**

**`config/difficulty.ts`(P2-5)는 앞으로 당기지 않는다.** P1이 그 파일에서 읽을 값은 S5의 동시 적 탄환 상한 280 한 칸뿐이므로, **스펙 §14.1에서 직접 읽고** P2-5가 나온 뒤 참조를 그쪽으로 옮긴다. 한 칸 때문에 `difficulty.ts` 전체를 선행으로 만들면 P2b가 그만큼 얇아지고, `progression.ts`·`scoring.ts`까지 함께 끌려온다.

`config/`는 로직이 없어서 성능 스파이크를 지연시키지 않는다. 이 네 작업은 값을 옮겨 적는 일이고, P1이 그 값을 읽는다. 나머지 P2 작업 8개는 P1과 병렬로 돈다.

새 순서:

```
P0  뼈대
P2a P2-0 · P2-1 · P2-3 · P2-12          ← P1이 읽을 값만 먼저
P1  성능 스파이크  ★게이트               ← P2b와 병렬
P2b P2-2 · P2-4 ~ P2-11 · P2-13
P3  코어 + 최소 루프  ★게이트
P4  렌더 이식
P5  전투 시스템
P6  화면 · 오디오 · 치트
P7  밸런싱과 검증
```

### 3.1 폰트 — 시스템 폰트 fallback을 기본으로 한다

D-03이 이미 "inline base64 폰트 때문에 초기 파싱이 눈에 띄게 느려질 때"를 이 결정이 나빠지는 조건으로 적었다. 서브셋하지 않은 한글 웹폰트 2종을 base64로 인라인하면 수 MB이고, P0의 의존성 제한(vite·vitest·typescript·eslint 외 0개)에 서브셋 도구가 없다.

**확정: 웹폰트를 번들하지 않는다.** `config/ui.ts`의 폰트 스택은 목업 `tokens.css:44-46`을 그대로 쓰되, 첫 항목인 웹폰트가 없으면 자동으로 다음으로 내려간다.

```
display  "Gowun Batang", "Nanum Myeongjo", "Apple SD Gothic Neo", serif
body     "IBM Plex Sans KR", "Pretendard", -apple-system, "Segoe UI", system-ui, sans-serif
data     "IBM Plex Mono", ui-monospace, "SF Mono", Menlo, Consolas, monospace
```

목업 README가 이미 "오프라인이면 시스템 폰트로 대체된다 — 레이아웃은 유지된다"고 적었다(`docs/sample_image/README.md:58`). 그 주장을 [09](09_검증_전략.md)의 환경 검사 항목으로 승격한다 — **웹폰트 없이 15화면이 레이아웃을 유지하는지 실제로 확인한다.**

폰트를 넣고 싶어지면 그때 서브셋 도구를 의존성에 추가하는 것이 순서다. 지금 넣으면 D-03이 이름 붙인 위험이 실현된다.

### 3.2 `tokens.css`는 이식하지 않는다

색의 단일 소스가 둘이 되면 안 된다. [03](03_파일_구조.md) §7과 [04](04_밸런스_데이터_설계.md) §11이 `config/palette.ts`를 단일 소스로 정했고, [08](08_화면과_UI.md)이 여러 곳에서 `tokens.css`를 인용한 것은 목업을 읽은 흔적이다.

**확정: `config/palette.ts`가 유일한 색 소스다.** 게임은 canvas에 그리므로 CSS 변수를 읽을 일이 없다. 필요한 CSS는 페이지 셸(body 배경, 캔버스 레터박스)뿐이고 `index.html`에 인라인한다.

08이 `tokens.css:NN`을 인용한 자리는 전부 `config/palette.ts`의 같은 값으로 읽는다.

### 3.3 스테이지 진입 연출 — 새 화면이 아니라 `play.ts`의 상태

[06](06_렌더링과_게임필.md) §3.3이 배경 정적 레이어(8.3MB, S2 기준 path op 약 350개)를 "스테이지 진입 연출 중"에 굽고 "그것이 전투 첫 프레임이 되면 안 된다"고 적었는데, [08](08_화면과_UI.md) §1의 화면 목록 7개에 그 연출이 없다.

**확정: 새 화면을 만들지 않는다.** `screens/play.ts`가 `entering` 상태를 갖는다.

```
play.ts 상태
  entering   스테이지명 표시 1.2초. 이 동안 배경을 굽는다. sim 정지
  combat     정상 진행
  lull       소강 3초 (§9.1)
  boss       보스전
  clear      클리어 연출
```

`entering` 1.2초는 보스 페이즈 전환 연출(§10.1)과 같은 길이다. 굽기가 그보다 오래 걸리면 굽기가 끝날 때까지 연장한다 — 8.3MB 오프스크린 fill은 수십 ms 수준이라 실제로는 항상 1.2초가 먼저 끝난다.

**08 §6이 금지한 "검은 화면 → 페이드 인"과 충돌하지 않는다.** 금지 대상은 **첫 페인트 전의 도입**이고, 이건 이미 어트랙트 루프가 돌고 있는 상태에서 스테이지로 넘어가는 전환이다.

## 4. 컴파일되지 않는 예제 — `BossPattern` 확정

[04](04_밸런스_데이터_설계.md) §8.2의 `boss-1-johong.ts` 예제가 같은 문서 §8.1의 union에 대해 컴파일되지 않는다. 실측 오류:

```
error TS2353: Object literal may only specify known properties,
  and 'name' does not exist in type '{ kind: "volley"; … }'.
error TS2322: Type '"summon"' is not assignable to type
  '"volley" | "spread" | "ring" | "arc" | "charge" | "mortar" | "barrage" | "lance"'.
```

**확정 — 세 가지를 union에 반영한다.**

1. `name: string`을 **모든 패턴의 공통 필드**로 올린다. 페이즈 패턴 배열을 읽을 때 이름이 없으면 어느 패턴인지 알 수 없고, 치트 메뉴와 디버그 오버레이가 이 이름을 표시한다.
2. `volley`에 `speedMul?: number`를 추가한다. §10.2 페이즈 2 일제사격 강화가 "탄속 ×1.1"을 요구한다.
3. `summon`을 9번째 kind로 정식 등재한다. §10.2 연막 돌격(E-D 4기 진입)과 §10.4 화공선 3척이 쓴다 — **두 곳이므로 프리미티브 자격이 있다**([04](04_밸런스_데이터_설계.md) §8의 자체 기준).

```ts
type BossPatternBase = { name: string };   // 모든 패턴이 갖는다

export type BossPattern = BossPatternBase & (
  | { kind: 'volley'; bullet: BulletId; count: number; tellSec: number;
      intervalSec: number; repeat: number; aim: 'player' | 'down';
      sourceSpread: number; speedMul?: number }
  | { kind: 'spread';  … }
  | { kind: 'ring';    … }
  | { kind: 'arc';     … }
  | { kind: 'charge';  … }
  | { kind: 'mortar';  … }
  | { kind: 'barrage'; … }
  | { kind: 'lance';   … }
  | { kind: 'summon'; enemy: EnemyId; count: number; formation: FormationId }   // ← §10 E-09가 삭제했다
);
```

**이 블록은 §10 E-08~E-10이 다시 고쳤다.** 최종 형태는 `summon`이 빠지고 `lance`가 `sim/lance.ts`로 나가고 `parallel`이 들어온 **8종**이다 — §10 E-09의 계산표를 보라. 위 블록은 그 판정이 무엇을 뒤집었는지 읽기 위해 남겨 둔다.

### 4.1 `boss-runner`의 exhaustiveness

[05](05_시스템_설계.md) §8.2의 실행기 계약에 한 줄 추가한다.

```ts
default: { const _never: never = pattern; throw new Error(`unhandled ${(_never as BossPattern).kind}`); }
```

이게 없으면 union에 kind를 추가하고 해석기를 안 고쳐도 컴파일이 통과하고, 보스가 그 패턴 차례에 아무것도 안 한다 — 타입 오류 0개, 테스트 통과, 게임만 조용히 고장.

## 6. D-09 머니샷 정정 — "한 발"이 아니라 "한 번의 패리"

**[01](01_설계_결정.md) D-09가 틀렸다.** 정정한다.

기존 정의는 "반사탄 **한 발**이 잡몹 여러 기를 차례로 지운다"였는데, 스펙 규칙상 **카드 없는 런에서 이 사건의 발생 횟수는 정확히 0이다.** §7.1 — "관통 | 기본 없음. **적 1기 명중 시 소멸**".

관통 카드 R02를 얻을 확률도 낮다. 레어 가중치 27/33/38/42%, 레어 10종, 슬롯 3개, 획득 4회:

```
1 − 0.9212 × 0.9042 × 0.8896 × 0.8788 = 34.9%
```

그마저 "나오면 무조건 고른다"를 가정한 값이고, 플레이어에게 "R02가 연쇄 카드"라는 정보는 게임 안 어디에도 없다. 그리고 R02가 있어도 S5에서는 연쇄가 안 난다 — W5 편성에서 한 방에 죽는 탄은 함포탄 P6 하나뿐이다(E-A 93HP vs P2 GREAT 49). 분열 카드는 오히려 계수 때문에 아무도 못 죽인다(R01+E01 = `0.65 × 0.55 = 0.3575`, P6 GREAT조차 68).

**확정 — 머니샷은 「한 번의 패리가 여러 발을 동시에 반사하는 순간」이다.**

스펙이 이미 공짜로 준다. §5.3 — "동일 활성 구간에 여러 탄환이 패리되면 **각 탄환이 자기 거리로 개별 등급을 받는다.**" 패리 한 번이 반경 70u 안의 탄 전부를 반사한다. 카드 0장에서도 상시 성립하고, 280발 밀도에서는 오히려 흔하다.

그리고 **승인된 목업이 처음부터 이것을 그리고 있었다** — 12번 화면의 제목이 「패리 성립 순간 — 5발 동시 반사」다(`docs/sample_image/README.md:51`).

바꿀 것 셋:

1. [01](01_설계_결정.md) D-09의 문장 — "반사탄 한 발이" → "한 번의 패리가".
2. [06](06_렌더링과_게임필.md) §6.1의 연쇄 정렬 키 — "관통 반사탄의 진행 벡터 투영" → **"패리 지점 기준 각도 순(시계 방향)"**. 부채꼴로 퍼지는 반사가 그대로 순차 연쇄로 읽힌다.
3. [06](06_렌더링과_게임필.md) §6.2의 `×N` 큐 단위 — 반사탄 단위 → **패리 이벤트 단위**. 그래야 R01·E01 분열탄도 같은 큐에 들어가고 `×N`이 실제로 뜬다.

0.04초 스태거는 그대로 둔다. 리서치의 "동시에 사라지면 삭제, 순차적이어야 연쇄"(`docs/research/claude_research_4/04_머니샷_사람들이_캡처하는_단일_시각사건.md:439`) 요건을 그것이 담당한다.

R02·R01·E01·R08은 이 머니샷의 **증폭 카드**로 남는다. 없어도 성립하고, 있으면 커진다.

## 7. 가독성 — 확정된 수정 5건

이 게임의 전제는 플레이어가 혼잡한 화면을 읽고 반응할 수 있다는 것이다. 그것을 위협하는 것부터 확정한다.

### 7.1 임팩트 프레임을 레이어 6층과 7층 사이로

[06](06_렌더링과_게임필.md) §4.5의 임팩트 프레임은 화면 전체를 `C.baek` alpha 0.88로 1~2프레임 덮는데, §2의 12층 레이어 계약에 자리가 없어 정의상 최상단이 된다.

그러면 §15.1이 "상시 시각 표시"로 못 박은 10u 코어가 0.033초 사라진다. 그 사이 sim은 이미 돌고 있고(히트스톱은 0.075초에 끝났다), S5 조총탄은 `1018 u/s × 0.033 = 34u` 이동한다 — **GREAT 밴드 전체(28u)보다 크다.** 계획의 최고 효과가 다음 GREAT의 밴드 통과를 통째로 가린다.

**확정: 6층(탄환)과 7층(플레이어) 사이에 그린다.**

잔상 기제는 고대비 전면 전환이 만드는 것이라 플레이어 실루엣이 위에 남아도 그대로 얻는다. 그리고 코어·패리 원·쿨다운 링·무적 링이 흰 화면 위에 청색으로 남아 판독 기준이 유지된다.

### 7.2 반사탄 구분축 — streak를 굽지 않고, 중앙에 불투명 점을 둔다

§17이 "적 탄환과 반사탄을 못 구분하면 **게임이 성립하지 않는다**"고 적었다. 그런데 최악 프레임에서 글로우 총량이 화면의 1.8배이고 전부 `lighter`라, 적 `#e23c2e`와 황 `#f5b324`는 2~3장만 겹치면 둘 다 백색으로 클리핑된다.

남는 축 셋 중 형태는 동일(같은 `shape`), 적색 rim은 `lineWidth 2.6`(450px에서 1.1px)에 **적 탄환 본체와 같은 색**이다. 진짜로 남는 것은 additive streak뿐인데, [06](06_렌더링과_게임필.md) §1.4가 그것을 두 번 손상시킨다.

**확정 세 가지:**

1. **streak를 스프라이트에 굽지 않는다.** 목업에서 streak는 `lighter` + `hexA(C.hwang, 0.35)`인데(engine.js:184-186), 구운 스프라이트는 `source-over` `drawImage`로 나가 가산 광채가 반투명 도장이 된다. 반사탄 240발이 서로를 가린다. 발당 stroke 1회를 유지한다.
2. **P4 수리검은 streak와 본체를 분리해 굽는다.** 목업에서 streak는 `ctx.rotate` **이전에** 그려져 `spin`의 영향을 받지 않는다(engine.js:183-195 → :196). 접으면 꼬리가 탄과 함께 빙빙 돈다.
3. **반사탄 중앙에 반경 `r × 0.45`의 불투명 `#0b0d13` 점을 둔다.** additive 클리핑은 밝기를 위로만 올리므로 어두운 구멍은 어떤 더미 위에서도 남는다. 굽기 대상이라 프레임 비용 0.

### 7.3 연쇄 중 trauma 상한 0.55

[06](06_렌더링과_게임필.md) §6.2가 스스로 적었다 — 연쇄 내내 trauma가 0.6~1.0에 머문다. `shake = trauma² × 26u`이므로 진폭 9.4~26u가 0.8초 지속되는데, §4.2 자신이 "흔들림 1회의 체감 길이는 0.1~0.3초"라고 적었다. 그리고 연쇄가 끝나도 웨이브는 시간 기반이라 탄막이 계속 온다.

**확정: 링크 3 이후 trauma 가산을 +0.12 → +0.04, 연쇄 중 trauma 상한 0.55(진폭 7.9u).** 연쇄가 한 번에 읽혀야 한다는 §17 요구는 `×N` 팝업과 0.04초 스태거가 담당한다.

### 7.4 파티클 동시 생존 상한 240

[06](06_렌더링과_게임필.md) §3.7의 스트레스 씬은 파티클 200개인데 §6.2는 링크마다 28개 × 최대 20링크 = 560개를 요구하고 수명이 연쇄 길이보다 길어 전부 동시 생존한다. 게이트가 재려는 프레임이 실제 최악 프레임이 아니다.

**확정: 동시 생존 상한 240, 링크 4 이상은 28 → 12로 감쇠.** [06](06_렌더링과_게임필.md) §6.3이 이미 R08 파편에 같은 규칙(28 → 18)을 만들었으므로 새 개념이 아니다. 그리고 §3.7의 스트레스 씬에 연쇄 상태를 추가한다.

### 7.4-B 드로우 콜 예산 초과 — 상한을 옮기지 않고 그대로 둔다

§7.2·§7.4·§7.5의 세 판정이 프레임당 드로우 콜을 늘린다 — 반사탄 스트릭 +240, 파티클 상한 +40, 예비동작 수렴선 +60. 합계가 [06](06_렌더링과_게임필.md) §3.5의 2,500 상한을 넘어 **2,616(+4.6%)**이 된다.

**확정: 상한을 고쳐 쓰지 않고, 초과 사실을 그대로 기록한 채 실측한다.**

> **실측 완료 (2026-08-07).** `probe.html`을 n=30으로 돌린 결과 실제 상한은 **2,013**(p95 기준)이다([13_프로브_측정결과.md](13_프로브_측정결과.md)). 예산 2,616은 **30% 초과**다. 변동계수가 9.8%라 소수점까지 말할 수는 없지만 30%는 그 편차 밖이다.
> 그리고 이 판정이 예상 밖의 방식으로 옳았다 — **실제 상한은 2,500보다 높은 게 아니라 낮았다.**
> 2,700으로 올려 썼다면 정확히 반대 방향으로 틀렸을 것이다.
> 대응은 상한 조정이 아니라 호출 수 감축이고, **잡몹 굽기(−480) 하나로는 부족하다** — 청해파문 스트립 굽기(−286)까지 넣어야 1,850으로 통과한다.


이유가 둘이다.

**① 2,500은 측정된 적이 없다.** [01](01_설계_결정.md) R-02가 이미 적었다 — 리서치 코퍼스 전체에 "탄환 N개 @ 60fps" 실측이 없다. 2,500은 추정이고 2,616도 추정이며, 4.6% 차이는 그 추정의 오차 범위 안에 있다. 측정 없이 상한을 2,700으로 고쳐 쓰는 것은 숫자만 바꾸고 아무것도 알아내지 못하는 행위다.

**② 늘어난 셋은 성능 항목이 아니라 §17 항목이다.** 스트릭은 "적 탄환과 반사탄을 못 구분하면 게임이 성립하지 않는다"를 지키는 유일한 포화 저항 축이고, 예비동작 수렴선은 "예비동작이 배경에 묻히면 불공정한 발사가 된다"를 지키며, 파티클 상한은 오히려 개수를 **줄이는** 규칙이다. **셋 다 성능을 위해 먼저 자를 수 없다** — 자르면 스펙 요구가 깨진다.

그래서 P1 게이트가 실패했을 때의 순서에서 이 셋은 제외된다. 순서는 [02](02_아키텍처.md) §5.5가 정한 대로 스펙 §14.3 T-07 — **동시 적 탄환 상한을 먼저 내린다.** 그 다음이 글로우 스프라이트 반경이고, [06](06_렌더링과_게임필.md) §3.5가 지목한 청해파문 스트립 굽기(−286)가 그 사이에 들어간다.

### 7.5 적 발사 예비동작에 색이 아닌 축을 준다

§17 — "예비동작이 배경에 묻히면 예고 없는 발사가 아니라 **불공정한 발사**가 된다." 그런데 목업의 예비동작은 적색 계열 additive 후광이 6% 커지고 알파가 0.16→0.32로 오르는 것뿐이고(engine.js:406-409), 그것을 덮는 탄환 글로우는 fill-rate 기준 17배에 색 계열이 같다.

**확정: 총구·시위로 수렴하는 짧은 선분 3개를 추가한다.** 반경 60u → 20u, `C.baek`, `source-over`, 예비동작 길이에 맞춰 수축. 20기 × 3 stroke = 60회로 예산의 2.6%다.

색이 아니라 **형태와 운동**이 신호를 나른다. §17이 "색만으로 구분하지 않는다"고 요구한 그대로다.

## 10. 엔지니어링 리뷰 반영 — 2차 판정

§1~§9는 devex·design·외부 관점 리뷰를 반영한 것이다. 그 뒤 엔지니어링 축 리뷰가 별도로 돌았고, 앞선 셋이 전부 놓친 것들을 찾았다. 여기 확정한다.

### E-01. 1/120 고정 스텝의 근거가 틀렸다. 병목은 sim이 아니라 입력 경로다

[02](02_아키텍처.md) §2.1은 "60Hz에서는 밴드가 통째로 빠져나간다"를 근거로 들었는데 **거짓이다.** 직접 계산하면:

```
최고속 탄  P3 (S5)  880 × 1.34 = 1179 u/s
1/60초 이동           19.65u
가장 좁은 밴드 GOOD    48 − 28 = 20u        →  19.65 < 20
```

**60Hz에서도 모든 밴드에 최소 1표본이 들어간다.** §2.1이 든 예(`d = 55 → 38 → 21`)조차 세 밴드를 전부 표본하고 있다 — 건너뛴 사례가 아니다.

진짜 문제는 다른 곳이다. §1의 그림에서 `input.beginFrame()`은 `while` 루프 **밖**이라 rAF 프레임당 1회고, [05](05_시스템_설계.md) §3.1의 C4 때문에 각 발사체의 등급은 **패리가 활성화된 첫 스텝의 거리 하나**로 확정된다. 그러므로 플레이어가 등급을 고를 수 있는 해상도는 sim 스텝(8.48u)이 아니라 press edge가 확정되는 프레임 간격 — 60Hz 디스플레이에서 `1018 × 1/60 = 16.97u`다. **§2.1이 60Hz sim을 기각하며 인용한 바로 그 숫자다.**

**확정: 스텝은 1/120으로 유지하되, `core/input.ts`가 이벤트 타임스탬프를 보관하고 `screens/play.ts`가 그 타임스탬프가 속한 sim 스텝에서 press를 소비한다.**

`KeyboardEvent.timeStamp`와 `PointerEvent.timeStamp`는 `performance.now()`와 같은 타임베이스라 변환이 필요 없다. 약 15줄이고, `core/input.ts`는 [09](09_검증_전략.md) §3.6의 비결정 소스 스캔 범위(`src/sim` · `src/config` · `src/core/rng.ts`) 밖이라 D-05를 위반하지 않는다.

이걸 해야 1/120이 값을 한다. 안 하면 프레임당 sim 비용만 2배다.

§2.1의 근거 문장도 다시 쓴다. 1/120을 고르는 옳은 이유는 "밴드 도달"이 아니라 **밴드당 2표본**이다 — `20u ÷ 1179 = 1/59`가 도달 하한, `10u ÷ 1179 = 1/118`이 2표본 하한이고 1/120은 후자의 첫 지점이다. 선택은 맞고 근거만 틀렸다.

### E-02. 히트스톱이 프레임 단위로 양자화되고 sim 시간을 버린다

[02](02_아키텍처.md) §1의 `simDt = hitstopRemaining > 0 ? 0 : realDt`는 프레임 중간에 히트스톱이 끝나도 그 프레임 전체의 sim 시간을 0으로 만든다. 60Hz 실측:

| 등급 | 설계값 | 실제 정지 | 오차 |
|---|---|---|---|
| NOT BAD | 0.02초 | 2프레임 33.3ms | **+67%** |
| GOOD | 0.05초 | 3프레임 50ms | ±0% |
| GREAT | 0.075초 | 5프레임 83.3ms | +11% |

설계된 체감 비율 `1 : 2.5 : 3.75`가 `1 : 1.5 : 2.5`로 압축되고, §17이 요구한 "등급별 정지 길이 차이가 체감되어야 한다"의 가장 중요한 구간(NOT BAD ↔ GOOD)이 가장 심하게 뭉개진다. §8-3이 이 증상을 진동 진폭으로 덮으려 했는데 **원인은 clock 식이다.**

**확정: `core/clock.ts`에서 3줄로 고친다.**

```ts
const freeze = Math.min(realDt, hitstopRemaining);
hitstopRemaining -= freeze;
simDt = realDt - freeze;
```

**그리고 `budgetWindow`의 "최근 1초"가 어느 시계인지 명시한다 — sim 초다.** 이게 정해지면 §5.3의 4.16회/초와 §3.2의 0.32초/초가 둘 다 성립하지만, **오직 sim 시계에서만** 성립한다.

```
sim 시계   1초에 4.1667회, 히트스톱 4.1667 × 0.075 = 0.3125  →  0.32 통과
실시간     1주기 = 0.24 sim + 0.075 정지 = 0.315초  →  3.175회/초 (−23.8%)
T-02 전제 (성공률 50%, 평균 GOOD) →  주기 0.265초  →  성공 1.887회/실시간초
```

**§14.4가 보스 HP 산출에 쓴 2.08회/초보다 9.3% 낮다.** `config/parry.ts`의 주석과 `clock.ts`의 시그니처에 "sim 초"임을 못 박고, `4.16회/초`가 플레이어 체감값이 아니라는 사실도 같은 자리에 적는다. 이 차이는 [11](11_구현_계획.md) P7-2의 실측 대상이다.

### E-03. 선입력 버퍼와 쿨다운이 서로 다른 시계로 돈다 — 같은 문서 안의 정면 충돌

[02](02_아키텍처.md) §1은 "히트스톱 중에 누른 패리는 정지가 풀리는 순간 발동해야 한다"고 요구하는데, §3.2의 표는 "입력 접수·**버퍼**"를 계속 돈다 열에, "패리 쿨다운"을 멈춘다 열에 넣었다. 그러면 GREAT 직후 버퍼 0.12초 중 실시간 0.083초가 사라지고(**69%**), 남은 0.037초 안에 쿨다운이 끝나야 하는데 쿨다운은 얼어 있어 끝나지 않는다. **§1이 "구조적으로 불가능해진다"고 경고한 바로 그것이 일어난다.**

**확정: 버퍼 감산을 `simDt`로 바꾸고 §3.2 표에서 "버퍼"를 멈춘다 열로 옮긴다.** 실시간에 남는 것은 press edge 검출뿐이다.

### E-04. 적·보스의 피격 크기가 계획 어디에도 없다 — P3-B를 시작할 수 없다

`EnemyDef`에 `hp`·`moveSpeedUPerSec`·`shape`는 있는데 **피격 반경도 히트박스도 없다.** 목업은 잡몹에 `ENEMIES[e.type].w * 0.6`(engine.js:1874)을 쓰고 보스에는 `hitW × hitH` 박스를 쓰는데(engine.js:1872-1873), `w`는 `render/enemy.ts`가 아는 값이고 `config/`에는 없다.

**보스 박스는 보스마다 다르다.** 목업 실측 — B1 `470×290` · B2 `240×300` · B3 `860×250` · B4 `460×240` · B5 `900×260`(+ 갑판의 사무라이 본체 `220×240`). 하나를 대표값으로 쓰면 안 된다.

**B3 포문 4기는 목업에서 사각형이 아니다.** `E-I`에 `hitW`가 없어 `w × 0.6 = 57.6` 원으로 떨어진다(engine.js:434). 그런데 §10.4의 부위 파괴가 성립하려면 선체와 겹치는 영역에서 포문이 먼저 판정을 가져가야 하고(§8.3), 그건 박스가 자연스럽다. `drawEnemy`의 `port` case가 그리는 판자 사각형에서 유도하면 `96 × 63`인데 목업 원보다 세로가 좁다. **초기값으로 쓰되 P2-9 소유자가 목업 감각과 대조해 재확인한다** — 이건 스펙이 침묵하는 자리라 실측이 정한다. 즉 P3-B(`collision.ts`)와 P5-1이 **render 소유 파일에서 숫자를 읽어야만 하는 상태**로 시작한다 — [03](03_파일_구조.md) §5의 계층 규칙 위반이고 [11](11_구현_계획.md) §10.1의 소유권 분할이 무너진다.

더해서 `core/sweep.ts`는 "선분 대 원"인데 B3의 선체와 포문 4기는 사각형이라 스윕이 적용되지 않는다.

**확정: P2-0의 `types.ts`에 `EnemyDef.hitRadiusU` · `BossDef.hitBox: {wU, hU}` · `BossPartDef.hitBox`를 추가하고, P2-4 · P2-8 · P2-9의 작업 지시에 값을 넣는다.** 목업의 `w × 0.6`을 초기값으로 옮겨 적으면 된다. `sweep.ts`에 선분–AABB 판정을 함께 둔다.

### E-05. `EffectiveStats`는 카드 목록만으로 결정되지 않는다 — 카드 4장이 모델을 깬다

| 카드 | 무엇이 문제인가 |
|---|---|
| **R05 연격** | "콤보 10마다 +10%(최대 +50%)". 콤보는 매 패리마다 오르고 3초 경과·피격으로 0이 된다. §11.6 2단계의 가산 %이므로 **2단계의 곱 전체가 콤보 종속**이다. "카드 변경 시에만 재계산"하면 R05 보유 런의 `reflectDamageMul`은 첫 패리 직후부터 계속 틀리다 |
| **N13 반보 물러서기** | "빈 패리 시 쿨다운 −40%". 쿨다운을 값 하나가 아니라 **둘**로 만드는데 §11.6 8단계에 자리가 없다. 그리고 INV-1 하한이 실효를 통째로 먹는다 — 아래 표 |
| **R10 무쌍** | "성립 시 쿨다운 즉시 종료, 최소 간격 0.12초". 8단계에 없고 스냅샷에 필드가 없다. [09](09_검증_전략.md) §3.3이 R10을 스택에 넣지만 그 기제는 한 줄도 검증하지 않는다 |
| **E03 거북선 등껍질** | 스테이지 시작 시 1중 충전. **카드 변경 없이 스테이지마다 값이 바뀐다** |

**N13의 실효를 빌드별로 계산하면 이렇다.** 카드 설명의 −40%가 실제로 나오는 빌드는 하나도 없다.

| 빌드 | 활성 | INV-1 하한 | 정상 쿨다운 | 빈 패리 쿨다운 | 실효 |
|---|---|---|---|---|---|
| 기본 (N13만) | 0.15 | 0.20 | 0.24 | `0.144 → 0.20` | **−17%** |
| + N05 ×3 | 0.18 | 0.23 | 0.24 | `0.144 → 0.23` | **−4%** |
| + N04 ×3 + N05 ×3 | 0.18 | 0.23 | `0.1968 → 0.23` | `0.118 → 0.23` | **정확히 0** |

N05만으로는 0이 되지 않는다 — 정상 쿨다운 0.24가 아직 하한 0.23 위에 있어 1칸이 남는다. **정상 쿨다운까지 하한에 닿아야** 두 값이 같아지고, 그건 N04 3중첩이 함께 있어야 한다. `config/cards/normal.ts`의 N13 항목에 이 표를 그대로 주석으로 단다 — 숫자를 바꾸려는 사람이 −40%라는 표기만 보고 판단하면 안 된다.

**확정: `EffectiveStats`를 「정적 스냅샷」과 「런타임 파생」으로 가른다.**

```ts
// 런타임 파생 — 카드 목록이 그대로여도 값이 바뀐다
reflectDamageMulFor(combo: number): number      // R05
cooldownSecFor(outcome: 'hit' | 'empty'): number // N13
r10ActiveMinGapSec: number | null                // R10
shieldCharges: number                            // E03
```

§8-17의 `clamps` 계약과 같은 급으로 P5-5의 작업 지시에 시그니처를 박는다. 지금 형태로는 P5-5 · P6-3 · P6-8 · P5-8 넷이 동시에 어긋난다.

### E-06. 카드로 패리 반경이 커지면 등급 없는 고리가 생긴다

C1은 `d ≤ R`을 스냅샷의 `parryRadiusU`로 읽는데, N03(+6u ×3) + R09(+18u)면 **R = 106u**다(§11.6 상한 150u 이내). 그런데 NOT BAD 밴드 상한은 `PARRY_BANDS[2].maxDistU = 70`으로 고정이고 §11.6 6단계는 `GREAT 상한 > GOOD 상한`만 고친다. 즉 **`70 < d ≤ 106`에서 C1은 통과하는데 어느 밴드에도 안 걸린다** — 등급이 `null`이면 데미지 배수·히트스톱·점수·무적이 전부 미정의다.

그리고 [09](09_검증_전략.md) §3.5.1의 `expect(PARRY_BANDS[2].maxDistU).toBe(PARRY.radiusU)`는 §5가 `lockoutSec`에 대해 고친 실수 — **유도해야 할 것을 두 곳에 저장하고 같은지 검사하는 것** — 을 그대로 반복한 자리다.

**확정: 마지막 밴드는 `maxDistU`를 저장하지 않는다.** `maxDistU: null`이 "반경까지"를 뜻하고, `sim/stats.ts`가 스냅샷을 만들 때 `parryRadiusU`로 채운다. `guards.ts`의 밴드 순서 검사에 `bands.at(-1).maxDistU === parryRadiusU`를 넣는다.

### E-07. 스윕이 필요한 곳은 셋이 아니라 하나다

| 판정 | 1/120s 상대 이동 | 반경 합 | 스윕 |
|---|---|---|---|
| 플레이어 피격 | 반사탄 2400 + 이동 900 = **27.5u** | 코어 10 + P2 6 = **16u** | **필요** |
| 반사탄 대 적 | 2400 + 적 420 = 23.5u | 적 26~58 + 탄 5~34 ≥ **31u** | 불필요 |
| 패리 대상 탐색 | 20u | 패리 원 지름 **140u** | 불필요 |

패리 원을 한 스텝에 관통하려면 140u를 움직여야 하는데 최고속이 20u다 — **7스텝은 원 안에 있다.** 게다가 스윕은 선분 위의 **최근접 거리**를 주는데 §5.3은 "패리 성립 프레임의 거리"로 등급을 정의하므로, 패리에 스윕을 쓰면 등급이 체계적으로 GREAT 쪽으로 편향되고 스펙 의미가 바뀐다.

**확정: [05](05_시스템_설계.md) §1의 9번(패리 판정)에서 스윕을 뺀다. 10번(피격)의 스윕은 상대 변위로 한다** — `Δ = 탄환 이동 − 플레이어 이동` 선분 대 정지 원. 지금처럼 탄환 선분 대 프레임 끝 플레이어 원으로 하면 마주 보고 움직일 때 최근접이 스텝 중간에 생겨 여전히 뚫린다.

덧붙여 [02](02_아키텍처.md) §2.2의 터널링 표가 근거로 든 **편전 P3는 게임 안에 발사원이 없다**(R-05). 실재하는 최소는 P2·P10의 6u이므로 `16u < 20u`이고 결론은 서지만, 인용 예를 P2로 바꾼다.

### E-08. 보스 패턴 DSL이 스펙의 동시 실행 4곳을 표현하지 못한다

[05](05_시스템_설계.md) §8.2의 실행기 계약은 "패턴 하나가 끝나야 다음이 시작한다. 겹치지 않는다"인데 스펙이 동시 실행을 네 곳에서 요구한다.

### E-09. `summon`의 두 번째 사용처가 타입상 표현 불가능하다

§4가 `summon`을 등재하며 "§10.2 연막 돌격과 §10.4 화공선 — 두 곳이므로 자격이 있다"고 적었는데, 시그니처는 `{ enemy: EnemyId; ... }`이고 **화공선은 §8.1의 아키타입 9종 어디에도 없다.** §10.4의 화공선은 "불타는 소형선이 플레이어 조준 후 돌진, 접촉 또는 하단 도달 시 폭발 → P9 생성"이라 E-D도 아니고 별개 개체다. 즉 **summon의 실제 사용처는 B1 연막 돌격 하나**이고 §8의 자체 기준에 걸린다.

### E-14. 렌더 상태 변경이 예산 어디에도 없다 — 그리고 공짜 최적화가 둘 있다

**상태 전환.** [06](06_렌더링과_게임필.md) §3.1의 발당 시퀀스는 `setTransform → 글로우 drawImage(lighter) → 본체 drawImage(source-over)`다. 탄환 520발마다 합성 모드가 왕복하므로 **프레임당 전환 1,040회 + alpha 변경 520회**인데 두 예산 어디에도 항목이 없다. 2D canvas GPU 래스터라이저는 합성 모드가 바뀔 때 배치를 flush하므로, 이것이 드로우 콜 2,616이나 fill 10.5M px보다 먼저 병목이 될 수 있다.

**비네트.** fill 예산의 **19.7%**(2.07M px)를 먹는데 중앙 약 절반은 alpha 0이라 목적지를 안 바꾸면서 blend 비용만 낸다.

**~~확정: 구운 비네트를 사각 링 4장으로 잘라 그린다.~~ — 실측으로 철회한다.**

> **하지 않는다 (2026-08-07 실측).** 대가가 0인 것은 맞지만 **얻는 것도 0이다.**
> `fill`이 1회에서 4회가 되어 호출이 3 늘고 픽셀 0.42M이 줄어드는데, 실측상 fill-rate는
> 필요치의 10.5배로 남아돌고 부족한 것은 호출 수다([13_프로브_측정결과.md](13_프로브_측정결과.md) §4.1).
> **순손해다.** 아래 유도는 왜 검토했는지의 기록으로 남긴다.


회수량은 **0.42M px(전체 fill의 4.0%)**다. 처음 이 판정을 쓸 때 1.0M(10%)로 적었는데 과대평가였다 — 사각 띠로 건너뛸 수 있는 것은 alpha 0인 원 **안에 들어가는 가장 큰 축정렬 사각형**, 즉 내접 정사각형뿐이다. engine.js:1660에서 내부 반경이 `1920 × 0.24 = 460.8`이므로 정사각형 한 변은 `460.8 × √2 = 651.6`, 면적 424,600 px다.

`fill`을 1회에서 4회로 늘리는 대신 얻는 값이고, **대가가 0인 유일한 손잡이라는 점은 그대로다.** 더 가져오려면(약 1.28M) alpha 0.1 등고선(r = 628)에서 잘라야 하는데 그러면 10% 검은 이음매가 보인다 — 그건 공짜가 아니므로 하지 않는다.

> 호출 고정비(1×1 스프라이트도 4.6~5.0µs)로 드러났다. 전문 [13_프로브_측정결과.md](13_프로브_측정결과.md).
 1080×1920 캔버스에 85×85 스프라이트를 `lighter`로 10,000회 `drawImage`하고 총 시간을 나눈다. 의존성 0, 15줄, `npm install` 없음.

§3.5가 이미 환산식을 적어 두었다 — `16.67ms ÷ 2,500 = 6.7µs`. **이 한 숫자가 2,500이라는 미측정 상한을 직접 측정값으로 대체한다.**

```
측정 t (µs/호출)   →   실제 상한 = 16,670 / t
t ≤ 1.5µs   상한 11,000+.  2,616도 3,136도 문제가 아니다. §7.4-B 논쟁 전체가 소멸
t ≈ 6.7µs   상한 2,500.   추정이 정확했고 초과가 실재한다
t ≥ 12µs    상한 1,389.   GPU 경로가 아니다. 상한 조정이 아니라 D-02 재검토
```

같은 파일에 `fillRect(0,0,1080,1920)`를 60회 돌려 Mpx/s를 재면 §3.6의 fill 예산(초당 630M px)도 같은 자리에서 검증된다. **두 숫자, 30줄, 30분.** 이걸 먼저 하면 P1은 "될까?"가 아니라 "예측한 값이 나오는가?"를 재는 시험이 되고, 실패 시 원인이 굽기인지 fill인지 상태 변경인지를 이미 알고 시작한다.

### E-19. 테스트가 덮는 것은 「한 번의 패리」와 「카드 산수」뿐이다

모듈 27개(sim 18 + core 9) 중 테스트가 닿는 것 **8개(약 30%)**. `boss.ts` · `boss-runner.ts` · `waves.ts` · `zones.ts` · `score.ts` · `run.ts` · `enemies.ts` · `formations.ts` · `bullets.ts` · `player.ts`에 케이스가 **0개**이고, `core/` 전체도 0개다.

[09](09_검증_전략.md) §1.2가 최악 실패 모드를 "테스트 초록불 + 게임 플레이 불가"로 못 박았는데, **런이 진행되는지를 보는 테스트가 하나도 없다.**

**확정 넷:**

1. **`tests/core.test.ts` 신설** (예산 6 → 7, P3-C3). `sweep.ts`(D-04가 "손맛의 절반"이라 부른 것) · `clock.ts`(0.32초 누적 창) · `input.ts`(선입력 버퍼) · `pool.ts` · `bus.ts`가 지금 전부 무검증이다. 11 §5.1은 "각각 단위 테스트를 함께 낸다"고 지시하는데 09 §3은 "6개 파일뿐"이라 **낼 곳이 없다.**
2. **`tests/progress.test.ts` 신설** (7 → 8). 다섯 케이스로 치명 경로를 덮는다 — ⓐ 웨이브 시간 전환 + 잔존 적 유지, ⓑ 보스 페이즈 정확히 1회 전환, ⓒ `boss-runner`가 미등록 `kind`에서 던진다, ⓓ 반사탄이 B3 포문 좌표에서 본체가 아니라 포문 HP를 깎는다, ⓔ 콤보 200에서 배수 3.0.
3. **다중 패리 케이스 추가.** §6이 머니샷으로 확정한 바로 그 사건인데 §3.1의 14개 케이스가 **전부 1발짜리**다. `d = 20 / 40 / 60`에 세 발을 두고 `grades = [GREAT, GOOD, NOT_BAD]` · `hitstopSec = 0.075`(1회) · `score = 400`(1회) · `combo += 3` · `event.count = 3`을 단언하면 **한 케이스가 §5.3의 네 문장을 전부 잠근다.**
4. **HR-06 지터 테스트가 설계상 반드시 실패한다.** `frameMs` 배열의 50ms가 `MAX_STEPS × FIXED_DT = 41.67ms`를 넘어 sim 시간이 13% 어긋난다. 배열 최댓값을 41.0으로 내리고, **버리기 경로는 별도 케이스로 명시 검증한다** — 지금은 이 경로가 우연히 실패로만 나타나고, 처음 빨간불을 본 사람이 `MAX_STEPS`를 올려 spiral of death 방어를 지울 위험이 있다.

### E-20. 히트스톱 누적 단언이 상한의 존재 이유가 되는 빌드를 검사하지 않는다

§5.1의 단언은 `1/0.24 × 0.075 = 0.3125 ≤ 0.32`로 통과가 보장돼 있다. 그런데 스펙 §5.3이 상한을 만든 이유를 직접 적었다 — "**쿨다운을 더 줄이는 카드(R10·E07)를 든 빌드는 이 계산을 넘어선다. 그 경우 누적 상한이 초과분을 잘라내며, 이것이 상한의 존재 이유다.**" E07 기본 쿨다운 0.19초로 계산하면 `1/0.19 × 0.075 = 0.395 > 0.32`다.

**확정: 단언을 `applyCardStack(['E07'])`의 결과 쿨다운으로 계산하고 초과를 확인한 뒤, `clock.ts`가 실제로 절단하는지를 `tests/core.test.ts`에서 슬라이딩 창 시뮬로 검증한다.**
