## 1. 런타임 한 장

```
requestAnimationFrame(now)
  │
  ├─ realDt = now − last                     실시간 경과. 상한 0.25초 (탭 복귀 대비)
  │
  ├─ clock.advance(realDt)                   히트스톱 잔여분만큼만 sim 시간에서 뺀다
  │     ├─ freeze = Math.min(realDt, hitstopRemaining)
  │     ├─ hitstopRemaining −= freeze
  │     └─ simDt = realDt − freeze
  │
  ├─ input.beginFrame()                      키 상태 스냅샷. press edge 확정
  │                                          히트스톱 중에도 여기는 계속 돈다
  │                                          press 시각은 이벤트 timeStamp로 보관 (§2.1)
  │
  ├─ accumulator += simDt
  ├─ while (accumulator >= FIXED_DT && steps < MAX_STEPS)     FIXED_DT = 1/120
  │     ├─ sim.step(world, FIXED_DT)         ← 게임 규칙 전부
  │     ├─ accumulator −= FIXED_DT
  │     └─ steps++
  │  (steps가 MAX_STEPS에 걸리면 남은 accumulator는 버린다 — spiral of death 차단)
  │
  ├─ alpha = accumulator / FIXED_DT          렌더 보간 계수
  ├─ render.frame(world, alpha, realDt)      ← 픽셀 전부. realDt는 연출 타이머용
  └─ audio는 sim이 발행한 이벤트를 큐에서 꺼내 재생
```

핵심 세 가지가 이 그림에 다 있다.

**입력은 히트스톱 중에도 접수된다.** `input.beginFrame()`이 `while` 루프 밖에 있고 `simDt`와 무관하다. 히트스톱이 최대 0.075초(GREAT)인데 선입력 버퍼가 0.12초(§5.1)이므로, 히트스톱 중에 누른 패리는 정지가 풀리는 순간 발동해야 한다. 정지 중 입력을 버리면 GREAT를 낸 직후의 연속 패리가 구조적으로 불가능해진다.

**실시간으로 도는 것은 press edge 검출뿐이다.** 버퍼 0.12초는 `simDt`로 감산한다 — 실시간으로 감산하면 위 문단이 요구한 것이 그 자리에서 깨진다(§3.2). 그리고 `beginFrame()`이 루프 밖이라는 사실은 등급 해상도에 값을 치르는데, 그 대가와 상환 방법이 §2.1이다.

**렌더는 `realDt`를 받고 sim은 `FIXED_DT`를 받는다.** 파티클 수명, 등급 팝업 상승, 화면 흔들림 감쇠는 연출이므로 실시간으로 돈다. 탄환 위치, 쿨다운, 무적 시간은 규칙이므로 고정 스텝으로 돈다. 이 둘을 섞으면 프레임률이 판정에 영향을 주고, 그게 HR-06이 금지한 것이다.

**`MAX_STEPS = 5`.** 프레임이 41ms 넘게 밀리면 남은 시간을 버린다. 버리지 않으면 밀린 프레임을 따라잡느라 다음 프레임이 더 밀리고, 그게 반복되면 게임이 멈춘다.

## 2. 고정 스텝을 1/120초로 잡은 계산

[01_설계_결정.md](01_설계_결정.md) D-04의 근거를 수치로 편다.

### 2.1 등급 판정의 표본 간격

스펙 §5.3의 밴드 폭:

| 밴드 | 범위 | 폭 |
|---|---|---|
| GREAT | `d ≤ 28` | 28u |
| GOOD | `28 < d ≤ 48` | **20u** |
| NOT BAD | `48 < d ≤ 70` | 22u |

표상 최고속은 S5 편전(P3) `880 × 1.34 = 1179 u/s`다. 실제로 이 탄을 쏘는 적은 게임 안에 없지만([01_설계_결정.md](01_설계_결정.md) R-05) 상한으로 쓰면 결론이 보수적인 쪽으로 선다. 실전 최다는 조총탄(P2) `760 × 1.34 = 1018 u/s`.

하한이 둘 있고, **1/120을 정당화하는 것은 둘째다.**

```
도달 하한   가장 좁은 밴드(GOOD 20u)를 한 스텝에 뛰어넘지 않을 것
            20u ÷ 1179 = 1/59

2표본 하한  가장 좁은 밴드 안에 표본이 두 개 들어갈 것
            10u ÷ 1179 = 1/118      ← 1/120이 이걸 넘어서는 첫 지점
```

**60Hz는 도달 하한을 이미 만족한다.** `1179 ÷ 60 = 19.65u < 20u`이므로 어느 밴드도 통째로 빠져나가지 않는다. 60Hz의 실제 문제는 밴드마다 표본이 하나뿐이라 **그 하나가 밴드의 어디에 떨어질지가 운**이라는 것이고, 두 표본이면 밴드의 앞쪽 절반과 뒤쪽 절반 중 어디를 노렸는지가 결과에 반영된다.

| 스텝 | 1179 u/s 이동 | 1018 u/s 이동 | GOOD 밴드(20u) 보장 표본 |
|---|---|---|---|
| 1/60 s | 19.65u | 16.97u | 1 |
| 1/120 s | **9.82u** | **8.48u** | **2** |
| 1/240 s | 4.91u | 4.24u | 4 |

1/240초까지 가지 않은 이유는 비용이다. 240Hz는 프레임당 최대 4스텝이고, 540개 엔티티를 4번 도는 것과 2번 도는 것의 차이가 저사양 기기에서 유의미하다.

### 2.1-B 1/120이 값을 하려면 입력 경로를 함께 고쳐야 한다

§1의 그림에서 `input.beginFrame()`은 `while` 루프 **밖**이라 rAF 프레임당 1회 돈다. 그리고 [05_시스템_설계.md](05_시스템_설계.md) §3.1의 C4가 각 발사체의 등급을 **패리가 활성화된 첫 스텝의 거리 하나**로 확정한다. 둘을 겹치면, 플레이어가 등급을 고를 수 있는 해상도는 sim 스텝(8.48u)이 아니라 press edge가 확정되는 프레임 간격이다 — 60Hz에서 `1018 ÷ 60 = 16.97u`. **위 표가 60Hz 열에 적어 둔 바로 그 숫자가 입력 경로에 그대로 남아 있다.**

**확정: `core/input.ts`가 이벤트 타임스탬프를 보관하고, `screens/play.ts`가 그 타임스탬프가 속한 sim 스텝에서 press를 소비한다.** `KeyboardEvent.timeStamp`와 `PointerEvent.timeStamp`는 `performance.now()`와 같은 타임베이스라 변환이 없다. 약 15줄이고, `core/input.ts`는 [09_검증_전략.md](09_검증_전략.md) §3.6의 비결정 소스 스캔 범위(`src/sim` · `src/config` · `src/core/rng.ts`) 밖이라 D-05를 위반하지 않는다.

이걸 안 하면 프레임당 sim 비용만 2배가 되고 얻는 것이 없다([12_통합_계약.md](12_통합_계약.md) §10 E-01).

### 2.2 터널링

| 물체 | 최고 속도 | 1/120s 이동 | 상대 반경 합 (플레이어 코어 10u 기준) |
|---|---|---|---|
| 조총탄 P2 (S5) | 1018 u/s | 8.5u | 16u — 안전 |
| **반사탄 상한** | **2400 u/s** | **20.0u** | 16u — **뚫린다** |

반경 합의 기준은 실재하는 가장 작은 탄인 P2·P10의 6u다. 더 작은 편전 P3(5u)은 게임 안에 발사원이 없으므로([01_설계_결정.md](01_설계_결정.md) R-05) 예로 들지 않는다. 그래도 `10 + 6 = 16u < 20u`이고 결론은 그대로다 — 반사탄 속도 상한 2400 u/s(§7.1)에서 점 표본 방식은 실패한다.

그래서 `core/sweep.ts`가 이전 위치와 현재 위치를 잇는 선분 대 원 판정을 한다. 2차 방정식 하나이고, 느린 물체에서도 올바르게 퇴화한다.

**그런데 이 판정이 필요한 곳은 셋이 아니라 하나다**([12_통합_계약.md](12_통합_계약.md) §10 E-07).

| 판정 | 1/120s 상대 이동 | 반경 합 | 스윕 |
|---|---|---|---|
| 플레이어 피격 (§4.2) | 반사탄 2400 + 플레이어 900 = **27.5u** | 코어 10 + P2 6 = **16u** | **필요** |
| 반사탄 대 적 (§7) | 2400 + 적 420 = 23.5u | 적 26~58 + 탄 5~34 ≥ **31u** | 불필요 |
| 패리 대상 탐색 (§5.2) | 20u | 패리 원 지름 **140u** | 불필요 |

패리 원을 한 스텝에 관통하려면 140u를 움직여야 하는데 최고 상대 이동이 20u다 — **어떤 탄도 최소 7스텝은 원 안에 있다.** 점 표본으로 놓칠 방법이 없다.

**패리에 스윕을 쓰면 안 되는 이유가 하나 더 있다.** 스윕이 주는 것은 선분 위의 **최근접 거리**인데, 스펙 §5.3은 등급을 **패리가 성립한 프레임의 거리**로 정의한다. 패리를 스윕으로 판정하면 등급이 체계적으로 GREAT 쪽으로 편향된다. 그건 최적화가 아니라 스펙 변경이다.

**남은 하나, 피격 스윕은 상대 변위로 한다.** 선분은 `Δ = 탄환 이동 − 플레이어 이동`이고 대상은 정지한 코어 원이다. 탄환 선분 대 프레임 끝 플레이어 원으로 잡으면 둘이 마주 보고 움직일 때 최근접이 스텝 중간에 생겨 여전히 뚫린다. 위 표의 27.5u가 그 상대 변위 값이다.

### 2.3 패리 타이머는 정수 스텝이 아니다

`0.24 ÷ (1/120) = 28.8`. 쿨다운이 스텝 경계에 안 떨어진다. 이건 문제가 아니다 — **타이머를 스텝 수가 아니라 초 단위 float로 감산**하기 때문이다(HR-06이 요구하는 바로 그것이다). 스텝 경계와 어긋나는 최대 8.3ms는 선입력 버퍼 0.12초가 흡수한다.

**절대 하지 말 것:** 어떤 타이머도 프레임 수로 세지 않는다. `frames--`가 코드에 한 줄이라도 들어오면 HR-06이 깨지고, 120Hz와 60Hz에서 게임 속도가 달라진다.

## 3. 히트스톱

히트스톱은 "몇 프레임 건너뛰기"가 아니라 **sim 시계를 멈추는 것**이다.

```
clock 상태
  hitstopRemaining : number   // 실시간 초. realDt에서 이만큼만 뺀다
  budgetWindow     : number[] // 최근 sim 1초 안에 소비한 히트스톱 기록  ← 실시간 1초가 아니다
```

**정지는 프레임 단위가 아니다.** `simDt = hitstopRemaining > 0 ? 0 : realDt`로 쓰면 프레임 중간에 히트스톱이 끝나도 그 프레임 전체의 sim 시간이 버려진다. 60Hz(프레임 16.67ms)에서 실제로 나오는 값:

| 등급 | 설계값 | 프레임 양자화 시 | 오차 |
|---|---|---|---|
| NOT BAD | 0.02초 | 2프레임 33.3ms | **+67%** |
| GOOD | 0.05초 | 3프레임 50.0ms | ±0% |
| GREAT | 0.075초 | 5프레임 83.3ms | +11% |

설계된 체감 비율 `1 : 2.5 : 3.75`가 `1 : 1.5 : 2.5`로 압축된다. §17이 요구한 "등급별 정지 길이 차이가 체감되어야 한다"가 **가장 중요한 구간인 NOT BAD ↔ GOOD에서 가장 심하게 뭉개진다** — 그 둘의 간격이 2.5배에서 1.5배로 줄기 때문이다. [12_통합_계약.md](12_통합_계약.md) §8-3이 이 증상을 진동 진폭으로 덮으려 했지만 원인은 clock 식이고, §1의 세 줄이 그것을 없앤다.

```ts
const freeze = Math.min(realDt, hitstopRemaining);
hitstopRemaining -= freeze;
simDt = realDt - freeze;
```

### 3.1 규칙

| 항목 | 값 | 근거 |
|---|---|---|
| 등급별 길이 | NOT BAD 0.02 / GOOD 0.05 / GREAT 0.075 초 | §5.3 |
| 동시 적용 | 불가. 같은 스텝 다중 패리 시 **최고 등급 1회만** | §3.2 |
| 누적 상한 | **sim** 1초당 총 **0.32초** | §3.2 |
| 피격 히트스톱 | 0.14초 | §4.2 |

누적 상한이 있는 이유는 스펙 §5.3이 계산해 두었다 — `4.16회/초 × 0.075초 = 0.312초 ≤ 0.32초`. 쿨다운을 더 줄이는 카드(R10·E07)를 든 빌드는 이 계산을 넘고, **그때 상한이 초과분을 잘라낸다.**

**단 그 계산은 sim 시계에서만 성립한다.** 히트스톱이 sim 시간을 멈춘다는 사실이 여기서 처음 값을 바꾼다.

```
sim 시계   1 ÷ 0.24 = 4.1667회/초.  4.1667 × 0.075 = 0.3125   →  0.32 통과
실시간     1주기 = 0.24 sim + 0.075 정지 = 0.315초             →  3.175회/초 (−23.8%)
T-02 전제  성공률 50%, 평균 GOOD
           1주기 = 0.24 + 0.5 × 0.05 = 0.265초 → 3.774회/초    →  성공 1.887회/실시간초
```

**§14.4가 보스 HP를 산출할 때 쓴 2.08회/초보다 9.3% 낮다.** 반올림 오차가 아니라 시계를 바꿔 읽은 값이고, 그만큼 모든 보스 HP가 두꺼워 보이게 만든다.

못 박을 것이 셋이다.

- `budgetWindow`의 "최근 1초"는 **sim 초**다. `clock.ts`의 시그니처에 그렇게 적는다.
- `config/parry.ts`의 주석에 `4.16회/초`가 **sim 시계 값이고 플레이어 체감값이 아니라는 것**을 같은 자리에 적는다.
- 1.887 대 2.08의 차이는 [11_구현_계획.md](11_구현_계획.md) P7-2의 실측 대상이다 ([12_통합_계약.md](12_통합_계약.md) §10 E-02).

### 3.2 무엇이 멈추고 무엇이 안 멈추나

| 멈춘다 (`simDt`로 감산) | 계속 돈다 (`realDt`) |
|---|---|
| 탄환 이동 | press edge 검출 |
| 적 행동·발사 주기 | 히트스톱 잔여 시간 자체 |
| 패리 쿨다운·활성·무적 | 화면 흔들림 감쇠 |
| **선입력 버퍼 0.12초** | 파티클·팝업 애니메이션 |
| 웨이브 타이머·보스 페이즈 | 오디오 |
| 장판 피해 주기 | |

**선입력 버퍼가 실시간으로 돌면 §1이 요구한 것이 그 자리에서 깨진다.** GREAT 히트스톱 0.075초 동안 버퍼가 계속 흐르면 0.12초 중 **62.5%**가 정지 안에서 소모되고 0.045초만 남는데, 그 0.045초 안에 끝나야 할 쿨다운은 같은 표에서 **얼어 있다** — 끝나지 않는다. §3이 없앤 프레임 양자화(60Hz에서 정지 0.083초)가 남아 있었다면 69%가 사라지고 0.037초만 남았다. 어느 쪽이든 결과는 같다: GREAT 직후의 연속 패리가 안 나온다.

**실시간에 남는 것은 press edge 검출뿐이다.** 눌린 사실은 정지 중에도 받고, 그 뒤의 시간 셈은 전부 sim 시계로 한다 ([12_통합_계약.md](12_통합_계약.md) §10 E-03).

**시각적 진동은 렌더에서만 한다.** 히트스톱 중 적을 흔들되 판정 위치는 고정한다 — 몸이 흔들리면 히트박스도 같이 움직여, 맞아야 할 공격이 빗나간다. 진폭은 시작이 크고 점점 작아진다. 상세 수치는 [06_렌더링과_게임필.md](06_렌더링과_게임필.md) §4.

## 4. 결정론

### 4.1 규칙 세 줄

1. `src/sim/**`의 어떤 파일도 `Math.random`, `Date.now`, `new Date`, `performance.now`를 부르지 않는다. `tests/determinism.test.ts`가 소스를 grep해서 이 규칙을 강제한다.
2. 난수는 `core/rng.ts`의 시드 인스턴스를 인자로 받는다. 런 시작 시 시드 하나를 정하고, 그 시드에서 파생한 스트림을 용도별로 나눈다 — 카드 추첨용, 보스 난사 각도용, 파티클 지터용. 한 스트림을 공유하면 파티클 개수를 바꿨을 때 카드 추첨이 달라진다.

   **`render/`와 `audio/`는 sim의 시드 스트림을 절대 쓰지 않는다.** 둘은 그냥 `Math.random()`을 써도 된다 — 규칙에 영향을 주지 않기 때문이다. 반대로 공유하면 음소거 여부가 난수 소비 횟수를 바꾸고, 같은 시드로 돌린 두 런이 갈라진다.
3. 시각은 누적 sim 시간(`world.timeSec`)이고, 이 값은 `FIXED_DT`만큼씩 정확히 증가한다.

### 4.2 이게 있어서 되는 것

| 되는 것 | 없으면 |
|---|---|
| 헤드리스 밸런스 시뮬 ([09](09_검증_전략.md)) | 스펙 §14.3의 T-01~T-07이 전부 측정 불가 |
| 입력 기록/재생 → 같은 장면 재촬영 | 30초 영상을 운으로 건져야 한다 |
| 버그 재현 | "가끔 그래요"로 끝난다 |
| 시각 회귀 테스트 | 목업과 대조가 불가능 |

리서치가 이 규칙을 어긴 프로젝트의 비용을 기록했다 — 도메인 로직 200줄에 동기화 계층 800줄, 3회 재작성, 3일 밤 디버깅(`docs/research/claude_research/06_7일_스코프와_AI_에이전트_프로세스.md:190-210`).

### 4.3 부동소수점

같은 시드·같은 입력이 **같은 기기에서** 같은 결과를 내면 충분하다. 기기 간 비트 단위 일치는 목표가 아니다 — 네트워크 동기화가 없으므로 필요가 없고, 그걸 보장하려면 고정소수점 수학이 필요해서 비용이 급등한다.

## 5. 성능 설계

### 5.1 최악 프레임

| 항목 | 수 |
|---|---|
| 잡몹 | 20 |
| 적 탄환 | 280 |
| 반사탄 | 240 |
| 장판 | 6 |
| 예고 도형 | 3~5 |
| 파티클 | 200~400 |

### 5.2 탄환을 굽는다

목업 `drawBullet`(engine.js:172-284)은 탄환 하나당 path 작도를 여러 번 한다 — `beginPath` / `moveTo` × N / `fill` / `stroke`, 거기에 글로우 스프라이트 1장, 반사탄이면 스트릭 1개와 링 1개. 520개면 프레임당 수천 번의 path 연산이다.

**대안: 부팅 시 탄환 스프라이트 30장을 오프스크린 캔버스에 굽는다.** 유도는 `패리 가능 10종 × 3상태`다([12_통합_계약.md](12_통합_계약.md) §1 C-04).

- **10종** — 탄환 12종에서 P9 화염 장판과 P12 관통 대창을 뺀 값이다. 둘은 `drawBullet`의 shape 분기에 case가 없고(engine.js:202-269) §6.1상 반사탄이 되지도 않으므로 탄환 스프라이트가 아니다.
- **3상태** — 적 탄환 / 반사탄 자해 유예 중 / 반사탄 정상. 유예 0.15초 동안에는 적색 rim을 그리지 않는다. §17이 요구한 유예 구분이 rim의 유무 그 자체이므로 상태가 2가 아니라 3이다.

글로우는 이 30장에 포함되지 않는다. **글로우 스프라이트 13색은 별도로 굽는다**([06_렌더링과_게임필.md](06_렌더링과_게임필.md) §3.1) — 색·반경 키로 캐시되는 별개 자산이고, 탄환 스프라이트가 그 위에 겹쳐 그려진다. 그러면 프레임당 탄환 하나의 비용이 `save → translate → rotate → drawImage → restore`가 된다.

```
굽기 비용:   탄환 30장 + 글로우 13색의 path 작도 — 부팅 시 1회, 수 ms
프레임 비용:  520 × drawImage(회전 포함) + 반사탄 240 × stroke 1회
```

`drawImage`는 GPU 텍스처 복사로 하드웨어 가속되고, path 렌더링보다 훨씬 싸다. 스프라이트 크기는 논리 크기의 4배로 구워 확대 시 뭉개지지 않게 한다.

**굽지 않는 것 셋.** 나머지는 전부 스프라이트로 접힌다.

| 대상 | 왜 못 굽나 | 대안 |
|---|---|---|
| **반사탄 모션 스트릭** | 목업에서 `globalCompositeOperation = 'lighter'` + `hexA(C.hwang, 0.35)`로 그린다(engine.js:184-186). 구운 스프라이트는 `source-over` `drawImage`로 나가므로 **가산 광채가 반투명 도장이 된다** — 빛나던 꼬리가 탁한 얼룩이 되고 240발이 서로를 가린다 | 발당 `stroke` 1회를 유지한다. 반사탄 240발 = stroke 240회 ([12_통합_계약.md](12_통합_계약.md) §7.2) |
| **P4 수리검의 본체와 스트릭** | 목업에서 스트릭은 `ctx.rotate` **이전에** 그려져 자체 회전 `b.spin`의 영향을 받지 않는다(engine.js:183-195 → :196). 한 장으로 접으면 꼬리가 탄과 함께 빙빙 돈다 | 스트릭과 본체를 **분리해서** 굽는다. 스트릭은 `ang + π/2`, 본체는 `ang + π/2 + spin` |
| **재패리 카운터 텍스트** | 값이 매번 다르다 | 재패리된 탄에만 그리므로 개수가 적다 |

스트릭을 굽지 않는 이유가 성능이 아니라 **가독성**이라는 점이 중요하다. §17이 "적 탄환과 반사탄을 못 구분하면 게임이 성립하지 않는다"고 적었는데, 최악 프레임에서 색축은 additive 포화로 소멸하고 형태는 두 진영이 동일하며 적색 rim은 450px에서 1.1px다. **가산 스트릭이 축소와 포화에 견디는 유일한 구분축이다.**

`P11 유도탄`의 꼬리 호는 속도 방향에만 종속이므로 회전으로 흡수되어 정상적으로 구워진다.

**상태 변경도 예산 항목이다.** 발당 시퀀스는 `setTransform → 글로우 drawImage(lighter) → 본체 drawImage(source-over)`라 탄환 하나마다 합성 모드가 왕복한다. 520발이면 **프레임당 전환 1,040회 + `globalAlpha` 변경 520회**인데, 이 숫자는 드로우 콜 예산에도 fill 예산에도 항목이 없다. 2D canvas의 GPU 래스터라이저는 합성 모드가 바뀔 때 배치를 flush하므로, **이것이 드로우 콜이나 fill-rate보다 먼저 병목이 될 수 있다.**

**확정: 탄환 층을 두 패스로 그린다.** 520발의 글로우를 `lighter`로 전부 그리고, 모드를 **한 번** 바꾸고, 본체를 `source-over`로 전부 그린다. 전환이 **1,040 → 2**가 된다. 반사탄 스트릭도 가산이므로 같은 `lighter` 패스에 합류한다.

안전한 이유가 둘이다. 글로우는 가산이라 겹치는 순서가 결과를 바꾸지 않는다. 그리고 [06_렌더링과_게임필.md](06_렌더링과_게임필.md) §2의 레이어 계약은 층 **사이**의 순서만 규정하므로, 탄환 층 **안**의 재배열은 계약을 건드리지 않는다 ([12_통합_계약.md](12_통합_계약.md) §10 E-14).

### 5.3 배경을 굽는다

목업의 배경 함수는 매 프레임 전부를 다시 그린다. `busanjin`(engine.js:1280-1359)만 해도 그라디언트 4단 + 능선 2 + 구름 4 + 왜선 6 + 말뚝 7 + 연기 3 + 페이드가 전부 path 작도다.

**스테이지 시작 시 정적 레이어를 오프스크린 1장으로 굽고, 프레임마다 그 1장을 `drawImage` 한 뒤 동적 레이어만 위에 그린다.**

| 스테이지 | 정적 (굽는다) | 동적 (매 프레임) |
|---|---|---|
| 부산진 | 그라디언트·여명·능선·구름·왜선·말뚝·연기·페이드 | 연무 흐름, 수면 반사 흔들림, 불티 |
| 동래성 | 그라디언트·능선·석성·여장·문루·지붕·홍예문·사다리·화살자국 | 재 낙하 |
| 한산도 | 그라디언트·상단광·섬·학익진 왜선·거북선 갑판 | 청해파문 2층, 포말, 물보라 |
| 행주산성 | 그라디언트·별·달·구름·능선·산성벽·목책·페이드·연기 | 횃불 명멸 5개, 불티 |
| 노량 | 그라디언트·번개·능선·구름 | 파문 2층, 포말, 불타는 왜선 4, 불티, 빗줄기 2층 |

비네트(engine.js:1659-1665)도 한 번만 굽는다. 화면 크기 방사형 그라디언트를 매 프레임 만드는 것이 가장 비싼 실수다.

정적 레이어 캐시는 **캔버스 크기가 바뀔 때만** 다시 굽는다.

### 5.4 절대 금지

리서치의 실측을 그대로 옮긴다(`docs/research/claude_research/09_코드만으로_만드는_비주얼과_오디오.md:605-621`). 측정 조건은 5개 데스크톱 브라우저 + 모바일 Safari에서 각 기법 100회.

| 금지 | 측정된 비용 |
|---|---|
| `ctx.shadowBlur` (그림자 붙은 호) | `fillRect` 대비 IE/Edge/Chrome/Opera **50배**, Firefox **100배** |
| 매 프레임 gradient 객체 생성 | IE11/Chrome/Opera에서 rect 대비 3배, **Firefox 100배**. 게다가 매번 GC 쓰레기를 만든다 |
| 필수 경로의 `ctx.filter` | MDN이 not Baseline으로 표시. 주요 브라우저 일부에서 동작 안 함 |
| `globalCompositeOperation` + 그림자 조합 | Chromium만 사양대로. Firefox/Safari/WPE가 각각 다름 |

**대신 쓰는 것:** 미리 구운 방사형 그라디언트 스프라이트 + `globalCompositeOperation = 'lighter'` + `globalAlpha`. 목업 `glowSprite`(engine.js:96-111)가 이미 이 방식이고 색·반경 키로 캐시한다. 그대로 가져간다.

### 5.5 검증되지 않은 가정

**리서치 코퍼스 전체에 "탄환 N개 @ 60fps" 실측이 없다.** 가장 가까운 수치는 "도형 500개는 60fps에서 여유"(`docs/research/claude_research_4/04_머니샷_사람들이_캡처하는_단일_시각사건.md:326`)인데 측정 조건이 다르다.

그러므로 위 §5.2~§5.4는 전부 **가정**이다. [11_구현_계획.md](11_구현_계획.md)의 1단계가 이 가정을 검증한다 — 게임 규칙 없이 750개 엔티티를 그리는 스트레스 씬을 먼저 만들고 프레임 타임을 잰다. 이 측정이 [01_설계_결정.md](01_설계_결정.md) D-02를 확정하거나 뒤집는다.

**그런데 D-02를 뒤집을 수 있는 상수는 P1 전체를 기다리지 않고 잴 수 있다.** P1은 P0 + P2a가 선행이고 스프라이트 30장·글로우 13색·스트레스 씬·오버레이가 다 있어야 첫 숫자가 나온다. 그 앞에 **의존성 0의 `probe.html` 30줄**을 둔다([12_통합_계약.md](12_통합_계약.md) §10 E-18). 재는 것은 둘뿐이다.

```
① 1080×1920 캔버스에 85×85 스프라이트를 lighter로 10,000회 drawImage  →  호출당 t (µs)
② fillRect(0, 0, 1080, 1920)을 60회                                    →  Mpx/s
```

①이 [06_렌더링과_게임필.md](06_렌더링과_게임필.md) §3.5의 미측정 상한 2,500을 직접 측정값으로 대체한다. 그 상한의 환산식이 이미 `16.67ms ÷ 2,500 = 6.7µs`이므로, 실제 상한은 `16,670 ÷ t`다.

| 측정 t | 실제 드로우 콜 상한 | 뜻 |
|---|---|---|
| ≤ 1.5µs | 11,000+ | 2,616도 3,136도 문제가 아니다. [12_통합_계약.md](12_통합_계약.md) §7.4-B의 초과 논쟁 전체가 소멸한다 |
| ≈ 6.7µs | 2,500 | 추정이 정확했고 초과가 실재한다 |
| ≥ 12µs | 1,389 | GPU 경로가 아니다. 상한 조정이 아니라 **D-02 재검토** |

②는 [06_렌더링과_게임필.md](06_렌더링과_게임필.md) §3.6의 fill 예산(초당 630M px)을 같은 파일에서 검증한다. **두 숫자, 30줄, 30분.**

이걸 먼저 하면 **P1이 "될까?"가 아니라 "예측한 값이 나오는가?"를 재는 시험이 된다.** 실패했을 때 원인이 굽기인지 fill인지 상태 변경(§5.2)인지를 이미 알고 시작한다.

측정 결과가 나쁠 때의 대응 순서는 스펙 §14.3 T-07이 정해 두었다 — **잡몹 상한이 아니라 동시 적 탄환 상한을 먼저 내린다.** 화면이 적으로 차 있는 장면이 상한을 올린 이유이므로 그것부터 깎지 않는다.

## 6. 피드백 이벤트

`sim/`은 소리를 낼 수 없고(계층 규칙, D-06) 파티클도 만들 수 없다. 그런데 §17의 사건들은 sim 안에서 일어난다. 이걸 잇는 것이 `core/bus.ts`다.

**범용 pub-sub이 아니다.** 이벤트 종류는 고정된 union type이고, 새 이벤트를 추가하려면 타입을 고쳐야 한다.

```ts
export type FeedbackEvent =
  | { kind: 'parry';        grade: ParryGradeId; x: number; y: number; count: number }
  | { kind: 'parryWhiff';   x: number; y: number }
  | { kind: 'reparry';      grade: ParryGradeId; prevGrade: ParryGradeId; x: number; y: number }
  | { kind: 'enemyKilled';  x: number; y: number; enemyId: EnemyId; chainIndex: number }
  | { kind: 'playerHit';    cause: 'enemyBullet' | 'reflectedBullet' | 'body' | 'zone' }
  | { kind: 'cooldownReady' }
  | { kind: 'bossPhase';    bossId: BossId; phase: number }
  // …
```

구독자는 셋이다. `render/particles.ts`(파티클·팝업), `render/camera.ts`(trauma 가산), `audio/sfx.ts`(소리). **구독자가 3개라서 버스가 정당화된다** — 하나였다면 직접 호출이 맞다.

`enemyKilled`의 `chainIndex`가 [01_설계_결정.md](01_설계_결정.md) D-09의 머니샷을 만든다. **한 번의 패리가 반사한 탄들이** 적을 잡을 때 인덱스가 0, 1, 2로 올라가고, 렌더와 오디오가 그 인덱스만큼 지연시켜 **동시 삭제가 아니라 순차 연쇄로 보이게 한다.** 인덱스의 단위는 반사탄 하나가 아니라 **패리 이벤트 하나**다([12_통합_계약.md](12_통합_계약.md) §6).

버스는 sim 스텝 안에서 큐에 쌓고, 스텝이 끝난 뒤 한 번에 비운다. sim 도중에 소비하면 구독자가 sim 상태를 중간에 읽게 되고, 그러면 스텝 순서에 따라 결과가 달라진다.

## 7. 카드가 파라미터를 바꾸는 경로

스펙 §11.6의 보정 순서는 9단계이고, INV-1과 INV-2가 서로 반대 방향으로 값을 자른다. 이게 어디에 사는지가 중요하다.

```
config/cards/*.ts        카드 정의 (효과 종류 + 수치)
        ↓
sim/cards.ts             보유 목록 → §11.6 1~9단계 실행
        ↓
sim/stats.ts             결과를 EffectiveStats 스냅샷 하나로 고정
        ↓
sim/parry.ts · sim/reflect.ts · sim/player.ts    스냅샷만 읽는다
```

**중요한 것은 마지막 줄이다.** 판정 코드는 카드를 모른다. `PARRY.radiusU`를 직접 읽지 않고 `stats.parryRadiusU`를 읽는다. 카드가 없으면 스냅샷이 `config/`의 기본값과 같을 뿐이다.

스냅샷의 **정적 부분**은 카드 목록이 바뀔 때만 다시 계산한다 — 카드 획득, 치트 메뉴 조작, 런 시작. 매 프레임 9단계를 다시 도는 것은 낭비이고, 더 중요하게는 중간에 값이 흔들릴 여지를 만든다.

**그런데 정적이지 않은 것이 넷 있다.** R05는 콤보에, N13은 패리 성패에, R10은 직전 성립 시각에, E03은 스테이지 시작에 따라 **카드 목록이 그대로여도** 값이 바뀐다. 이 넷은 스냅샷 필드가 아니라 런타임 파생 접근자로 낸다 — 시그니처는 [05_시스템_설계.md](05_시스템_설계.md) §10.3이 계약으로 고정한다([12_통합_계약.md](12_통합_계약.md) §10 E-05).

스냅샷에는 **어느 상한·불변 조건이 값을 잘랐는지도 함께 담는다.** 스펙 §18.4가 치트 메뉴에 이 정보를 표시하라고 요구했고, 이유도 적어 두었다 — INV-1이 쿨다운을 0.197초에서 0.23초로 되돌리는 것 같은 상호작용은 숫자로 보이지 않으면 실측 중에 원인을 잘못 짚는다.

## 8. 하드 규칙을 코드가 지키게 만들기

스펙 §2의 HR-01~HR-09는 "밸런싱으로 완화할 수 없는 제약"이다. 문서에만 있으면 조용히 썩는다.

`sim/guards.ts`가 이것들을 개발 빌드에서 실행 가능한 검사로 만든다. 릴리스 빌드에서는 트리 셰이킹으로 사라진다.

| 규칙 | 검사 방법 | 언제 |
|---|---|---|
| HR-02 원거리 적 최소 1기 | `config/stages/*`의 모든 웨이브 편성을 훑어 원거리 아키타입 존재 확인 | 테스트 시점 (정적) |
| HR-03 적 탄환 0인 상태 2.0초 초과 금지 | 타이머 유지, 초과 시 오류 | 매 스텝 |
| HR-05 예고 도형은 3종뿐 | 예고 생성 시 종류 검사 | 생성 시 |
| HR-07 반사탄은 양쪽에 유효 | 반사탄 생성 시 소유자 플래그 검사 | 생성 시 |
| HR-08 보스는 상단 영역 | 지정된 돌진 패턴 외 y 범위 검사 | 매 스텝 |
| HR-09 최소 비행 시간 0.45초 | 발사 시 거리 ÷ 속도 검사 | 발사 시 |
| INV-1 · INV-2 | 스냅샷 재계산 직후 검사 | 카드 변경 시 |

**HR-04(패리 불가 공격은 회피 가능한 안전 지대를 남긴다)는 자동 검사가 어렵다.** 안전 지대의 존재는 기하 문제이고, 장판 6개가 겹친 순간의 잔여 면적을 계산해야 한다. 이건 자동화를 시도하기보다 [09_검증_전략.md](09_검증_전략.md)의 수동 검토 항목으로 남긴다. 자동화한 척하는 것이 안 한 것보다 나쁘다.

## 9. 빌드

### 9.1 개발

```
npm run dev        Vite dev server. 밸런스 파일 저장 → 전체 새로고침 (HMR 아님)
npm run test       Vitest
npm run typecheck  tsc --noEmit
npm run lint       ESLint (계층 규칙 포함)
npm run verify     typecheck + test + headless 밸런스 리포트
```

**HMR은 이 프로젝트에서 안 된다**([12_통합_계약.md](12_통합_계약.md) §8-8). `config/` 아래에 로직을 금지했으므로([01_설계_결정.md](01_설계_결정.md) D-06) 어떤 모듈도 `import.meta.hot.accept` 경계를 선언할 수 없고, 경계가 없으면 Vite는 매번 전체 페이지 새로고침을 보낸다. **결과는 런이 타이틀로 초기화되는 것이다** — 숫자 하나를 고칠 때마다 S5 보스까지 다시 걸어가야 한다는 뜻이고, 그건 D-10이 없애려던 바로 그 비용이다.

그래서 `dev/capture.ts`가 진입점을 복원한다(12 §8-9). 치트 진입 지점(스테이지·웨이브·페이즈·카드·라이프)을 `sessionStorage`에 쓰고, 부팅 시 `sim/run.ts`의 공개 함수로 되돌린다. 새로고침 자체를 막지는 못하지만 되돌아가는 비용이 0이 된다.

`npm run verify`가 게이트다. 리서치의 실패 사례가 정확히 이 지점이다 — "테스트 초록불 + 게임 플레이 불가"(`docs/research/claude_research/06_7일_스코프와_AI_에이전트_프로세스.md:120-122`). 타입과 단위 테스트만으로는 "60초 동안 데미지 0"을 못 잡는다. `verify`에 헤드리스 리포트가 들어가는 이유다.

### 9.2 산출

```
npm run build      →  dist/index.html  (단일 파일, JS·CSS inline. 웹폰트는 번들하지 않는다)
```

Vite 설정에서 `assetsInlineLimit`를 충분히 올리고 단일 파일 플러그인으로 청크를 합친다. 결과물은 더블클릭으로 `file://`에서 열린다.

**`file://`에서 확인해야 할 것 두 가지.** ① AudioContext는 사용자 제스처 이후에만 소리가 난다 — 이건 프로토콜과 무관하지만 첫 화면이 무음인 상태를 개발자가 한 번도 못 보므로 별도 확인이 필요하다. ② 웹폰트를 번들하지 않으므로([12_통합_계약.md](12_통합_계약.md) §3.1) 폰트 스택의 첫 항목이 기기에 설치돼 있지 않으면 시스템 폰트로 떨어진다. 목업 README가 "레이아웃은 유지된다"고 적었지만(`docs/sample_image/README.md:58`) 그건 측정된 적이 없으므로 15화면 전부를 실제로 확인한다([01_설계_결정.md](01_설계_결정.md) D-03).
