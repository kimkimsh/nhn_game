## 2. 이 트리가 이 모양인 이유

### 2.1 `config/`를 세 계층 중 맨 앞에 세운 이유

요구는 "수치를 열어서 쉽게 고칠 수 있게"인데, 이걸 만족시키는 조건은 **파일 하나를 열었을 때 그 안에 로직이 없는 것**이다. 로직이 섞이면 숫자를 고칠 때마다 그 로직을 읽고 안 깨지는지 확인해야 한다.

그래서 `config/` 아래 파일은 **선언과 주석만** 있고, `import`는 같은 폴더의 `ids.ts` / `types.ts` 두 개뿐이다. 계산식이 필요하면 그건 `sim/`에 있다.

### 2.2 폴더가 아니라 파일로 나눈 기준

`stages/` · `bosses/` · `cards/`만 하위 폴더를 가진다. 나머지는 파일 하나다. 기준은 하나다 — **항목이 5개 이상이고, 항목 하나가 20줄을 넘는가.**

| 대상 | 항목 수 | 항목당 분량 | 판정 |
|---|---|---|---|
| 스테이지 | 5 | 웨이브 3~5개 + 배경 파라미터 = 60~90줄 | 폴더 |
| 보스 | 5 | 페이즈 2~4 × 패턴 2~3 = 80~150줄 | 폴더 |
| 카드 | 31 | 5~12줄 | 폴더 (등급별 3파일) |
| 탄환 | 12 | 8줄 | 파일 하나 |
| 잡몹 | 9 | 10줄 | 파일 하나 |
| 진입 형태 | 6 | 6줄 | 파일 하나 |

탄환 12종을 12파일로 쪼개지 않은 이유는 표로 볼 때 값을 비교할 수 있어야 하기 때문이다. 스펙 §6.1도 표 하나다. **비교하며 고치는 것은 한 파일, 독립적으로 고치는 것은 파일 분리** — 이게 이 트리의 유일한 분할 규칙이다.

### 2.3 `render/`가 `engine.js` 구조를 그대로 따르는 이유

목업 `docs/sample_image/_shared/engine.js`는 승인된 아트 디렉션 그 자체다. 이식 시 함수를 재배치하면 원본과 대조가 불가능해지므로, **원본의 함수 하나가 새 파일의 함수 하나에 1:1 대응**하도록 옮긴다. 어느 함수가 어느 파일로 가는지는 [06_렌더링과_게임필.md](06_렌더링과_게임필.md) §1의 이식표에 있다.

`render/frame.ts`의 레이어 순서도 원본 `render()`(engine.js:1934-1980)를 그대로 지킨다:

```
배경 → 씬 페인트 → 장판 → 예고 → 적 → 탄환 → **임팩트 프레임** → 플레이어 → 파티클 → 팝업 → 비네트 → HUD → 오버레이
```

이 순서는 미학이 아니라 **가독성 계약**이다. 탄환이 적보다 위에 있어야 탄이 적 뒤로 숨지 않고, 플레이어가 탄환보다 위에 있어야 10u 코어가 절대 가려지지 않는다.

### 2.4 `dev/`를 제출 빌드에서 빼지 않는 이유

스펙 §18.6이 정했다 — "치트 모드는 제출 빌드에도 그대로 포함한다." 소스에서도 지우지 않는다. 대신 `dev/`의 어떤 코드도 `sim/`을 import하지 않고 **`sim/`이 제공하는 공개 조작 함수만 호출**한다. 그래야 스펙 §18.1의 "전투 규칙 자체는 하나도 바뀌지 않는다"가 구조로 보장된다.

## 3. 이름 규칙

### 3.1 파일 이름

- 전부 소문자 kebab-case. `boss-3-atakebune.ts`, `card-select.ts`.
- 스테이지·보스 파일은 **번호를 앞에** 둔다. 파일 목록이 스펙 순서대로 정렬되게 하려는 것이고, 정렬이 흐트러지면 "S4가 어디 있더라"가 매번 생긴다.
- 복수형은 항목 여러 개를 담은 표에만 쓴다. `bullets.ts`(12종 표) vs `parry.ts`(패리 하나의 파라미터).

### 3.2 식별자

| 대상 | 형태 | 예 |
|---|---|---|
| 설정 테이블 | `SCREAMING_SNAKE` | `BULLETS`, `PARRY`, `STAGE_SCALING` |
| 테이블 안의 키 | 스펙의 ID 그대로 | `'P2'`, `'E-A'`, `'N01'`, `'F-3'` |
| 타입 | `PascalCase` | `BulletDef`, `EnemyId`, `BossPhase` |
| 함수 | `camelCase`, 동사로 시작 | `judgeParry`, `applyCardStack`, `spawnWave` |
| 불리언 | `is` / `has` / `can` | `isParryable`, `hasShield`, `canFire` |
| 시간 값 | 접미사 `Sec` | `activeSec`, `cooldownSec`, `graceSec` |
| 거리 값 | 접미사 `U` | `radiusU`, `speedUPerSec` |

**시간에 `Sec`를 붙이는 것은 규칙이 아니라 안전장치다.** 스펙 HR-06이 "모든 시간 파라미터는 초로 정의한다. 프레임 수나 밀리초로 정의하지 않는다"고 못 박았는데, 코드에서 `cooldown = 0.24`를 보면 초인지 프레임인지 알 수 없다. `cooldownSec = 0.24`는 알 수 있다.

### 3.3 스펙 참조

**`config/` 아래 모든 값에는 스펙 절 번호가 붙는다.** 형식은 `§5.1` 처럼 절 번호만 쓰고 줄 번호는 쓰지 않는다 — 스펙이 개정되면 줄 번호가 먼저 썩기 때문이다.

### 3.4 「드로우 콜」이 세는 것

[06_렌더링과_게임필.md](06_렌더링과_게임필.md)의 두 표가 이 단어를 다르게 세어서 같은 최악 프레임의 예산 초과가 4.6%도 되고 25.4%도 됐다([12_통합_계약.md](12_통합_계약.md) §10 E-15). 차이가 정확히 520회, 즉 탄환 한 발당 `setTransform` 한 번이다.

**드로우 콜은 `drawImage` · `fill` · `stroke` · `fillText` 네 호출만 센다.**

`setTransform` · `globalAlpha` · `globalCompositeOperation`은 드로우 콜이 아니라 **상태 호출**이다. 둘을 합쳐 세면 어느 표가 어느 기준으로 적힌 것인지 알 수 없어져서, 상한을 넘었는지조차 표마다 답이 달라진다.

**상태 호출에 별도 예산을 두지 않는다.** [12](12_통합_계약.md) §10 E-14가 그것을 요구했지만 [13](13_프로브_측정결과.md) §4.3의 실측이 `setTransform`을 **비용 0**으로 냈고 합성 모드 전환도 측정 한계 아래였다. 잴 값이 0인 예산은 예산이 아니다 — 세지 않고, 대신 두 패스 정렬은 대가가 0이므로 그대로 한다([06](06_렌더링과_게임필.md) §3.1).

## 4. 주석 규칙

주석이 지켜야 할 것은 하나뿐이다: **삭제했을 때 코드·타입·파일명에서 되찾을 수 없는 것을 담고 있을 것.**

### 4.1 `config/` — 주석이 가장 두꺼운 곳

각 파일 맨 위에 **파일 헤더**가 온다. 세 줄이고, 세 줄 다 필수다.

```ts
/**
 * 패리 파라미터 — 스펙 §5.1 · §5.3
 *
 * 이 파일의 값을 바꾸면 게임의 손맛이 통째로 바뀐다. 쿨다운을 내리면 난사가 되고,
 * 등급 밴드를 넓히면 GREAT가 흔해진다. INV-1·INV-2는 수치가 아니라 제약이므로
 * 바꾸지 않는다 — 그 둘이 깨지면 sim/guards.ts가 개발 모드에서 오류를 낸다.
 */
```

각 필드에는 **단위와 절 번호**가 붙는다. 값의 의미가 자명하지 않으면 한 줄 더 붙인다.

```ts
export const PARRY = {
  radiusU: 70,          // §5.1 패리 원 반경 (u)
  activeSec: 0.15,      // §5.1 활성 시간 (s)
  cooldownSec: 0.24,    // §5.1 쿨다운 (s) — 활성 시작 시점 기준. sim 초당 최대 4.16회
  bufferSec: 0.12,      // §5.1 선입력 버퍼 (s) — 쿨다운 종료 이 시간 전부터 입력 접수
  invulnSec: 0.14,      // §5.1 패리 성립 시에만 부여되는 무적 (s). 빈 패리는 무적 없음
  graceSec: 0.15,       // §7.1 자해 유예 (s)
} as const satisfies ParryConfig;
```

**`lockoutSec`는 여기 없다.** §5.1의 재입력 불가 구간 0.09초는 `cooldownSec − activeSec`이므로 **저장하지 않고 유도한다**([12_통합_계약.md](12_통합_계약.md) §5). 0.09를 리터럴로 두면 쿨다운이나 활성을 고칠 때 한쪽만 바뀌어 관계가 조용히 깨진다 — 그리고 그 관계는 타입이 못 잡는다.

**밴드처럼 순서에 의미가 있는 배열은 순서 자체를 주석으로 밝힌다.**

```ts
/** §5.3 등급 밴드. 좁은 것부터 나열한다 — 판정이 "d를 덮는 첫 밴드"를 고르기 때문이다. */
export const PARRY_BANDS = [
  { id: 'GREAT',   maxDistU: 28, damageMul: 3.5, speedMul: 2.6, hitstopSec: 0.075, score: 400 },
  { id: 'GOOD',    maxDistU: 48, damageMul: 2.0, speedMul: 1.8, hitstopSec: 0.05,  score: 150 },
  { id: 'NOT_BAD', maxDistU: null, damageMul: 1.0, speedMul: 1.3, hitstopSec: 0.02,  score: 50  },
  //             ↑ null = "패리 반경까지". 카드로 반경이 106u까지 커지므로 70을 박으면
  //               70 < d ≤ 106 에 등급 없는 고리가 생긴다 (12 §10 E-06)
] as const satisfies readonly ParryBand[];
```

**값이 다른 값에서 유도된 것이면 저장하지 말고 유도한다.** 두 곳에 두면 한쪽만 고쳐서 관계가 깨지고, 그 어긋남은 타입이 못 잡는다.

```ts
/** §5.1 재입력 불가 구간 (s). 저장하지 않는다 — 관계가 곧 정의다 */
export const PARRY_LOCKOUT_SEC = PARRY.cooldownSec - PARRY.activeSec;   // 0.09
```

같은 판정이 `PARRY_BANDS`의 마지막 밴드에도 걸린다. `maxDistU: null`이 "패리 반경까지"를 뜻하고 `sim/stats.ts`가 스냅샷을 만들 때 `parryRadiusU`로 채운다 — 70을 리터럴로 박으면 카드로 반경이 커졌을 때 등급 없는 고리가 생기고([12_통합_계약.md](12_통합_계약.md) §10 E-06), 그렇다고 두 곳에 저장하고 같은지 검사하면 위 실수를 이름만 바꿔 반복하는 것이다.

### 4.2 `sim/` — 계약과 순서만

`sim/`의 주석은 네 가지 중 하나만 말한다: 이 함수가 보장하는 것 / 호출 순서 제약 / 타입이 못 잡는 불변 조건 / 왜 더 단순한 형태가 아닌지.

```ts
/**
 * 같은 스텝에서 패리 판정을 피격 판정보다 먼저 돌린다 (§5.1).
 * 이 순서가 뒤집히면 §5.3의 대형 탄환 GREAT가 성립하는 즉시 피격으로 처리된다 —
 * 참격파(P5, 반경 34u)는 GREAT 밴드(d ≤ 28) 안에서 이미 코어를 덮고 있기 때문이다.
 */
export function stepCombat(world: World, dt: number): void
```

수치를 주석에 복사하지 않는다. `config/`가 유일한 소스이고, 복사본은 반드시 어긋난다.

### 4.3 `render/` — 이식 출처와 규칙 인코딩

목업에서 옮겨 온 함수는 **출처를 적는다.** 원본과 대조해야 할 일이 반드시 생긴다.

```ts
/** 이식: docs/sample_image/_shared/engine.js drawBullet (172-284) */
```

그리고 **그림이 게임 규칙을 담고 있는 자리는 그 규칙을 적는다.** 이게 없으면 나중에 "예뻐 보이게" 고쳐서 규칙을 지워 버린다.

```ts
// 황색 코어에 적색 링. 반사탄은 내 데미지원이지만 나에게도 유효하다 (HR-07).
// 아군 색으로만 칠하면 안전하다고 오해한다 (§17).
```

### 4.4 쓰지 않는 주석

- 아래 줄을 그대로 옮긴 것. `// 라이프를 1 줄인다` 위의 `life -= 1`
- 날짜·작성자·변경 이력·티켓 번호. git이 더 잘 한다
- `// TODO: 나중에 최적화` 처럼 발동 조건이 없는 것
- 구획 배너, 이모지
- `@param bulletId 탄환 ID` 처럼 이름이 이미 말한 것

### 4.5 언어

**코드 파일 안의 주석은 한국어로 쓴다.** 이 프로젝트의 유일한 원본 계약 문서(`docs/spec/기능_명세서.md`)가 한국어이고, 주석의 핵심 기능이 그 문서의 어느 절과 이어지는지 밝히는 것이기 때문이다. 절 제목과 용어를 번역하면 대조가 끊긴다.

기술 용어와 API 이름은 영어 그대로 둔다 — `AudioContext`, `requestAnimationFrame`, `hitstop`, `trauma`.

## 5. 의존 규칙 — 빌드가 강제한다

```
config  ←  sim  ←  screens  →  render  →  config
   ↑                              ↓
  core  ←───────────────────────  core
```

| 계층 | import 해도 되는 것 | 절대 안 되는 것 |
|---|---|---|
| `config/` | 같은 폴더의 `ids.ts` · `types.ts` | 그 외 전부 |
| `core/` | 없음 (완전 독립) | 전부 |
| `sim/` | `config/`, `core/` | `render/`, `audio/`, `screens/`, `document`, `window`, `canvas` |
| `render/` | `config/`, `core/`, `sim/`의 **타입만** | `sim/`의 상태 변경 함수 |
| `audio/` | `config/`, `core/` | `sim/`, `render/` |
| `screens/` | 전부 | — |
| `dev/` | `config/`, `core/`, `sim/`의 공개 조작 함수 | `sim/` 내부 |

`eslint.config.js`가 이 표를 `no-restricted-imports`로 구현한다. 위반은 경고가 아니라 빌드 실패다.

**`render/`가 `sim/`의 타입만 읽는다는 규칙이 이 표에서 가장 중요하다.** 렌더가 sim 상태를 한 줄이라도 바꾸면, 프레임률이 판정에 영향을 주기 시작한다 — HR-06이 금지한 바로 그것이다.

## 6. 파일 크기 상한

한 파일 **400줄**을 넘기면 쪼갠다. 예외는 `render/enemy.ts`와 `render/backgrounds/*.ts` 하나뿐이다 — 목업 원본이 이미 그 크기이고(`drawEnemy` 397-837 = 440줄), 함수 하나를 쪼개면 원본과의 1:1 대조가 끊긴다.

상한이 있는 이유는 미학이 아니다. 파일이 커지면 병렬 구현 시 두 에이전트가 같은 파일을 잡게 되고, 리서치가 그 결과를 적었다 — "Two teammates editing the same file leads to overwrites"(`docs/research/claude_research/06_7일_스코프와_AI_에이전트_프로세스.md:324-329`).

## 7. "이걸 고치려면 어디를 열까" 표

`src/config/README.md`에도 같은 표를 둔다.

| 고치고 싶은 것 | 파일 |
|---|---|
| 게임이 너무 어렵다 / 쉽다 | `config/difficulty.ts` (스테이지별 배율. 보스 HP는 여기 없다 — [12_통합_계약.md](12_통합_계약.md) §5) |
| 패리가 너무 후하다 / 빡빡하다 | `config/parry.ts` (반경, 활성 시간, 등급 밴드) |
| 특정 잡몹이 너무 세다 | `config/enemies.ts` (해당 ID 줄의 `hp`) |
| 특정 보스가 너무 오래 산다 | `config/bosses/boss-N-*.ts` (`hp`) |
| 보스 패턴을 바꾸고 싶다 | `config/bosses/boss-N-*.ts` (페이즈별 패턴 배열) |
| 어느 웨이브에 뭐가 나오는지 | `config/stages/stage-N-*.ts` |
| 탄이 너무 빠르다 / 느리다 | `config/bullets.ts` (기본 속도) 또는 `config/difficulty.ts` (스테이지 배율) |
| 카드 효과 수치 | `config/cards/{normal,rare,epic}.ts` |
| 카드가 잘 안 나온다 | `config/cards/draw-table.ts` (회차별 등급 가중치) |
| 히트스톱이 짧다 / 길다 | `config/parry.ts` — 등급 밴드의 `hitstopSec`가 단일 소스다([12_통합_계약.md](12_통합_계약.md) §5). 피격 히트스톱만 `config/feel.ts`의 `playerHit`이고, `config/player.ts`는 이 값을 갖지 않는다([12_통합_계약.md](12_통합_계약.md) §10 E-13) |
| 흔들림·파티클이 약하다 / 과하다 | `config/feel.ts` (셰이크 티어·파티클 강도) |
| 소리가 마음에 안 든다 | `config/audio.ts` (신스 파라미터) |
| 색을 바꾸고 싶다 | `config/palette.ts` — **단, 색 하나에 규칙 하나다. 규칙 없는 색은 추가하지 않는다.** 목업의 `tokens.css`는 이식하지 않으므로 이 파일이 유일한 색 소스다([12_통합_계약.md](12_통합_계약.md) §3.2) |
| HUD 위치·크기 | `config/ui.ts` |
| 라이프 개수, 무적 시간 | `config/player.ts` |
| 점수 배분 | `config/scoring.ts` |
| 화면 전체 상한 (장판 6개, 잡몹 20기 등) | `config/playfield.ts` — **동시 적 탄환 상한만 여기가 아니라 `config/difficulty.ts`**의 스테이지별 칸이다. 그 값은 난이도 축 3이라 스테이지마다 다르다([12_통합_계약.md](12_통합_계약.md) §10 E-13) |
