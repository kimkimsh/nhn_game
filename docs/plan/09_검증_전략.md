# 09. 검증 전략

**이 문서의 목적 한 줄:** 「환도(還刀)」가 "테스트는 초록불인데 게임이 안 되는" 상태로 제출되지 않게 하는 것.

전제: [01_설계_결정.md](01_설계_결정.md) D-04(고정 스텝 1/120초 + 스윕 충돌) · D-05(시드 난수 주입) · D-10(치트 모드는 1일차 인프라). 대상 파일과 경로는 전부 [03_파일_구조.md](03_파일_구조.md)의 트리를 그대로 쓴다.

검증 대상 계약은 [`docs/spec/기능_명세서.md`](../spec/기능_명세서.md)이고, **이 문서는 스펙의 수치를 하나도 바꾸지 않는다.** 스펙 안에서 서로 어긋난 곳을 발견하면 여기서 고치지 않고 §3.9에 기록만 한다.

## 1. 무엇을 검증하는가

실패는 세 가지 종류로만 온다. 셋은 원인이 다르고, 잡는 도구가 다르고, **하나를 잡는 도구가 나머지 둘을 전혀 못 잡는다.**

| 실패 종류 | 증상 | 잡는 도구 |
|---|---|---|
| **(a) 규칙 위반** | 하드 규칙이나 불변 조건이 어느 순간부터 조용히 성립하지 않는다. 화면은 멀쩡하고 예외도 안 난다 | 런타임 가드(`src/sim/guards.ts`) + 단위 테스트(`tests/`) |
| **(b) 밸런스 이탈** | 빌드도 되고 실행도 되는데 플레이가 불가능하거나 시시하다 | 헤드리스 밸런스 시뮬(`src/dev/headless.ts`) |
| **(c) 시각 회귀** | 리팩터가 그려지는 그림을 바꿨다. 규칙은 그대로인데 승인된 아트 디렉션이 아니게 된다 | 목업 정지 프레임 대조(`docs/sample_image/`) |

### 1.1 (a) 규칙 위반

이 게임의 하드 규칙은 대부분 **어겨도 즉시 티가 나지 않는다.** HR-09(최소 비행 시간 0.45초)가 깨지면 "가끔 못 피하는 탄이 있다"로 보이지 규칙 위반으로 보이지 않는다. INV-2(무적 ≤ 쿨다운 × 0.75)가 깨지면 "이 빌드가 좀 강하네"로 보인다. 스펙 §11.6의 보정 순서 8단계처럼 **INV-1과 INV-2가 서로 반대 방향으로 값을 자르는** 구조에서는, 순서 한 칸이 뒤바뀌어도 결과 숫자가 그럴듯해서 눈으로 못 잡는다.

그래서 하드 규칙은 문장이 아니라 **실행되는 단언**으로 존재해야 한다(§2).

### 1.2 (b) 밸런스 이탈 — 초록불은 게임이 된다는 증거가 아니다

리서치가 이 실패를 실측 수치와 함께 기록했다. yurukusa의 기록은 이렇다.

> "The tests passed. The code compiled. The game launched. And the game was unplayable."
> (`docs/research/claude_research/05_기술_스택_선정.md:194-202`)

구체 증상은 **60초를 플레이하는 동안 누적 데미지 0**, 그리고 재미 구간이 10~30초여야 하는데 **레벨업이 3.9초마다** 발생한 것이었다. 상위 판정 문서가 이것을 AI 에이전트 개발의 최악 실패 모드로 못 박았다 — "**테스트 초록불 + 게임 플레이 불가**"(`docs/research/claude_research/00_제약_조건표_종합.md:397`). 같은 문서가 JAMER 벤치마크를 인용한다: 에이전트가 컴파일 통과율은 77.3% → 82.7%로 올렸지만 런타임 행동 품질은 "no gains"였고, 결론은 "the bottleneck lies in architectural design rather than syntactic correctness"였다.

**이 프로젝트에서 같은 실패가 어떤 모습으로 올지도 이미 이름이 있다.** 스펙 §14.4가 B3의 추정 여유를 +169%, B5를 +117%로 적어 두고 "실제로는 반사 각도가 맞지 않아 빗나가는 비율이 크므로 명중률 축을 실측한 뒤 HP를 재산정한다"고 남겼다. 즉 **반사탄 명중률이라는 축이 통째로 미측정 상태다.** 명중률이 낮으면 B3가 29초가 아니라 90초짜리 벽이 되고, 높으면 3초에 녹는다. 어느 쪽이든 단위 테스트는 전부 통과한다.

`tests/`가 초록불인 것은 §1.1을 통과했다는 뜻이지 게임이 된다는 뜻이 아니다. **(b)를 잡는 것은 오직 §4의 헤드리스 시뮬뿐이다.**

### 1.3 (c) 시각 회귀

`docs/sample_image/`의 15장은 예시 그림이 아니라 **승인된 아트 디렉션 그 자체**다. `_shared/engine.js`가 스펙의 수치를 그대로 들고 있어서 화면에 뜬 GREAT는 실제로 `d ≤ 28`에서 성립한 GREAT이고, 반사탄 방향도 `v' = v − 2(v·n)n`이 낸 값이다(`docs/sample_image/README.md`).

그런데 목업의 그림이 담고 있는 것은 미학만이 아니다. **가독성 계약이 그림에 인코딩되어 있다.** 탄환이 적보다 위에 있어야 탄이 적 뒤로 숨지 않고, 플레이어가 탄환보다 위에 있어야 10u 코어가 절대 안 가려진다(§15.1). 패리 불가 대상은 색이 아니라 **형태**로 구분된다(§17). 이 규칙들은 렌더 코드를 "예뻐 보이게" 만지는 순간 조용히 지워진다. §5가 그것을 잡는다.

## 2. 런타임 가드 — `src/sim/guards.ts`

### 2.1 가드가 되는 조건

가드는 **개발 빌드에서만 돌고, 위반하면 즉시 던진다.** `import.meta.env.DEV` 분기 안에 두어 프로덕션 번들에서는 통째로 사라진다. 치트 모드(`src/dev/`)는 제출 빌드에 남지만(§18.6) 가드는 남지 않는다 — 둘은 다른 물건이다.

**헤드리스 시뮬에서는 던지는 대신 런을 중단하고 리포트를 `"status": "guard-violation"`으로 표시한다.** 규칙이 깨진 런의 격파 시간과 명중률은 밸런스 데이터가 아니기 때문이다. 스펙 §18.5가 오염된 런에 대해 쓴 논리와 같다 — 틀렸을 때의 손해가 한쪽으로만 나야 한다.

### 2.3 불변 조건 가드

INV-1·INV-2는 **카드 실효 수치를 다시 계산할 때마다** 검사한다. 재계산이 도는 시점은 세 곳이다 — 카드 선택 확정(§11.1), 치트 메뉴의 카드 변경(§18.4 "변경 즉시 §11.6의 보정 순서를 다시 실행"), 그리고 런 시작.

| ID | 조건 (§5.1) | 검사식 | 위반 시 |
|---|---|---|---|
| **INV-1** | 쿨다운 ≥ 활성 시간 + 0.05초 | `cooldownSec >= activeSec + 0.05` — 단 E07 보유 시 `cooldownSec === activeSec + 0.04` (§11.6의 E07 예외) | throw |
| **INV-2** | 패리 유래 무적 ≤ 쿨다운 × 0.75 | `invulnSec <= cooldownSec * 0.75 + ε` | throw |

여기서 중요한 것은 **가드가 보정을 하지 않는다**는 점이다. 보정은 §11.6의 7·8단계가 이미 했어야 하는 일이고, 가드는 그 보정이 실행되지 않았거나 순서가 틀렸을 때 잡는 그물이다. 가드가 값을 고치기 시작하면 보정 로직의 버그가 영원히 안 보인다.

| 보스 격파 연출 2.0초 | 정지 후 리셋 | §10.1이 모든 적 탄환을 지우도록 규정 |

| **살아 있는 모든 발사원이 HR-09로 억제된 상태** | **정지. 그리고 면제가 걸린 사실을 리포트에 남긴다** | [01](01_설계_결정.md) §4-C S-04. 보스 정위치(`y ≤ 520`)와 플레이어 영역(`y ≥ 620`)의 최소 거리 100u가 보스가 쓰는 어떤 탄종의 억제 거리(최소 145u, 최대 458u)보다도 작아서, 플레이어가 보스 바로 아래에 붙으면 **정상 플레이인데 발사원 전체가 억제된다.** 면제가 없으면 가드가 사람 플레이와 헤드리스 양쪽에서 던진다 |

**마지막 행은 다른 넷과 성격이 다르다.** 앞의 넷은 스펙이 규정한 구간이라 면제가 정답이지만, 이건 **스펙 두 규칙이 부딪히는 자리를 가드가 안 던지게 막아 둔 임시 조치**다. 그래서 리포트에 남긴다 — 면제가 얼마나 자주 걸렸는지가 곧 S-04가 실제 플레이에서 얼마나 자주 발생하는지의 측정값이고, 스펙 개정 판단의 근거가 된다. **면제는 가드만 잠재우고 교착 자체는 못 고친다는 사실도 같이 적는다.**

### 2.5 HR-04는 어디까지 자동화되는가

정직하게 나누면 3단이고, **3단은 자동화되지 않는다.**

| 단 | 검사 내용 | 자동화 |
|---|---|---|
| **1단 — 전면 차단 금지** | 활성 패리 불가 위협(P9·E06 장판, P12 관통선, 돌진 궤적, 보스 본체)의 합집합이 플레이어 이동 영역 `x ∈ [70, 1010]`, `y ∈ [620, 1830]`(§3.1)을 **전부 덮지 않는다.** HR-04 본문의 "화면 전체를 덮는 패리 불가 공격은 금지된다"를 글자 그대로 옮긴 것이다 | **가능.** 이동 영역을 격자로 나눠(격자 간격은 검사 도구의 파라미터이지 스펙 값이 아니다) 빈 칸 존재를 단언 |
| **2단 — 예고 시간 안에 닿는 안전 지대** | 예고가 발동한 시점의 플레이어 위치에서 `이동 속도 520 u/s × 예고 시간` 안에 도달할 수 있는 빈 칸이 있는지. 예고 시간은 §6.2가 준다 — 착탄 예고 원 1.2초(→ 624u), 관통 예고선 0.8초(→ 416u), 돌진 방향선 1.0초(→ 520u) | **가능.** 단 직선 거리 근사이고 경로에 다른 위협이 있는지는 보지 않는다 |
| **3단 — 실제로 피할 만한가** | 적 탄환이 동시에 깔린 상태에서 그 안전 지대로 가는 경로가 실제로 열려 있는지, 그 이동이 패리를 포기해야만 가능한지 | **불가능.** 사람이 플레이해서 판단한다 |

3단이 자동화되지 않는 이유는 계산량이 아니라 **판정 기준이 없기 때문이다.** "피할 수 있다"는 탄막 밀도·플레이어 실력·패리를 포기할 가치가 있는지가 모두 섞인 값이고, 스펙에 그 임계값이 없다. 임계값을 여기서 지어내면 그 숫자가 스펙보다 위에 서게 된다.

**그래서 3단은 §7 완료 정의의 수동 항목으로 옮긴다.** 대상은 P9·E06 장판이 나오는 S4·S5, P12가 나오는 S5 W4 이후, 그리고 보스 돌진 패턴이다. 치트 모드(§18.3)로 각 구간에 직접 들어가 확인하며, 확인했다는 사실이 기록으로 남아야 한다.

```ts
/** 플레이어 정면(위쪽) 거리 d에 조총탄 하나만 두고, 그 탄이 플레이어로 내려오는 세계. */
```

**다중 패리 케이스 한 개가 §5.3의 네 문장을 전부 잠근다**([12](12_통합_계약.md) E-19). [12](12_통합_계약.md) §6이 머니샷을 「한 번의 패리가 여러 발을 동시에 반사하는 순간」으로 확정했는데, 위 표의 나머지 14개 케이스는 **전부 1발짜리**였다 — 계획의 최고 장면에 테스트가 하나도 없었다. `d = 20 / 40 / 60`이면 세 밴드가 한 번에 걸리므로, 등급을 발마다 매기는 것과 등급 종속 값을 1회만 적용하는 것이 같은 단언 묶음 안에서 갈린다.

**콤보만 스펙 두 절이 갈린다.** §5.3은 "히트스톱·점수·콤보는 그중 최고 등급 기준으로 **1회만** 적용한다"이고 §12.2는 "패리로 발사체를 1발 처리할 때마다 +1 (**다중 패리는 개수만큼 증가**)"이다. 콤보에는 등급별 값이 없어 "최고 등급 기준"이 뜻을 못 가지므로 **테스트는 §12.2를 따른다** — §5.3의 "1회만"은 등급에 종속된 값(히트스톱·점수)에 걸리는 문장으로 읽는다.

### 3.2 `tests/reflect.test.ts` — 반사 공식과 데미지 계산 순서

**반사 공식** (§5.5) `v' = v − 2(v·n)n`, `n = normalize(탄환위치 − 플레이어위치)`.

| 케이스 | 기대 | 출처 |
|---|---|---|
| 정면 패리 | `v' ≈ −v`. 쏜 적 방향으로 되돌아간다 | §5.5 |
| 가장자리 패리 | 크게 꺾여 옆으로 튄다. `\|v'\| = \|v\|` (배수 적용 전) | §5.5 |
| 모든 성립 케이스 | `v' · n > 0`. 반사탄은 **언제나** 플레이어에게서 멀어지며 출발 | §5.5 |
| 속도 | 편전 P3 880 u/s × S5 탄속 1.34 × GREAT 2.6 = 3066 → **2400으로 절단** | §6.1, §14.1, §5.3, §7.1 |
| 수명 | 3.0초 후 소멸. 재패리 시 3.0초로 재설정 | §7.1, §7.4 |
| 자해 유예 | 재패리마다 0.15초 새로 시작 | §7.4 |
| **유도 소멸** | 유도 중인 P11(잔여 0.8초)을 패리 → 반사탄의 `homingRemainingSec === 0`, 이후 스텝에서 방향이 `normalize(v')` 그대로 유지된다 | [01](01_설계_결정.md) §4-B S-12 · §7.1 "유도 \| 기본 없음" |
| **R03 예외** | 같은 조건에 R03 보유 → 유도가 다시 붙되 대상은 **가장 가까운 적**이다. 플레이어가 아니다 | §11.4 R03 |

`v' · n > 0`이 이 파일에서 제일 중요하다. HR-07이 반사탄을 플레이어에게 유해하게 만들었는데도 반사 즉시 자기 탄에 맞지 않는 이유가 이 부등식 하나이기 때문이다(§5.5). 이것을 개별 케이스로 두지 않고 **모든 성립 케이스에 대한 사후 조건**으로 건다.

**데미지 계산 순서** (§7.2) — 스펙의 검산 예시 두 개를 그대로 테스트로 옮긴다.

| 예시 | 계산 | 기대 |
|---|---|---|
| 1 | 조총탄 BRP 14, GREAT, N01 3중첩(+45%), R04(GREAT 시 ×1.5) | `14 × 3.5 × 1.45 × 1.5` → **106** |
| 2-a | 함포탄 BRP 55, NOT BAD, 카드 없음 | `55 × 1.0` → **55** |
| 2-b | 같은 탄을 추격해 GREAT로 재패리 | `55 × 3.5` → **192** (누적 아님) |

```ts
import { describe, expect, it } from 'vitest';
import { reflect } from '../src/core/vec';
import { computeReflectDamage, reparry } from '../src/sim/reflect';

describe('§5.5 반사 공식', () => {
  it('정면으로 받으면 쏜 방향으로 되돌아간다', () => {
    const n = { x: 0, y: -1 };                    // 탄환이 플레이어 바로 위
    const v = { x: 0, y: 760 };                   // 아래로 내려오는 중
    const out = reflect(v, n);
    expect(out.x).toBeCloseTo(0, 6);
    expect(out.y).toBeCloseTo(-760, 6);
  });

  it('가장자리로 받으면 크게 꺾이고 속력은 보존된다', () => {
    const n = { x: 0.6, y: -0.8 };
    const v = { x: 0, y: 760 };
    const out = reflect(v, n);
    expect(out.x).toBeCloseTo(729.6, 3);
    expect(out.y).toBeCloseTo(-212.8, 3);
    expect(Math.hypot(out.x, out.y)).toBeCloseTo(760, 3);
  });

  it('반사탄은 언제나 플레이어에게서 멀어진다 (v·n < 0 → v′·n > 0)', () => {
    for (let deg = 0; deg < 360; deg += 7) {
      const a = (deg * Math.PI) / 180;
      const n = { x: Math.cos(a), y: Math.sin(a) };
      const v = { x: -n.x * 500 + n.y * 300, y: -n.y * 500 - n.x * 300 };  // v·n = −500
      const out = reflect(v, n);
      expect(out.x * n.x + out.y * n.y).toBeGreaterThan(0);
    }
  });
});

describe('§7.2 데미지 계산 순서', () => {
  it('예시 1 — 조총탄 GREAT + N01×3 + R04', () => {
    expect(computeReflectDamage({
      brp: 14,               // §6.1
      gradeMul: 3.5,         // §5.3 GREAT
      additivePct: 0.45,     // §11.3 N01 +15% × 3중첩
      conditionalMul: 1.5,   // §11.4 R04
      splitCoef: 1,
    })).toBe(106);
  });

  it('예시 2 — 재패리는 직전 데미지가 아니라 언제나 BRP에서 다시 시작한다', () => {
    const first = computeReflectDamage({ brp: 55, gradeMul: 1.0, additivePct: 0, conditionalMul: 1, splitCoef: 1 });
    expect(first).toBe(55);

    const again = reparry({ brp: 55, previousDamage: first }, { gradeMul: 3.5 });
    expect(again.damage).toBe(192);              // 55 × 3.5, 55 × 1.0 × 3.5가 아니다
    expect(again.lifetimeSec).toBe(3.0);         // §7.4 수명 재설정
    expect(again.graceSec).toBe(0.15);           // §7.4 자해 유예 재시작
  });
});
```

> **소수점 주의.** 예시 1의 실제 곱은 `14 × 3.5 × 1.45 × 1.5 = 106.575`인데 스펙 §7.2는 중간값을 `106.5`로 적었다. §7.2의 6단계가 "소수점 내림"이므로 두 경로 모두 최종값 **106**에서 만난다. 테스트는 최종값만 단언한다 — 중간 표기를 단언하면 스펙의 반올림 표기에 코드가 묶인다.

#### 3.3.1 밴드 순서 보정(6단계)은 현재 카드로는 발동하지 않는다

§11.6이 "결과가 `GREAT 상한 > GOOD 상한`이 되면 GREAT 상한을 GOOD 상한 값으로 자른다"고 규정했다. 그런데 밴드를 건드리는 카드를 전부 모아 최댓값을 계산하면 이렇다.

| 카드 | 효과 | 최대 중첩 | 밴드 기여 |
|---|---|---|---|
| N07 굳은살 | GOOD 밴드 상한 +4u | 2 | GOOD +8 |
| N08 정신 집중 | GREAT 밴드 상한 +3u | 2 | GREAT +6 |
| E05 영점 패리 | GREAT 밴드 상한 +10u | 1 | GREAT +10 |
| R09 넓은 인식 | GREAT 밴드 상한 −6u | 1 | GREAT −6 |

GREAT 상한의 도달 가능한 최댓값은 `28 + 6 + 10 = 44`(R09를 안 들었을 때)이고, GOOD 상한의 도달 가능한 최솟값은 **48**이다 — GOOD을 내리는 카드가 없기 때문이다. `44 < 48`이므로 **6단계는 현재 31종 카드 표에서 구조적으로 발동할 수 없다.**

그래서 테스트를 두 갈래로 나눈다.

```ts

    expect(orderBands({ greatMaxU: 52, goodMaxU: 48, radiusU: 70 }))
      .toEqual({ greatMaxU: 48, goodMaxU: 48, radiusU: 70 });
  });

  it('실제 카드 표로 만들 수 있는 모든 빌드에서는 발동하지 않는다', () => {
    for (const build of everyLegalBandBuild()) {          // R09 × {0,1} × N08 × {0,1,2} × E05 × {0,1} × N07 × {0,1,2}
      const stats = applyCardStack(build);
      expect(stats.greatMaxU).toBeLessThan(stats.goodMaxU);
      expect(stats.clamps.map((c) => c.step)).not.toContain(6);
    }
  });
});
```

두 번째 테스트가 **회귀 감시 장치**다. 나중에 GOOD 밴드를 내리는 카드나 GREAT를 더 올리는 카드가 추가되면 이 테스트가 먼저 빨간불이 되고, 그때 6단계가 처음으로 살아 있는 코드가 된다.

### 3.4 `tests/caps.test.ts` — §3.2의 세 가지 상한 처리는 서로 다르다

#### 3.5.1 단일 소스 단언 — 같은 숫자가 두 곳에 살지 않는가

타입이 못 잡는 것은 값 **사이의 관계**뿐인데, 이 계획의 실제 고장은 전부 거기서 난다. [12_통합_계약.md](12_통합_계약.md) §5가 중복된 수치 넷을 한쪽으로 확정했고, **테스트는 확정된 쪽만 읽는다.**

| 값 | 단일 소스 | 테스트가 읽지 않는 곳 |
|---|---|---|
| 히트스톱 등급별 | `config/parry.ts`의 `PARRY_BANDS[].hitstopSec` | `feel.ts`의 `HITSTOP_SEC` — 등급 3개는 삭제됐고 `playerHit`과 `HITSTOP_BUDGET_PER_SEC`만 남는다 |
| 보스 HP | `BossDef.hp` (`config/bosses/boss-N-*.ts`) | `difficulty.ts`의 `bossHp` 열 — 삭제됐다 |
| `lockoutSec` | **유도한다.** `cooldownSec − activeSec` | `parry.ts`에 저장된 리터럴 — 저장하지 않는다 |
| `peakEnemies` | **헤드리스 리포트가 계산한다** (§4.3의 `peaks.enemies`) | `difficulty.ts`에 손으로 적은 값 — 삭제됐다. 실제 도달치는 `config/stages/*`가 만든다 |

관계 단언 6줄이 그것을 잠근다([12](12_통합_계약.md) §5.1).


세 번째 단언이 특히 중요하다. **삭제한 필드는 삭제된 채로 있어야 한다** — 누군가 편의로 `bossHp`를 되살리면 그 순간부터 보스 HP가 두 곳에 살고, 두 값이 어긋나는 날 어느 쪽이 진짜인지 알 방법이 없다.

**히트스톱 단언이 둘로 갈린 이유**([12](12_통합_계약.md) E-20). 원래 있던 단언 하나는 `1 / 0.24 × 0.075 = 0.3125 ≤ 0.32`라 **통과가 보장돼 있었다** — 누적 상한을 코드에서 통째로 지워도 초록불이다. 그런데 스펙 §5.3이 상한을 만든 이유를 직접 적어 두었다.

> 쿨다운을 더 줄이는 카드(R10·E07)를 든 빌드는 이 계산을 넘어선다. 그 경우 누적 상한이 초과분을 잘라내며, **이것이 상한의 존재 이유다.**

E07은 활성 시간 + 0.04초가 곧 쿨다운이므로 기본값에서 **0.19초**이고(§11.5), `1 / 0.19 × 0.075 = 0.395`로 0.32를 **23.4% 넘는다.** 그래서 두 번째 단언은 리터럴이 아니라 `applyCardStack(['E07'])`의 결과 쿨다운에서 계산하고, **초과 자체를 확인한다.**

**초과한 뒤 `clock.ts`가 실제로 잘라내는지는 여기서 못 본다.** 그건 값 사이의 관계가 아니라 동작이다. §3.7의 `core.test.ts`가 슬라이딩 창 시뮬로 그 절단을 검증한다.

§12.2의 콤보 경고 구간도 같은 성격이다 — `COMBO_WARN_SEC = 0.8`초가 `config/scoring.ts`에 하나만 존재하고([12](12_통합_계약.md) §8-5. [06](06_렌더링과_게임필.md)이 0.6초, [07](07_오디오_설계.md)이 0.8초로 갈렸던 자리다), 게이지가 적색으로 바뀌는 비율은 `COMBO_WARN_SEC / COMBO_HOLD_SEC`로 유도한다. `config/ui.ts`는 그 비율을 저장하지 않는다([08](08_화면과_UI.md) §9).

### 3.6 `tests/determinism.test.ts` — D-05가 실제로 지켜지는지

세 가지를 본다. 앞의 둘은 결과를, 셋째는 원인을 본다.

**소스 검사의 범위를 `src/sim/`·`src/config/`·`src/core/rng.ts`로 한정한 것은 의도적이다.** 시드 값 자체는 어딘가에서 만들어져야 하고, 그 자리는 `screens/`나 `dev/`다. `core/rng.ts`를 포함시킨 이유는 mulberry32가 순수 함수여야 하기 때문이다 — 여기에 `Math.random()`이 한 줄 들어가면 나머지 두 테스트가 전부 무의미해진다.

**`src/render/`는 `Math.random`만 따로 막는다.** 규칙이 sim과 다르기 때문이다 — 렌더는 `realDt`를 인자로 받으므로 시각 API를 부를 이유가 없지만, **난수는 자기 몫의 시드 스트림으로 뽑아야 한다**([02_아키텍처.md](02_아키텍처.md) §4.1). 두 요구가 걸려 있다: §5의 시각 회귀가 픽셀을 대조하려면 같은 상태가 같은 그림을 내야 하고, [06](06_렌더링과_게임필.md) §7의 촬영 재현도 프레임 단위로는 그것이 있어야 성립한다. [06](06_렌더링과_게임필.md) §1.11이 목업 `burst`의 `Math.random()`(engine.js:1927-1928)을 D-05 위반으로 지목한 것이 이 검사가 잡을 자리다. **`src/audio/`는 넣지 않는다** — 소리는 픽셀에도 판정에도 남지 않아 재현 대상이 아니다.

`performance.now()`까지 막은 것은 HR-06 때문이다. sim 안에서 실시간을 읽으면 프레임률이 판정에 영향을 주기 시작한다.

**지터 배열의 최댓값이 50.0ms였고, 그대로 두면 이 테스트는 설계상 반드시 실패한다**([12](12_통합_계약.md) E-19). [11](11_구현_계획.md) §5.1이 `MAX_STEPS = 5`로 정했고 `FIXED_DT = 1/120초`이므로 한 프레임이 소화할 수 있는 최대치는 `5 × 8.333 = 41.67ms`다. 50.0ms 프레임은 6스텝을 요구하는데 루프가 5에서 끊고 나머지 **8.33ms를 버린다** — spiral of death를 막는 그 장치가 정확히 여기서 작동한다. 5프레임 주기의 실시간 124.63ms 중 sim에 도달하는 것이 108.33ms뿐이라 **13.1%가 사라지고**, `stateHash`와 `simSec` 단언이 둘 다 깨진다.

**그래서 배열 최댓값을 41.0으로 내리고, 버리기 경로에 별도 케이스를 준다.** 누적기는 스텝을 뽑고 나면 언제나 `FIXED_DT = 8.333ms` 미만이므로 `41.0 + 8.33 = 49.33 < 5 × 8.333 + 8.333 = 50.0`이고, **어떤 프레임에서도 5스텝을 안 넘어 버려지는 시간이 0이 된다.**

**별도 케이스가 없으면 이 경로는 우연한 빨간불로만 나타난다.** 그리고 그것을 처음 본 사람이 할 가장 자연스러운 일은 `MAX_STEPS`를 올리는 것이다 — spiral of death 방어를 지우는 행위이고, 지운 사람은 자기가 무엇을 지웠는지 모른다. 그러므로 **sim 시간이 실시간에 정당하게 뒤진다는 사실 자체를 단언으로 적어 둔다.** 프레임 50ms × 100회면 실시간 5.000초에 sim 4.167초로 16.7% 뒤지고, 그게 버그가 아니라 규격이다.

```ts
import { describe, expect, it } from 'vitest';
import { createClock } from '../src/core/clock';
import { applyCardStack } from '../src/sim/cards';
import { PARRY_BANDS } from '../src/config/parry';
import { HITSTOP_BUDGET_PER_SEC } from '../src/config/feel';

describe('§3.2 히트스톱 누적 상한 — 초과분이 실제로 잘린다', () => {
  it('E07 빌드로 1초를 채우면 정지 총량이 0.32초에서 멈춘다', () => {
    const cooldownSec = applyCardStack(['E07']).cooldownSec;      // 0.19
    const great = PARRY_BANDS[0].hitstopSec;                      // 0.075
    const clock = createClock();
    let frozen = 0;

    // sim 1초 동안 쿨다운마다 GREAT 패리 — 요청이 초당 1/0.19 × 0.075 = 0.395초로 상한을 넘는다
    for (let t = 0; t < 1.0; t += cooldownSec) {
      frozen += clock.requestHitstop(great, t);                   // 실제로 승인된 길이를 돌려준다
    }
    expect(frozen).toBeLessThanOrEqual(HITSTOP_BUDGET_PER_SEC);   // 0.32
    expect(frozen).toBeCloseTo(HITSTOP_BUDGET_PER_SEC, 3);        // 상한에 닿는다 — 안 닿으면 창이 틀렸다
  });

  it('창은 sim 초로 민다 — 실시간으로 밀면 상한이 느슨해진다', () => {
    const clock = createClock();
    clock.requestHitstop(0.075, 0.0);
    expect(clock.budgetUsedSec(0.99)).toBeCloseTo(0.075, 6);      // 아직 창 안
    expect(clock.budgetUsedSec(1.01)).toBeCloseTo(0, 6);          // 창을 벗어났다
  });
});
```

두 번째 케이스가 [12](12_통합_계약.md) E-02의 나머지 절반이다. 같은 0.32초라도 실시간 창으로 밀면 1주기가 `0.24 + 0.075 = 0.315`초라 초당 3.175회가 되고, 그러면 상한이 사실상 안 걸린다. **`clock.ts`의 시그니처가 "sim 초"임을 못 박는 자리가 여기다.**

### 3.8 `tests/progress.test.ts` — 런이 실제로 진행되는가

## 4. 헤드리스 밸런스 시뮬 — `src/dev/headless.ts`

### 4.1 무엇인가

캔버스 없이 sim만 실시간보다 빠르게 돌리고, **숫자로 된 리포트 하나**를 뱉는다. §1.2의 실패를 잡는 유일한 도구다.

성립 조건은 D-05 하나다 — 같은 시드가 같은 결과를 내야 이 리포트가 근거가 된다. 그리고 D-10이 나머지 절반을 댄다. §14.4의 검산표가 전제하는 조건은 **"카드 미획득 상태"**인데, 정상 진행으로는 S3 보스를 카드 0장으로 만날 수가 없다. 치트 모드의 스테이지 자유 입장(§18.3)과 카드 자유 선택(§18.4)이 그 조건을 만든다.

> 치트로 만든 런은 §18.5에 따라 오염으로 표시되지만, **§14의 실측 데이터로서는 유효하다.** §18.1이 "치트 모드가 조작하는 것은 진행 상태뿐이고 전투 규칙 자체는 하나도 바뀌지 않는다"고 규정했고, 애초에 §18을 만든 이유가 T-05·T-06·T-07의 측정이다. 오염 표시가 배제하는 것은 **점수 기록**이지 밸런스 수치가 아니다.

### 4.2 입력을 어디서 받는가 — 여기가 제일 틀리기 쉽다

두 가지 모드가 있고, **둘의 용도가 다르다.**

| 모드 | 무엇 | 장점 | 한계 |
|---|---|---|---|
| **기록 재생** | `dev/capture.ts`로 사람이 한 판 친 입력을 그대로 다시 먹인다 | 실제 플레이의 성공률·등급 분포가 그대로 나온다 | **밸런스를 고치면 즉시 어긋난다.** 입력이 시각 기반이라 탄속을 1% 바꾸면 그 뒤 전부가 딴 판이 된다. 영상 촬영과 버그 재현용 |
| **스크립트 봇** | 가장 가까운 접근 중인 발사체의 예측 거리가 목표 밴드를 지나는 순간 패리를 넣는 반응형 로직 | 밸런스를 고쳐도 계속 유효하다 | 봇의 실력이 곧 측정값이 된다 |

**밸런스 측정의 기본은 봇이다.** 그런데 봇을 "잘 치도록" 만들면 안 된다. §14.4의 보스 HP는 **패리 성공률 50%, 평균 등급 GOOD(×2.0), 재패리 0회**라는 T-02의 전제 위에 세워져 있다. 성공률 100%짜리 봇으로 잰 격파 시간은 §14.4의 어떤 칸과도 비교할 수 없다.

그래서 봇은 **타이밍 오차 파라미터**를 하나 갖는다. 목표 거리에 대한 오차를 주입된 시드 RNG에서 뽑고(D-05를 지켜야 하므로 `Math.random()`이 아니다), **측정된 성공률이 T-02의 50%에 맞도록 그 오차를 먼저 보정한다.** 보정이 끝난 뒤에야 보스 격파 시간이 §14.4와 같은 축 위에 놓인다.

봇의 캘리브레이션 자체가 첫 번째 리포트 항목이다.

**그런데 위 문단이 정한 것은 봇의 「언제」뿐이고 「어디」가 비어 있다.** 이 게임에서는 그 둘이 같은 급이 아니다 — 스펙 §5.5가 **"몸 위치가 조준이다"**라고 못 박았기 때문에, 봇이 어디에 서 있는지가 반사각을 정하고 반사각이 명중률을 정하고 명중률이 곧 보스 격파 시간이다. 위치 정책을 안 정하면 §14.4의 어느 칸과도 비교할 수 없는 숫자가 나오고, 무엇보다 [01](01_설계_결정.md) R-03이 이 리포트에 맡긴 **반사탄 명중률** 자체가 위치 정책의 함수가 된다.

**봇의 이동 정책을 셋으로 고정한다.**

| # | 규칙 | 왜 |
|---|---|---|
| 1 | **보스전 중 `y ≥ 1000`을 유지한다** | [01](01_설계_결정.md) §4-C S-04. 그 위로 올라가면 보스의 발사원 전체가 HR-09로 억제되어 측정이 숫자 대신 `guard-violation`으로 끝난다. **이 제약은 리포트 머리에 찍는다** — 플레이어 영역의 약 30%를 안 밟고 나온 값이라는 사실이 값과 같이 다녀야 한다 |
| 2 | **가장 가까운 접근 중인 발사체를 향해 x축으로만 정렬한다.** y는 1번의 하한과 §3.1의 상한(1830) 사이에서 고정 | §5.5상 정면으로 받을수록 반사탄이 쏜 적에게 곧게 돌아간다. x 정렬은 그 "정면"을 만드는 최소 행동이고, 이보다 영리하게 만들면 봇 실력이 측정값이 된다(위 문단과 같은 이유) |
| 3 | **반사탄을 쫓지 않는다.** 재패리 0회가 T-02의 전제다 | §7.4가 재패리를 "위치를 버리고 사오는 딜 증폭"으로 정의했고 §14.4가 그것을 지속 DPS에서 뺐다. 봇이 쫓으면 전제를 벗어난다 |

**세 규칙 다 리포트에 명시하고, 바꾼 채로 잰 값은 §14.4와 대조하지 않는다.** 봇의 타이밍 오차를 T-02의 50%에 맞춘 것과 같은 이유다 — 전제를 맞춰야 비교가 성립한다.

**S5의 `peaks.enemies == 20`은 §9.7의 편성으로 만족될 수 없다.** W5 자체가 `E-A ×6 + E-E ×4 + E-G ×3 + E-H ×3 = 16`이므로, 20에 닿으려면 W4의 생존자가 **정확히 4기** W5가 절정에 이르는 14초 동안 살아 있어야 한다. 그런데 W4 편성은 `E-I ×3 + E-F ×4 + E-C ×4`이고 **E-F는 통과형(F-6)이라 화면을 지나가 버리고, E-C는 하강해 화면 밖으로 나간다.** 남는 후보는 E-I 3기뿐이다. 즉 `== 20`은 편성이 주지 않는 수를 요구하는 합격선이고, 그대로 두면 리포트가 영구 빨간불이 된다.

**그래서 합격선을 「≥ 18 **그리고** 스폰 지연 1회 이상」으로 고친다.** §9.7이 실제로 요구한 것은 숫자 20 자체가 아니라 **"신규 스폰이 지연되는 상황이 의도적으로 발생하는 유일한 구간"**이고, 지연 발생 여부가 그 요구의 직접 관측값이다. 18은 W5의 16에 잔존 2기를 더한 값 — 편성이 실제로 만들 수 있는 범위 안이다.

**둘 중 하나라도 못 채우면 그때 손대는 것은 합격선이 아니라 W4다.** 조정 규칙은 하나다 — **W4의 잔류형(E-I)을 3 → 5로 올린다.** E-F와 E-C는 정의상 남지 않으므로 그 둘의 수를 늘려도 피크가 안 오르고, W5 편성을 늘리면 §14.1의 동시 잡몹 상한 20을 웨이브 하나로 채워 "잔존이 합쳐져 닿는다"는 §9.7의 문장이 뜻을 잃는다.

### 4.5 반사탄 명중률 — 손익분기점을 미리 계산해 둔다

§14.4의 추정 DPS는 **모든 반사탄이 맞는다**는 가정 위에 있다. 실제 명중률을 `h`라 하면 실측 DPS ≈ 추정 DPS × h이므로, **목표 격파 시간을 정확히 맞추는 명중률**을 §14.4의 두 열만으로 미리 뽑을 수 있다.

| 보스 | 필요 DPS | 추정 DPS | 손익분기 명중률 `h*` | 뜻 |
|---|---|---|---|---|
| B1 | 60.4 | 58.2 | **103.8%** | 100%를 넘으므로 어떤 명중률로도 24초에 못 죽는다. §14.4가 −4%를 그대로 두기로 한 것과 같은 말이다 |
| B2 | 83.3 | 100.5 | **82.9%** | 명중률이 83% 아래면 27초를 넘긴다. 다섯 중 가장 빡빡하다 |
| B3 | 110.3 | 297 | **37.1%** | §14.4가 "+169%, 포문 각도 제약으로 실효 하락"이라고 적은 그 여유의 실체 |
| B4 | 120.3 | 150.8 | **79.8%** | |
| B5 | 137.8 | 299.5 | **46.0%** | |

리포트는 `measuredHitRate`와 `breakEvenHitRate`를 나란히 찍는다. **두 값의 대소가 곧 T-01의 판정이다.** 그리고 이 표가 §14.4의 "추정치만으로 HP를 올리지 않는다"를 실행 가능한 절차로 바꾼다 — 실측 `h`를 얻은 뒤 `HP_new = HP × (h / h*)` 로 재산정하고, 그 결과를 §14.4 표에 다시 적는다.

B2가 다섯 중 제일 위험하다는 것이 이 계산의 부수 결과다. §14.4가 "+21%"라고만 적어 둔 칸이 명중률 축에서는 83%를 요구한다.

**T-03의 검사식을 스펙의 논리 그대로 옮긴다.** §14.4가 E-B 궁병을 "경계 — 조총탄(14)으로는 3발. 실전에서는 두 탄종이 섞여 공급되므로 통과로 본다"고 판정했다. 따라서 검사는 웨이브 단위가 아니라 **스테이지 단위**로 공급 탄종을 모은다.

```ts
it('T-03 — S1 원거리 잡몹은 NOT BAD 3발 이내 (§14.4)', () => {
  const stage1Brp = [14, 10];                       // §9.3 편성이 공급하는 P2 조총탄 · P1 화살
  const best = Math.max(...stage1Brp);              // NOT BAD 배수는 ×1.0 (§5.3)
  for (const id of ['E-A', 'E-B'] as const) {       // 근접형 E-C · E-D는 T-03에서 제외
    expect(Math.ceil(ENEMIES[id].hp / best)).toBeLessThanOrEqual(3);
  }
});
```

E-A는 `ceil(30 / 14) = 3`, E-B는 `ceil(36 / 14) = 3`으로 통과한다. **다만 S1 W3은 편성이 E-B ×5 + E-D ×5라 조총탄 공급원이 없고, 화살만으로는 `ceil(36 / 10) = 4`발이 필요하다.** §14.4가 이 상태를 알고 통과로 판정했으므로 테스트도 스테이지 단위로 두되, 이 사실을 주석으로 남긴다 — 나중에 W3에서 체감이 나쁘다는 보고가 오면 원인을 다시 찾을 필요가 없다.

## 5. 시각 회귀 — 목업 정지 프레임 대조

### 5.1 대조가 가능한 이유

목업은 애니메이션이 아니라 **결정론적으로 계산된 한 프레임**이다. `_shared/engine.js`의 `still()`이 씬을 고정 스텝으로 앞으로 돌린 뒤 딱 한 번 그린다. 주소에 `?at=<초>`를 붙이면 같은 런의 다른 순간이 나오고, 발행된 프레임이 정확히 그렇게 골라졌다(`engine.js:2009-2012`).

그리고 결정적인 것 하나가 이미 노출되어 있다.

```js
window.HWSTATE = s;    // engine.js:2035 — still()이 그린 그 상태 객체 그대로
```

**이것이 대조의 접합부다.** 게임의 렌더러에게 목업과 같은 상태를 먹일 수 있다.

### 5.2 하네스 설계

**먼저 의존성 문제를 닫는다.** 아래 1번이 브라우저 드라이버를 요구하는데 [11](11_구현_계획.md) §2가 "`vite`·`vitest`·`typescript`·`eslint` 외 의존성 0개"를 못 박았다. 둘 다 지킬 수는 없으므로 **범위를 갈라 푼다.**

| 구분 | 규칙 |
|---|---|
| **런타임·번들 의존성** | **0개 그대로.** D-03의 목적이 여기다 — `dist/index.html` 한 파일이 오프라인에서 열리고, 제출물에 라이선스 고지가 붙지 않는 것 |
| **`devDependencies`** | 시각 회귀 하네스에 한해 **브라우저 드라이버 1개를 허용한다.** `tests/visual/`에서만 쓰고 `dist/`에 한 바이트도 안 들어간다 |

**이 예외를 여기 적는 이유는 그것이 공짜가 아니기 때문이다.** [11](11_구현_계획.md) §11이 시각 회귀 하네스를 **잘라내기 4순위**로 이미 정해 두었으므로, 드라이버 설치가 막히거나 시간이 모자라면 **하네스와 함께 이 의존성도 사라진다.** 그때 §5는 수동 대조로 내려가고 판정 주체는 그대로 사람이다(§5.4).

```
1. Playwright가 docs/sample_image/12_parry_moment/index.html?at=2.32 를 연다
2. window.HWSTATE 를 JSON으로 직렬화 (엔티티 좌표·속도·소유권·HP·HUD 값)
3. 그 JSON을 게임의 sim 상태 형태로 옮긴다 (어댑터 1개, tests 밖의 dev/ 아래)
4. 오프스크린 캔버스 1080×1920 에 render/frame.ts 를 그대로 호출해 그린다
5. 목업 캔버스 이미지와 픽셀 대조. 텍스트 영역은 마스킹
6. 사람이 최종 판정
```

**3번이 필수이고, 재시뮬레이션은 금지다.** 목업은 `dt = 1/60`으로 돌지만(`engine.js:2008`) 게임은 D-04에 따라 `1/120`으로 돈다. 같은 시각까지 다시 돌리면 위치가 다르게 나오고, 그 차이는 버그가 아니라 설계 결정이다. **상태를 주입하는 것만이 두 렌더러를 같은 조건에 세운다.**

4번에서 `trauma`(화면 흔들림 누산값)는 0으로 강제한다 — 목업도 정지 프레임에서 같은 처리를 한다(`engine.js:2021`).

### 5.4 정직하게 — 이 하네스는 오탐을 낸다

세 가지가 픽셀을 흔든다.

1. **폰트.** 목업은 Google Fonts를 링크로 부르고 오프라인이면 시스템 폰트로 대체된다(`docs/sample_image/README.md`). `still()`이 `document.fonts.ready` 이후 한 번 더 그리는 것도(`engine.js:2032-2033`) 폰트 도착 여부로 결과가 달라진다는 자백이다. → **텍스트가 그려지는 영역은 전부 마스킹하고, 텍스트의 존재 여부만 별도로 검사한다.**
2. **안티에일리어싱.** 캔버스 2D의 곡선 래스터화는 브라우저와 GPU에 따라 1~2 단계 다르다. → 채널당 허용 오차와 허용 픽셀 비율을 둔다. **이 두 값은 하네스의 조절 손잡이이지 스펙 값이 아니며, 첫 초록불에서 실측해 고정한다.**
3. **목업 자체가 틀린 곳.** [10_스펙_목업_불일치.md](10_스펙_목업_불일치.md)가 목업과 스펙이 어긋난 22곳을 판정했다. 그중 목업이 틀린 것으로 판정된 자리는 **게임이 목업과 달라지는 것이 정상**이다. → 해당 영역은 마스킹하거나, 판정을 반영해 목업을 다시 렌더한 것을 기준선으로 삼는다. **판정 반영 전에는 기준선을 고정하지 않는다.**

그래서 최종 판정은 사람이 한다. 리서치가 같은 결론을 적었다 — "3. 시각 회귀 ... 사람이 눈으로 최종 판정"(`docs/research/claude_research/05_기술_스택_선정.md:371` 부근의 3단 검사표). 하네스의 역할은 **어디가 달라졌는지 좁혀 주는 것**이지 합격을 선언하는 것이 아니다.

### 5.5 15장 중 어느 것을 고정할 것인가

기준은 하나다 — **그 화면이 담고 있는 것이 장면인가 규칙인가.** 규칙을 담은 화면만 고정한다.

| 화면 | 고정 | 그 화면이 잠그는 것 |
|---|---|---|
| `12_parry_moment` | **필수** | 등급 밴드 · 반사 공식 · 5발 동시 반사 · 코어 비가림. 이 게임 전체가 이 한 프레임에 들어 있다 |
| `01_stage1_busanjin` | **필수** | §15.1 HUD 전 요소. 라이프·점수·콤보·쿨다운 링·코어·진행도가 한 화면에 다 있다 |
| `07_stage4_haengju` | **필수** | 패리 불가 화염 장판. 색이 아니라 **형태(해칭)** 로 구분한다는 §17 규칙 |
| `09_stage5_noryang` | **필수** | 잡몹 20기 밀도 + 관통 대창 예고선. 예고 3종 중 하나 |
| `08_boss4_daetong` | **필수** | 착탄 예고 원 + 장판 누적. 예고 3종 중 둘째 |
| `04_boss2_samurai` | **필수** | 돌진 방향선(회피) vs 참격파(패리). 예고 3종 중 셋째이자, **예고가 있으면 피하고 없으면 받아친다**는 HR-05의 교육 구조가 한 화면에 있는 유일한 자리 |
| `13_result` | 권장 | §12.3의 항목 전체가 실제로 표시되는지 |
| `11_card_select` | 권장 | §15.2의 요구 항목 — 중첩 전후 표시, 리롤 잔여 |
| `06_boss3_atakebune` | 권장 | §15.1의 파괴 가능 부위 개별 게이지 |

예고 3종(HR-05)이 세 화면에 나뉘어 있어서, **고정 대상 6장이 예고 규칙 전체를 덮는다.** 이것이 필수와 권장을 가른 실제 기준이다.

### 5.6 기준선 촬영 런은 R06을 실제로 획득한다

목업의 `maxLife`가 스테이지마다 다르다. **S1·S2는 3칸, S3부터는 4칸이다.**

| 화면 | `maxLife` |
|---|---|
| `01_stage1_busanjin/scene.js:7` · `02_boss1/scene.js:8` · `03_stage2/scene.js:7` · `04_boss2_samurai/scene.js:8` | **3** |
| `05_stage3/scene.js:7` · `06_boss3/scene.js:10` · `07_stage4/scene.js:7` · `08_boss4/scene.js:8` · `09_stage5/scene.js:7` · `10_boss5/scene.js:8` · `12_parry_moment/scene.js:28` · `14_pause/scene.js:25` | **4** |

런의 초기 `maxLife`는 3이고 카드로만 오른다(08 §1.2). 그러므로 목업이 그린 것은 **S2 클리어 직후의 2회차 카드 화면에서 R06(최대 라이프 +1, 라이프 +1)을 고른 런**이다 — S2 보스전에서 아직 3칸이고 S3에서 4칸이므로 획득 시점이 그 사이로 좁혀진다.

**기준선 런은 그 상태를 정상 진행으로 만든다** ([12_통합_계약.md](12_통합_계약.md) §8-15). 치트로 최대 라이프를 올리는 길은 막혀 있다 — 메뉴를 여는 순간 오염 표시가 뜨고(§18.5), 그 표시는 화면 하단 전체 폭 띠라(08 §2.3 b) **모든 대조 프레임에 들어간다.** 오염 띠가 박힌 기준선은 §18.6이 실격 사유로 지목한 화면 그 자체이고, 그것과 대조해서 통과한 게임 화면도 같은 띠를 갖게 된다.

그래서 촬영·기준선 런의 카드 획득은 시나리오에 못 박는다 — **2회차에 R06이 제시되는 시드를 고정하고 그것을 고른다.** 시드와 선택 순서는 §4.7의 시나리오 파일과 같은 자리에 커밋한다.

**H-01과 H-03이 이 표의 무게중심이다.** 나머지는 코드가 맞는지를 묻지만 이 둘은 **규칙이 사람에게 전달됐는지**를 묻고, 전달 실패는 어떤 테스트로도 안 잡힌다.

### 7.3 게이트 순서

완료 선언 직전에 이 순서로 돈다. 앞이 빨간불이면 뒤는 돌리지 않는다 — 규칙이 깨진 상태의 밸런스 수치와 스크린샷은 읽을 가치가 없다.

```
1. npx vitest run                       (§3 전체, 필터 없음)
2. npm run headless -- --all            (§4의 시나리오 5종)
3. 시각 회귀 6장                          (§5.5 필수 목록)
4. 브라우저·환경 E-01 ~ E-11             (§6)
5. 완료 정의 D-01 ~ D-07 · H-01 ~ H-04   (§7)
```

## 8. 테스트를 언제 돌리나

### 8.1 구현 중에는 좁게

지금 고친 코드 때문에 깨질 수 있는 테스트만 돌린다. Vitest는 필터를 이미 갖고 있다.

```bash
vitest run -t "d = 28.01 → GOOD"                # 케이스 하나
vitest run tests/parry.test.ts                   # 파일 하나
vitest run tests/cards.test.ts -t "E07 예외"      # 파일 안의 이름 일치 케이스
```

전체를 중간에 돌리면 몇 분이 나가고, 방금 한 편집을 되돌릴 판단은 그 몇 분이 지나기 전에 필요하며, 필요했던 결과 하나가 관심 없는 결과 수백 개 밑에 묻힌다.

### 8.2 마지막에 한 번, 게이트로

마지막 편집이 끝난 뒤 **필터 없이** 전체를 돌린다. 이건 형식이 아니라 관문이다. **통과한 뒤에 완료를 보고하며, 통과와 동시에 보고하거나 통과 전에 보고하지 않는다.**

```bash
npx vitest run
```

### 8.3 좁히기는 무엇이 도는지만 정한다

**무엇이 합격인지는 정하지 않는다.** 실패하는 케이스를 마침 제외하는 필터를 고르는 것은 그 테스트를 건너뛴 것과 같은 행위이며, 예의만 더 갖췄을 뿐이다. 마찬가지로 §4의 헤드리스 시나리오에서 실패하는 보스만 빼고 돌리거나, §5의 대조 대상에서 달라진 화면만 빼는 것도 같다.

돌릴 수 없는 것이 있으면 — 브라우저가 없어서 E-10을 못 쟀다든가 — **못 쟀다고 말한다.** 침묵은 통과로 읽히고, 그것이 절대로 하면 안 되는 유일한 주장이다.
