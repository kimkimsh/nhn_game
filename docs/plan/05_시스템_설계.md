# 05. 시스템 설계

`src/sim/` 아래의 규칙 코드가 무엇을 보장하고 어떤 순서로 도는지. 전제: [02_아키텍처.md](02_아키텍처.md) §1(런타임)·§6(피드백 버스)·§7(카드 경로).

`sim/`은 canvas도 document도 모른다. 색상값도 좌표 리터럴도 없다 — 전부 `config/`에서 온다.

## 1. 한 스텝의 순서

`sim.step(world, dt)`가 하는 일. **이 순서는 임의가 아니고, 바꾸면 스펙이 깨지는 자리가 네 곳 있다.** 각각 표시했다.

```
 1. 타이머 감산            쿨다운, 활성, 무적, 자해 유예, 콤보 유지, 장판 지속, **선입력 버퍼**
                          전부 simDt로 깎는다. 실시간에 남는 것은 press edge 검출뿐이다 (12 E-03)
 2. 입력 소비              이동 벡터 확정, 패리 press edge + 선입력 버퍼 확인
 3. 플레이어 이동          §4.1 이동 영역 클램프
 4. 웨이브 진행            §9.1 시각 기반 전환, 스폰 예약, 소강, 강제 퇴장
                          + §9.7 관통 대창 — sim/lance.ts 갱신 (예고 0.8초 → 판정 0.4초)
 5. 적 스폰                §3.2 잡몹 상한 20 검사 → 초과면 지연 (취소 아님)
 6. 적 행동·발사           §8.1 아키타입 행동, 발사 주기, HR-09 억제 거리 검사
                          + §3.2 동시 적 탄환 상한 검사 → 초과면 억제 (잡몹·보스 **양쪽**)
 7. 보스 진행              §10.1 페이즈 전환, 패턴 순환, 패턴 내부 스케줄
                          B5 페이즈 4는 여기서 sim/lance.ts의 같은 함수를 부른다 (§8.2)
 8. 발사체 적분            §6 이동, P11 유도, 수명, 경계 소멸  ← 10번 스윕용 이전 위치 저장
 9. ★ 패리 판정            §5.2 C1~C5 → §5.3 등급 → §5.5 반사 → §7.2 데미지
                          → §5.1 패리 무적 0.14초 부여 (성립했을 때만)
                          → §5.3 히트스톱 설정 (최고 등급 1회, §3.2 누적 상한 검사)
                          ← 점 표본. 스윕 안 쓴다
10. ★ 피격 판정            §4.2 플레이어 코어 vs 적 탄환·적 본체·반사탄  ← 상대 변위 스윕
11.   반사탄 대 적 판정     §7.3 방패 규칙 포함
12.   장판 판정            §4.3 0.5초 간격 + §9.6 동시 6개 상한 → 초과면 가장 오래된 것부터 제거
                          P9(적)와 E06(카드)이 같은 6개를 공유한다 (§11.5)
13.   상한 정리            §3.2 반사탄 240 초과 시 가장 오래된 것부터 소멸
14.   점수·콤보 정산       §12. **콤보 리셋 판정도 여기 하나가 갖는다** — 1번이 타이머를 깎고
                          여기서만 만료·갱신을 확정한다. 두 곳에서 보면 같은 스텝에 둘 다 일어난다
15.   런 상태 검사         §13.3 라이프 0 → 게임오버
16.   가드 검사            HR-01~09 · INV-1/2 (개발 빌드만)
17.   이벤트 큐 배출       §17 피드백을 render·audio에 넘긴다
```

### 바꾸면 깨지는 네 곳

**① 9번이 10번보다 앞이다.** 스펙 §5.1이 명시했다 — "같은 프레임에서 패리 판정을 피격 판정보다 먼저 처리한다. 이 순서가 없으면 §5.3의 대형 탄환 GREAT가 성립하는 즉시 피격으로 처리된다."

참격파(P5)는 반경 34u이고, GREAT 밴드는 `d ≤ 28`이다. `d = 44`에서 이미 탄 가장자리가 코어(10u)에 닿는다. 즉 **GREAT가 성립하는 모든 위치에서 참격파는 이미 플레이어를 덮고 있다.** 순서가 뒤집히면 대형 탄환의 GREAT는 영원히 나오지 않고, 스펙 §5.3이 "몸으로 받아내는 감각"이라 부른 것이 사라진다.

**② 8번이 9번보다 앞이고, 8번에서 이전 위치를 저장한다.** 두 이유가 서로 다른 번호를 향한다. 9번은 적분 **후** 위치로 판정해야 한다 — 적분 전에 재면 한 스텝 늦은 거리로 등급이 매겨진다. 10번은 이전 위치가 있어야 스윕의 선분을 만들 수 있다([02_아키텍처.md](02_아키텍처.md) §2.2).

**그리고 스윕을 쓰는 것은 10번 하나뿐이다** ([12_통합_계약.md](12_통합_계약.md) §10 E-07).

- **11번(반사탄 대 적)** — 한 스텝 상대 이동 23.5u에 반경 합이 최소 31u다. 못 넘는다.
- **9번(패리)** — 패리 원 지름 140u에 최고 상대 이동 20u라 어떤 탄도 최소 7스텝은 원 안에 있다. 놓칠 방법이 없다. 그리고 **놓칠 수 없다는 것보다 더 중요한 이유가 있다**: 스윕이 주는 것은 선분 위의 최근접 거리인데 스펙 §5.3은 등급을 **패리가 성립한 프레임의 거리**로 정의한다. 패리를 스윕으로 판정하면 등급이 GREAT 쪽으로 체계적으로 편향되고, 그건 최적화가 아니라 스펙 변경이다.
- **10번(피격)** — 선분은 탄환 궤적이 아니라 **상대 변위** `Δ = 탄환 이동 − 플레이어 이동`이고, 대상은 정지한 코어 원이다. 탄환 선분 대 프레임 끝 플레이어 원으로 잡으면 둘이 마주 보고 움직일 때 최근접이 스텝 중간에 생겨 여전히 뚫린다.

**③ 5번이 6번보다 앞이다.** 같은 스텝에 스폰된 적이 그 스텝에 발사하면 예비동작 없이 탄이 나온다. 스폰된 적의 발사 주기는 다음 스텝부터 돈다.

**④ 13번이 9번보다 뒤다.** 반사탄 상한 정리를 패리보다 먼저 하면, 상한에 걸린 순간의 패리가 실패한다. 스펙 §3.2가 못 박았다 — "패리는 언제나 성립해야 하므로 신규 반사탄을 버리지 않는다." 새로 만들고 나서 가장 오래된 것을 지운다.

## 2. 상한 처리 — 셋이 서로 다르다

스펙 §3.2의 세 상한은 **처리 방식이 전부 다르다.** 같게 구현하면 테스트는 통과하는데 게임 감각이 틀어진다.

| 대상 | 상한 | 초과 시 | 왜 |
|---|---|---|---|
| 적 탄환 | 스테이지별 80~280 | **신규 발사 억제.** 화면의 탄을 지우지 않는다. 억제된 발사는 취소되고 다음 주기를 기다린다 | 이미 날아오는 탄이 사라지면 플레이어가 읽던 정보가 증발한다 |
| 반사탄 | 240 | **가장 오래된 것부터 소멸.** 신규는 항상 만든다 | 패리는 언제나 성립해야 한다 |
| 잡몹 | 20 | **신규 스폰 지연.** 상한 아래로 내려갈 때까지 기다린다. 예정 편성은 **취소되지 않는다** | 편성이 취소되면 웨이브 설계가 무의미해진다 |

`sim/caps.ts`가 이 셋을 별개 함수로 갖는다. 하나의 일반화된 "상한 처리"로 묶으면 차이가 지워진다.

## 3. 패리 — `sim/parry.ts`

### 3.1 성립 조건

활성 구간의 **매 스텝**, 아래를 모두 만족하는 발사체가 패리된다. 대상은 적 탄환과 반사탄 양쪽이다(§7.4).

| 조건 | 내용 | 구현 주의 |
|---|---|---|
| C1 | `d ≤ R` — 발사체 중심과 플레이어 중심 사이 거리 | `R`은 `config/parry.ts`가 아니라 **카드 반영 후 스냅샷**에서 읽는다. `d`는 이 스텝의 점 거리다 — 스윕의 최근접 거리가 아니다(§1 ②) |
| C2 | 접근 중일 것 — `v · n < 0`, `n = normalize(발사체위치 − 플레이어위치)` | 스쳐 지나간 것은 안 잡힌다. 반사탄이 보통 여기서 걸러진다 |
| C3 | 패리 가능 플래그 | `config/bullets.ts`의 `isParryable`. P9·P12는 항상 false |
| C4 | 이번 활성 구간에서 아직 패리되지 않았을 것 | **활성 구간 ID를 발사체에 기록한다.** 반사 → 즉시 재패리 무한 반복을 막는다 |
| C5 | 반사탄이면 자해 유예 0.15초가 지났을 것 | §7.1 |

**목업이 여기서 틀렸고 실게임은 다르게 해야 한다.** 목업의 `parry()`(engine.js:1767-1810)는 **입력 순간 1회만** 전체 탄을 훑는다. 스펙 §5.2는 활성 구간의 매 프레임 판정을 요구하고, 그 이유도 적혀 있다 — "활성 구간 도중 새로 반경 안에 들어온 발사체도 그 진입 프레임에 판정된다. 따라서 일찍 누르면 탄환이 원의 바깥 가장자리에서 걸려 낮은 등급이 나오고, 늦게 누를수록 높은 등급이 나온다."

이게 이 게임의 타이밍 설계 전체다. 1회 판정으로 만들면 **누르는 타이밍이 등급에 영향을 주지 않게 된다.**

**C1의 `R`이 카드로 커지면 등급 없는 고리가 생긴다.** N03 3중첩(+6u × 3 = +18u)에 R09(+18u)를 더하면 `70 + 36 = 106u`이고, §11.6 5단계의 반경 상한 150u에 걸리지 않는다. 그런데 밴드 상한은 `PARRY_BANDS[2].maxDistU = 70`으로 고정이고, §11.6 6단계는 `GREAT 상한 > GOOD 상한`만 고친다. 그래서 **`70 < d ≤ 106`은 C1을 통과하고 어느 밴드에도 안 걸린다.** 등급이 `null`이면 데미지 배수·히트스톱·점수·패리 무적이 **전부 미정의**다 — 기본값도 예외 처리도 없다.

**확정: 마지막 밴드는 `maxDistU`를 저장하지 않는다.**

```ts
maxDistU: null   // "반경까지". sim/stats.ts가 스냅샷을 만들 때 parryRadiusU로 채운다
```

`guards.ts`의 밴드 순서 검사에 `bands.at(-1).maxDistU === parryRadiusU`를 넣는다. 두 곳에 저장하고 같은지 검사하는 대신 한 곳에서 유도하는 것이고, [12_통합_계약.md](12_통합_계약.md) §5가 `lockoutSec`에 대해 내린 판정과 같은 형태다 (§10 E-06).

### 3.2 등급과 다중 패리

```
각 발사체는 자기 거리로 개별 등급을 받는다        §5.3
히트스톱 · 점수 · 콤보는 최고 등급 기준 1회만      §5.3 · §3.2
콤보는 처리한 발사체 개수만큼 증가                §12.2
무적은 1회분만. 등급에 따라 길이가 달라지지 않는다  §5.1
```

콤보만 개수를 세고 나머지는 1회라는 점이 헷갈리기 쉽다. 스펙 §12.2가 "다중 패리는 개수만큼 증가"라고 별도로 적었다.

### 3.3 빈 패리

활성 구간에 패리된 발사체가 0개인 경우. **이 게임의 유일한 억제 장치다.**

| 항목 | 값 |
|---|---|
| 무적 | **없음.** 활성 구간 내내 평소처럼 피격된다 |
| 콤보 | 리셋되지 않고 증가하지도 않는다 |
| 점수·히트스톱 | 없음 |
| 쿨다운 | 정상. N13 보유 시 `cooldownSecFor('empty')` — 명목 −40%지만 INV-1 하한에 막혀 실효 −17% (§10.3) |

빈 패리 판정은 **활성 구간이 끝나는 시점**에 확정된다. 활성 중간에 "아직 0개"라고 판정하면, 뒤늦게 들어온 탄을 놓친다.

## 4. 반사 — `sim/reflect.ts`

### 4.1 방향

```
n  = normalize(발사체위치 − 플레이어위치)
v' = v − 2 (v · n) n
반사탄 속도  = |v'| × 등급 속도 배수 × 카드 보정,  상한 2400 u/s
반사탄 방향  = normalize(v')
```

C2가 `v · n < 0`인 것만 통과시키므로 반사 후에는 언제나 `v' · n > 0`이다. **즉 반사탄은 반드시 플레이어에게서 멀어지는 방향으로 출발한다.** HR-07로 반사탄이 유해해졌는데도 반사 즉시 자기 탄에 안 맞는 이유가 이 부수 효과다. 맞으려면 플레이어가 그 탄을 따라가야 한다.

이건 우연이 아니라 구조적 보장이므로, **`sim/guards.ts`가 반사 직후 `v' · n > 0`을 검사한다.** 이 부등식이 깨지면 게임의 안전 전제가 무너진다.

### 4.2 데미지 계산 순서

```
1. 기준값     = 탄환 BRP        ← 재패리여도 언제나 여기서 다시 시작한다
2. 등급 배수  × 스냅샷의 `bands[i].damageMul`   ← 리터럴로 박지 않는다
3. 가산 보정  카드의 "+N%"를 전부 더해 한 번에 곱한다
4. 조건부 배수 R04(GREAT ×1.5) 등
5. 분열 감쇠  R01 · E01 등의 개별 계수
6. 최종       소수점 내림
```

**1번이 핵심이다.** 직전 데미지에 배수를 다시 곱하면 GREAT 3연속에서 `3.5⁴ = 150배`가 나온다. 재패리로 달라지는 것은 이번에 받은 등급뿐이다.

**2번을 `1.0 / 2.0 / 3.5` 리터럴로 쓰면 E05를 표현할 수 없다.** E05 영점 패리가 "GREAT 데미지 배수 3.5 → **5.0**"이므로(§11.5), 배수는 `config`의 상수가 아니라 **스냅샷의 밴드**에서 읽어야 한다(§10.3의 `bands`). 같은 이유로 §11.6 6단계의 밴드 보정도 이 경로로 들어온다.

스펙 §7.2의 검산 두 개를 그대로 테스트로 만든다.

```
조총탄 BRP 14, GREAT, N01 3중첩(+45%), R04 보유
  14 × 3.5 × 1.45 × 1.5 = 106.5 → 106

함포탄 BRP 55, NOT BAD로 받은 뒤 추격해 GREAT로 재패리, 카드 없음
  1회차 (NOT BAD)  55 × 1.0 = 55
  재패리   (GREAT)  55 × 3.5 = 192      ← 누적이 아니라 등급 재판정의 결과
```

### 4.3 반사탄은 플레이어에게도 유효하다 (HR-07)

| 항목 | 값 |
|---|---|
| 판정 대상 | 적 + 플레이어 양쪽 |
| 자해 유예 | 반사 성립 후 0.15초. 이 동안 피격 판정과 패리 판정을 **모두** 하지 않는다 |
| 피격 시 | 라이프 −1, 그리고 **그 반사탄 자신은 소멸한다** |
| 수명 | 3.0초. 재패리 시 재설정 |
| 관통 | 기본 없음. 적 1기 명중 시 소멸 (R02로 변경) |
| **유도** | **반사되는 순간 잃는다.** 아래 |

**P11 유도탄은 반사되면 유도를 즉시 잃고 직진한다** ([01](01_설계_결정.md) §4-B S-12). 스펙 §7.1이 반사탄의 유도를 "**기본 없음** (카드 R03으로 부여)"으로 적었으므로, 반사탄이 유도를 갖는 경로는 R03 하나뿐이고 원래 탄이 들고 있던 유도는 소유권이 뒤집히는 순간 사라진다. 구현은 한 줄이다 — 반사 시 `homingRemainingSec = 0`.

```
반사 전  적이 쏜 P11이 1.2초 동안 플레이어를 초당 120° 쫓는다        §6.1
반사 후  유도 소멸. §5.5의 v'로 직진한다
         R03 보유 시에만 다시 유도가 붙는다 — 대상은 플레이어가 아니라 가장 가까운 적  §11.4
```

**남겨 두면 규칙이 뒤집힌다.** 유도를 유지하면 플레이어가 쳐낸 탄이 **플레이어를 다시 쫓아온다** — HR-07이 반사탄을 플레이어에게 유해하게 만든 것은 "따라가면 맞는다"(§7.1)는 대가이지 "쫓아온다"가 아니다. 그리고 §5.5가 보장한 `v' · n > 0`(반사탄은 언제나 멀어지며 출발한다)이 유도 때문에 다음 스텝에 깨진다.

**피격을 일으킨 반사탄이 소멸하는 것**(§4.2)이 놓치기 쉽다. 적에게 명중했을 때와 같은 처리이고, 무적이 끝난 직후 같은 탄에 다시 맞는 상황을 막는다.

파생 발사체 — R01 쌍검 분열탄, E01 학익진 분열탄, R08 파편, E02 화전, E06 화공 장판 — 은 **전부 반사탄과 같은 규칙을 따른다.** 플레이어에게 유해하고, 재패리 가능하고, 자해 유예 0.15초가 똑같이 붙는다.

### 4.4 방패병

```
정면에서 들어온 반사탄 1회 무효화 → 방패 파괴 → 이후 정상 피해
측면·후면에서 들어온 반사탄은 방패를 무시한다
```

"정면"의 판정은 목업 구현(engine.js:1876-1885)이 정확하다 — 반사탄의 속도 벡터가 위쪽을 향하고(`vy < 0`), 세로 성분이 가로 성분보다 클 때(`|vy| > |vx|`). 이게 곧 스펙 §7.3의 정답 행동을 만든다: **원형 거울 반사로 각도를 틀어 옆에서 때린다.**

## 5. 피격 — `sim/collision.ts`

```
0. E03 보호막 검사        run.shieldCharges > 0 이면 consumeShield()로 1중 소모하고
                          무적 1.5초만 부여한 뒤 여기서 끝낸다 — 라이프는 안 줄어든다
1. 라이프 −1
2. 플레이어 중심 반경 280u 내의 모든 적 탄환 즉시 소멸
   ← 반사탄은 지우지 않는다. 플레이어의 자산이다
   ← 다만 피격을 일으킨 반사탄 자신은 소멸한다
3. 무적 1.5초
4. 콤보 0
5. 히트스톱 0.14초
6. 라이프 0이면 게임오버 (§13.3)
```

2단계의 예외 두 개가 정확해야 한다. **적 탄환만 지우고, 반사탄은 남기되, 나를 맞힌 그 반사탄 하나는 지운다.**

**0단계가 없으면 E03 거북선 등껍질이 아무 일도 안 한다.** 스펙 §11.5 — "피격을 무효화하는 보호막 3중. 스테이지 시작 시 1중 충전(최대 3중). **소모 시 라이프는 줄지 않고 무적 1.5초만 부여**". **충전 수는 `EffectiveStats`가 아니라 `RunState`가 갖는다** — 여기서 소모하고 스테이지 시작마다 `rechargeShieldAtStageStart(max = 3)`으로 되채우는 **가변 상태**이기 때문이다. 스냅샷은 읽기 전용이고, 거기 두면 소모를 쓸 자리가 없다. `EffectiveStats`에는 능력치인 `shieldMaxCharges`(보유 시 3, 미보유 0)만 남는다. 1단계를 무조건 「라이프 −1」로 시작하면 보호막은 스냅샷에만 존재하고 게임에는 없다.

**0단계는 콤보를 리셋하지 않는다.** §12.2의 리셋 조건은 "유지 시간 경과 또는 플레이어 **피격**"인데, 보호막이 막은 것은 피격이 성립하지 않은 것이다 — 라이프가 안 줄었으므로 4단계도 같이 건너뛴다. 히트스톱과 trauma는 준다: 무언가 막혔다는 사실은 §17이 요구하는 읽혀야 할 사건이다.

**5번의 0.14초는 `config/feel.ts`의 `playerHit`에 산다.** 여기가 §4.2 피격 처리이므로 `config/player.ts`가 자연스러워 보이지만, 그러면 같은 숫자가 두 파일에 생긴다 — 등급별 히트스톱은 `config/parry.ts`의 `PARRY_BANDS`에, 피격 히트스톱은 `feel.ts`에만 두는 것이 [12_통합_계약.md](12_통합_계약.md) §5와 §10 E-13의 단일 소스 판정이다.

무적 중에는 적 탄환·적 본체·반사탄·장판 모두 무해하며, **무적 중에도 패리는 정상 동작한다.**

### 5.1 무적이 두 종류다

| 종류 | 길이 | 조건 | 스펙 |
|---|---|---|---|
| 패리 무적 | 0.14초 | 패리가 **성립**했을 때만. 빈 패리는 없음 | §5.1 |
| 피격 무적 | 1.5초 | 피격 시 | §4.2 |

**둘을 한 필드에 담을 수 없다.** 피격 무적 1.5초가 도는 중에도 패리는 정상 동작하고(§4.2), 패리가 성립하면 패리 무적이 0.14초로 다시 설정된다(§5.1) — **두 개가 동시에 살아 있는 구간이 실재한다.** 한 필드에 쓰면 짧은 쪽이 긴 쪽을 덮어써 1.5초 보호가 0.14초로 잘린다.

```ts
hitInvulnUntilSec:   number;   // §4.2 피격 1.5초
parryInvulnUntilSec: number;   // §5.1 패리 성립 0.14초. INV-2가 자른다
// 실효 보호 = max(둘). 표시는 06 §5.9가 둘을 다른 그림으로 나눈다
```

`sim/player.ts`가 둘을 따로 갱신하고 판정은 `max`를 본다. **원인 기록은 그 위에 얹는다** — 스펙 §17이 둘을 시각적으로 구분하라고 요구하지는 않지만, 지금 목업은 둘을 같은 파선 링 하나로 그리고 있어 구분이 불가능하다. 처리는 [06_렌더링과_게임필.md](06_렌더링과_게임필.md) §5.

패리 무적이 겹치면 남은 시간에 더하지 않고 **0.14초로 다시 설정**한다(§5.1).

## 6. 적 — `sim/enemies.ts`

### 6.1 발사 억제 (HR-09)

예고 도형이 없는 탄환은 눈으로 보고 반응할 시간이 필요하므로, 비행 시간 0.45초를 규칙으로 보장한다.

```
억제 거리 = 실제 탄속 × 0.45초
플레이어까지 거리 < 억제 거리  →  이번 발사 취소, 다음 주기를 기다린다
```

최악 조건 검산: 조총탄 P2 `760 × 1.34(S5) = 1018 u/s` → 억제 거리 **458u**.

**이 규칙이 "적이 코앞에서 쏘는" 상황을 구조적으로 없앤다.** 근접 위협은 이 규칙에 걸리지 않는 수단이 담당한다 — E-C·E-D의 본체 접촉, 보스 돌진. 그리고 그것들은 **전부 예고 표시 대상이다**(HR-05).

**보스전에서는 이 규칙이 §3.1과 부딪힌다** ([01](01_설계_결정.md) §4-C S-04). 플레이어 영역이 `y ≥ 620`이고 보스 정위치가 `y ≤ 520`이라 최소 중심간 거리가 **100u**인데, 보스가 쓰는 가장 느린 탄(B4의 P7, S4 배율에서 322 u/s)의 억제 거리조차 **145u**다. 즉 플레이어가 보스 바로 아래에 붙으면 **어떤 보스도 아무것도 못 쏜다.** B5 기준으로는 `y ∈ [620, 978]`의 358u 띠 전체가 그렇고, 이는 세로 이동 폭의 29.6%다. 그러면 탄이 없어 반사탄도 없고(HR-01), 게임이 양쪽 다 멈춘 채 HR-03 가드가 던진다.

그때까지의 구현 규칙 둘을 여기서 지킨다.

- **HR-09는 그대로 적용한다.** 억제된 보스 발사는 §8.2대로 패턴 안에서 건너뛴다.
- **HR-03 타이머는 「살아 있는 모든 발사원이 HR-09로 억제된 상태」 동안 누산을 멈춘다.** 소강 3초와 같은 면제 처리이고, 면제가 걸린 사실은 [09](09_검증_전략.md) §2.4의 면제 구간 표와 헤드리스 리포트에 남긴다.

**이 임시 규칙이 덮지 못하는 것을 같이 적는다** — 가드가 안 던질 뿐 교착 자체는 남는다. 진짜 고침은 스펙 §3.1의 경계나 §10의 페이즈 구성을 바꾸는 일이라 이 기획안이 할 수 없다.

### 6.2 행동 종류

`config/enemies.ts`의 `behavior` 필드가 고르는 것.

| behavior | 동작 | 쓰는 적 |
|---|---|---|
| `holdAndFire` | 진입 후 정지, 예비동작 → 발사, 주기 반복 | E-A, E-E, E-G, E-H |
| `strafeAndFire` | 좌우 왕복하며 발사 | E-B |
| `descend` | 하강만. 접촉 피해 | E-C |
| `charge` | 방향선 1.0초 예고 → 직선 돌진 | E-D |
| `crossPass` | 측면 진입 → 반대편 통과. **정지하지 않는다** | E-F |
| `mounted` | 모함에 부착. 스스로 움직이지 않는다 | E-I |

`crossPass`는 목업의 여러 씬이 틀리게 구현했다(화면 끝에서 반사되어 왕복). 스펙 §8.2 F-6은 통과이고 정지하지 않는다. 상세는 [10_스펙_목업_불일치.md](10_스펙_목업_불일치.md).

모든 적은 화면 하단 경계(y=1920)를 넘으면 소멸하며 **점수를 주지 않는다**(§8.1).

## 7. 웨이브 — `sim/waves.ts`

```
스테이지 시작
  → 웨이브 1..N (시간 기반 진행)
  → 소강 3초
  → 보스 등장 → 격파 → 클리어
  → 카드 선택 (S1~S4만)
```

| 규칙 | 내용 |
|---|---|
| 전환 | **시간 기반.** 이전 웨이브의 적을 다 못 잡아도 다음 웨이브가 시작된다 |
| 잔존 적 | 그대로 유지. 동시 잡몹 상한 20에 걸리면 신규 스폰이 지연된다 |
| 마지막 웨이브 후 | 잔존 잡몹은 **마지막 웨이브 종료 즉시 퇴장을 시작해 소강 3초 안에 화면을 뜬다.** 퇴장한 적은 점수를 주지 않는다 |
| 소강 3초 | HR-03의 유일한 예외. **플레이어가 무적이 아니고, 잔존 반사탄은 유지된다** |

**스펙의 「4초 유예」를 3초로 당긴 이유** ([01](01_설계_결정.md) §4-B S-07). §9.1이 잔존 잡몹에 4초 유예를 주는데 바로 다음 줄의 소강은 3초이고 "적 탄환 없음"이다. 4 > 3이므로 원문대로 구현하면 **잔존 적이 소강 내내 살아서 쏘고**(S1 기준 0:43–0:46) 남은 1초는 보스전까지 넘어간다 — HR-03의 유일한 예외라고 이름 붙인 구간이 그 자리에서 깨진다. 퇴장 시작 시점을 당기는 쪽이 잃는 것이 가장 적다: 유예의 목적은 "방금 스폰된 적이 즉사하지 않게"인데 그건 3초로도 충분하고, 소강의 목적("적 탄환 없음")은 1초라도 어기면 규칙이 사라진다.

소강 구간이 완전한 안전 구간이 아니라는 점이 중요하다(§9.1). 잔존 반사탄은 플레이어에게도 유효하므로(HR-07), 소강 중에 자기 탄에 맞을 수 있다.

## 8. 보스 — `sim/boss.ts` + `sim/boss-runner.ts`

### 8.1 공통 규칙 (§10.1)

| 항목 | 값 |
|---|---|
| 위치 | 플레이필드 상단 고정 (HR-08). 좌우 이동 가능, 상하는 지정 패턴에서만 |
| 페이즈 전환 | HP 임계값 도달 시. 연출 **1.2초** 동안 보스 무적, 신규 발사 정지 |
| 전환 시 탄환 | 화면의 기존 적 탄환은 **유지**된다 — HR-03을 만족시키기 위함 |
| 패턴 루프 | 정해진 목록을 **순환**한다. 무작위가 아니다 (B5 페이즈 4만 예외) |
| 패턴 간 간격 | 0.8초 |
| 격파 연출 | 2.0초. 이 동안 모든 적 탄환 소멸, 플레이어 무적 |

**"전환 시 기존 탄환 유지"가 HR-03과 직결된다.** 전환 연출 1.2초 동안 신규 발사가 멈추는데, 여기서 화면을 비우면 적 탄환 0인 상태가 1.2초 이어진다. 다음 패턴의 예비동작까지 더하면 2.0초를 넘길 수 있다.

### 8.2 패턴 실행기

`boss-runner.ts`가 `config/bosses/patterns.ts`의 `BossPattern`을 해석한다. **`kind`는 9종이다** — `volley` · `spread` · `ring` · `arc` · `charge` · `mortar` · `barrage` · `parallel` · `summon`. [12_통합_계약.md](12_통합_계약.md) §4가 등재한 9종에서 §10이 `lance`를 빼고 `parallel`을 넣었고, 한 번 뺐던 `summon`은 E-09-정정이 되돌렸다.

| 변경 | 근거 |
|---|---|
| `summon` **유지** | E-09가 「사용처 1곳」을 이유로 한 번 지웠다가 **E-09-정정이 되살렸다.** 스펙 `기능_명세서.md:645`가 B1 페이즈 2의 순환을 `일제사격 강화 → 연막 돌격 → 난사 → 반복`으로 못 박았으므로 연막 돌격은 **순환 패턴**이고, `boss-runner.ts`가 `BossPattern`만 해석하는 이상 진입 훅으로는 순환에 낄 수 없다. 훅으로 만들면 E-D 4기가 페이즈당 1회로 끝난다. **B3 화공선만 B3 전용 패턴으로 남는다** — 화공선은 §8.1 아키타입에 없어 `EnemyId`를 못 가진다 |
| `lance` 이탈 | 두 번째 사용처인 §9.7 S5 W4 배경 함대는 웨이브 위협이라 `config/stages/stage-5-noryang.ts`에 살고 `sim/waves.ts`가 돌린다. `boss-runner.ts`는 `BossPattern`만 해석하므로 그 코드에 닿지 못한다. **`sim/lance.ts` 하나로 만들어 웨이브와 B5 페이즈 4가 같은 함수를 부른다** (E-10) |
| `parallel` 추가 | 아래 (E-08) |

**`parallel`은 발사 패턴이 아니라 결합자다.**

```ts
{ kind: 'parallel'; parts: readonly BossPattern[] }
```

`charge.onEnd`와 `mortar.onImpact`는 **후속** 하나만 붙일 수 있어 병렬을 못 만드는데, 스펙이 동시 실행을 네 곳에서 요구한다.

| 스펙 | 요구 |
|---|---|
| §10.6 B5 P4 전탄 발사 | 링 20발 + 조총 7발 + 함포 4발 **동시** |
| §10.5 B4 P3 초토화 | 예고 원 4개 + 불화살 비 **동시 진행** |
| §10.6 B5 P4 화공 총공세 | 예고 원 5개 + 불화살 비 15발 |
| §10.4 B3 P3 최후 포격 | 함포 6발 부채꼴 **+** 신관 링 탄막 |

실행기는 `parts`를 **같은 시각에** 스케줄하고, **가장 긴 자식이 끝날 때** 패턴 전체가 끝난 것으로 본다.

**`charge`와 `barrage`의 필드도 스펙 사용처를 못 덮고 있었다** (E-11).

```
charge   holdSec         §10.4 "y=1100까지 내려온 뒤 3초 유지", §10.6 "y=1200, 2.5초 유지"
         returnToStart   같은 두 곳의 "복귀"
         duringInterval? { bullet, intervalSec } — §10.3 B2 P3 "돌진 중 0.2초 간격으로 수리검".
                         onEnd는 종료 시점만 주므로 돌진 도중을 표현할 수 없다
barrage  origin          'boss' | 'topSpan'. §10.5 불화살 비는 보스가 아니라 상단 전역에서 떨어진다
         spanU?          그 전역의 폭
```

실행기의 계약:

- **패턴 사이는 겹치지 않는다.** 패턴 하나가 끝나야 다음 패턴이 시작한다. 이 규칙은 패턴 **안**에 적용되지 않는다 — `parallel`의 자식들은 겹치는 것이 목적이다.
- **예고 도형이 없는 발사만** HR-09 억제 거리 검사를 받는다. 억제된 발사는 그 패턴 안에서 **건너뛴다** — 패턴 전체를 지연시키지 않는다.
- **예고가 붙은 것은 억제하지 않는다.** HR-09의 조문이 "**예고 표시가 없는 탄환은**"으로 시작하고(스펙 §2), §6.2가 예고 3종(착탄 예고 원 P7 · 관통 예고선 P12 · 돌진 방향선)을 "패리로 해결할 수 없어 회피가 유일한 대응"인 공격에 붙였다. 그것들까지 억제하면 **B4의 곡사 포격과 B2·B3·B5의 돌진이 근거리에서 통째로 사라진다** — §6.2가 근접 위협을 담당시킨 바로 그 수단들이다. 즉 `mortar`·`charge`와 `sim/lance.ts`는 억제 대상이 아니다.
- `charge`와 `mortar`는 예고를 반드시 발행한다. 예고 없이 실행하면 `guards.ts`가 오류를 낸다 (HR-05). `BossPattern`을 떠난 `sim/lance.ts`도 같은 검사를 받는다.
- `charge`의 안전 지대 폭은 프리미티브 파라미터이고, `guards.ts`가 0보다 큰지 검사한다 (HR-04).
- **`kind` 분기는 `default`로 끝난다.** 아홉 갈래 전부를 처리한 뒤 마지막에 이 한 줄을 둔다.

```ts
default: { const _never: never = pattern; throw new Error(`unhandled ${(_never as BossPattern).kind}`); }
```

이게 없으면 union에 kind를 하나 추가하고 해석기를 안 고쳐도 **타입 오류 0개, 테스트 통과, 보스만 그 패턴 차례에 조용히 아무것도 안 하는** 상태가 된다([12_통합_계약.md](12_통합_계약.md) §4.1). `never` 대입이 컴파일 시점에 그 누락을 오류로 바꾼다.

### 8.3 부위 파괴 (B3)

```
포문 HP 300 (고정값. 잡몹 E-I의 200 × 배율과 별개다)
포문 파괴 → 그 발사 위치가 영구 정지
본체는 포문이 남아 있어도 계속 피격된다
페이즈 2 진입 = 포문 2개 파괴 또는 본체 HP 60% 이하 (선착)
```

"선착" 조건이 두 개의 독립 트리거를 만든다. 하나를 만족한 뒤 다른 하나가 만족돼도 페이즈 전환은 한 번만 일어난다.

**판정 도형이 원이 아니다.** B3의 선체는 `hitBox 860 × 250`, 포문 넷은 `96 × 63`이라 `core/sweep.ts`의 선분–원으로는 못 푼다. [12](12_통합_계약.md) §10 E-04가 **선분–AABB를 같은 파일에 두라**고 확정했고, 부위 우선 판정이 그것을 쓴다.

**부위는 본체보다 먼저 판정한다.** 목업이 여기서 실패했다 — 선체 히트박스(`hitW 860 × hitH 250`)가 포문 네 개의 좌표를 전부 덮고 있는데, 충돌 루프가 배열 순서대로 훑다가 첫 명중에서 끊긴다(engine.js:1869-1891). 그 결과 **반사탄이 포문에 도달할 방법이 없다.** 화면에 보이는 포문 HP는 손으로 넣은 값이다.

이건 사소한 버그가 아니다. 스펙 §10.4가 이 보스의 유일한 새 축을 "어느 포문을 먼저 부술지라는 표적 선택"이라고 적었으므로, 판정 순서가 틀리면 B3의 설계 의도 전체가 실행되지 않는다. 실게임의 충돌 판정은 **부위 목록을 먼저 훑고, 어느 부위에도 맞지 않았을 때만 본체를 검사한다.** 겹치는 히트박스에서 어느 쪽이 이길지는 배열 순서가 아니라 규칙이 정해야 한다.

## 9. 장판 — `sim/zones.ts`

| 항목 | 값 |
|---|---|
| 피해 | 코어 진입 즉시 1회, 이후 **0.5초마다** 반복 (§4.3) |

| 동시 존재 상한 | **6개**. 초과 생성 시 가장 오래된 것부터 제거 (§9.6) |
| 공유 | P9(적)와 E06(플레이어 카드)이 **같은 6개 상한을 공유한다** (§11.5) |

상한을 공유하는 이유가 §11.5에 있다 — 잡몹 상한이 20기라 이 규칙이 없으면 한 번의 다수 처치로 화면이 장판으로 덮인다.

**피해 판정은 그려진 다각형 외곽선 자체를 쓴다. 원이 아니다 — 내접원도 `z.r`도 아니다.** 목업의 장판은 꼭짓점 반경이 `z.r`의 0.86~1.085배로 흔들리는 7각형이라(engine.js:295), 판정을 원으로 잡으면 어느 반경을 골라도 오차가 남는다. 지금처럼 `z.r`을 쓰면 "안 닿았는데 맞았다"와 "닿았는데 안 맞았다"가 동시에 나고([10_스펙_목업_불일치.md](10_스펙_목업_불일치.md) A20), 내접원으로 낮춰 잡으면 후자만 남을 뿐 사라지지 않는다. 패리로 지울 수 없는 위협이라 이 오차가 그대로 억울한 피격이 된다.

꼭짓점 7개짜리 점-다각형 포함 검사는 비용이 무시할 수준이고, **승인된 7각형 아트를 한 픽셀도 바꾸지 않는다** — 고치는 것은 sim뿐이다. 스펙 §17의 "피해 판정 범위와 표시 범위가 일치해야 한다"가 이것으로 정확히 충족된다([12_통합_계약.md](12_통합_계약.md) §8-6이 A20의 ⓐ를 택했고, 06 §1.4의 ⓑ는 취소됐다).

**E06 화공 장판은 플레이어에게도 유효하다**(§11.5). HR-04를 위반하지 않는 이유는 생성 위치다: 장판은 반사탄이 적에게 명중한 지점에 생기고, 적 활동 영역은 `y ∈ [-200, 1000]`인 반면 플레이어 영역은 `y ∈ [620, 1830]`이다. 겹치는 띠는 `y ∈ [620, 1000]`뿐이고 플레이어는 언제든 아래쪽 830u를 쓸 수 있다.

### 10.2 검산 두 건을 테스트로

스펙 §11.6의 최악 조합 검산을 그대로 `tests/cards.test.ts`에 넣는다. 이 둘이 통과하지 않으면 9단계 구현이 틀린 것이다.

```
검산 1 — E07 없음.  N04×3 + N05×3 + N10 + R10
  쿨다운   0.24 × 0.82 = 0.197        → 하한 0.15 통과
  활성     0.15 + 0.03 = 0.18

  무적     0.14 + 0.03 = 0.17
  INV-2    0.23 × 0.75 = 0.1725       → 0.17 통과 (안 잘림)
  결과     활성 0.18 / 쿨다운 0.23 / 무적 0.17  → 초당 4.35회

검산 2 — E07 포함.  E07 + N04×3 + N05×3 + N10 + R10
  활성     0.18
  쿨다운   E07 예외 → 0.18 + 0.04 = 0.22   (INV-1의 0.23을 건너뛴다)
  무적     0.17
  INV-2    0.22 × 0.75 = 0.165        → 0.165로 하향
  결과     활성 0.18 / 쿨다운 0.22 / 무적 0.165  → 초당 4.55회, 반사탄 데미지 −25%
```

검산 1의 결론이 중요하다 — 기본값 대비 쿨다운 단축이 **0.01초에 그친다.** 쿨다운 축은 이미 포화 상태이고, 카드로 더 빨라지는 길은 R10의 조건부 초기화뿐이다.

### 10.3 스냅샷

`EffectiveStats`의 **정적 부분**은 카드 목록이 바뀔 때만 다시 계산한다 — 카드 획득, 치트 메뉴 조작, 런 시작.

**스냅샷은 어느 상한·불변 조건이 값을 잘랐는지도 담는다.**

**그리고 카드 목록만으로 결정되지 않는 값이 넷 있다.** "카드 변경 시에만 재계산"을 그대로 쓰면 이 넷이 조용히 틀린 값을 낸다.

| 카드 | 무엇이 깨지나 |
|---|---|
| **R05 연격** | "콤보 10마다 +10%, 최대 +50%". 콤보는 매 패리마다 오르고 3초 경과나 피격으로 0이 된다. §11.6 **2단계의 가산 %**이므로 2단계의 곱 전체가 콤보 종속이고, R05를 든 런의 `reflectDamageMul`은 **첫 패리 직후부터 계속 틀리다** |
| **N13 반보 물러서기** | "빈 패리 시 쿨다운 −40%". 쿨다운이 값 하나가 아니라 **둘**이 되는데 §11.6 8단계에 그 자리가 없다. 계산하면 `0.24 × 0.6 = 0.144`가 INV-1 하한 `0.15 + 0.05 = 0.20`에 막혀 실효는 **−17%**이고, N05 3중첩과 함께 들면 하한이 0.23으로 올라 **정확히 0**이 된다(§10.2 검산 1이 이미 0.197을 0.23으로 되돌린다) |
| **R10 무쌍** | "성립 시 쿨다운 즉시 종료, 최소 간격 0.12초". 8단계에도 없고 스냅샷에 필드도 없다. [09_검증_전략.md](09_검증_전략.md) §3.3이 R10을 스택에 넣지만 그 기제는 한 줄도 검증하지 않는다 |
| **E03 거북선 등껍질** | 스테이지 시작 시 1중 충전. **카드 변경 없이 스테이지마다 값이 바뀐다** |

**확정: 타입을 「정적 스냅샷」과 「런타임 파생」으로 가른다.**

```ts
type EffectiveStats = {
  // 정적 — 카드 목록이 바뀔 때만 다시 계산한다
  parryRadiusU: number;
  parryActiveSec: number;
  parryInvulnSec: number;
  bands: readonly ParryBand[];        // 마지막 밴드의 maxDistU는 여기서 parryRadiusU로 채워진다 (§3.1)
                                      // N07·N08·R09·E05가 §11.6 6단계에서 이 배열을 고친다
  comboHoldSec: number;               // §12.2 기본 3.0. N11 3중첩이 4.5로 늘린다 — HUD 게이지의 분모다
  moveSpeedUPerSec: number;
  // …
  /** §18.4 어느 단계에서 어느 규칙이 어떤 값을 얼마로 잘랐는지 */
  clamps: Array<{
    step: number;                                            // 잘린 단계. 값 범위는 1~8이다 — 9단계(스냅샷 확정)는
                                                             // 아무것도 자르지 않으므로 여기 나타날 수 없다 (12 §8-17)
    rule: 'INV-1' | 'INV-2' | 'hardLimit' | 'bandOrder';     // 자른 규칙
    field: string;                                           // 잘린 필드 이름
    after: number;                                           // 자른 뒤의 값
  }>;

  // 런타임 파생 — 카드 목록이 그대로여도 값이 바뀐다
  reflectDamageMulFor(combo: number): number;        // R05
  cooldownSecFor(outcome: 'hit' | 'empty'): number;  // N13
  r10ActiveMinGapSec: number | null;                 // R10
  shieldMaxCharges: number;                          // E03 보유 시 3, 미보유 0 — 능력치다.
                                                     // 현재 충전 수는 RunState가 갖는다 (§5)
};
```

`parryCooldownSec`와 `reflectDamageMul`이 필드에서 사라진 것이 요점이다. 둘은 **호출 시점의 상태 없이는 값이 없는 것**이고, 필드로 두면 그 사실이 감춰진다.

**필드 이름 네 개는 계약이다** — `step` · `rule` · `field` · `after`([12_통합_계약.md](12_통합_계약.md) §8-17). 소비자가 셋이라서 그렇다: 치트 메뉴가 그대로 표시하고(§18.4), 카드 선택 화면이 "이 카드는 상한에 막혀 효과가 없다"를 여기서 읽고, `tests/cards.test.ts`의 검산 두 건이 어느 규칙이 잘랐는지까지 대조한다. 셋이 각자 다른 이름을 기대하면 한 곳을 고칠 때 나머지 둘이 조용히 어긋난다.

잘리기 전 값을 따로 담지 않는 이유는 `step`이 그 자리를 메우기 때문이다. 같은 `field`의 항목을 `step` 순으로 늘어놓으면 앞 항목의 `after`가 곧 뒤 항목의 입력값이고, 9단계 전체가 한 줄로 읽힌다.

**런타임 파생 넷의 시그니처도 같은 급의 계약이다**([12_통합_계약.md](12_통합_계약.md) §8-17 · §10 E-05). `clamps`와 함께 P5-5의 작업 지시에 그대로 박는다 — 지금 형태로는 P5-5(스냅샷) · P6-3(카드 화면) · P6-8(치트 메뉴) · P5-8(테스트) 넷이 동시에 어긋난다.

스펙 §18.4가 이유를 적었다 — INV-1이 쿨다운을 0.197초에서 0.23초로 되돌리는 것 같은 상호작용은 숫자로 보이지 않으면 실측 중에 원인을 잘못 짚는다.

### 10.4 제시 가능 조건 (§11.2)

추첨 풀에서 제외하는 세 경우:

- 최대 중첩 수에 도달한 카드
- 중첩 불가 카드를 이미 보유한 경우
- 효과가 무의미한 경우 (N14 회복 — 라이프가 최대치일 때)

어떤 등급 풀이 비면 한 단계 아래로 내리고, 노말이 비면 위로 올린다.

## 11. 점수·콤보 — `sim/score.ts`

| 항목 | 규칙 |
|---|---|
| 콤보 증가 | 패리로 발사체를 1발 처리할 때마다 +1. 다중 패리는 개수만큼 |
| 재패리 | +1. 일반 패리와 동일하게 센다 |
| 유지 시간 | 마지막 패리 성공 후 **3.0초** |
| 경고 구간 | 남은 유지 시간이 `COMBO_WARN_SEC` 이하일 때. `config/scoring.ts`의 0.8초 하나를 render와 audio가 같이 읽는다([12_통합_계약.md](12_통합_계약.md) §8-5) |
| 리셋 | 유지 시간 경과 **또는** 플레이어 피격 (반사탄에 맞은 경우 포함) |
| 빈 패리 | 영향 없음 (증가도 리셋도 안 함) |
| 배수 | `1.0 + floor(콤보 / 10) × 0.1`, **상한 3.0** |
| 스테이지 전환 | 콤보는 넘어가지 않는다. 스테이지 시작 시 0 |

**상한 3.0 클램프를 빠뜨리기 쉽다.** 목업 HUD(engine.js:1729)에 이 클램프가 없고, 표시 최대값이 88(×1.8)이라 드러나지 않았을 뿐이다. 콤보 200 이상에서 스펙을 넘는다.

재패리 점수는 등급 점수의 **50%**다 (NOT BAD 25 / GOOD 75 / GREAT 200).

노히트 클리어에 별도 보상은 없다 — 남은 라이프 보너스(라이프 × 2,000)로 이미 반영돼 있다(§12.2).

타이틀 → S1 → [클리어] → 카드 → S2 → 카드 → S3 → 카드 → S4 → 카드 → S5 → [클리어] → 엔딩·결과

| 항목 | 규칙 |
|---|---|
| 라이프 | 5스테이지 전체 공유. 클리어로 회복되지 않는다 (§13.2) |

**누적 상한을 실제로 터뜨리는 빌드는 E07이 아니라 R10이다.** E07은 쿨다운을 0.19초로 만들어 `1/0.19 × 0.075 = 0.395`인데, R10은 성립 시 쿨다운을 즉시 끝내고 최소 간격 0.12초만 남기므로 `1/0.12 × 0.075 = **0.625**`다. [12](12_통합_계약.md) §10 E-20이 E07을 지목했지만 더 센 것이 옆에 있었다 — `tests/core.test.ts`의 슬라이딩 창 시뮬은 **둘 다** 넣는다.

**HR-04는 절반만 자동화된다.** 돌진·관통의 안전 폭은 파라미터라 검사할 수 있지만, 장판 6개가 겹친 순간의 잔여 이동 가능 면적은 기하 문제다. 자동화를 시도하기보다 [09_검증_전략.md](09_검증_전략.md)의 수동 검토 항목으로 남긴다 — **자동화한 척하는 것이 안 한 것보다 나쁘다.**

## 14. 치트 모드가 sim에 붙는 지점

스펙 §18.1이 못 박았다 — "치트 모드가 조작하는 것은 진행 상태뿐이다. 전투 규칙 자체는 하나도 바뀌지 않는다."

이걸 구조로 보장하는 방법: **`dev/cheat-menu.ts`는 `sim/`의 내부에 접근하지 않고, `sim/run.ts`가 공개한 세 함수만 부른다.**

```ts
/** §18.3 스테이지 자유 입장. 진입 시 기존 적·탄환·반사탄·장판을 모두 제거하고 콤보를 0으로 만든다 */
export function jumpTo(run: RunState, target: StageEntryPoint): void

/** §18.4 카드 직접 지정. 최대 중첩 수는 넘을 수 없다. 변경 즉시 §11.6의 9단계를 다시 실행한다 */
export function setCards(run: RunState, cards: ReadonlyArray<{ id: CardId; stack: number }>): void

/** §18.3 라이프 지정. 1 ~ 현재 최대 라이프 */
export function setLives(run: RunState, lives: number): void
```

세 함수 모두 §14.1의 스테이지 파라미터를 정상값으로 적용한다. 치트로 건너뛰어도 적 HP 배율·탄속 배율·예비동작 시간·동시 탄환 상한은 그대로다(§18.3).

**최대 중첩을 넘기지 못하게 하는 이유**(§18.4): §11.6의 최악 조합 검산 두 개가 "정상 플레이로 도달 가능한 가장 극단적인 빌드"를 가정하고 쓰인 것이다. N04를 4중첩으로 만들 수 있게 하면 그 검산이 다루지 않는 조합이 생기고, 그 결과로 카드 계수를 조정하면 실제로는 존재할 수 없는 빌드에 맞춰 밸런스를 깎게 된다.

**런 오염**(§18.5)은 `run.ts`가 관리한다. 치트 메뉴를 연 순간 플래그가 서고, 아무것도 안 바꾸고 닫아도 남으며, 런 도중에는 해제되지 않는다. 판정이 단순해야 하는 이유도 스펙에 있다 — 오염 판정은 틀렸을 때 손해가 한쪽으로만 나야 한다.
