## 1. 원칙

네 개다. 전부 "이걸 어기면 무엇이 깨지는가"가 붙는다.

### 1.1 소리는 정보의 강화(reinforcement)이지 전달(delivery)이 아니다

**소리에만 실린 정보를 0개로 만든다.** 스펙 §17이 직접 요구한다 — "위 표에서 '시각·청각 신호'를 요구하는 항목은 **음소거 상태에서도 시각만으로 전부 구분 가능해야 한다.** 소리에만 실린 정보가 있으면 음소거가 곧 정보 손실이 된다." 연구 09:887이 같은 문장을 설계 규칙으로 적었다.

이 원칙이 이 문서의 나머지를 지배한다. §3의 표에 **"짝지은 시각"** 열이 있는 이유가 이것이고, 그 열이 비어 있는 사건은 소리를 만들지 않는다.

예외는 스펙 §17이 명시적으로 열어 둔 한 줄뿐이다 — "반대로 소리가 유일하게 맡는 역할도 있다. 쿨다운 종료처럼 화면 밖에서 일어나는 사건은 시선을 뺏지 않고 알릴 수 있는 유일한 수단이 소리다." 이 경우에도 시각 대체물이 있어야 하고(§6.2 표), 다만 그 시각 대체물은 시선을 요구한다는 차이가 남는다.

### 1.2 소리를 트리거하는 코드 경로마다 짝이 되는 시각 변화가 있어야 한다

연구 09:884 — "오디오 이벤트와 시각 이벤트를 1:1로 페어링한다. ... 체크리스트로 검증한다."

구조로 강제한다. `audio/sfx.ts`의 어떤 함수도 `sim/`이나 `screens/`에서 직접 호출되지 않고, [02_아키텍처.md](02_아키텍처.md) §6의 **피드백 이벤트 버스**(`core/bus.ts`)를 구독해서만 발화한다. 같은 이벤트를 `render/impact.ts`·`render/particles.ts`가 함께 구독한다. 즉 소리와 그림이 같은 이벤트에서 갈라져 나오므로, 소리만 있고 그림이 없는 사건은 이벤트 타입을 하나 더 만들어야만 성립한다 — 실수로는 생기지 않는다.

검증 체크리스트는 §6.3에 있다.

### 1.3 음소거 토글(M)이 곧 `ctx.resume()`을 부르는 첫 제스처다

Chrome autoplay 정책은 사용자 제스처 전에 `AudioContext`를 `suspended`로 둔다(연구 09:762 — "if you call `osc.start()` before `ctx.resume()`, the first chord goes silently into the void"). 그리고 심사자는 소리를 켜야 한다는 사실을 알아야 한다.

스펙 §16.1·§16.3이 이미 `M`을 전투 중과 타이틀 양쪽에 배정했고, §15.1이 "음소거 상태 — 현재 음소거인지 한눈에 보여야 한다"를 HUD 요구사항으로 넣었다. 그러므로 **하나의 컨트롤이 두 문제를 동시에 푼다**(연구 09:886). 다만 M만 기다리면 M을 안 누르는 플레이어는 영원히 무음이므로, 실제 구현은 "첫 클릭 또는 첫 키 입력 중 무엇이든 먼저 오는 것"에서 `resume()`을 부르고 M은 그중 하나일 뿐이다(§2.5 코드).

### 1.4 심사자가 처음 보는 몇 초는 구조적으로 무음이다. 개발자는 이 상태를 한 번도 안 본다

연구 09:878-889의 결론이다 — "심사자가 페이지를 열고 처음 보는 몇 초는 **무조건 무음**이다. ... 개발자는 소리를 켜고 테스트했으므로 이 상태를 한 번도 본 적이 없다."

그래서 **무음 플레이스루 1회가 완료 조건이다.** 연구 09:1162가 D7 작업 목록에 넣었고, 이 문서는 그것을 §6.3의 체크리스트로 구체화한다. 실행하지 않은 채로 "소리 완료"를 보고하지 않는다.

## 2. 신스 기본기 — `src/audio/synth.ts`

전부 oscillator / noise buffer / gain envelope / biquad filter 네 가지뿐이다. 연구 09:666 — "전부 오실레이터 / 노이즈 버퍼 / 게인 엔벨로프 / 바이쿼드 필터만 쓴다. 오디오 파일 0개."

### 2.1 파형 성격

연구 09:670-675의 표를 그대로 쓴다. 이 게임에서 어느 파형이 어디에 배정됐는지를 오른쪽 열에 붙였다.

| 파형 | 성격 | 일반적 용도 | 이 게임에서의 배정 |
|---|---|---|---|
| `sine` | 순수, 부드러움 | 메뉴, UI 피드백 | 콤보 끊김 경고, 무적 종료. **전투 중 다른 어떤 소리도 순수 sine을 쓰지 않는다** — 그래서 작아도 뚫고 들린다 |
| `triangle` | 따뜻함, 속이 빔 | 베이스라인, 둔탁한 충격, BGM | 콤보 상승, 쿨다운 틱, 처치음 저역 레이어, BGM 전체 |
| `square` | 밝고 거침 | 아케이드 효과음, 점프, 펀치 | GREAT 상단 레이어, 예비동작 마지막 블립 |
| `sawtooth` | 버즈, 공격적 | 레이저, 엔진, 알람 | 피격 하강 스윕, **예고 표시 3종 전용** |

**`sawtooth`를 예고 표시 3종의 전용 파형으로 잠근 것이 이 표에서 가장 중요한 배정이다.** 스펙 §6.2가 "예고 도형이 보이면 피해라, 안 보이면 받아쳐라"를 게임의 학습 규칙으로 못 박았는데, 그 규칙을 소리 쪽에서도 한 축으로 인코딩한 것이다. 버즈 음색이 들리면 패리로 해결할 수 없는 공격이다.

### 2.2 엔벨로프

```ts
/**
 * 지수 감쇠 엔벨로프. peak 도달 후 0.001까지 떨어뜨리고 노드를 반환한다.
 * 시작값이 0이 아니라 0.0001인 것은 exponentialRamp가 0을 지날 수 없기 때문이다(§2.5 함정 1).
 */
export function envelope(
  ctx: AudioContext,
  peak: number,
  attackSec: number,
  decaySec: number,
  atSec: number,
): GainNode
{
  const g = ctx.createGain();
  g.gain.setValueAtTime(0.0001, atSec);
  g.gain.exponentialRampToValueAtTime(peak, atSec + attackSec);
  g.gain.exponentialRampToValueAtTime(0.001, atSec + attackSec + decaySec);
  return g;
}
```

### 2.3 화이트 노이즈 버퍼

```ts
/**
 * 지수 감쇠가 미리 곱해진 화이트 노이즈 버퍼.
 * decay가 작을수록 앞머리만 남는다 — 8ms 버퍼에 decay 50이면 UI 클릭, 0.28초 버퍼에 decay 900이면 폭발 몸통.
 * 0.2초를 넘는 버퍼는 호출마다 새로 만들지 않고 캐시한다. 변화는 필터 쪽 랜덤이 만든다.
 */
export function noiseBuffer(
  ctx: AudioContext,
  durSec: number,
  decay: number,
  rng: Rng,
): AudioBuffer
{
  const len = Math.max(1, Math.floor(ctx.sampleRate * durSec));
  const buf = ctx.createBuffer(1, len, ctx.sampleRate);
  const data = buf.getChannelData(0);
  for (let i = 0; i < len; i++)
  {
    data[i] = (rng.next() * 2 - 1) * Math.exp(-i / decay);
  }
  return buf;
}
```

`data[i] = (Math.random() * 2 - 1) * Math.exp(-i / 50)` 형태는 연구 09:731의 프로덕션 코드 그대로다. 바꾼 것은 `Math.random()` → 주입된 `rng`, 그리고 `50`을 파라미터로 뺀 것 두 가지다.

**`rng`는 sim의 시드 RNG가 아니다.** `audio/`는 자기 전용 인스턴스를 하나 갖고 `sim/`과 절대 공유하지 않는다. 공유하면 음소거 여부가 난수 소비 횟수를 바꾸고, 그 순간 D-05(결정론)가 깨져 헤드리스 밸런스 시뮬과 입력 재생이 둘 다 무의미해진다.

### 2.4 필터

```ts
export function filterNode(
  ctx: AudioContext,
  type: BiquadFilterType,
  hz: number,
  q: number,
): BiquadFilterNode
{
  const f = ctx.createBiquadFilter();
  f.type = type;
  f.frequency.value = hz;
  f.Q.value = q;
  return f;
}

/** 컷오프를 시간에 걸쳐 쓸어내린다. 폭발·처치·보스 격파가 전부 이 하나에 의존한다. */
export function sweepCutoff(
  f: BiquadFilterNode,
  fromHz: number,
  toHz: number,
  atSec: number,
  durSec: number,
): void
{
  f.frequency.setValueAtTime(fromHz, atSec);
  f.frequency.exponentialRampToValueAtTime(Math.max(20, toHz), atSec + durSec);
}
```

연구 09:713 — "**White noise through a lowpass filter gives you that boom. Layer in a low tone and you get impact.** ... **Small changes in filter cutoff make a big difference.**" 마지막 문장 때문에 컷오프 값은 전부 `config/audio.ts`로 뺀다. 이 게임에서 가장 자주 만지게 될 숫자가 그것이다.

### 2.5 반드시 지키는 함정 5개

| # | 함정 | 대응 | 출처 |
|---|---|---|---|
| 1 | `exponentialRampToValueAtTime`은 0에 도달할 수 없다 | 목표값을 **0.001**로 둔다. 시작값도 0이면 안 되므로 0.0001에서 출발한다 | 연구 09:758 |
| 2 | 첫 사용자 제스처 전에는 `AudioContext`가 `suspended`다 | 첫 클릭·키 입력에서 `ctx.resume()`. §1.3 | 연구 09:762-768 |
| 3 | 게인 버스를 분리하지 않으면 음소거·믹싱이 불가능하다 | `masterGain → destination`, `sfxGain`·`musicGain → masterGain` | 연구 09:773-776 |
| 4 | 같은 소리가 반복되면 기계적으로 들린다 | 트리거마다 피치 **±3%** 랜덤. 예외 하나는 §3.8 | 연구 09:780 |
| 5 | oscillator를 `stop()` 하지 않으면 노드가 샌다 | 모든 소스에 `stop()`을 반드시 걸고 `onended`에서 `disconnect()` | 연구 09:784 |

함정 2·3의 구현:

```ts
// src/audio/context.ts (발췌)

let ctx: AudioContext | null = null;
let masterGain: GainNode;
let sfxGain: GainNode;
let musicGain: GainNode;

export function initAudio(): void
{
  if (ctx) { return; }
  ctx = new AudioContext();
  masterGain = ctx.createGain();
  sfxGain = ctx.createGain();
  musicGain = ctx.createGain();
  masterGain.gain.value = AUDIO.mixer.masterGain;
  sfxGain.gain.value = AUDIO.mixer.sfxGain;
  musicGain.gain.value = AUDIO.mixer.musicGain;
  masterGain.connect(ctx.destination);
  sfxGain.connect(masterGain);
  musicGain.connect(masterGain);
}

/**
 * 첫 사용자 제스처에서 한 번만 컨텍스트를 깨운다.
 * M(§16.1) 뿐 아니라 아무 클릭·키 입력이든 이 경로로 들어온다 — M만 기다리면
 * M을 누르지 않는 플레이어에게는 게임 전체가 무음으로 끝난다.
 */
export function resumeOnFirstGesture(): void
{
  const kick = (): void =>
  {
    document.removeEventListener('click', kick);
    document.removeEventListener('keydown', kick);
    initAudio();
    void ctx!.resume();
  };
  document.addEventListener('click', kick);
  document.addEventListener('keydown', kick);
}
```

함정 4의 구현:

```ts
/** 트리거마다 피치를 ±3% 흔든다. 이 게임에서 초당 4회 이상 반복되는 소리가 실제로 있다(§5.1 쿨다운 0.24초). */
export function jitter(hz: number, rng: Rng): number
{
  const spread = AUDIO.mixer.pitchJitter;   // 0.03
  return hz * (1 + (rng.next() * 2 - 1) * spread);
}
```

### 2.6 동시 발성 상한

스펙 §3.2의 전역 상한이 적 탄환 280 · 반사탄 240 · 잡몹 20을 허용한다. 한 프레임에 같은 소리가 20개 나면 합산되어 클리핑되고, 20개가 각자 노드를 만들면 함정 5가 실제 누수로 나타난다.

| 규칙 | 값 | 이유 |
|---|---|---|
| 동시 활성 보이스 상한 | 24 | 초과 시 가장 오래된 보이스를 `stop()` 하고 새 것을 받는다 |
| 같은 이벤트 병합 창 | 0.03초 | 이 창 안에 같은 이벤트가 N번 오면 소리는 **1회만** 내고 게인을 `1 + 0.12 × (N − 1)`배(상한 1.6배)로 올린다 |
| 병합 예외 | 연쇄 처치(§3.6) | 연쇄는 **의도적으로 시간축에 늘어놓는 것**이므로 병합하면 D-09가 통째로 무너진다 |
| 다중 패리 | 최고 등급 1회 | 스펙 §5.3 — "히트스톱·점수·콤보는 그중 **최고 등급 기준으로 1회만** 적용한다." 소리도 같은 규칙을 따른다 |

## 3. 사건별 사운드 사양

스펙 §17의 표를 한 줄씩 훑는다. 각 사건에 대해 발화 시점 / 소스 / 주파수 경로 / 길이 / 게인 / 필터 / 짝지은 시각 / config 필드를 지정한다.

|---|---|---|---|---|---|---|---|---|

### 3.1 패리 성공 3등급 — 이 문서에서 가장 중요한 세 소리

스펙 §17 첫 줄이 "등급별로 **명확히 다른** 시각·청각 신호. 세 등급이 서로 헷갈리면 안 된다"이다.

**금속 코어는 셋이 공유한다.** 8ms 지수 감쇠 노이즈 버퍼를 bandpass(중심 4000~5000Hz 랜덤, Q 3)로 통과시킨 것 — 연구 09:726-742의 프로덕션 UI 클릭 코드 그대로다. 이 조합이 칼날이 부딪히는 금속음의 정체이고, 세 등급이 같은 행위라는 사실을 이것이 전달한다.

**구분은 네 축을 동시에 움직여 만든다.** 한 축만 쓰면 스피커 품질이나 재생 환경 하나에 구분이 통째로 걸린다.

| 축 | NOT BAD | GOOD | GREAT | 왜 이 축인가 |
|---|---|---|---|---|
| **음정 방향** | 없음 (노이즈만) | **하강** 880 → 620Hz | **상승** 1320 → 1560Hz | 결정적 축. 무음정 / 하강 / 상승은 어떤 환경에서도 서로 안 섞인다 |
| bandpass 중심 | 3800Hz | 4400Hz | 5000Hz | 연구 09:737의 `4000 + random()*1000` 범위를 세 등급으로 쪼갠 것. 위로 갈수록 날이 선다 |
| bandpass Q | 3 | 3 | **4** | GREAT만 더 좁혀 "핑" 하는 여운을 남긴다 |
| 길이 | 0.053s | 0.093s | 0.208s | 히트스톱 0.02 / 0.05 / 0.075초(§5.3)와 같은 방향. 소리가 정지 시간을 넘어 이어지므로 정지가 길게 느껴진다 |
| 게인 | 0.30 | 0.40 | 0.52 | 보조 축. 이것만으로는 구분하지 않는다 |
| 저역 서브 | 없음 | 없음 | 160 → 80Hz | GREAT에만 무게를 준다. §5.3의 "대형 탄환을 몸으로 받아낸다"는 감각의 소리 쪽 대응 |

**바꾼 것.** 연구 09:737의 UI 클릭은 게인 `0.5 + random()*0.15`인데, 그것은 다른 소리가 전혀 없는 UI 전용 페이지 기준이다. 전투 중에는 처치음·피격음·BGM이 같은 버스를 쓰므로 0.30~0.52로 내렸다. 랜덤 폭도 `random()*1000`(±1000Hz)에서 중심의 ±3%(§2.5 함정 4)로 좁혔다 — 등급 구분이 대역 중심에 실려 있으므로 랜덤이 넓으면 등급이 서로 침범한다.

```ts
// src/audio/sfx.ts (발췌)

import { AUDIO } from '../config/audio';
import type { ParryGrade } from '../config/ids';
import { audioCtx, sfxBus, audioRng } from './context';
import { envelope, noiseBuffer, filterNode, jitter, playTone } from './synth';

/**
 * 패리 성공음 (§5.3 · §17).
 * 세 등급은 네 축을 동시에 움직여 구분하지만, 그중 정체를 결정하는 것은 음정 방향 하나다 —
 * NOT BAD는 음정이 없고, GOOD은 내려가고, GREAT는 올라간다. 대역·길이·게인만으로 나누면
 * 노트북 스피커에서 세 소리가 같은 "탁"으로 뭉친다.
 * 금속 코어(8ms 노이즈 → bandpass)는 셋이 공유한다. 같은 행위라는 사실이 그것으로 전달된다.
 */
export function playParry(grade: ParryGrade): void
{
  const ctx = audioCtx();
  const t = ctx.currentTime;
  const rng = audioRng();
  const p = AUDIO.parry[grade];

  const clang = ctx.createBufferSource();
  clang.buffer = noiseBuffer(ctx, AUDIO.parry.clangSec, AUDIO.parry.clangDecay, rng);
  const band = filterNode(ctx, 'bandpass', jitter(p.bandHz, rng), p.bandQ);
  const clangGain = envelope(ctx, p.gain, 0.001, p.tailSec, t);
  clang.connect(band).connect(clangGain).connect(sfxBus());
  clang.start(t);
  clang.stop(t + AUDIO.parry.clangSec + p.tailSec + 0.02);

  for (const layer of p.tones)
  {
    playTone({
      wave: layer.wave,
      fromHz: jitter(layer.fromHz, rng),
      toHz: jitter(layer.toHz, rng),
      gain: layer.gain,
      durSec: layer.durSec,
      atSec: t + layer.delaySec,
    });
  }
}
```

`playTone`은 연구 손맛 03:287-298의 15줄 `tone()` 함수를 TypeScript로 옮긴 것이다. 12ms 어택, `setValueAtTime(0.0001)` → `exponentialRampToValueAtTime(gain, t + 0.012)` → `exponentialRampToValueAtTime(0.0001, t + dur)`, `stop(t + dur + 0.02)`. 바꾼 것은 글라이드 목표(`toHz`)를 선택이 아니라 필수 인자로 만든 것뿐이다 — 이 게임에서 음정이 고정된 톤은 쿨다운 틱 하나뿐이라(§3.8) 기본값을 두면 그 하나 때문에 나머지 전부가 인자를 넘겨야 한다.

### 3.2 빈 패리 — "닿지 않았다 = 무적이 없다"

스펙 §17 — "성공과 구분되는 별도 신호. **무적이 붙지 않았다는 사실이 그 자리에서 읽혀야 한다** — 이것을 오해하면 §5.4의 억제 구조가 전달되지 않는다."

**규칙 하나로 푼다: 금속 대역(3.5~5.5kHz bandpass)의 유무가 곧 접촉의 유무이고, 접촉의 유무가 곧 무적의 유무다.**

빈 패리는 그 대역을 통째로 비운다. lowpass 900Hz를 통과한 노이즈 + triangle 220 → 150Hz, 길이 0.07초, 게인 0.12. 칼이 허공을 가르는 둔한 바람 소리가 되고, 성공음의 날카로운 금속 성분이 **없다는 사실 자체**가 신호다. 임의로 다른 소리를 배정한 게 아니라 물리적 인과를 그대로 옮긴 것이므로, 플레이어가 규칙을 따로 배우지 않아도 된다.

게인 0.12는 성공 최저 등급(0.30)의 40%다. 빈 패리는 §5.4에 따라 콤보도 점수도 히트스톱도 없는 사건이므로, 소리의 크기도 그 급을 따라간다.

### 3.3 재패리

스펙 §17 — "일반 패리와 다른 신호. 특히 낮은 등급으로 받았던 탄을 높은 등급으로 다시 쳐냈을 때, 데미지가 올랐다는 사실이 읽혀야 한다."

두 층으로 나눈다.

| 층 | 내용 | 근거 |
|---|---|---|
| **재패리라는 사실** | 해당 등급 패치 0.03초 **앞에** 12ms 클릭(bandpass 6500Hz, Q 6, 게인 0.18)을 붙인다. 두 번 때린 소리가 된다 | §7.4는 재패리를 "다시 매긴 등급으로 보내는 행위"로 정의한다. 등급 패치를 그대로 쓰되 앞에 붙이는 것이 그 정의에 대응한다 |
| **등급이 올랐다는 사실** | 이번 등급 > 직전 등급일 때만 triangle 2음 880 → 1320Hz(각 45ms, 게인 0.14)를 등급 패치 뒤에 잇는다 | §7.2 — "재패리로 달라지는 것은 **이번에 받은 등급뿐이다.**" 그러므로 등급이 오른 경우에만 추가 신호가 정당하다 |

등급이 같거나 내려간 재패리에는 상승 아르페지오가 붙지 않는다. 붙이면 소리가 거짓말을 한다 — §7.2의 계산상 NOT BAD로 다시 친 탄은 데미지가 오히려 내려간다.

880 → 1320Hz는 완전 5도다. 연구 09:720의 파워업 아르페지오(660/880/990/1320)에서 앞뒤 두 음만 남긴 것이고, 4음을 다 쓰면 0.2초가 되어 다음 패리(최소 간격 0.24초, §5.1)와 겹친다.

### 3.4 반사탄 발생

스펙 §17의 요구는 "적 탄환과 반사탄이 **색·형태로 즉시 구분**"인데, 이것은 시각 계약이다([06_렌더링과_게임필.md](06_렌더링과_게임필.md)). 소리의 몫은 발사 순간의 표시뿐이고, 그 순간은 패리 성공과 **같은 프레임**이다.

그래서 독립 소리로 만들지 않고 패리 패치에 얹는 레이어로 둔다. sawtooth 300 → 620Hz, 0.05초, highpass 400Hz(금속 코어의 몸통 대역을 비켜간다), 게인 `0.10 × 등급 반사 속도 배수 / 1.3`. 등급 배수는 §5.3의 1.3 / 1.8 / 2.6이므로 실제 게인은 0.10 / 0.138 / 0.20이 된다 — **빠르게 나가는 반사탄이 더 크게 튀어나가는 소리를 낸다.**

레이어이므로 §2.6의 병합 창을 적용하지 않는다. 이미 패리 소리가 최고 등급 1회로 병합돼 있고, 반사탄 레이어는 그 1회에 얹힌다.

### 3.6 다수 동시 처치 — 머니샷

D-09가 이 게임의 단일 시각 사건으로 지정한 장면이고, 그 결정의 근거가 "**동시에 사라지면 그냥 삭제고, 순차적이어야 연쇄다**"(D-09가 인용한 `claude_research_4/04:439`)이다.

**사건의 단위는 반사탄 한 발이 아니라 한 번의 패리다**([12](12_통합_계약.md) §6). 스펙 §5.3이 "동일 활성 구간에 여러 탄환이 패리되면 각 탄환이 자기 거리로 개별 등급을 받는다"고 정했으므로, 패리 한 번이 반경 70u 안의 탄 전부를 반사하고 그 반사탄들이 만든 처치가 하나의 연쇄가 된다. 시각 쪽은 그 처치를 **패리 지점 기준 각도 순(시계 방향)**으로 0.04초씩 어긋나게 낸다([06_렌더링과_게임필.md](06_렌더링과_게임필.md) §6.1). 그러므로 `playKillChain`의 `linkCount`도 **패리 이벤트 하나가 낸 처치 총수**이지 반사탄별 수가 아니다 — 반사탄 단위로 세면 분열탄에서 길이 1짜리 연쇄가 N개 나고, 아래 음정 상승이 한 번도 안 들린다.

**소리는 같은 0.04초 간격을 쓰되, 링크마다 음정을 올린다.** 간격만 두면 같은 소리가 여덟 번 나는 것으로 들리고 그건 연쇄가 아니라 반복이다. 음정이 오르면 **끝나지 않았다**는 정보가 매 링크에 실리고, 그게 연쇄의 청각적 정체다.

| 항목 | 값 | 근거 |
|---|---|---|
| 링크 간격 | 0.04초 | D-09의 시각 스태거와 **같은 값을 쓴다.** 다른 값을 쓰면 소리와 그림이 어긋난 것으로 들린다 |
| 링크 n의 음정 | `180 × 1.12ⁿ` Hz (n = 0부터) | 1.12는 반음 두 개(≈1.122)에 가까운 비율. 온음 계단이라 음악적으로 읽힌다 |
| 음정 상한 | n ≤ 7 (→ 399Hz) | 8링크 이상은 음정을 고정하고 대신 게인을 링크당 −0.06(하한 0.10) |
| 3링크 이상 확인음 | triangle 660 / 880 / 1320Hz, 각 40ms, 게인 0.22 | 연구 09:720 파워업 아르페지오. 990을 빼고 4음 → 3음으로 줄여 0.12초에 맞춤 |
| 병합 | **금지** | §2.6의 유일한 예외 |

```ts
/**
 * 연쇄 처치 (D-09 · §17 "다수 동시 처치").
 * linkCount 는 패리 이벤트 하나가 낸 처치 총수다. 반사탄별로 세면 분열탄에서 길이 1짜리
 * 연쇄가 N개 나서 음정 상승이 한 번도 안 들린다 (12 §6).
 * 링크 간격 0.04초는 render 쪽 스태거와 같은 값이다 — 소리만 다른 간격을 쓰면
 * 한 사건이 두 번 일어난 것으로 들린다.
 * 음정 상승이 이 함수의 존재 이유다. 같은 소리를 여덟 번 내면 그것은 반복이지 연쇄가 아니다.
 */
export function playKillChain(linkCount: number): void
{
  const ctx = audioCtx();
  const t0 = ctx.currentTime;
  const c = AUDIO.chain;

  for (let n = 0; n < linkCount; n++)
  {
    const stepped = Math.min(n, c.pitchCapIndex);
    const toneHz = c.baseHz * Math.pow(c.stepRatio, stepped);
    const fade = Math.max(c.gainFloor, c.gain - c.gainFalloff * Math.max(0, n - c.pitchCapIndex));
    scheduleKill(t0 + n * c.linkGapSec, toneHz, fade);
  }

  if (linkCount >= c.confirmMinLinks)
  {
    scheduleArp(t0 + linkCount * c.linkGapSec, c.confirmArpHz, c.confirmNoteSec, c.confirmGain);
  }
}
```

### 3.7 플레이어 피격 — 원인이 구분되어야 한다

스펙 §17 — "라이프 감소 + 무적 진입이 즉시 읽혀야 한다. **원인이 적 탄환인지 반사탄인지 구분되어야 한다.**" 이 구분이 §14.3 T-06(반사탄 자해 비율 실측)과 §12.3의 "반사탄 자해로 잃은 라이프 수" 항목의 근거가 되므로, 플레이어가 실제로 구분해서 인지해야 통계가 의미를 갖는다.

**임의의 두 소리를 배정하지 않는다. 원인을 소리로 그대로 옮긴다.**

| 원인 | 소리 | 왜 이 소리인가 |
|---|---|---|
| 적 탄환 | sawtooth **200 → 50Hz**, 80ms, 게인 급감 + lowpass 400Hz 노이즈 몸통 | 연구 09:697의 레시피 그대로. "**Downward sweeps feel like impact even without a sample**"(09:699) |
| 반사탄 (자해) | **앞머리에 bandpass 4600Hz 금속 클랭** + sawtooth 900 → 90Hz, 140ms + lowpass 520Hz 몸통 | 자기 칼 소리가 앞에 붙은 피격음이다. 그 반사탄을 만든 것이 자신의 패리이므로, 소리도 패리음에서 시작해 피격음으로 떨어진다 |

바꾼 것은 두 가지다. ① 연구 레시피에 노이즈 몸통 레이어를 더했다 — sawtooth 스윕만으로는 라이프 1 손실(§4.2)의 무게가 안 나온다. ② 자해 쪽 스윕을 200Hz가 아니라 900Hz에서 시작해 140ms로 늘렸다. 시작점이 금속 대역 근처라 앞머리 클랭과 이어지고, 폭이 넓어 "멀리서 내가 보낸 것이 돌아왔다"가 된다.

```ts
/**
 * 피격음 (§4.2 · §17).
 * 원인 구분은 §12.3의 "반사탄 자해로 잃은 라이프 수"와 §14.3 T-06의 실측 전제다 —
 * 플레이어가 원인을 그 자리에서 알아야 그 통계가 의미를 갖는다.
 * 자해음이 금속 클랭으로 시작하는 것은 임의의 차이가 아니라 원인 그 자체다. 그 반사탄을 만든 것이
 * 자신의 패리이므로, 소리도 패리음에서 출발해 피격음으로 떨어진다.
 */
export function playHit(cause: 'ENEMY' | 'REFLECT'): void
{
  const ctx = audioCtx();
  const t = ctx.currentTime;
  const rng = audioRng();
  const p = AUDIO.hit[cause];

  if (p.clangHeadGain > 0)
  {
    const head = ctx.createBufferSource();
    head.buffer = noiseBuffer(ctx, AUDIO.parry.clangSec, AUDIO.parry.clangDecay, rng);
    const band = filterNode(ctx, 'bandpass', jitter(p.clangHeadHz, rng), 3);
    const headGain = envelope(ctx, p.clangHeadGain, 0.001, 0.05, t);
    head.connect(band).connect(headGain).connect(sfxBus());
    head.start(t);
    head.stop(t + 0.06);
  }

  const sweep = ctx.createOscillator();
  sweep.type = 'sawtooth';
  sweep.frequency.setValueAtTime(jitter(p.fromHz, rng), t);
  sweep.frequency.exponentialRampToValueAtTime(jitter(p.toHz, rng), t + p.sweepSec);
  const sweepGain = envelope(ctx, p.gain, 0.004, p.sweepSec + 0.02, t);
  sweep.connect(sweepGain).connect(sfxBus());
  sweep.start(t);
  sweep.stop(t + p.sweepSec + 0.06);

  const body = ctx.createBufferSource();
  body.buffer = noiseBuffer(ctx, p.bodySec, AUDIO.hit.bodyDecay, rng);
  const lp = filterNode(ctx, 'lowpass', p.bodyHz, 1);
  const bodyGain = envelope(ctx, p.bodyGain, 0.003, p.bodySec, t);
  body.connect(lp).connect(bodyGain).connect(sfxBus());
  body.start(t);
  body.stop(t + p.bodySec + 0.03);
}
```

### 3.8 쿨다운 종료 — 피로하지 않아야 한다

스펙 §17 — "다시 패리 가능해진 순간을 소리 또는 시각으로 알린다. **초당 4회 이상 반복되므로 신호가 피로하지 않아야 한다.**" 정확히는 초당 최대 4.16회(§5.1, `1 / 0.24초`)다.

그리고 이것이 스펙 §17이 소리에게만 맡긴 유일한 항목이다 — "쿨다운 종료처럼 화면 밖에서 일어나는 사건은 시선을 뺏지 않고 알릴 수 있는 유일한 수단이 소리다." 플레이어의 눈은 내려오는 탄에 있지 자기 발밑의 링에 있지 않다.

피로를 막는 장치가 네 개다.

| 장치 | 값 | 이유 |
|---|---|---|
| 게인 | **0.055** | 연구 손맛 03:287의 기본 `gain=0.14`를 40% 수준으로 내렸다. 원본은 UI 클릭 기준값이고 이건 초당 4회다 |
| 길이 | 0.05초 | 원본 `dur=0.12`의 절반 이하. 0.24초 주기에 0.12초 소리는 화면의 절반이 이 소리가 된다 |
| 대역 격리 | highpass 1200Hz, 1760Hz 고정 | 1760Hz 위쪽은 다른 어떤 패치도 주요 성분을 두지 않는 자리다(패리 금속 코어는 3800Hz 이상, 처치음은 1800Hz 이하) |
| **패리 성공 직후 억제** | 직전 0.18초 안에 패리 성공음이 났으면 **내지 않는다** | 패리에 성공한 플레이어는 이미 쿨다운이 시작된 걸 안다. 이 억제 하나가 실제 발화 빈도를 절반 이하로 떨어뜨린다 |

**이 소리 하나만 피치 랜덤(§2.5 함정 4)을 끈다.** 함정 4는 반복음이 기계적으로 들리는 걸 막으라는 규칙인데, 쿨다운 틱은 기계여야 한다. 흔들리는 틱은 오류음으로 들리고, 일정한 틱은 메트로놈으로 들려서 의식에서 배경으로 내려간다. **배경으로 내려가는 것이 이 소리의 목표다.** `config/audio.ts`의 `cooldown.pitchJitter: 0`이 이 예외를 값으로 남긴다.

### 3.9 적 발사 예비동작

스펙 §17 — "궤적 예고가 없으므로(HR-05) **곧 쏜다는 사실**만은 확실히 읽혀야 한다. 예비동작이 배경에 묻히면 예고 없는 발사가 아니라 불공정한 발사가 된다."

triangle 300 → 520Hz 상승, lowpass 1400Hz, 게인 0.09. **상승 자체가 신호다** — 연구 09:687의 점프음이 "sweeps the frequency *upward* rather than down, creating a rising whistle tone"으로 기대감을 만든 것과 같은 구조다. 길이는 고정이 아니라 §14.1의 스테이지별 예비동작 시간에 맞춰 늘였다 줄인다. 확산·링은 0.4초, 참격파는 0.7초 고정(§6.2)이므로 그 값이 그대로 소리 길이가 된다.

마지막 0.08초에 square 640Hz 블립(게인 0.07)을 얹는다. 발사 순간을 예측 가능하게 만드는 것이 목적이고, 이게 없으면 상승음이 언제 끝나는지 몰라 예비동작이 "곧"이 아니라 "언젠가"가 된다.

**동시 발성 상한 4.** 잡몹 20기가 동시에 예비동작에 들어갈 수 있는데(§3.2), 20개의 상승음은 소리가 아니라 소음이다. 5번째부터는 소리를 내지 않는다 — §1.1대로 예비동작의 시각 표시(§15.1 "적 본체의 상태 변화만으로 읽혀야 한다")가 이미 충분 조건이므로, 소리가 빠져도 정보가 빠지지 않는다.

### 3.10 예고 표시 3종

§2.1에서 sawtooth를 이 세 소리에 잠갔다. 셋의 공통점은 스펙 §6.2가 정의한다 — "전부 패리로 지울 수 없고, 판정이 순간적으로 발생하며, 회피만이 대응책이다(HR-04)." 그러므로 셋은 **한 가족**으로 들려야 하고, 동시에 어느 것인지도 구분돼야 한다.

파형을 공유하고 엔벨로프로 구분한다.

| 예고 | 길이(§6.2) | 엔벨로프 | 주파수 | 필터 | 이 모양인 이유 |
|---|---|---|---|---|---|
| 착탄 예고 원 (P7) | 1.2초 고정 | **펄스** 0.10초 ×3, 간격 0.30초 | 180Hz 고정 | lowpass 900 | 원이 수축하는 리듬과 맞춘다. 마지막 펄스 뒤 0.3초가 착탄이다 |
| 관통 예고선 (P12) | 0.8초 고정 | **연속** 상승 | 240 → 300Hz | bandpass 1200, Q 8 | 끊김 없는 위잉 소리. 선이 계속 거기 있다는 사실과 대응한다 |
| 돌진 방향선 | 1.0초 고정 | **연속** 게인 증가 0.10 → 0.16 | 120 → 90Hz 하강 | lowpass 300 | 저역 럼블. 커지면서 낮아지는 것이 "다가온다"이다 |

세 소리는 각각 펄스 / 지속 상승 / 지속 하강이므로 파형이 같아도 안 섞인다.

### 3.11 장판 진입

§4.3 — "장판 영역 안에 플레이어 코어가 들어가면 **0.5초 간격**으로 피격 판정."

**진입 순간에만 소리를 낸다.** 노이즈 → bandpass 700Hz(Q 1.2) 0.35초 + triangle 90Hz 서브, 게인 0.22. 불길이 훅 하고 감싸는 소리다.

장판 안에 있는 동안은 **아무 소리도 내지 않는다.** 0.5초마다 오는 피해는 §4.3이 "§4.2와 동일하게 처리"라고 정했으므로 §3.7의 피격음이 그대로 난다. 지속 루프를 추가하면 안 되는 이유는 둘이다 — ① 스펙 §17이 장판에 요구한 것은 "경계가 명확해야 한다"이고 그건 시각 요구다. ② 지속음은 4.0초(P9 지속 시간, §6.1) 동안 다른 모든 소리를 덮는다. **이 절은 "여기에 루프를 넣지 마라"를 적기 위해 존재한다.**

### 3.12 보스 페이즈 전환 · 격파

| 사건 | 연출 길이 | 구성 | 근거 |
|---|---|---|---|
| 페이즈 전환 | 1.2초(§10.1) | triangle+square 3음 **하강** 440 / 330 / 220Hz(각 0.22초, 게인 0.24) + 노이즈 스웰(lowpass 200 → 2000Hz, 게인 0 → 0.18, 0.9초) | 스펙 §17 "패턴이 바뀐다는 사실을 **사전에** 알린다". 하강 3음이 먼저 나고 스웰이 그 위로 차오르다 새 페이즈 시작 시점에 정점을 찍는다 |
| 격파 | 2.0초(§10.1) | 노이즈 0.9초(lowpass 2400 → 120Hz, 게인 0.50) + triangle 서브 80 → 40Hz(0.7초, 게인 0.25) → 0.55초 뒤 4음 팡파르 440 / 660 / 880 / 1320Hz(각 0.09초, 게인 0.22) | §3.5 처치 패치를 3배로 키운 것 + 연구 09:720 파워업 아르페지오. 원본 50ms를 **90ms로 늘렸다** — 50ms면 획득음으로 들리고, 격파는 획득이 아니다 |

전환은 하강, 격파는 상승이다. 둘 다 보스 HP 바(§15.1)와 짝을 이룬다 — 전환은 눈금 통과, 격파는 바 소멸.

### 3.13 카드 선택 · 리롤 · 확정

전투가 멈춘 화면이므로(§11.1 "선택 중 게임 정지") 다른 소리와 겹칠 걱정이 없다. 대신 셋이 서로 안 헷갈려야 한다.

| 동작 | 패치 | 근거 |
|---|---|---|
| 커서 이동 | 연구 09:726-742의 UI 클릭 그대로 — 8ms 노이즈, bandpass `4000 + rand()×1000`, Q 3. **게인만 `0.5 + rand()×0.15` → 0.22로 내렸다** | 원본 게인은 이 소리 하나만 나는 페이지 기준이고, 여기엔 BGM(§4)이 깔린다 |
| 리롤 (`R`, §16.2) | sine **150 → 400Hz 상승** 글라이드, 0.06초, 게인 0.30 | 연구 09:746-752의 팝(400 → 150Hz 하강)을 **뒤집은 것**. "버리고 다시 뽑는다"는 상승이다 |
| 선택 확정 | triangle 2음 **660 → 880Hz**, 각 50ms, 게인 0.26 | 연구 09:718의 획득음 그대로. 카드 획득은 문자 그대로 pickup이다 |

리롤은 하나의 연속 글라이드, 확정은 두 개의 분리된 음이다. 방향이 둘 다 상승이지만 음 개수가 달라 섞이지 않는다. 리롤이 남아 있지 않을 때(§16.2 "남은 횟수가 0이면 입력이 무시된다")는 아무 소리도 내지 않는다 — 거부음을 추가하면 §15.2의 "소진 후에는 사용 불가임이 보여야 한다"와 정보가 중복되고, 무음이 곧 "입력이 접수되지 않았다"이다.

### 3.15 소리를 주지 않기로 한 항목

스펙 §17의 표에 있으나 전용 소리를 만들지 않는 항목들이다. 빠뜨린 게 아니라 판단이므로 이유를 남긴다.

| 항목 | 소리 없음의 이유 | 무엇이 대신하는가 |
|---|---|---|
| 히트스톱 | 소리가 아니라 시간이다. 소리를 얹으면 "정지"에 소리가 나는 모순이 된다 | 등급별 패치 길이(0.053 / 0.093 / 0.208초)가 정지 길이(0.02 / 0.05 / 0.075초)와 같은 방향으로 늘어난다. 소리가 정지를 넘어 이어지므로 정지가 길게 들린다 |
| 자해 유예 종료 (0.15초) | 패리 성공마다 0.15초 뒤에 소리가 하나씩 더 붙으면 사건 밀도가 두 배가 된다. 초당 4.16회 × 2 = 8.3회다 | 반사탄 색 전환(§17 "그 유예가 끝나는 시점이 구분되어야 한다" → [06_렌더링과_게임필.md](06_렌더링과_게임필.md)) |

## 4. 절차적 BGM

**스코프 최하위다.** [01_설계_결정.md](01_설계_결정.md) D-08이 이미 중단 규칙을 못 박았다 — SFX가 안 끝나면 BGM은 미루는 게 아니라 버린다. §7에서 다시 다룬다. 이 절은 "만들게 되면 이대로 만든다"이다.

### 4.1 필요한 음악 이론은 세 개뿐이다

연구 09:812-829.

```ts
// src/audio/bgm.ts (발췌)

/** 반음 간격 배열. 이것이 스케일의 전부다. */
const MAJOR = [0, 2, 4, 5, 7, 9, 11] as const;
const MINOR = [0, 2, 3, 5, 7, 8, 10] as const;

/** 코드 = 스케일에서 1·3·5번째를 쌓은 것. degree는 0부터 센 도수다. */
function chordTones(tonicMidi: number, scale: readonly number[], degree: number): number[]
{
  return [0, 2, 4].map((p) =>
  {
    const idx = degree + p;
    return tonicMidi + Math.floor(idx / 7) * 12 + scale[idx % 7];
  });
}

/** 진행 = 도수의 순서 있는 목록. i–VII–VI–V 는 [0, 6, 5, 4] 다. */
function midiToHz(midi: number): number
{
  return 440 * Math.pow(2, (midi - 69) / 12);
}
```

### 4.2 합성 규칙 4개

연구 09:834-837이 지정한 그대로다.

| # | 규칙 | 원문 근거 |
|---|---|---|
| 1 | 오실레이터는 **`triangle`** | "sawtooth is too harsh, sine is too thin, square sounds like a Game Boy. **triangle lands in the middle**" (09:834) |
| 2 | 어택 **20ms**, 짧은 **linear** 릴리스 | "A 20 ms attack and a short linear release is enough to avoid clicks" (09:835) |
| 3 | 각 오실레이터 게인을 **코드 음 수로 나눈다** | "Stacking 3 or 4 oscillators at full volume sums to clipping. **Multiply each oscillator's gain by 1/tones.length**" (09:836) |
| 4 | 마스터에 **lowpass 2400Hz 하나** | 09:837 |

규칙 2가 §2.5 함정 1의 예외라는 점을 짚어 둔다. **BGM의 코드 음은 `linearRampToValueAtTime`을 쓰므로 0에 도달할 수 있다.** 지수 램프의 0.001 규칙은 SFX에만 걸린다. 여기서 지수를 쓰면 음이 절대 안 꺼져 코드가 겹쳐 쌓인다.

### 4.3 look-ahead 스케줄러 — `setInterval`로 노트를 직접 재생하지 않는다

연구 09:854 — "**Notes are not triggered 'when the loop runs,' but are placed on the AudioContext timeline using absolute timestamps.**" `AudioContext.currentTime`은 소수점 15자리 정확도를 갖는다(09:852).

```ts
let nextChordTime = 0;
let step = 0;
let timerId = 0;

/** MDN 공식 패턴(연구 09:843-851). setTimeout은 "언제 다시 볼지"만 정하고, 노트 시각은 전부 절대 타임스탬프다. */
function scheduler(): void
{
  const ctx = audioCtx();
  while (nextChordTime < ctx.currentTime + BGM.scheduleAheadSec)
  {
    scheduleChord(nextChordTime, step);
    step += 1;
    nextChordTime += (60 / BGM.bpm) * BGM.beatsPerChord;
  }
  timerId = window.setTimeout(scheduler, BGM.lookaheadMs);
}

function scheduleChord(atSec: number, index: number): void
{
  const ctx = audioCtx();
  const degree = BGM.progression[index % BGM.progression.length];
  const tones = chordTones(BGM.tonicMidi, BGM.scale, degree);
  const durSec = (60 / BGM.bpm) * BGM.beatsPerChord;
  const perVoice = BGM.chordGain / tones.length;   // 규칙 3

  for (const midi of tones)
  {
    const osc = ctx.createOscillator();
    osc.type = 'triangle';                          // 규칙 1
    osc.frequency.value = midiToHz(midi);

    const g = ctx.createGain();
    g.gain.setValueAtTime(0, atSec);
    g.gain.linearRampToValueAtTime(perVoice, atSec + BGM.attackSec);          // 규칙 2
    g.gain.setValueAtTime(perVoice, atSec + durSec - BGM.releaseSec);
    g.gain.linearRampToValueAtTime(0, atSec + durSec);

    osc.connect(g).connect(musicBus());
    osc.start(atSec);
    osc.stop(atSec + durSec + 0.02);                // §2.5 함정 5
  }
}
```

`scheduleAheadSec`는 0.1, `lookaheadMs`는 25로 시작한다. 이 두 값은 프레임률이 흔들려도 노트가 밀리지 않게 하는 여유이고, 탭이 백그라운드로 가면 `setTimeout`이 1초로 조여지므로 그 경우 BGM은 §6의 음소거와 같은 경로로 정지시킨다.

## 6. 음소거 · 믹서

### 6.1 M 키의 동작

스펙 §16.1(전투 중) · §16.3(타이틀·일시정지)이 `M`을 배정했고, "전환은 언제든 가능하다"(§17)가 조건이다.

| 동작 | 구현 | 왜 이렇게 |
|---|---|---|
| 음소거 켜기 | `masterGain.gain.linearRampToValueAtTime(0, now + 0.02)` | **컨텍스트를 정지시키지 않는다.** `ctx.suspend()`를 쓰면 BGM 스케줄러의 `currentTime` 기준이 멈춰 해제 시 노트가 한꺼번에 쏟아진다 |
| 음소거 끄기 | `masterGain`을 `AUDIO.mixer.masterGain`으로 20ms 복귀 | 20ms 램프는 클릭 노이즈 방지용이다. 즉시 대입하면 파형이 끊기며 딱 소리가 난다 |
| 첫 M 입력 | `resumeOnFirstGesture()`의 `kick` 경로를 타므로 컨텍스트가 깨어난다 | §1.3. 다만 M은 그 경로의 여러 입력 중 하나일 뿐이다 |
| 상태 표시 | HUD 상시 (§15.1 "현재 음소거인지 한눈에 보여야 한다") | — |
| 새 소리 트리거 | 음소거 중에도 **정상적으로 노드를 만들고 재생한다** | `masterGain`이 0이므로 안 들릴 뿐이다. 트리거 자체를 막으면 음소거 코드 경로가 무음 전용 경로가 되어 §1.2의 1:1 페어링이 음소거일 때만 다르게 돈다 |

마지막 줄이 중요하다. **음소거는 출력 단 하나만 바꾼다.** 그 위쪽은 소리가 켜져 있을 때와 완전히 동일하게 돈다.

### 6.2 음소거 시 각 소리를 대체하는 시각

§1.1의 원칙상 대부분의 항목은 애초에 시각이 주(主)이고 소리가 보조다. 아래 표는 "소리가 없을 때 이 정보가 어디서 오는가"를 한 줄씩 확인한 것이다.

| 사건 | 음소거 시 정보 출처 | 스펙 근거 |
|---|---|---|
| 패리 3등급 | 등급 텍스트 팝업 — 등급별 색·크기 구분 | §15.1 "패리 판정" |
| 빈 패리 | 무적 링이 **생기지 않는다.** 성공 시에만 링이 켜진다 | §15.1 "무적 상태 ... 성공 순간과 무적 시작이 같은 신호로 읽혀야 한다" |
| 재패리 · 등급 상승 | 타수 표시 + 데미지 팝업 | §15.1 "재패리 — 몇 번째로 쳐냈는지가 읽혀야 한다" |
| 반사탄 발생 | 색·형태 전환 | §17 "색·형태로 즉시 구분" |
| 적 처치 / 연쇄 | 파편 버스트 + 0.04초 순차 소멸 | D-09 |
| 피격 (원인 구분) | 라이프 아이콘 감소 + 원인 탄의 색(반사탄은 황핵·적링) | §15.1 · §17 |
| **쿨다운 종료** | **링이 완성되는 순간 반경 50u → 56u로 0.08초 ease-out 확장한 뒤 소멸** | §15.1 "패리 쿨다운 — 플레이어 주변 링으로 표시" · [06](06_렌더링과_게임필.md) §1.7 · [12](12_통합_계약.md) §8-1 |
| 적 발사 예비동작 | 총구·시위 발광, 사격 자세 | §15.1 "적 본체의 상태 변화만으로 읽혀야 한다" |
| 예고 3종 | 예고 원·선·방향선 그 자체 | §15.1 |
| 장판 진입 | 장판 경계 | §17 "경계가 명확해야 한다" |
| 보스 페이즈 / 격파 | HP 바의 페이즈 눈금 통과 / 바 소멸 | §15.1 "페이즈 임계값을 눈금으로 표시" |
| 콤보 상승 / 경고 | 콤보 숫자·배수 + 유지 시간 게이지 | §15.1 "유지 시간이 줄어드는 게이지 동반" |

**쿨다운 종료 한 줄만 위험도가 다르다.** 나머지는 시선이 이미 가 있는 곳에서 정보가 오지만, 쿨다운 링은 플레이어 발밑이라 탄을 보는 동안은 안 보인다. 그래서 스펙 §17이 이 항목만 소리의 고유 역할로 인정했고, §15.1이 "링이 채워지는 것이 시각적 잡음이 되지 않아야 한다"는 반대 방향 제약까지 걸어 두었다. **음소거 상태에서 쿨다운을 못 읽는 문제는 소리로 풀 수 없다.** 절충은 **링이 완성되는 순간 반경 50u → 56u로 0.08초 ease-out 확장한 뒤 소멸하는 것**이다([06](06_렌더링과_게임필.md) §1.7, [12](12_통합_계약.md) §8-1). 1프레임 밝기 상승을 쓰지 않는 이유는 이 사건이 초당 최대 4.16회(§3.8) 일어나기 때문이다 — 1프레임 점멸이 초당 4.16회면 신호가 아니라 스트로브다. 0.08초 확장은 같은 주기 안에서도 시작과 끝이 있는 하나의 움직임으로 읽힌다. 실제로 읽히는지는 §6.3의 무음 플레이스루에서 확인한다.

### 6.3 무음 플레이스루 체크리스트 — 완료 조건

연구 09:1162가 D7 작업으로 지정했고, 연구 09:889이 이유를 적었다 — "개발자는 소리를 켜고 테스트했으므로 이 상태를 한 번도 본 적이 없다."

**절차.** 브라우저 탭을 새로 열고, 아무 입력도 하기 전에 시작해서, 소리를 한 번도 켜지 않고 스테이지 1부터 5까지 통과한다. 치트 모드로 스테이지를 건너뛰어도 되지만(§18) 각 스테이지에서 최소 30초는 실제로 플레이한다.

| # | 확인 항목 | 통과 기준 |
|---|---|---|
| 1 | 패리 3등급 | 세 등급을 각 10회씩 내고, 팝업만 보고 등급을 맞힌다. **10회 중 10회** |
| 2 | 빈 패리 | 빈 패리 직후 일부러 피격당해 본다. "무적이 없었다"가 화면에서 읽혔는가 |
| 3 | 피격 원인 | 반사탄 자해 3회, 적 탄환 피격 3회. 매번 원인을 즉시 알았는가 |
| 4 | **쿨다운 종료** | 탄막 한가운데에서 링을 안 보고 패리를 연타했을 때, 입력이 씹히는 느낌이 나는가. **이 항목이 가장 실패하기 쉽다** |
| 5 | 연쇄 처치 | **패리 한 번으로 3발 이상을 동시에 반사해 3기 이상 처치.** 연쇄임이 한 번에 읽혔는가 ([12](12_통합_계약.md) §6). 카드 없이 성립해야 하는 항목이다 — 관통 카드 R02를 전제로 잡으면 34.9%의 런에서만 검사할 수 있다 |
| 6 | 적 발사 예비동작 | 배경이 가장 복잡한 S5 노량에서, 예비동작이 배경에 묻히지 않았는가 (§17) |
| 7 | 예고 3종 | 셋을 서로 구분했는가. 그리고 "예고 도형 = 회피"라는 규칙이 소리 없이도 학습되는가 (§6.2) |
| 8 | 콤보 끊김 | 게이지만 보고 끊기기 전에 반응할 수 있는가 |
| 9 | 보스 페이즈 | 전환 예고를 눈으로만 받았는가 (§17 "사전에 알린다") |
| 10 | 카드 선택 | 커서 이동·리롤·확정이 각각 화면에서 확인되는가 |

한 항목이라도 실패하면 **소리를 고치는 게 아니라 시각을 고친다.** 실패는 §1.1 위반의 증거다.

## 7. 스코프와 중단 규칙

### 7.1 SFX가 BGM보다 앞이다. 예외 없다

D-08이 결정으로 못 박았고 그 근거가 연구 09:1175의 중단 규칙 표다 — "D5 종료 | SFX 6종이 안 끝남 | **BGM 포기.**"

**미루는 게 아니라 버린다.** BGM을 D6·D7으로 미루면 그 이틀이 프로파일링·브라우저 3종 검증·무음 플레이스루·AI 활용 문서(연구 09:1158-1167)의 몫이라 결국 그것들이 밀린다. 결정 시점에 잘라 내는 것이 이 규칙의 전부다.

### 7.2 티어와 구현 순서 — 아래에서부터 자른다

**티어는 통째로 넣거나 통째로 뺀다. 절대 반만 만들지 않는다.** 반쯤 만든 티어는 어떤 처치는 소리가 나고 어떤 처치는 안 나는 상태이고, 그건 미완성이 아니라 버그로 읽힌다.

| 티어 | 내용 | 이 티어까지 있으면 성립하는 것 |
|---|---|---|
| **A** | 패리 3등급, 빈 패리, 피격 2종, 적 처치 | **최소 일관 집합.** 플레이어가 하는 일(패리)과 그 결과(반사·처치·피격)가 전부 소리를 갖는다. 여기서 멈춰도 게임이 조용한 게 아니라 "절제된" 것으로 들린다 |
| **B** | 연쇄 처치, 쿨다운 종료 틱, UI 3종 | D-09 머니샷과 §17이 소리에게만 맡긴 항목이 들어온다. **영상 촬영의 실질 하한선이 여기다** |
| **C** | 보스 페이즈 전환·격파, 발사 예비동작, 예고 3종 | 스펙 §17 표의 사건이 전부 덮인다 |
| **D** | 콤보 상승·경고, 장판 진입, 반사탄 발생 레이어, 무적 종료 | 보조 신호. 없어도 정보 손실이 없는 것들만 모았다 |
| **E** | 절차적 BGM (§4) | — |

구현 순서도 A → E다. 각 티어 끝이 잘라 낼 수 있는 지점이고, [11_구현_계획.md](11_구현_계획.md)의 게이트가 이 경계를 쓴다.

### 7.3 티어별 중단 신호

| 시점 | 조건 | 조치 |
|---|---|---|
| 오디오 작업 시작 후 반나절 | 티어 A가 안 끝남 | 등급 구분 축을 네 개에서 **음정 방향 하나로 줄인다**(§3.1). 나머지 세 축은 값만 복사해 둔다. 축을 줄여도 §17의 "세 등급이 헷갈리면 안 된다"는 유지된다 |
| 티어 B 착수 시 | 연쇄 처치 스태거가 render 쪽과 안 맞음 | **소리를 고치지 않고 값을 맞춘다.** `chain.linkGapSec`은 render의 스태거를 따라가는 종속값이지 독립 파라미터가 아니다 |
| 티어 C 중 | 예고 3종이 서로 안 구분됨 | 파형을 바꾸지 말고 **엔벨로프만** 다시 나눈다(§3.10). sawtooth 전용 배정은 §2.1의 규칙이라 여기서 깨면 학습 규칙이 무너진다 |
| 티어 D 이후 | 남은 시간이 반나절 미만 | **BGM 착수하지 않는다.** 착수했다가 미완성으로 남으면 스테이지 5개 중 두 개만 음악이 있는 상태가 되고, 그건 없느니만 못하다 |
| 아무 때나 | 무음 플레이스루(§6.3)에서 실패 항목 발생 | 남은 티어 작업을 멈추고 **시각 쪽을 먼저 고친다.** §1.1이 이 문서의 상위 원칙이다 |

### 7.4 BGM을 만들게 됐을 때의 내부 순서

여기서도 자를 수 있게 배치한다.

1. 스케줄러 + 코드 패드 (§4.3) — 이것만 있어도 다섯 스테이지가 전부 음악을 갖는다
2. 스테이지별 키·BPM·진행 적용 (§4.4의 `stages` 배열)
3. 아르페지오 텍스처 (S2·S4·S5)
4. 노이즈 드럼
5. 보스 변주 (BPM +12, 2코드, lowpass 3200)
6. 카드 선택 화면 장조

1번만 있고 2~6이 없으면 다섯 스테이지가 같은 음악이지만 **음악이 없는 스테이지는 없다.** 이 순서가 그 성질을 지킨다.
