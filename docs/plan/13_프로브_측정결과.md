# 13. 프로브 측정 결과

[12_통합_계약.md](12_통합_계약.md) §10 E-18이 지시한 30줄 프로브를 실제로 돌린 결과. **[01_설계_결정.md](01_설계_결정.md) R-02가 이 문서로 닫힌다.**

측정 파일: 저장소 루트의 [`probe.html`](../../probe.html). 의존성 0, 빌드 0. 브라우저로 열면 다시 잰다.

## 1. 측정 환경

| 항목 | 값 |
|---|---|
| GPU | ANGLE (Intel, Mesa Intel(R) Iris(R) Xe Graphics (RPL-P), OpenGL ES 3.2) |
| 가속 | **하드웨어 가속 확인됨** — SwiftShader·llvmpipe 아님 |
| 브라우저 | Chrome 150 (Linux x86_64) |
| 캔버스 | 1080 × 1920, `alpha: false` |
| 방법 | 워밍업 후 측정, 시행마다 `getImageData` 1회로 큐 배출. 초기 실행은 시행 5회 × 10,000회,
  이후 기준값은 **시행 30회 × 10,000회**로 다시 쟀다(§3.1) |

**가속 여부를 자가 보고하게 만든 것이 이 측정의 유효 조건이다.** 소프트웨어 래스터라이저로 떨어진 채 잰 숫자는 D-02(Canvas 2D)를 반증하지 못한다.

## 1-B. 이 측정의 한계 — 어느 결론이 튼튼하고 어느 것이 아닌가

**먼저 읽어야 할 절이다.** 아래 숫자를 인용하기 전에 무엇이 검증됐고 무엇이 아닌지 알아야 한다.

Canvas 2D는 비동기로 큐잉되므로 측정하려면 큐를 비워야 하고, 이 프로브는 `getImageData(0,0,1,1)`로 비운다. 그런데 **1080×1920 GPU 캔버스의 readback은 수십 ms가 될 수 있다.** 그러면 측정값이 이렇게 된다.

```
측정값 = d + R/N        d = 진짜 호출 비용,  R = flush 비용,  N = 반복 횟수
N = 10,000, R = 45ms  →  R/N = 4.5 µs
```

**4.5µs는 §2.1이 "순수 호출 고정비"라고 부른 4.96µs와 거의 같다.** 즉 그 분해가 flush를 N으로 나눈 값을 보고 있었을 가능성이 있다.

| 결론 | 튼튼한가 | 왜 |
|---|---|---|
| **`setTransform`은 공짜** | **튼튼** | 두 측정의 **차이**라 flush가 양쪽에서 상쇄된다 |
| **합성 모드 전환은 측정 한계 아래** | **튼튼** | 같은 이유. 게다가 부호가 실행마다 뒤집혔다 |
| **fill이 병목이 아니다** | **튼튼** | 여유가 8.5~10배라 오염이 있어도 결론이 안 바뀐다. 그리고 오염은 이 여유를 **더 크게** 만드는 방향이다 |
| **D-02(Canvas 2D) 유지** | **튼튼** | 판정 구간 가운데이고, 오염은 `t`를 부풀리는 방향이라 실제로는 더 안전한 쪽 |
| 비용의 70~76%가 호출 고정비 | **미검증** | flush를 나눠 본 것일 수 있다 |
| 상한 2,013 (p95) | **하한으로만 유효** | 오염이 `t`를 부풀리므로 **진짜 상한은 이보다 높다** |
| 예산 30% 초과, 굽기 두 개 필요 | **보수적 추정** | 상한이 실제로 더 높으면 초과가 줄거나 사라진다 |

**오염의 방향이 한쪽이라는 점이 중요하다.** flush는 측정값을 **부풀리기만** 한다. 그러므로 위 표의 "미검증" 항목들은 전부 **비관적인 쪽으로 틀렸을** 가능성만 있고, 낙관적인 쪽으로 틀릴 수는 없다. 상한 2,013은 안전하게 쓸 수 있는 **하한**이다.

**해소하는 방법은 한 번의 측정이다.** `probe.html`에 N-스윕(500 / 2,000 / 10,000 / 40,000)과 `flush` 절대 비용 측정을 넣어 두었다. N을 키울수록 값이 줄면 그 감소분이 flush이고, 수렴하면 남는 값이 진짜 호출 비용이다. **이 세션에서는 브라우저 세션이 응답하지 않아 돌리지 못했다 — P1의 첫 작업이 이것이다.**

그때까지 [06](06_렌더링과_게임필.md) §3.6의 손잡이 재정렬은 **가설로 취급한다.** "픽셀보다 호출"이라는 방향 자체는 fill 여유 8.5~10배가 독립적으로 지지하지만, 잡몹 굽기의 −480이 상한 대비 몇 %인지는 상한이 확정된 뒤에 다시 센다.

### 2.1 비용 분해 — **§1-B의 유보가 걸리는 곳이 여기다**

같은 방법으로 네 가지를 더 재서 7.33µs가 어디서 오는지 갈랐다. 다만 아래 "호출 오버헤드"에는 `flush`를 N으로 나눈 값이 섞여 있을 수 있고, 그 크기가 우연히 비슷하다 — **§1-B를 먼저 보라.**

| 측정 | 값 | 무엇이 다른가 |
|---|---:|---|
| JS 루프만 (그리기 없음) | **0.000 µs** | 루프 자체는 공짜다 |
| 1×1 스프라이트, 흩뿌림 | **4.960 µs** | fill이 사실상 0. **순수 호출 오버헤드** |
| 85px, 한 자리에 겹쳐 그리기 | **6.510 µs** | + fill 1.55µs |
| 85px, 512자리에 흩뿌림 | **7.060 µs** | + 프레임버퍼 산포 0.55µs |

```
7.06 µs  =  4.96 (호출 오버헤드)  +  1.55 (fill)  +  0.55 (산포)
              70%                    22%             8%
```

**`drawImage` 한 번의 비용 중 70%가 무엇을 그리든 붙는 고정비로 보인다.** 스프라이트를 1×1로 줄여도 5µs가 남는다. **단 이 5µs가 진짜 호출 비용인지 `flush` 분산분인지는 아직 갈리지 않았다**(§1-B). `probe.html`의 N-스윕이 그것을 가른다.

## 3. 도출

### 3.1 단일 실행으로 판단하면 안 된다

처음 두 번의 실행이 서로 달랐다 — `t = 7.330` 과 `t = 6.090`, **20% 차이**다. 그래서 표본을 30으로 늘려 다시 쟀다.

| 통계 (n = 30, 각 10,000회) | 값 |
|---|---:|
| 최소 | 5.720 µs |
| p25 | 6.690 µs |
| **중앙값** | **7.140 µs** |
| p75 | 7.590 µs |
| **p95** | **8.280 µs** |
| 최대 | 8.670 µs |
| 표준편차 | 0.708 |
| 변동계수 | **9.8%** |

**변동계수 9.8%는 무시할 수 없다.** 이 측정으로 "예산이 상한을 몇 % 넘는다"를 소수점까지 말할 수 없고, 말하려고 하면 그건 측정이 아니라 반올림 운이다.

### 3.2 어느 백분위로 계획할 것인가 — p95다

상한은 고르는 백분위에 따라 갈린다.

| 기준 | t | 상한 (16,670 ÷ t) |
|---|---:|---:|
| 최소 (낙관) | 5.720 | 2,914 |
| 중앙값 | 7.140 | **2,335** |
| **p95 (보수)** | **8.280** | **2,013** |

**p95를 쓴다.** [06](06_렌더링과_게임필.md) §3.7.2의 게이트가 **p99 프레임 타임 ≤ 16.67ms**이기 때문이다. 프레임의 99%가 예산 안에 들어와야 한다면, 호출 비용의 중앙값이 아니라 꼬리를 견뎌야 한다. 중앙값으로 계획하면 게이트를 절반만 만족시키는 설계가 나온다.

## 4. 기획안이 바뀌는 것 셋

### 4.1 fill-rate는 병목이 아니다 — 06 §3.6의 전제가 뒤집혔다

> fill 여유(8.5~10배)는 §1-B의 오염과 무관하게 튼튼하다. 다만 **손잡이 재정렬의 정확한 %는 상한이 확정된 뒤 다시 센다.**


[06](06_렌더링과_게임필.md) §3.6은 "호출 수보다 이쪽이 위험하다"로 시작했다. **정반대다.**

```
필요 fill-rate      630 Mpx/s
실측 fill-rate  5,386 ~ 6,380 Mpx/s     →  8.5 ~ 10배 여유
```

그리고 §2.1의 분해가 같은 방향을 가리킨다 — 비용의 대부분이 픽셀과 무관하다. **픽셀을 줄이는 최적화는 이 게임에서 거의 아무 효과가 없다.** 이 결론은 분해가 `flush`에 오염됐더라도 성립한다 — fill 여유 8.5~10배 하나만으로 이미 서기 때문이다.

이게 §3.6의 손잡이 목록을 통째로 재정렬한다. 픽셀을 줄이는 것(글로우 반경, 비네트 띠)은 무의미에 가깝고, **호출 수를 줄이는 것만 값을 한다.**

| 손잡이 | 줄이는 것 | 실측 기준 효과 |
|---|---|---|
| **잡몹 굽기** (20기 × 25회 → 20회) | 호출 **−480** | **−24%** (480 ÷ 2,013). 단일 최대 손잡이 |
| 청해파문 스트립 굽기 (304 stroke → 18) | 호출 −286 | **−14%** |
| T-07 동시 적 탄환 상한 | 호출 (탄당 2~3회) | 상한을 내린 만큼 비례 |
| ~~글로우 반경 축소~~ | 픽셀만 | **거의 0.** §17만 깨고 얻는 게 없다 |
| ~~비네트 사각 띠 4장~~ | 픽셀 0.42M, 호출 **+3** | **순손해.** fill 여유가 8.5~10배다 |

**[12](12_통합_계약.md) §10 E-14가 비네트 띠 분할을 "대가 없는 유일한 손잡이"로 확정했는데, 대가가 없는 건 맞지만 얻는 것도 없다.** `fill` 1회가 4회가 되어 호출이 3 늘고 픽셀 0.42M이 줄어드는데, 실측상 픽셀은 남아돌고 호출이 모자란다. **순손해다 — 하지 않는다.**

반대로 §3.6이 3~4순위로 밀어 둔 **잡몹 굽기가 실제로는 1순위**다.

### 4.2 예산 초과가 실재한다. 그리고 손잡이 하나로는 못 덮는다

> **§1-B를 먼저 보라.** 아래는 오염 가능성을 감안하지 않은 값이고, 상한이 실제로 더 높으면 초과가 줄거나 사라진다. 보수적으로 계획하는 근거로만 쓴다.


```
실측 상한 (p95)   2,013
기획안 예산        2,616        →  30% 초과
```

[12](12_통합_계약.md) §7.4-B가 "측정 없이 상한을 2,700으로 고쳐 쓰지 않는다"고 판정했는데, **고쳐 썼으면 정확히 반대 방향으로 틀렸을 것이다** — 실제 상한은 2,500보다 높은 게 아니라 낮다. 유보가 옳았다.

**손잡이를 하나만 쓰면 부족하다.**

| 단계 | 호출 | p95 상한 2,013 대비 |
|---|---:|---|
| 현재 예산 | 2,616 | +30% |
| + 잡몹 굽기 (−480) | 2,136 | **+6% — 아직 넘는다** |
| + 청해파문 스트립 굽기 (−286) | **1,850** | **−8% 통과** |

처음 단일 실행(상한 2,274)으로 계산했을 때는 잡몹 굽기 하나로 덮인다고 적었는데, **표본을 늘리고 p99 게이트에 맞는 백분위를 쓰니 두 개가 필요하다.** 이게 n=1로 판단하면 안 되는 이유의 실례다.

중앙값 기준(2,335)으로는 잡몹 굽기 하나로 통과하지만, 그건 프레임의 절반만 통과한다는 뜻이다.

**P1 게이트의 첫 과제는 두 굽기를 함께 넣고 다시 재는 것이다.**

### 4.3 `setTransform`은 공짜다 — E-15의 정의 논쟁이 소멸한다

```
drawImage 단독          7.200 µs
setTransform + rotate + drawImage   7.060 µs
```

차이가 음수이고 시행 편차 안이다. **상태 호출은 비용이 없다.**

[12](12_통합_계약.md) §10 E-15가 "드로우 콜을 `drawImage`/`fill`/`stroke`/`fillText`만 센다"고 정의를 확정했는데, 그 정의가 실측으로 정당화됐다 — §3.1이 세던 520회의 `setTransform`은 예산에 들어갈 이유가 없다.

**두 패스 최적화(E-14)의 이득은 측정되지 않았다.**

| 실행 | 왕복 | 두 패스 | 차이 |
|---|---:|---:|---:|
| 1회차 | 11.980 | 11.540 | +0.440 (전환 1회 0.220µs) |
| 2회차 | 11.700 | 11.860 | **−0.160 (음수)** |

두 번의 부호가 반대다. 그리고 §3.1이 보인 대로 이 측정의 변동계수는 9.8%인데, 찾으려는 차이는 12µs의 1~4%다 — **노이즈보다 작다.**

**정직한 결론: 이 하드웨어에서 합성 모드 전환 비용은 측정 한계 아래다.** E-14의 두 패스 규칙은 유지하되(공짜이고, [06](06_렌더링과_게임필.md) §3.7.1이 지목한 배칭 가능성의 방향이기도 하다), **이것이 예산을 유의미하게 줄여 준다고 계산에 넣지 않는다.** 12 §10 E-14가 적었던 "1,040 → 2 전환"은 사실이지만, 그 절약분이 프레임 예산에서 차지하는 크기는 이 측정으로 확인되지 않았다.

## 5. 이 측정이 닫는 것과 열어 두는 것

**닫힌다.**

- [01](01_설계_결정.md) R-02 — "동시 탄환 수 대 프레임률의 실측 데이터가 없다". 이제 있다. **단 상한은 확정값이 아니라 안전한 하한이다**(§1-B).
- [12](12_통합_계약.md) §10 E-18의 판정 분기 — `t = 7.33µs`는 세 구간 중 가운데(`1.5 < t < 12`)다. **D-02(Canvas 2D)는 유지된다.** GPU 경로가 살아 있고, 상한이 게임 규모와 같은 자릿수다.
- [12](12_통합_계약.md) §7.4-B의 유보 — 초과가 실재하는 것으로 판명. 다만 대응은 상한 조정이 아니라 호출 수 감축이다.

**열어 둔다.**

- **이 숫자는 이 기기의 값이다.** Intel Iris Xe 통합 그래픽이고, 심사자의 기기는 더 빠를 수도 느릴 수도 있다. `probe.html`이 저장소에 있으므로 다른 기기에서 다시 재면 된다.
- **`drawImage` 5µs 고정비가 정상인지는 확인되지 않았다.** GPU 경로가 살아 있는데도 호출당 5µs면 Chrome의 Canvas2D가 이 패턴에서 배치를 못 하고 있을 가능성이 있다. 배치가 되는 조건(같은 스프라이트 연속, 합성 모드 고정)을 찾으면 상한이 크게 오를 수 있고, **§4.1의 두 패스 정렬이 이미 그 방향이다.** P1에서 확인할 값이다.
- **실제 프레임은 `drawImage`만으로 이뤄지지 않는다.** 배경 동적 레이어의 `stroke`, HUD의 `fillText`, 장판의 `fill`은 따로 재지 않았다. P1의 스트레스 씬이 그 합을 잰다.
