# 08. 화면과 UI

**이 문서의 목적 한 줄:** 전투가 아닌 모든 화면과, 전투 위에 겹치는 모든 표시를 확정한다 — 무엇이 어디에 몇 px로 그려지고, 어떤 키가 무엇을 하고, 화면이 바뀔 때 어떤 상태가 지워지고 어떤 상태가 남는지.

## 1. 화면 상태 기계

### 1.1 화면 목록

| 화면 | 파일 | sim 진행 | 전투 프레임을 배경으로 그리나 |
|---|---|---|---|
| 타이틀 | `src/screens/title.ts` | **돈다** (어트랙트 루프, §6) | 자기 자신이 전투다 |
| 전투 | `src/screens/play.ts` | 돈다 | — |
| 카드 선택 | `src/screens/card-select.ts` | **멈춘다** (§11.1 "선택 중 게임 정지") | 그린다 |
| 일시정지 | `src/screens/pause.ts` | **멈춘다** (§13.4) | 그린다 |
| 결과 | `src/screens/result.ts` | 멈춘다 | 그린다 |
| 치트 메뉴 | `src/dev/cheat-menu.ts` | **멈춘다** (§18.2) | 아래 화면을 그대로 두고 겹친다 |
| 모바일 미지원 안내 | `src/screens/unsupported.ts` | **시작하지 않는다** (§16.6) | 없음 (캔버스 자체를 만들지 않는다, §7) |

전이는 `src/screens/manager.ts`가 소유한다.

**치트 메뉴만 화면이 아니라 오버레이다.** §18.2가 "종료 | 같은 입력 또는 Esc. **메뉴만 닫히며** 이미 적용한 변경은 되돌아가지 않는다"고 적었다 — 닫으면 아래 화면으로 *돌아가는* 것이 아니라 아래 화면이 계속 거기 있었다는 뜻이다. 그래서 매니저의 상태는 화면 하나가 아니라 `{ screen, cheatOpen: boolean }` 한 쌍이다.

**일시정지·카드 선택·결과는 전투 프레임을 배경으로 그리지만 별개의 화면이다.** 목업 셋이 전부 그렇게 그렸다 — `14_pause/scene.js:104` `rgba(5,6,10,0.78)`, `11_card_select/scene.js:184` `rgba(5,6,10,0.86)`, `13_result/scene.js:52` `rgba(4,5,9,0.9)`. 카드 선택 목업의 주석이 이유를 적었다: "the field stays visible under the dim: the run has not restarted"(`11_card_select/scene.js:183`). 런이 이어지고 있다는 사실 자체가 화면의 정보다.

### 1.1.1 `play.ts`의 상태 — 화면을 늘리지 않는다

[06_렌더링과_게임필.md](06_렌더링과_게임필.md) §3.3이 배경 정적 레이어(8.3MB, S2 기준 path op 약 350개)를 "스테이지 진입 연출 중"에 굽고 **그것이 전투 첫 프레임이 되면 안 된다**고 적었는데, 위 화면 목록 일곱 개에 그 연출이 들어갈 자리가 없다.

**여덟 번째 화면을 만들지 않는다.** `screens/play.ts`가 상태를 갖는다 ([12_통합_계약.md](12_통합_계약.md) §3.3).

| 상태 | 내용 | sim |
|---|---|---|
| `entering` | 스테이지명 표시 1.2초. 이 동안 배경 정적 레이어를 굽는다 | 정지 |
| `combat` | 정상 진행 | 돈다 |
| `lull` | 소강 3초 (§9.1) | 돈다 |
| `boss` | 보스전 | 돈다 |
| `clear` | 클리어 연출 | 돈다 |

`entering`의 1.2초는 보스 페이즈 전환 연출(§10.1)과 **같은 길이**다 — 이 게임이 "장면이 바뀐다"고 말하는 시간이 하나여야 한다. 굽기가 그보다 오래 걸리면 굽기가 끝날 때까지만 연장한다. 8.3MB 오프스크린 fill은 수십 ms 수준이라 실제로는 언제나 1.2초가 먼저 끝난다.

**§6.4가 금지한 「검은 화면 → 페이드 인」과 충돌하지 않는다.** 그 금지의 대상은 **첫 페인트 전의 도입**이고, `entering`은 이미 어트랙트 루프가 돌고 있는 상태에서 스테이지로 넘어가는 전환이다. 첫 페인트는 여전히 게임 화면이다.

연출 자체의 소유자는 P6-1이다([11](11_구현_계획.md) §8).

전이표가 참조할 필드를 먼저 확정한다. 전부 `sim/run.ts`(§13 런 생명주기)가 소유한다.

| 필드 | 초기값 | 수명 | 근거 |
|---|---|---|---|
| `life` | 3 | 런 전체. **스테이지 클리어로 회복되지 않는다** | §4.1 · §13.2 |
| `maxLife` | 3 (상한 5) | 런 전체. 카드로만 증가 | §4.1 |
| `score` | 0 | 런 전체 | §12.1 |
| `combo` | 0 | **스테이지.** 스테이지 시작마다 0 | §12.2 |
| `maxCombo` | 0 | 런 전체 (결과 화면 항목) | §12.3 |
| `cards` | 빈 배열 | 런 전체. 게임오버 시 전부 소실 | §11.1 · §13.3 |
| `rerollUsed` | `false` | 런 전체. 게임오버 시 초기화 | §11.1 |

`life`와 `combo`의 수명이 다른 것이 이 표의 핵심이다. 라이프는 5스테이지를 관통해 공유되고(§13.2) 콤보는 스테이지마다 끊긴다(§12.2). 둘을 같은 자리에서 초기화하면 규칙이 조용히 뒤집힌다.

### 1.3 진행 흐름

§13.1이 정한 순서다.

```
타이틀 → S1 → 카드 → S2 → 카드 → S3 → 카드 → S4 → 카드 → S5 → 엔딩·결과
```

- **카드 선택은 S1~S4 클리어 직후에만, 총 4회 열린다. S5 뒤에는 열리지 않는다**(§11.1 "획득 시점 | 스테이지 1·2·3·4 클리어 직후. **총 4회**", §9.1 "업그레이드 카드 선택 (스테이지 1~4만)").
- **라이프는 다섯 스테이지를 관통해 공유되며 클리어로 회복되지 않는다**(§13.2). 클리어가 주는 것은 회복이 아니라 점수다 — 남은 라이프 × 2,000(§12.1).
- **콤보는 스테이지 시작 시 0이다**(§12.2). 카드 선택 화면을 지나 다음 스테이지가 시작되는 순간 0이 된다.
- 스테이지 5를 클리어하면 런이 끝난다. 무한 모드도 추가 스테이지도 없다(§13.1).
- 난이도 선택이 없으므로 타이틀에 난이도 항목을 두지 않는다(§13.1).

**엔딩은 별도 화면이 아니다.** §13.1이 "엔딩 · 결과 화면"을 한 항목으로 묶었고, 목업이 그것을 결과 화면의 머리말 두 줄로 구현했다 — `13_result/scene.js:63-69`의 「노량 · 최종 결전 종료」/「돌려주었다」. 게임오버로 들어온 결과 화면은 이 두 줄만 다른 문구로 바뀐다(§5.2).

### 1.4 전이표

`무엇이 초기화되나` 열은 §1.2 표의 필드 이름을 쓴다. 표에 없는 필드는 전부 유지된다.

**그런데 §1.2의 표에는 런 스칼라만 있고 월드 엔티티가 없다.** 위 규칙을 그대로 읽으면 어트랙트 루프의 살아 있는 E-A·E-B와 탄환이 T-03을 타고 S1으로 넘어오고, S(n)의 잔존 반사탄·장판이 T-05를 타고 S(n+1)로 넘어가며, T-15는 게임오버 프레임의 엔티티를 그대로 둔 채 다시 시작한다. 08 자신이 치트 경로에서는 이 위험을 이름 붙였는데(T-14 「화면의 적·적 탄환·반사탄·장판 전부 제거」, §8.1이 인용한 §18.2 "어느 스테이지의 파라미터로 계산된 탄환인지가 불분명해진다") 정상 경로에는 적용하지 않았다.

**T-09의 해석을 밝혀 둔다.** §16.1은 "치트 모드는 전투 중 직접 진입할 수 없다(§18.2). Shift + F9는 **일시정지 화면으로 먼저 보낸다**"고만 적었다. 「먼저」를 "일시정지만 시키고 메뉴는 안 연다"로 읽을 수도 있다. **그렇게 읽지 않는다** — 그러면 한 번 누른 키가 자기가 이름 붙인 일을 절반만 하고 멈추고, 사용자는 왜 메뉴가 안 떴는지 알 수 없다. 일시정지 상태는 §18.2의 진입 가능 시점이므로 이어서 여는 것이 규칙 위반도 아니다. 그래서 T-09는 일시정지 전이와 메뉴 열기를 한 입력으로 처리한다.

**T-11의 도착지가 타이틀인 이유.** §12.3은 결과 화면을 "런 종료 시(**클리어 또는 게임오버**)"에 띄운다고 규정했다. 런 포기는 둘 중 어느 쪽도 아니다. 그러므로 런 포기는 결과 화면을 거치지 않고 타이틀로 간다.

**T-07이 아무것도 지우지 않는 이유.** §13.3의 1단계는 "즉시 게임 정지, 결과 화면 표시"이고 카드 소실은 3단계 — **재시작을 선택한 뒤**다. 게임오버 시점에 카드를 지우면 §12.3이 요구하는 「획득 카드 목록」을 표시할 수 없다.

## 2. HUD 사양

### 2.1 HUD가 그려지는 자리

`render/frame.ts`의 레이어 순서는 목업 `render()`(`engine.js:1934-1980`)를 그대로 지킨다. HUD와 관련해 그 순서가 정하는 것이 둘 있다.

| 사실 | 근거 | 결과 |
|---|---|---|
| HUD는 화면 흔들림 밖에서 그린다 | `engine.js:1975`의 `ctx.restore()`가 흔들림 `translate`를 되돌린 **뒤에** `:1978`이 `drawHud`를 부른다 | **라이프·점수·보스 바는 흔들리지 않는다.** §15.1이 라이프에 "남은 수를 **즉시 셀 수 있는** 형태"를 요구하는데, 흔들리는 숫자는 셀 수 없다 |
| HUD는 비네트 위, 화면 오버레이 아래 | `engine.js:1977-1979` — `vignette` → `drawHud` → `scene.overlay` | 일시정지·카드 선택·결과의 딤이 HUD를 덮는다. **덮여도 지우지 않는다** — §18.5의 오염 표시가 상시여야 하므로(§2.4) |

좌표는 전부 논리 플레이필드 단위 `u`다(§3.1, 1080×1920). 픽셀이 아니다.

### 2.2 승인된 요소표 — `drawHud` (engine.js:1669-1740)

폰트 스택은 세 개뿐이고 단일 소스는 `config/ui.ts`의 `FONTS`(§9)다: `data` = `"IBM Plex Mono", ui-monospace, …`, `body` = `"IBM Plex Sans KR", "Pretendard", …`, `display` = `"Gowun Batang", "Nanum Myeongjo", …`. 목업의 `tokens.css`는 이식하지 않는다 — 게임은 canvas에 그리므로 CSS 변수를 읽을 일이 없다([12_통합_계약.md](12_통합_계약.md) §3.2). HUD는 **전부 `data`(모노)** 를 쓴다. 숫자가 자릿수에 따라 흔들리면 안 되기 때문이다.

**웹폰트는 번들하지 않는다** ([12_통합_계약.md](12_통합_계약.md) §3.1). 서브셋하지 않은 한글 웹폰트 2종을 base64로 인라인하면 수 MB이고, 그것이 D-03이 이 결정을 뒤집는 조건으로 직접 이름 붙인 위험 — "inline base64 폰트 때문에 초기 파싱이 눈에 띄게 느려질 때" — 그 자체다. P0의 의존성 제한(vite·vitest·typescript·eslint 외 0개)에 서브셋 도구도 없다. 따라서 위 세 스택의 **첫 항목은 실행 환경에 거의 없고, 실제로는 시스템 폰트로 해석된다.** 이 문서의 모든 좌표·크기는 그 상태에서 성립해야 하며, [09_검증_전략.md](09_검증_전략.md) §6 E-11이 15화면의 레이아웃이 웹폰트 없이 유지되는지를 실제로 확인한다.

### 2.3 목업이 그리지 않은 요소 — §15.1 · §18.5 추가분

`drawHud`에 없지만 스펙이 요구하는 것이 넷이다. 그중 셋은 HUD에, 하나는 플레이어에 붙는다.

#### (a) 음소거 상태 상시 표시 — §15.1

| 항목 | 값 |
|---|---|
| 요구 | §15.1 "음소거 상태 \| 현재 음소거인지 한눈에 보여야 한다" |
| 왜 장식이 아닌가 | §17이 "소리가 유일하게 맡는 역할도 있다. **쿨다운 종료**처럼 화면 밖에서 일어나는 사건은 … 음소거 시에는 이 항목들이 §15.1의 시각 표시로 대체된다"고 적었다. 즉 이 표시는 **플레이어가 지금 어떤 피드백 채널을 잃었는지**를 알려 준다 |
| 위치 | 오른쪽 정렬 `(1044, 1864)` |
| 폰트 | `500 22px` 모노 |
| 켜짐 (정상) | `♪` — `C.baekFaint` `#5d6675` |
| 음소거 | `MUTE` — `C.baek` `#ede6d8` (불투명), 글자 위를 가로지르는 선 1개 |

**자리 선정 근거.** 상단 띠는 `drawHud`가 전부 점유한다 — 라이프(`y 39~69`), 점수(`y 14~76`), 스테이지·진행도(`y 14~54`), 보스가 있으면 보스 바와 이름(`y 82~116`, `x 70~1010`). 반면 **오른쪽 아래 사분면은 `drawHud`가 한 획도 긋지 않는 유일한 영역**이다(콤보 블록은 `x 40~278`, `y 1809~1885`로 왼쪽에만 있다). 왼쪽 아래 콤보와 좌우 대칭이 되고, 새 색도 필요 없다.

**정상 상태를 흐리게, 이상 상태를 진하게** 칠하는 이유는 하나다. 음소거는 플레이어가 스스로 켠 상태이고, 잊어버렸을 때만 문제가 된다. 잊어버리게 만들지 않으려면 이상 상태 쪽이 눈에 띄어야 한다.

#### (b) 치트 모드 오염 표시 — §18.5

| 항목 | 값 |
|---|---|
| 요구 | §18.5 "인게임 표시 \| HUD에 **상시 표시**. 정상 플레이 중인지 아닌지가 언제나 보여야 한다" |
| 표시 시점 | 치트 메뉴를 **연 순간부터**. 아무것도 바꾸지 않고 닫아도 남는다 (§18.5) |
| 해제 | **런 도중에는 해제되지 않는다.** 재시작해야 초기화된다 (§18.5 · T-15) |
| 위치 | 전체 폭 띠 `(0, 1898, 1080, 22)` |
| 형태 | `render/primitives.ts`의 `hatch`(사선 해칭)로 채운 띠 + 가운데 정렬 `(540, 1914)`에 `치트 — 오염된 런` |
| 색 | 해칭 `hexA(baek, 0.22)`, 글자 `C.baek`. **새 팔레트 항목을 만들지 않는다** |

**색이 아니라 형태로 표시하는 이유.** 팔레트는 색 하나에 규칙 하나다([03_파일_구조.md](03_파일_구조.md) §7). `jeok`은 적, `hwang`은 반사탄, `cheong`은 플레이어, `takjeok`은 패리 불가다(`config/palette.ts` — 색의 단일 소스이며 `tokens.css`는 이식하지 않는다, [12](12_통합_계약.md) §3.2). 오염 표시에 이 중 아무거나 재사용하면 그 색의 의미가 두 개가 된다. 사선 해칭은 어느 게임 요소도 쓰지 않는 형태이므로 새 규칙을 만들지 않고 새 뜻을 얻는다.

**모서리 배지가 아니라 전체 폭 띠인 이유.** §18.6이 "§18.5의 오염 표시가 HUD에 떠 있는 화면은 **그대로 실격 사유**가 되므로 촬영 전에 반드시 확인한다"고 적었다. 모서리 배지는 크롭 한 번에 사라진다. 전체 폭 띠는 프레임 전체를 보는 한 놓칠 수 없다.

**화면 전체를 덮는 워터마크는 쓰지 않는다.** 크롭 내성은 더 좋지만, 치트 모드가 존재하는 이유 자체가 §14.3의 실측이고 그중 T-07이 **프레임률 측정**이다(§18.1). 측정 도구가 측정을 흔들면 안 된다.

**다만 그 근거를 fill-rate로 대면 안 된다 — 실측이 뒤집었다.** 이 자리에 원래 "전면 오버레이는 fill-rate를 먹는다"고 적었는데, [13_프로브_측정결과.md](13_프로브_측정결과.md) §4.1이 fill 여유를 **8.5~10배**로 재서 fill-rate가 병목이 아님을 보였다. 전면 fill 한 번(2.07M px)은 실측 fill-rate에서 0.33ms이고 그것도 미리 구우면 `drawImage` 한 번이다. **실제 이유는 가독성이다** — 전면 워터마크는 §15.1이 상시 표시로 못 박은 10u 코어와 등급 팝업 위에 상시로 얹히고, 그러면 오염된 런에서 잰 T-05·T-06이 「치트 때문에 다른 것」이 아니라 「화면이 가려져서 다른 것」이 된다. 띠는 플레이 영역(`y ≤ 1830`) 밖이라 그 문제가 없다.

### 2.4 플레이어에 그리는 것 (HUD 아님)

§15.1이 요구하는 표시 중 넷이 플레이어 몸에 붙는다. 전부 `render/player.ts`이며 **흔들림 안쪽**에서 그린다 — 플레이어와 같이 흔들려야 붙어 있는 것으로 읽힌다.

| 요소 | 반경·형태 | 색 | 출처 | §15.1 요구 |
|---|---|---|---|---|

**쿨다운 링의 잡음 억제 규칙.** 기본 쿨다운 0.24초는 초당 4.16회다(§5.1). 그런데 카드 빌드에 따라 그보다 빨라진다 — R10이 성립 시 쿨다운을 즉시 끝내고 **최소 간격 0.12초**만 남기므로 초당 최대 **8.33회**다. 초당 8회로 채워지는 링은 스트로브다. §17이 "쿨다운 종료 \| 초당 4회 이상 반복되므로 **신호가 피로하지 않아야 한다**"고 요구하므로 규칙을 하나 둔다:

```
링 알파 = 0.9 × clamp(실효 쿨다운(초) / 0.24, 0, 1)
```

쿨다운이 짧아질수록 링이 옅어져, 0.12초 구간에서는 알파가 절반(0.45)까지 내려간다. **기하를 바꾸지 않고 존재감만 줄인다** — 링이 아예 사라지면 §15.1의 표시 요구가 깨지기 때문이다.

**0.06초가 아니라 0.12초인 이유.** 스펙 §11.6의 검산 1 블록이 R10의 최소 간격을 0.06초로 적었지만 그것은 개정 전 값이고, §11.4·§14.4·§19가 전부 **0.12초**다([01](01_설계_결정.md) §4-B S-02). 채택값이 0.12초이므로 이 규칙이 막아야 할 최대 빈도도 12.5회가 아니라 8.33회다.

**쿨다운 종료 신호는 링 자체가 낸다** ([12_통합_계약.md](12_통합_계약.md) §8-1). 링이 한 바퀴를 완성하는 순간 **반경 `50u → 56u`로 0.08초 ease-out 확장한 뒤 소멸한다.** 1프레임 밝기 상승으로 처리하지 않는 이유는 이 사건이 기본 쿨다운에서 초당 4.16회이고(§5.1), 그 빈도의 1프레임 점멸은 신호가 아니라 스트로브이기 때문이다 — §17이 "쿨다운 종료 \| 초당 4회 이상 반복되므로 **신호가 피로하지 않아야 한다**"고 요구한 그 자리다. 소리는 §17이 배정한 대로 같은 사건을 함께 알리고("화면 밖에서 일어나는 사건은 시선을 뺏지 않고 알릴 수 있는 유일한 수단이 소리다"), 음소거 시에는 이 확장이 유일한 신호가 된다.

**등급 팝업은 여기에도 HUD에도 없다.** `NOT BAD / GOOD / GREAT` 텍스트 팝업(§15.1)은 패리가 일어난 **월드 좌표**에 뜬다 — `engine.js:1959-1974`(폰트 `700 (40 + (1−k)×12)px` 모노, `easeOut(k) × 46`만큼 상승, 색은 등급색 `GREAT #f5b324` / `GOOD #35b7e0` / `NOT BAD #ede6d8`). 레이어 순서상 「팝업」은 플레이어와 파티클 다음, 비네트 앞이다([03_파일_구조.md](03_파일_구조.md) §2.3). 이 문서의 범위 밖이며 `render/impact.ts`가 가져간다.

### 2.5 목업에서 그대로 옮기면 안 되는 것

세 개다. 앞의 둘은 지시된 항목이고, 셋째는 이식 작업에서 같은 종류의 사고를 낼 자리라 함께 적는다.

#### A. 콤보 배수에 상한이 없다 — `engine.js:1729`

```js
ctx.fillText('×' + (1 + Math.floor(h.combo / 10) * 0.1).toFixed(1), …);
```

§12.2의 배수는 `1.0 + floor(콤보/10) × 0.1`이고 **상한이 3.0**이다. 목업 식에는 `min`이 없다. 이 식은 콤보 200에서 정확히 3.0에 닿고, **콤보 210부터 `×3.1`을 표시한다** — 실제 점수는 3.0으로 잘려 있는데 화면만 더 큰 숫자를 말한다.

목업 어느 씬에서도 드러나지 않는다. 가장 높은 콤보가 `09_stage5_noryang/scene.js:7`의 73(→ ×1.7)이라 상한 근처에 가 본 적이 없기 때문이다. **그림으로는 검증되지 않는 종류의 버그**이고, 그래서 이식 시 반드시 걸러야 한다.

**고칠 방법은 `min`을 넣는 것이 아니다.** 배수를 렌더에서 다시 계산하는 것 자체를 없앤다. `sim/score.ts`가 이미 그 값을 갖고 있고, `render/`는 sim의 상태를 **읽기만** 한다([03_파일_구조.md](03_파일_구조.md) §5). 렌더가 규칙을 한 번 더 구현하면 두 구현이 반드시 어긋나며, 이 줄이 바로 그 어긋남이다.

```
render/hud.ts 는 world.score.comboMultiplier 를 문자열로 만들기만 한다.
계산은 sim/score.ts, 상한 3.0은 config/scoring.ts.
```

#### B. 콤보 감쇠 게이지가 실제 패리 시각과 무관하다 — `engine.js:1733`

```js
var g = clamp(1 - ((t % 3) / 3), 0, 1);
```

`t`는 씬의 벽시계 시간이다. 이 식은 주기 3초짜리 톱니파이며 **마지막 패리 시각을 한 번도 읽지 않는다.** 정지 이미지 한 장에서는 들키지 않는다 — 주기 3초가 §12.2의 유지 시간 3.0초와 우연히 같아서 어느 순간을 잘라 봐도 그럴듯한 값이 나온다.

실제 게임에서 이 식이 만드는 거짓은 셋이다.

| 상황 | 올바른 동작 | 톱니파가 하는 동작 |
|---|---|---|
| 패리 성공 직후 | 게이지가 가득 참 | 아무 반응 없음. `t`만 흐른다 |
| 패리 없이 2.9초 경과 | 거의 비어 적색 (§17 "끊기기 직전임을 알린다") | `t % 3` 값에 따라 가득 차 있을 수도 있다 |
| 플레이어 피격 (§12.2 리셋 조건) | **즉시 0**, 콤보 블록 사라짐 | 계속 톱니를 그린다 |

고친 식:

```
유지시간 = stats.comboHoldSec        ← 상수가 아니다. 카드 반영 후의 실효값
남은시간 = 유지시간 − (누적 sim 시간 − 마지막 패리 성공 시각)
g        = clamp(남은시간 / 유지시간, 0, 1)
```

**분모가 상수면 안 된다.** N11 사기 진작이 "콤보 유지 시간 +0.5초, 최대 중첩 3"(§11.3)이므로 유지 시간은 최대 **4.5초**까지 늘어난다. `COMBO_HOLD_SEC = 3.0`으로 나누면 N11 3중첩 빌드에서 게이지가 **콤보가 실제로 끊기기 1.5초 전에 이미 0에 닿고 적색으로 바뀐다** — §17이 요구한 "끊기기 직전임을 알린다"의 정반대다. [10](10_스펙_목업_불일치.md) A11이 이미 이 판정을 내렸는데("분모는 상수가 아니라 카드 반영 후의 실효값을 읽는다") §11의 요약표가 「마지막 패리 시각」 쪽 절반만 옮겨 적었다.

같은 이유로 **경고 구간 비율도 유도한다** — `COMBO_WARN_SEC / stats.comboHoldSec`이지 `/ 3.0`이 아니다.

`COMBO_WARN_SEC = 0.8`과 기본 유지 시간 3.0초는 `config/scoring.ts`(§12.2), 실효 유지 시간은 `sim/stats.ts`의 스냅샷, 두 시각은 `sim/score.ts`가 소유한다. **`Date.now()`도 `performance.now()`도 쓰지 않는다** — [01_설계_결정.md](01_설계_결정.md) D-05가 금지했고, 여기서 어기면 콤보 게이지가 프레임률에 따라 달라져 §14.3의 실측이 재현되지 않는다.

#### C. (추가) 부위 게이지가 흔들림 밖에서 그려진다

§2.3 (c)의 포문 게이지는 `scene.overlay`에 있다(`06_boss3_atakebune/scene.js:47`). `render()`는 흔들림 `translate`를 `:1975`에서 되돌린 **뒤** `:1979`에서 `scene.overlay`를 부른다. 반면 포문 본체는 `:1947`의 `drawEnemy`가 흔들림 **안쪽**에서 그린다.

즉 화면이 흔들리는 동안 **포문은 움직이고 게이지는 가만히 있다.** 흔들림 진폭은 최대 26u(`engine.js:1937-1940`)이고 게이지 폭이 130u이므로, 최대 어긋남이 게이지 폭의 20%다. 눈에 보인다.

`render/hud.ts`로 옮길 때 **월드에 붙는 표시는 흔들림 안쪽에서 그린다.** §2.1이 정한 "HUD는 흔들리지 않는다"는 화면 좌표에 고정된 요소(라이프·점수·보스 바·콤보)에만 적용되는 규칙이고, 부위 게이지는 화면이 아니라 **부위에** 붙어 있다. 두 규칙이 충돌하는 것이 아니라 대상이 다르다.

§15.2가 요구하는 「카드 정보 \| 이름, 효과 설명, **정확한 수치**, 현재 중첩 / 최대 중첩」이 이 표의 이름·효과·중첩 세 줄에 대응한다. **수치는 반올림하거나 「약」을 붙이지 않는다** — 목업이 「반사탄 데미지 +15%」, 「GREAT 배수 3.5 → 5.25」처럼 계산된 값을 그대로 적었다(`:15-31`). 이 화면은 §11.6의 보정 결과를 플레이어에게 처음 보여주는 자리이고, 여기서 흐려지면 카드 선택이 감으로 바뀐다.

**「현재 값 → 선택 후 값」 판은 이미 보유 중인 카드에만 그린다**(§15.2 "중첩 카드 \| **이미 보유 중이면** 「현재 값 → 선택 후 값」을 함께 표시"). 보유하지 않은 카드에는 이 판을 통째로 생략하고, 그 자리를 비운다. 자리를 다른 것으로 채우지 않는 이유는 세 장의 세로 리듬이 어긋나면 비교가 어려워지기 때문이다.

**선택 후 값은 §11.6의 보정 순서를 실제로 돌려서 얻는다.** 「+15% → +30%」 같은 단순 가산이면 눈으로도 맞지만, 밴드 경계·쿨다운·무적은 INV-1·INV-2와 개별 상한이 값을 자른다. 카드를 고르기 전과 후의 스냅샷 두 개를 `sim/stats.ts`에서 받아 차이를 표시한다 — §8.4의 치트 메뉴 실효 수치 표와 **같은 데이터원**이다. 두 화면이 다른 숫자를 말하면 둘 중 하나는 거짓이다.

| 항목 | 규칙 | 근거 |
|---|---|---|

| 재추첨 범위 | 직전에 나왔던 카드도 다시 나올 수 있다. 같은 화면 안의 중복만 금지 | §11.1 |

**등급을 다시 뽑는 것이 리롤의 전부다.** §11.1이 직접 이유를 적었다 — "카드 자체만 다시 뽑으면 노말 3장이 나온 화면에서 리롤해도 **노말 3장이 다시 나와** 리롤이 사실상 무의미해진다. 등급까지 다시 뽑아야 §11.2의 회차별 가중치(4회차 기준 에픽 18%)에 한 번 더 도전하는 의미가 생긴다."

구현으로 옮기면 한 줄이다: **리롤은 「3장 다시 뽑기」가 아니라 「§11.2 추첨 절차 1~4단계 전체 재실행」이다.** 등급 추첨(1단계)을 건너뛰고 풀에서만 다시 뽑는 구현은 스펙 위반이다. 목업도 화면에 그렇게 못 박아 두었다 — 「다시 뽑으면 등급부터 다시 추첨한다」(`11_card_select/scene.js:248`).

**버튼의 두 상태.** 목업은 남은 상태만 그렸으므로(`:230-241`) 소진 상태를 여기서 확정한다. 새 색은 만들지 않는다.

| 상태 | 테두리 | 주 텍스트 | 보조 텍스트 | 입력 |
|---|---|---|---|---|
| 남음 1 | `hexA(baek, 0.4)` 선 2 | `R  다시 뽑기` — `C.baek` `600 36px` 모노 | `런당 1회 · 남음 1` — `C.baekFaint` `400 22px` 본문 | 접수 |
| 남음 0 | `hexA(baek, 0.12)` 선 2 | `R  다시 뽑기` — `C.baekFaint` | `런당 1회 · 남음 0` | **무시** |

**소진돼도 버튼을 지우지 않는다.** 사라지면 "왜 R이 안 먹지"가 되고, 남아 있으면 "이미 썼구나"가 된다. §15.2의 "소진 후에는 **사용 불가임이 보여야 한다**"는 없애라는 뜻이 아니라 못 쓴다는 사실이 보이라는 뜻이다.

### 3.4 보유 카드 목록

§15.2가 "보유 목록 \| 지금까지 획득한 카드를 **항상 확인 가능**"을 요구한다. 화면에 상시 있는 것과 `Tab`으로 펼치는 것 두 층이다.

| 층 | 형태 | 위치 | 출처 |
|---|---|---|---|
| 상시 (칩 줄) | 라벨 `보유 카드` + 가로선 + 카드마다 둥근 테두리 칩 | 라벨 `(80, 1320)` `500 24px` 모노 `C.baekFaint` / 선 `(80,1344)→(1000,1344)` `hexA(baek,0.12)` / 칩 `y 1372`, `h 50`, r4, 폭 `글자폭 + 34`, 간격 14, 테두리 `hexA(baek,0.2)`, 글자 `C.baekMute` `400 25px` 본문 `(칩x+17, 1404)` | `11_card_select/scene.js:203-218` |
| `Tab` 홀드 (상세) | ID · 이름 ×중첩 · 효과 수치를 카드마다 3열로. 일시정지 화면의 목록과 **같은 형태** | `14_pause/scene.js:79-102`의 기하를 그대로 | §16.2 |

`Tab`을 **누르고 있는 동안만** 펼친다. §16.1이 전투 중 `Tab`을 "누르고 있는 동안 오버레이 표시"로 정의했고, §16.2는 카드 선택 화면의 `Tab` 동작을 자세히 적지 않았다. 같은 키가 화면마다 다른 방식(홀드 vs 토글)으로 동작하면 §16.5가 키 리매핑을 없앤 이유 — 조작이 두 가지뿐이라 외울 것이 없어야 한다 — 가 무너진다. **홀드로 통일한다.**

**1회차의 보유 목록은 비어 있다.** 그때는 칩 대신 `아직 없다`를 `C.baekFaint`로 같은 자리에 적는다. **라벨과 가로선은 지우지 않는다** — 줄 자체가 사라지면 이 기능이 없는 것처럼 읽히고, 2회차에 갑자기 나타나면 화면이 바뀐 것으로 보인다.

> **목업 vs 스펙 — 스펙이 이긴다.**
> `11_card_select/scene.js:34`가 `HELD = ['N02 발놀림 ×1', 'N01 검격 연마 ×1']`로 **보유 카드 2장**을 그렸는데, 같은 화면이 `STAGE 1  CLEAR`(`:189`)와 「4회 중 1회차」(`:196`), 「등급 추첨 1회차 — 노말 70 / 레어 27 / 에픽 3」(`:247`)을 표시한다. 즉 **첫 번째 카드 화면**이다.
> §11.1은 "시작 보유 카드 \| **없음.** 스테이지 1은 언제나 카드 0장으로 시작한다"이고 "획득 시점 \| 스테이지 1·2·3·4 클리어 직후"다. 첫 카드 화면은 S1 클리어 직후이므로 그 시점의 보유 카드는 **정확히 0장**이다.
> 같은 오류가 카드 자체에도 있다. 첫 장 N01이 `중첩 1 / 3`과 「보유 +15% → +30%」를 표시하는데(`:19-21`), 1회차에 N01을 보유하고 있을 방법이 없다. **1회차에는 어떤 카드에도 「현재 → 선택 후」 판이 붙지 않으며 중첩은 전부 `0 / 최대`다.**
> 목업의 이 부분은 §15.2의 두 표시 요구(보유 목록 · 중첩 전후 값)를 **한 장에 전부 보여 주려고** 만든 합성 화면이다. 그림으로서는 옳고 게임 상태로서는 불가능하다. 실제 구현은 회차에 맞는 상태만 그린다.

### 3.5 선택과 확정 — 2단계

§15.2 "선택 확정 \| 오조작 방지를 위해 확정 단계 필요". §16.2 "선택 확정은 §15.2의 확정 단계를 거친다. **첫 입력은 카드를 고르고, 두 번째 입력이 확정이다.**"

| 상태 | 화면 | 다음 입력이 하는 일 |
|---|---|---|
| 선택 없음 (화면 진입 직후) | 세 장 모두 비강조. 확정 버튼 비활성 (`hexA(hwang, 0.25)`) | 좌우/`A`·`D` → 가운데 카드 선택 · `Enter`/`Space` → **가운데 카드 선택만** · 카드 클릭 → 그 카드 선택만 · 커서 올리기 → 그 카드 선택 |
| 선택 있음 | 선택된 카드가 `translate(0,−18)` + 등급색 글로우 + 테두리 5 (`:62-70`) | `Enter`/`Space` → **확정** · 선택된 카드 클릭 → **확정** · 좌우/`A`·`D` → 선택 이동 · 다른 카드 클릭 → 그 카드로 선택 이동(확정 아님) |

**진입 직후에 아무 카드도 선택돼 있지 않아야 한다.** 기본 선택을 두면 화면에 들어오자마자 누른 `Enter` 한 번이 확정이 되어 §16.2의 "첫 입력은 카드를 고르고"가 성립하지 않는다.

**선택되지 않은 카드를 클릭하면 선택만 되고 확정되지 않는다.** 마우스는 「커서 올리기 = 이동, 클릭 = 확정」이라 보통은 hover가 첫 입력 역할을 한다(§16.2). 그러나 커서가 빠르게 들어오면서 같은 프레임에 눌리면 hover와 click이 한 사건이 되어 확정 단계가 사라진다. 클릭을 「이미 선택된 카드」에만 확정으로 취급하면 그 경로가 막힌다.

확정 버튼은 목업 그대로다 — `(120, 1500, 400, 88)` r6, 테두리 `C.hwang` 선 2.5, `glow(320, 1544, 210, hwang, 0.1)`, 글자 `ENTER  확정` `C.hwang` `600 36px` 모노 `(320, 1556)`(`:220-228`). 다만 라벨은 `Enter` 하나만 적어 두면 §16.2의 `Space`·클릭이 없는 것처럼 읽히므로, 하단 조작 안내 줄(`:244`)에 세 가지를 전부 적는다(§10).

### 3.6 리롤이 선택을 지운다

`R`을 누르면 세 장이 전부 교체된다. **그 순간 선택 인덱스를 `null`로 되돌린다.**

지우지 않으면 이런 일이 생긴다 — 플레이어가 2번 카드를 고른 상태에서 리롤하면, 인덱스 2는 살아 있는데 그 자리의 카드는 처음 보는 다른 카드다. 다음 `Enter` 한 번이 **한 번도 읽지 않은 카드를 확정한다.** §15.2가 확정 단계를 요구한 이유가 정확히 이것(오조작 방지)이므로, 인덱스를 살려 두는 것은 확정 단계를 우회하는 구멍이다.

**보유 카드가 여기 있는 이유.** 이 화면의 실질적 기능이다 — 목업 README가 "싸우는 동안 볼 수 없는 것 = 지금 내 빌드"라고 적었다. 전투 중의 `Tab` 오버레이는 게임을 멈추지 않으므로(§16.1) 천천히 읽을 수 없다.

§12.3은 "총 패리 **시도** 대비 성공률"이라고만 적었다. 「시도」를 정의하지 않으면 같은 플레이가 다른 숫자를 낸다.

### 5.3 목업이 스펙과 어긋난 두 곳 — 스펙이 이긴다

#### A. 「최대 콤보 88 (×3.0 상한 도달)」 — 배수가 틀렸다

`13_result/scene.js:42`:

```js
['최대 콤보', '88  (×3.0 상한 도달)'],
```

§12.2의 배수는 `1.0 + floor(콤보 / 10) × 0.1`, 상한 3.0이다. 콤보 88을 넣으면:

```
1.0 + floor(88 / 10) × 0.1 = 1.0 + 8 × 0.1 = 1.8
```

**×1.8이다. ×3.0이 아니고, 상한에 닿지도 않았다.** 상한 3.0에 닿으려면 `floor(콤보/10) = 20`, 즉 **콤보 200 이상**이 필요하다.

**규칙.** 이 행은 `maxCombo`와, 그 콤보에서의 배수를 `sim/score.ts`가 계산한 값 그대로 적는다. `(상한 도달)` 주석은 **배수가 실제로 잘렸을 때만** 붙인다 — 즉 `maxCombo ≥ 200`일 때만.

§2.5 A와 **같은 뿌리의 사고**다. 한쪽은 렌더가 배수를 다시 계산했고, 한쪽은 사람이 손으로 적었다. 둘 다 `sim/score.ts`가 소유한 값을 바깥에서 복제한 결과다.

#### B. 획득 카드가 6장이다 — 상한은 4장

`13_result/scene.js:33-38`:

```js
var CARDS = [
  ['N01', '검격 연마 ×3', '#d8d2c4'],
  ['R04', '되받아치기',   '#3b82f6'],
  ['E05', '영점 패리',    '#a855f7'],
  ['N02', '발놀림',       '#d8d2c4']
];
```

줄은 4개지만 **획득 횟수는 `3 + 1 + 1 + 1 = 6회**다. N01 `×3`은 N01을 세 번 골랐다는 뜻이다(§11.6 "같은 카드 중첩 \| 효과 수치를 **가산**한다 (N01 3중첩 = +45%)").

§11.1은 획득 시점을 "스테이지 1·2·3·4 클리어 직후. **총 4회**"로, 선택을 "반드시 1장 선택"으로 규정했다. 한 런에서 고를 수 있는 카드는 **정확히 4장이 상한**이고, 그보다 적을 수는 있어도(중간에 죽으면) 많을 수는 없다.

**규칙.** 획득 카드 목록의 **중첩 수 총합 = 완료한 카드 화면 수**이며, 이 값은 4를 넘지 않는다.

| 런의 결말 | 총합 |
|---|---|
| S5 클리어 | 4 |
| S4 클리어 후 S5에서 게임오버 | 4 |
| S2에서 게임오버 | 1 |
| S1에서 게임오버 | 0 (목록 자리에 `없음` 표기, 줄은 유지) |

목업의 6장은 등급 세 종류의 칩 색을 한 화면에 다 보여 주려다 넘어간 것이다. 실제 구현에서는 `cards` 배열을 그대로 펼쳐 그리면 자동으로 4 이하가 된다.

### 5.4 치트 오염 표시

§12.3의 9번 항목 — "치트 모드 사용 여부 — 사용했다면 **오염된 런**임을 명시한다(§18.5)". §18.5는 여기에 두 가지를 더 얹는다: "결과 화면 \| §12.3에 오염 여부를 명시한다", "점수 \| **기록·순위 대상에서 제외한다**".

| 상태 | 문구 | 색·형태 | 총점 |
|---|---|---|---|
| 미사용 | `치트 모드 미사용 — 기록 대상 런` | `C.cheong` `500 25px` 모노 `(90, 1462)` (`:147-149`) | 그대로 |
| 사용 | `치트 모드 사용 — 오염된 런 · 기록 제외` | `C.baek`, 뒤에 §2.3 (b)와 **같은 사선 해칭 판** | 값 오른쪽에 `기록 제외` 병기 |

**정상 런도 문구를 적는다.** 오염 시에만 표시하면, 표시가 없는 화면이 "정상"인지 "그 표시를 안 만든 것"인지 구별되지 않는다. 목업이 이미 그렇게 그렸고 README가 이유를 적었다 — "미사용 = 기록 대상 런"(`13_result/README.md:7`).

오염 표시에 **HUD와 같은 사선 해칭**을 쓰는 것은 두 화면의 표시가 같은 사실을 말하기 때문이다. §18.6이 촬영 전 확인 대상으로 지목한 것도 이 표시다.

### 5.5 입력 — 목업이 스펙과 어긋난 셋째 곳

§16.3의 결과 화면 행은 명확하다.

| 동작 | 입력 |
|---|---|
| 메뉴 항목 이동 | **상하 방향키 / `W` · `S`** |
| 항목 실행 (다시 하기 / 타이틀로) | **`Enter` / `Space` / 클릭** |

그런데 목업은 `R  다시 한 판`(`:154-157`)과 `ESC  타이틀로`(`:159-161`)를 **가로로** 배치했다.

> **목업 vs 스펙 — 스펙이 이긴다. 세 가지가 어긋난다.**
> 1. **`R`은 결과 화면의 키가 아니다.** §16.2에서 `R`은 카드 선택 화면의 **리롤** 키다. §16.3의 결과 화면 행에 `R`은 없다. 같은 키가 화면마다 다른 뜻을 갖는 것은 조작이 두 가지뿐인 이 게임(§16.1)에서 만들 이유가 없는 혼란이다.
> 2. **`ESC`도 결과 화면의 키가 아니다.** §16.3에서 `Esc`는 일시정지의 「즉시 계속하기」에만 배정돼 있다.
> 3. **가로 배치가 `↑ ↓` 이동과 맞지 않는다.** §16.3이 항목 이동을 상하 방향키와 `W`·`S`로 정했으므로 항목은 **세로로 쌓인다.** 일시정지 메뉴(§4.3)가 이미 세로다.
>
> **판정.** 항목은 「다시 하기」/「타이틀로」 두 개, **세로 배치**, 이동은 ↑ ↓ · `W` · `S`, 실행은 `Enter` / `Space` / 클릭. 상자 기하는 일시정지 메뉴(`14_pause/scene.js:146-164`)의 `(300, y, 480, 92 / 78)` r6 규격을 재사용한다 — 두 화면이 같은 조작을 받으므로 같은 모양이어야 한다.

**「다시 하기」에는 확정 단계가 붙는다**(§16.3 "런 포기와 **다시 하기는** 반드시 확정 단계를 거친다"). 목업에는 확정 단계가 없다. 규칙은 §4.5와 동일하다 — 메뉴를 확정 패널로 교체하고, 기본 커서는 「아니오」에 둔다.

다시 하기가 하는 일은 §13.3이다 — 스테이지 1부터, **획득한 카드 전부 소실**, 라이프·최대 라이프·점수·콤보 전부 초기값, 리롤 사용 여부 초기화(§11.1), 오염 표시 초기화(§18.5). 목업 하단 줄(`:163-165`)이 이미 그 사실을 적어 두었다 — 「재시작하면 카드는 전부 사라지고 스테이지 1부터 시작한다.」 **이 줄을 지우지 않는다.** 확정 패널이 뜨기 전에 결과를 미리 알려 주는 유일한 문장이다.

### 6.2.1 어트랙트 루프는 기록된 입력을 재생한다 — 자동 패리가 아니다

목업은 `HW.autoParry`(`00_title/scene.js:56`)로 패리를 성립시켰지만 **그 방법은 이식하지 않는다.** [06_렌더링과_게임필.md](06_렌더링과_게임필.md) §1.10이 `autoParry()`를 폐기하며 이유를 적었다 — 그 함수가 남으면 「자동 패리」라는 **규칙 밖 경로가 코드에 상주한다.** 타이틀에서 도는 것이 진짜 플레이가 아니게 되고, §17이 요구한 신호들도 그만큼 가짜가 된다.

**확정: 미리 녹화한 입력을 고정 시드 위에서 재생한다** ([12_통합_계약.md](12_통합_계약.md) §1 C-03).

```
D-05 의 결정론이 같은 시드 + 같은 입력 → 같은 결과를 보장한다
   ↓
타이틀 어트랙트 = 녹화된 입력 배열 + 고정 시드의 재생
```

| 항목 | 값 |
|---|---|
| 녹화 위치 | `src/screens/title-attract.ts`에 **입력 배열 리터럴로 박는다.** 외부 파일을 읽지 않으므로 D-03의 단일 파일 빌드를 깨지 않는다 |
| 규칙 밖 경로 | 없다. `sim/`이 받는 것은 사람이 친 것과 구별되지 않는 입력이다 |

| 녹화 시점 | **P7.** 그전까지 타이틀은 정적 화면이다 — 어트랙트 루프가 없는 것이 잘못된 어트랙트 루프보다 낫다 |
| 부수 산출 | **같은 녹화가 제출 영상의 소스다.** 따로 만들 것이 하나 준다 |

| 원 | 마크 반경 (u) | 대응 밴드 | 밴드 값 | 비율 검산 |

### 6.4 촬영 제약 — 0초 프레임은 이미 게임 화면이어야 한다

리서치의 체크 항목 C-1이 명령형이다:

> **C-1. 0초 프레임에 게임 화면이 있다.** 검은 화면, 로고, 팀명, 타이틀 카드 전부 금지.
> — `docs/research/claude_research/03_30초_영상_전달력.md:452`

같은 문서 `:285` — "**GIF의 첫 프레임이 결정적이다.** 검은 화면으로 절대 시작하지 마라. 로딩에 실패하면 정지 이미지처럼 보인다."

이 화면에 걸리는 결론이 둘이다.

1. **제출 영상은 타이틀에서 시작하지 않는다.** 30~60초 영상([01_설계_결정.md](01_설계_결정.md) §5)의 첫 프레임은 전투여야 한다. 타이틀은 심사자가 빌드를 열었을 때의 첫 화면이지 영상의 첫 화면이 아니다.
2. **그러나 타이틀 자신의 0프레임도 게임 화면이어야 한다.** 어트랙트 루프가 이미 돌고 있는 상태로 첫 페인트가 나가고, 검은 화면 → 페이드 인 같은 도입을 두지 않는다. [01_설계_결정.md](01_설계_결정.md) D-03의 단일 파일 인라인 빌드에는 네트워크 대기가 없으므로 가릴 로딩 구간 자체가 없다.

### 6.5 플레이어 y=540은 구도 예외다 — 목업 구도를 그대로 쓴다

`00_title/scene.js:31`이 `playerY: 540`을 주고, `:47-48`의 `tick`이 `s.player.y = 545 + Math.cos(t * 0.51) * 55`로 **y ∈ [490, 600]** 범위를 그린다.

§3.1의 플레이어 이동 가능 영역은 **`y ∈ [620, 1830]`** 이다. 목업의 궤적은 전 구간이 그 바깥이다.

목업이 플레이어를 위로 올린 이유는 명확하다 — 스크림이 `y ≈ 0.39 × 1920 = 749`에서 이미 불투명도 0.88에 도달하므로(`:63-64`), 정상 위치인 `y ≥ 620` 아래쪽에 있는 플레이어는 로고 판 뒤에 묻힌다.

> **판정: 승인된 목업 구도가 그대로 선다** ([10_스펙_목업_불일치.md](10_스펙_목업_불일치.md) A12 · [12_통합_계약.md](12_통합_계약.md) §8-7).
> 구도를 렌더 쪽에서 다시 푸는 길 — 스크림의 불투명 무릎을 아래로 내리거나, 로고 블록 전체를 옮기거나, 어트랙트 루프를 위쪽에 더 좁게 프레이밍하거나 — 은 **택하지 않는다.** 10 A12가 이 자리를 구도 예외로 판정했고, 판정 근거의 우선순위상 외형은 `docs/sample_image/`가 정한다. 승인된 구도를 렌더 쪽에서 다시 푸는 것은 이긴 쪽을 고치는 일이다.
> **대신 코드에 사실을 적는다.** `screens/title.ts`는 `sim/player.ts`의 §3.1 클램프를 **거치지 않는 별도 경로**이고, 그 사실이 파일 주석으로 남아야 한다 — 그래야 나중에 "플레이어가 왜 여기 있지"를 조사하는 사람이 클램프 버그를 찾아 헤매지 않는다. 게임 플레이의 플레이어 위치는 언제나 `sim/player.ts`가 정하며, 이 예외는 타이틀 화면 한 곳에서 끝난다.
> 어트랙트 루프의 sim 자체는 §6.2.1대로 정상적으로 돈다 — 예외는 **그리는 위치 하나**이지 규칙이 아니다.

## 7. 모바일 미지원 안내

### 7.1 이 화면이 존재하는 이유

§16.6의 마지막 문단이 그대로 근거다:

> 모바일 안내를 넣는 것은 제출물이 **링크 클릭만으로 열리는 공개 웹 빌드**이기 때문이다. 심사자가 휴대폰으로 열어 볼 가능성이 있고, 그때 조작이 안 되는 화면을 그대로 두면 **미지원이 아니라 고장으로 읽힌다.**

[01_설계_결정.md](01_설계_결정.md) §5가 이 프로젝트를 로컬 실행 전제로 두면서도 "빌드 산출물은 그대로 정적 호스팅에 올릴 수 있는 형태로 둔다"고 했으므로, 이 화면은 여전히 필요하다.

**따라서 이 화면의 완료 조건은 「폰에서 열었을 때 *미지원*이라고 읽히는 것」이다.** 빈 화면, 검은 캔버스, 잘린 레이아웃, 멈춘 로딩 — 전부 「고장」으로 읽히므로 실패다.

### 7.2 무엇을 판정하나

§16.6의 지원 조건은 "키보드 또는 마우스가 있는 PC 브라우저"이고, 미지원은 "터치 조작 일체. 모바일·태블릿 브라우저"다.

| 규칙 | 내용 |
|---|---|
| 판정식 | `matchMedia('(any-pointer: fine)').matches` 가 **참이면 지원** |
| 왜 `any-pointer` 인가 | `pointer: fine`은 **주** 포인터만 본다. 터치스크린 노트북은 주 포인터가 `coarse`로 보고되면서 마우스도 달려 있는데, `pointer`로 판정하면 이 기기가 미지원으로 튕긴다. `any-pointer`는 "정밀 포인터가 **하나라도** 있는가"를 묻는다 |
| userAgent 문자열 | **쓰지 않는다.** 기기 목록은 반드시 낡고, 하이브리드 기기를 못 가른다. §16.6이 요구하는 것은 기기 종류가 아니라 **입력 능력**이다 |
| 게임패드 | 판정에 넣지 않는다. §16.6이 미지원으로 명시했으므로 있어도 없는 것과 같다 |
| 탈출구 | 안내 화면에서 **물리 `keydown`이 한 번이라도 오면 타이틀로 보낸다**(T-18) |

**탈출구가 필요한 이유.** §16.1의 이동에는 마우스 배정이 없다 — 이동은 `WASD` / 방향키뿐이다. 즉 실제로는 **키보드가 필수**이고 §16.6의 "키보드 **또는** 마우스"는 느슨하게 적힌 것이다. 그런데 키보드의 존재는 feature detection으로 알 수 없다. 그래서 판정은 포인터로 하되, 판정이 틀렸을 때(예: 키보드가 붙은 태블릿) 실제 `keydown` 하나가 그것을 뒤집게 한다. 비용은 이벤트 리스너 하나이고, 틀린 판정으로 플레이 가능한 사람을 막는 것보다 싸다.

### 7.3 무엇을 보여 주나

§16.6 — "모바일 접속 시 \| 게임을 시작하지 않고 **PC에서 플레이해 달라는 안내를 표시한다**".

| 규칙 | 내용 |
|---|---|
| 게임을 시작하지 않는다 | sim 루프를 돌리지 않고, `AudioContext`를 만들지 않고([03_파일_구조.md](03_파일_구조.md) §1 `audio/context.ts`가 지연 생성이다), 스프라이트를 굽지 않는다 |
| 캔버스를 만들지 않는다 | **이 화면만 DOM/CSS로 그린다.** `boot/canvas.ts`의 DPR·스케일 경로가 실패하거나 어긋나도 안내는 떠야 한다. 안내 화면이 캔버스에 의존하면, 캔버스가 문제인 상황에서 안내도 같이 죽는다 |
| 내용 1 — 결론 | PC 브라우저에서 열어 달라는 한 줄 |
| 내용 2 — 이유 | §16.6이 적은 두 가지를 그대로: **동시 입력**(이동과 패리가 동시에 들어가야 하는데 한 손가락이 두 역할을 다툰다) · **판정 가림**(패리 등급이 거리로 정해지므로 10u 코어가 보여야 하는데 손가락이 그 위를 덮는다) |
| 내용 3 — 조작 | `이동  WASD · 방향키` / `패리  SPACE · J · 좌클릭` — 왜 터치로 대체되지 않는지가 이 두 줄로 읽힌다 |
| 서체·색 | 타이틀과 같은 값 — 폰트 스택은 `config/ui.ts`의 `FONTS.display` / `FONTS.body`, 색은 `config/palette.ts`의 `baek` · `hwang` · `ink900`. 이 화면만 DOM/CSS이므로 그 몇 값을 `index.html`의 인라인 셸 CSS에 그대로 적는다 — `tokens.css`는 이식하지 않는다([12](12_통합_계약.md) §3.2). **만든 화면으로 보여야 한다** |
| 반응형 | 세로 폰 화면에서 스크롤 없이 들어가도록 상대 단위로 짠다 |

**세로 비율을 사과하지 않는다.** §16.6이 못 박았다 — "**플레이필드가 9:16 세로인 것은 모바일을 겨냥한 것이 아니다.** 탄막이 위에서 내려오고 플레이어가 아래에 있는 종스크롤 슈팅에서 세로 화면은 **장르 관례**이며, §3.1의 좌표계는 그 구조에서 나왔다. 세로 비율을 보고 터치 조작을 전제해서는 안 된다."

따라서 안내 문구는 「모바일 버전 준비 중」, 「세로 화면인데 죄송합니다」 같은 말을 쓰지 않는다. 9:16은 장르 선택의 결과이지 모바일 약속이 아니다.

## 8. 치트 메뉴

`src/dev/cheat-menu.ts`. 스펙 §18 전체. [01_설계_결정.md](01_설계_결정.md) D-10이 이것을 후반 편의 기능이 아니라 **초기 인프라**로 확정했다.

[03_파일_구조.md](03_파일_구조.md) §2.4의 구조 제약이 여기 그대로 걸린다 — `dev/`의 어떤 코드도 `sim/` 내부를 import하지 않고 **`sim/`이 제공하는 공개 조작 함수만 호출**한다. 그래야 §18.1의 "전투 규칙 자체는 하나도 바뀌지 않는다"가 구조로 보장된다.

### 8.1 진입과 종료

| 항목 | 값 | 근거 |
|---|---|---|
| 진입·종료 입력 | **`Shift + F9`** | §18.2 |
| 진입 가능 시점 | 타이틀 화면 / **일시정지 중** / 카드 선택 화면 | §18.2 |
| 진입 불가 시점 | **전투 진행 중** | §18.2 |
| 전투 중 `Shift + F9` | 일시정지로 보낸 뒤 메뉴를 연다 (T-09) | §16.1 |
| 종료 | 같은 입력 또는 `Esc`. 메뉴만 닫히며 **이미 적용한 변경은 되돌아가지 않는다** | §18.2 |
| 게임 시간 | 메뉴가 열려 있는 동안 모든 타이머·탄환·쿨다운 정지 (§13.4와 동일) | §18.2 |

**전투 중 진입을 막은 이유 — 상태 정합성.** §18.2가 직접 적었다: "탄환이 날아오는 도중에 스테이지가 교체되면 **어느 스테이지의 파라미터로 계산된 탄환인지가 불분명해진다.**"

구체적으로 무엇이 불분명해지는지는 §14.1의 표가 말해 준다. 탄속 배율이 S1 1.00에서 S5 1.34로, 동시 적 탄환 상한이 80에서 280으로, 발사 예비동작이 0.95초에서 0.55초로 달라진다. S1의 배율로 만들어져 날아가던 탄환이 S5로 갈아탄 세계에 남으면, **그 탄환은 어느 스테이지 표의 항목도 아니다.** 그 상태에서 측정한 무엇도 §14의 근거가 될 수 없고, 치트 모드는 오직 측정을 위해 존재한다(§18.1).

기능이 막히지는 않는다 — §18.2가 명시했듯 "전투 중에 쓰고 싶으면 `Esc`로 일시정지한 뒤 열면 된다". 화면 정리(§8.3)가 진입 시 남은 발사체를 전부 제거하므로, 일시정지를 거치면 어느 스테이지에도 속하지 않는 탄환이 남지 않는다.

`Shift + F9`가 진입 입력인 것도 규칙이다. §18.2 — "**Shift + F9는 §16의 어떤 게임 조작키와도 겹치지 않는다.** F5(새로고침)·F11(전체화면)·F12(개발자 도구)와 Ctrl+Shift+I / Ctrl+Shift+J는 브라우저가 먼저 가져가므로 진입 입력으로 쓰지 않는다."

### 8.2 입력

§16.4가 다섯 줄이다. 「항목 이동 \| 방향키」와 「값 변경 \| 좌우 방향키」가 겹쳐 보이므로 축을 나눈다.

| 동작 | 입력 |
|---|---|
| 열기·닫기 | `Shift + F9` |
| 닫기 | `Esc` |
| 항목 이동 | **↑ ↓** |
| 값 변경 | **← →** |
| 적용 | `Enter` |

**`Enter`가 필요한 것과 필요 없는 것이 다르다 — 스펙이 그렇게 정했다.**

| 대상 | 반영 시점 | 근거 |
|---|---|---|
| 카드 부여·제거 | **변경 즉시.** §11.6의 보정 순서를 그 자리에서 다시 실행한다 | §18.4 "반영 시점 \| 변경 즉시 §11.6의 보정 순서 1~9를 다시 실행한다" |
| 라이프 값 | 변경 즉시 | §18.3 |
| 스테이지·진입 지점·보스 페이즈 | **`Enter`로 적용.** 적용은 화면 전환을 동반한다 (T-14) | §16.4 · §18.3 |

카드가 즉시 반영되는 것이 이 도구의 쓸모다 — 값을 하나 올리고 실효 수치 표(§8.4)가 어떻게 잘리는지를 **입력과 같은 프레임에** 보는 것이 §18.4가 "이 기능의 핵심"이라고 부른 동작이다. 카드에도 `Enter` 확정을 붙이면 그 루프가 두 배로 길어진다.

### 8.3 설정할 수 있는 것

#### 스테이지 자유 입장 (§18.3)

| 항목 | 값 |
|---|---|
| 스테이지 | 1 ~ 5 |
| 진입 지점 | **스테이지 시작(W1 0:00)** / **특정 웨이브 시작** / **소강 구간 시작(보스 직전)** |
| 보스 페이즈 | B1~B5의 임의 페이즈. **보스 HP를 해당 페이즈의 상한값으로 설정** |
| 라이프 | 기본은 진입 시점 값 유지. `1 ~ 현재 최대 라이프` 범위에서 직접 지정 |
| 콤보 | 0으로 초기화 (§12.2의 스테이지 전환 규칙과 동일) |
| 화면 정리 | 기존 적·적 탄환·반사탄·장판을 **모두 제거** |
| 카드 | **현재 보유 카드를 그대로 들고 간다. 건너뛴 스테이지의 카드가 자동 지급되지 않는다** |
| 리롤 | 사용 여부를 초기화할 수 있다 |

보스 HP 계산의 예를 §18.3이 직접 들었다 — "B5 페이즈 3 지정 시 HP를 5100의 50%인 **2550**으로". 페이즈 경계는 각 보스 절에 있다(예: §10.6의 B5는 100→75→50→25%). 표에는 계산 결과를 함께 띄운다.

| 보스 | 총 HP | 페이즈 경계 (§10) | 페이즈 지정 시 HP |
|---|---|---|---|
| B1 | 1450 | 100% / 55% | 1450 / 797.5 |
| B2 | 2250 | 100% / 65% / 30% | 2250 / 1462.5 / 675 |
| B3 | 2000 (본체) + 포문 4×300 | P2 = 포문 2기 파괴 **또는** 본체 60% (선착) / P3 = 본체 35% | §8.3의 B3 주의 참조 |
| B4 | 3850 | 100% / 60% / 30% | 3850 / 2310 / 1155 |
| B5 | 5100 | 100% / 75% / 50% / 25% | 5100 / 3825 / 2550 / 1275 |

**B3만 규칙이 다르다.** §10.4의 P2 진입 조건이 "포문 2개 파괴 **또는** 본체 HP 60% 이하 (**선착**)"이므로 HP 하나로 페이즈가 결정되지 않는다. 치트로 B3 P2를 지정할 때는 **본체 HP를 60%(1200)로 두고 포문 2기를 파괴 상태로 만든다** — 둘 중 하나만 맞추면 정상 플레이에서 도달할 수 없는 조합(예: 포문 4기 생존 + P2)이 생기고, 그 상태의 측정치는 §14의 근거가 될 수 없다.

**리롤 초기화가 왜 항목인지**도 §18.3이 적었다 — "카드 추첨 화면 자체를 반복 검증할 때 필요하다." 리롤은 런당 1회뿐이므로(§11.1) 초기화 수단이 없으면 리롤 동작을 한 런에 한 번밖에 확인할 수 없다.

**카드를 자동 지급하지 않는 이유**도 같은 절에 있다 — "자동으로 4장을 추첨해 주면 **무작위가 섞여 같은 조건을 두 번 재현할 수 없다.** 테스트에서 필요한 것은 「그럴듯한 빌드」가 아니라 「지정한 빌드」다."

#### 업그레이드 카드 자유 선택 (§18.4)

| 항목 | 규칙 |
|---|---|
| 선택 대상 | **31종 전체.** 등급 추첨 가중치(§11.2)와 제시 가능 조건을 무시하고 목록에서 직접 고른다 |
| 중첩 | 각 카드의 **최대 중첩 수까지** 자유롭게. **최대 중첩 수 자체는 넘을 수 없다** |
| 제거 | 개별 카드 제거, 전체 초기화 |
| 즉발 효과 | N14(라이프 +1)·R06(최대 라이프 +1, 라이프 +1)은 부여 순간 1회 발동. **제거해도 이미 오른 라이프는 되돌리지 않는다** |
| 상한·불변 조건 | INV-1 · INV-2 · 쿨다운 하한 · 반경 상한 · 이동 속도 상한 · 반사탄 속도 상한이 **전부 정상 적용된다** |

목록은 31종을 등급별로 묶어 보여 준다 — 노말 N01~N14(14종) / 레어 R01~R10(10종) / 에픽 E01~E07(7종), §11.3~§11.5. 각 줄은 `{ID}  {이름}   {현재} / {최대}` 형식이고, 최대에 도달한 카드는 `C.baekFaint`로 내려 더 못 올린다는 사실이 보이게 한다.

### 8.4 실효 수치 표 — 이 도구의 핵심

§18.4가 못 박았다 — "**실효 수치 표시가 이 기능의 핵심이다.** §11.6의 보정 순서는 여러 단계이고 INV-1·INV-2가 서로 다른 방향으로 값을 자른다. 검산 1에서 N04 3중첩이 쿨다운을 0.197초로 내렸는데 **INV-1이 0.23초로 되돌리는 것 같은 상호작용은, 숫자로 보이지 않으면 실측 중에 원인을 잘못 짚게 된다.**"

그래서 표시 요구가 「값」이 아니라 「값 + 무엇이 잘랐는지」다. §18.4의 표시 항목 목록: **활성 시간 / 쿨다운 / 패리 무적 / 패리 반경 / 등급 밴드 경계 / 반사탄 데미지 배수**, 그리고 **어떤 상한이나 불변 조건이 값을 잘랐는지.**

표는 다섯 열이다.

| 항목 | 기본값 | 카드 반영 후 (원값) | 최종 | 자른 규칙 |
|---|---|---|---|---|

§11.6의 최악 조합 검산 1(N04 3중첩 + N05 3중첩 + N10 + R10, E07 없음)을 넣으면 이렇게 나온다.

| 항목 | 기본값 | 카드 반영 후 | 최종 | 자른 규칙 |
|---|---|---|---|---|
| 활성 시간 | 0.150초 | 0.180초 | **0.180초** | — |
| 쿨다운 | 0.240초 | 0.197초 | **0.230초** | **INV-1** (활성 0.180 + 0.05) |
| 패리 무적 | 0.140초 | 0.170초 | **0.170초** | — (INV-2 한도 0.1725초, 통과) |
| 패리 반경 | 70u | 70u | **70u** | — |
| GREAT 밴드 상한 | 28u | 28u | **28u** | — |
| GOOD 밴드 상한 | 48u | 48u | **48u** | — |
| 반사탄 데미지 배수 | ×1.00 | ×1.00 | **×1.00** | — |
| (파생) 초당 최대 패리 | 4.16회 | — | **4.35회** | — |

검산 2(E07 포함)를 넣으면 잘리는 자리가 바뀐다.

| 항목 | 기본값 | 카드 반영 후 | 최종 | 자른 규칙 |
|---|---|---|---|---|
| 쿨다운 | 0.240초 | 0.220초 | **0.220초** | **E07 예외** (활성 0.180 + 0.04, INV-1의 0.230을 건너뜀) |
| 패리 무적 | 0.140초 | 0.170초 | **0.165초** | **INV-2** (0.220 × 0.75) |
| 반사탄 데미지 배수 | ×1.00 | ×0.75 | **×0.75** | — (E07의 **−25%**) |

두 표가 다른 자리에서 잘린다는 사실이 §18.4가 말한 "서로 다른 방향으로 값을 자른다"이고, 그것이 「자른 규칙」 열이 존재하는 이유 전부다.

**표에 네 행이 더 붙는다 — 런타임 파생이다** ([12](12_통합_계약.md) §10 E-05). 카드 목록이 그대로여도 값이 바뀌는 것들이라 정적 스냅샷 행과 섞으면 안 된다. 치트 메뉴는 E-05가 이름 붙인 세 소비자 중 하나이고, 이 넷이 없으면 N13이나 R05를 든 빌드에서 표가 **패리가 한 번 성립하는 순간 틀린 값이 된다.**

| 항목 | 읽는 곳 | 비고 |
|---|---|---|
| 쿨다운 (빈 패리) | `cooldownSecFor('empty')` | N13. 명목 −40%인데 INV-1 하한에 막혀 실효는 빌드별로 −17% / −4% / **정확히 0**이다([12](12_통합_계약.md) §10 E-05의 표를 그대로 띄운다) |
| 반사탄 데미지 배수 (콤보 *n*) | `reflectDamageMulFor(combo)` | R05. 현재 콤보를 인자로 넣은 값과 콤보 0일 때의 값을 나란히 보인다 |
| R10 최소 간격 | `r10ActiveMinGapSec` | 미보유면 `—`. 보유면 **0.12초**(§11.4) |
| E03 보호막 중첩 | `shieldCharges` | 스테이지 시작마다 1중 충전되므로 카드 변경 없이 바뀐다 |

이 네 행에는 「기본값」 열을 채우지 않는다 — 기본값이라는 것이 없는 값들이다.

**E07의 데미지 대가는 −25%다. −20%가 아니다.** 스펙이 자기 자신과 어긋난 자리이고([01](01_설계_결정.md) §4-B S-01), §11.5 본문과 §19 결정 기록이 −25%인 반면 §11.6 검산 2 블록만 개정 전 −20%를 들고 있다. **채택값은 −25%**이므로 이 표의 배수는 ×0.75다 — [05](05_시스템_설계.md) §10.2의 검산 2와 같은 값이어야 한다.

**「자른 규칙」 열은 UI가 역산하지 않는다.** `sim/cards.ts`가 §11.6의 보정 순서를 실행할 때 **결과를 값 하나가 아니라 `(값, 적용된 상한 ID)` 쌍으로** 내보내고, `sim/stats.ts`가 그 스냅샷을 읽기 전용으로 노출한다([03_파일_구조.md](03_파일_구조.md) §1 — "`stats.ts` \| 카드 반영 후의 실효 수치 (읽기 전용 스냅샷)"). 메뉴는 그 스냅샷을 표로 옮기기만 한다. UI가 "0.197이 0.230이 됐으니 INV-1이겠거니" 하고 추측하면, 두 상한이 같은 값을 만들어 내는 경계에서 틀린 이름을 말한다.

**같은 스냅샷을 카드 선택 화면의 「현재 → 선택 후」도 쓴다**(§3.2). 두 화면이 같은 빌드에 대해 다른 숫자를 말하는 상태를 구조적으로 만들 수 없게 하려는 것이다.

> **참고 — 스펙과 [03_파일_구조.md](03_파일_구조.md)의 단계 수가 다르다.** 스펙 §11.6의 「보정 순서」 블록은 1~8의 **8단계**이고, §18.4는 "보정 순서 1~9", 03 §1은 "§11.6 보정 순서 9단계"라고 적었다. 이 문서와 구현은 **스펙 §11.6에 실제로 나열된 8단계**를 기준으로 삼는다. 단계 수를 세는 방식의 차이일 뿐 어느 문서도 단계의 내용을 다르게 적지 않았다.

### 8.5 절대 하지 않는 것

§18.1의 「미포함」 열이 전부다. 이유도 한 문장으로 같다 — "**전투 규칙을 바꾼 상태의 플레이는 실측 데이터가 아니다.**"

| 금지 | 왜 |
|---|---|
| **무적** | §18.1 — "무적으로 도달한 보스 격파 시간은 T-01의 근거가 될 수 없다" |
| **원턴킬** | 같은 이유. 격파 시간이 목표치와 비교 불가능해진다 |
| **탄환 소거** (전투 규칙으로서의) | §3.2의 상한 도달 처리가 "적 탄환 \| 신규 발사를 **억제**한다. 이미 화면에 있는 탄환을 지우지 않는다"인데, 소거 버튼은 그 규칙을 무효화한다. **§18.3의 「화면 정리」와 혼동하지 말 것** — 그것은 스테이지 진입 시 1회 실행되는 상태 초기화이지 전투 중 누르는 버튼이 아니다 |
| **§14.1 스테이지 파라미터 변경** | 적 HP 배율·탄속 배율·예비동작 시간·동시 탄환 상한. §18.3 — "치트로 건너뛰어도 **정상값이다**" |
| **최대 중첩 초과 부여** | §18.4 — "§11.6의 최악 조합 검산 두 개는 「정상 플레이로 도달 가능한 가장 극단적인 빌드」를 가정하고 쓴 것이다. … **치트 모드로 만들 수 있는 빌드의 범위는 정상 플레이의 범위와 정확히 같아야 한다**" |
| **불변 조건 무시** | INV-1·INV-2·쿨다운 하한 0.15초·패리 반경 상한 150u·이동 속도 상한 900 u/s·반사탄 속도 상한 2400 u/s는 치트에서도 전부 적용된다 (§18.4 · §11.6) |
| **즉발 효과 되돌리기** | N14·R06으로 오른 라이프는 카드를 제거해도 내려가지 않는다. §18.4가 이유를 적었다 — "되돌리면 **라이프가 음수가 될 수 있다**" |

### 8.6 런 오염 (§18.5)

| 항목 | 규칙 |
|---|---|
| 표시 시점 | **치트 메뉴를 연 순간부터.** 아무것도 바꾸지 않고 닫아도 표시는 남는다 |
| 인게임 표시 | HUD에 **상시** (§2.3 b) |
| 결과 화면 | 오염 여부를 명시 (§5.4) |
| 점수 | 기록·순위 대상에서 제외 |
| 해제 | **런 도중에는 해제되지 않는다.** 재시작해야 초기화된다 (T-15) |

**아무것도 바꾸지 않고 닫아도 오염인 이유**를 §18.5가 적었다 — "「무엇을 바꿨을 때만 오염」으로 만들면 오염 여부 자체가 또 하나의 판정 규칙이 되고, 그 규칙에 구멍이 생기면 §14의 실측 데이터에 치트 플레이가 섞여 들어간다. **오염 판정은 틀렸을 때 손해가 한쪽으로만 나야 한다** — 멀쩡한 런을 오염으로 표시하면 한 판 더 하면 되지만, 오염된 런을 정상으로 기록하면 그 수치가 튜닝 근거가 된다."

구현으로 옮기면: 플래그를 세우는 자리는 **메뉴가 열리는 경로**(T-09 · T-12)와 **`sessionStorage` 복원 경로**(T-02b) 둘이다. 후자를 빠뜨리면 새로고침 한 번이 치트로 만든 런을 정상 런으로 되살리는데, §18.5가 금지한 방향이 정확히 그쪽이다 — "오염된 런을 정상으로 기록하면 그 수치가 튜닝 근거가 된다". 그래서 저장 payload에 `contaminated`를 같이 넣는다. 값이 바뀌는 자리마다 세우면 빠뜨린 자리가 곧 구멍이 된다. 플래그는 `sim/run.ts`가 소유하고(스테이지 전환을 넘어 살아남아야 하므로), `dev/cheat-menu.ts`가 공개 함수로 세우며([03_파일_구조.md](03_파일_구조.md) §5), `render/hud.ts`가 읽는다.

**§18.6과의 연결.** 치트 모드는 제출 빌드에 그대로 포함되고 소스에서도 지우지 않는다. 대신 "**제출 영상에는 쓰지 않는다** … §18.5의 오염 표시가 HUD에 떠 있는 화면은 그대로 실격 사유가 되므로 촬영 전에 반드시 확인한다." 그래서 오염 표시가 모서리 배지가 아니라 전체 폭 띠다(§2.3 b) — 촬영본을 확인하는 사람이 **놓칠 수 없어야** 그 확인이 의미가 있다.

### 8.7 화면

플레이어에게 보여 주는 화면이 아니라 도구다. 그래서 명조체(`--font-display`)를 쓰지 않고 **전부 모노(`--font-data`)** 로 짠다.

| 요소 | 값 |
|---|---|
| 딤 | `rgba(5,6,10,0.92)` — 다른 화면보다 진하다. 표를 읽는 화면이므로 아래 전장이 방해가 된다 |
| 좌열 (`x 80 ~ 520`) | 설정 항목. 스테이지 / 진입 지점 / 보스 페이즈 / 라이프 / 리롤 / 카드 목록 |
| 우열 (`x 560 ~ 1000`) | §8.4의 실효 수치 표 |
| 커서 | 현재 항목의 행 배경을 `hexA(baek, 0.08)`로 채우고, 값 부분을 `C.hwang`으로 |
| 값 변경 가능 표시 | 값 좌우에 `‹ ›` — ← → 로 바뀌는 항목임을 알린다 |
| 상단 | `치트 모드 — 이 런은 오염된 것으로 기록된다` (§18.5). **열자마자 보인다** |
| 하단 | `↑ ↓ 항목    ← → 값    Enter 적용    Esc 닫기` (§16.4) |

### 10.2 공통 규칙 (§16.5)

| 항목 | 규칙 | 구현으로 옮기면 |
|---|---|---|
| **입력 지연** | 프레임 1개 이내 | `keydown`을 **이벤트 타임스탬프와 함께** 큐에 넣고, `screens/play.ts`가 **그 타임스탬프가 속한 sim 스텝**에서 소비한다([12](12_통합_계약.md) §10 E-01). `KeyboardEvent.timeStamp`·`PointerEvent.timeStamp`는 `performance.now()`와 같은 타임베이스라 변환이 없다. 「그 프레임의 첫 스텝」으로 처리하면 등급 해상도가 60Hz 프레임 간격(1018 × 1/60 = 16.97u)으로 되돌아가 1/120이 값을 못 한다. dt = 1/120이므로 60Hz 화면에서 한 프레임에 sim 스텝이 두 번 돈다([01_설계_결정.md](01_설계_결정.md) D-04) — 프레임 단위로 비우면 같은 눌림이 두 스텝에 걸쳐 두 번 소비될 수 있다 |
| **키 리매핑** | **지원하지 않는다** | 설정 화면도, 저장도 없다. §16.5가 이유를 적었다 — 조작이 이동과 패리 두 가지뿐이고 각각에 대체 입력이 이미 둘씩 있다 |
| **동시 입력** | 이동 + 패리는 **어떤 조합으로도** 동시 접수 | 눌린 키를 `Set`으로 들고 매 스텝 읽는다. 키는 `event.code`(물리 위치)로 식별한다 — `event.key`는 레이아웃과 Shift에 따라 값이 바뀌어 `W`와 `w`가 갈리고 비 QWERTY 배열에서 WASD가 어긋난다. 리매핑이 없으므로(위) 물리 위치가 유일하게 안정적인 기준이다 |
| **브라우저 예약키** | `F5` · `F11` · `F12` · `Ctrl+Shift+I` · `Ctrl+Shift+J` · `Ctrl+Shift+C` 에 **어떤 동작도 배정하지 않는다** | 브라우저가 먼저 가져간다. 위 통합표에 이 조합이 하나도 없다는 것이 검사 방법이다 |
| **`Tab`** | 브라우저 기본 동작(포커스 이동)을 막고 게임 입력으로 처리 | `keydown`에서 `preventDefault()`. 막지 않으면 첫 `Tab`에 포커스가 캔버스를 떠나 이후 키가 전부 사라진다 |
| **접수 방식** | 패리는 **눌림(press) 순간에만** 접수한다(§5.1). 나머지 동작도 같다. **누르고 있는 동안 반복 발동하는 입력은 이동뿐이다** | 눌림 판정은 `Set`에 없던 키가 들어온 순간이다. `keydown`의 OS 자동 반복(`event.repeat === true`)은 버린다 — 안 버리면 패리 버튼을 누르고만 있어도 자동 반복이 눌림으로 들어와 §5.1의 "누르고 있어도 활성이 연장되지 않는다"가 깨진다 |

### 10.3 표에 없지만 필요한 처리

표의 셋은 스펙이 직접 말하지 않았지만 위 규칙을 구현하면 반드시 따라 나온다. **추가한 동작이 아니라, 추가한 규칙이 남긴 구멍을 막는 것이다.** 표 뒤의 탭 자동 일시정지만 출처가 다르다 — 그것은 [12_통합_계약.md](12_통합_계약.md)가 확정한 동작이다.

| 처리 | 왜 필요한가 |
|---|---|
| `blur` / `visibilitychange` 시 눌린 키 `Set`을 **비운다** | 동시 입력을 `Set`으로 구현했으므로 `keyup`을 못 받으면 키가 영원히 눌린 상태로 남는다. `Alt+Tab`으로 창을 떠났다 돌아오면 플레이어가 한 방향으로 계속 흘러가 탄에 맞는다 |
| 일시정지 재개 시 **선입력 버퍼를 비운다** (T-10 · §4.4) | §5.1의 0.12초 선입력 버퍼가 정지 직전 눌림을 붙들고 있으면 재개 순간 저절로 패리가 나간다 |
| `M`이 만드는 첫 사용자 제스처로 `AudioContext`를 만든다 | 브라우저는 사용자 제스처 없이 오디오를 시작하지 못한다([03_파일_구조.md](03_파일_구조.md) §1 `audio/context.ts`가 "지연 생성 + 첫 제스처 resume"). 타이틀에서 `M`이 §16.3의 정식 입력이므로 그것도 제스처로 취급한다 |

**탭을 벗어나면 자동으로 일시정지한다** ([12_통합_계약.md](12_통합_계약.md) §1 C-01).

```
document.visibilityState === 'hidden'  →  즉시 일시정지 (§4.1과 같은 정지, §13.4)
복귀                                    →  3 · 2 · 1 카운트다운 후 재개
```

카운트다운 중에는 **어떤 입력도 받지 않는다.** 카운트다운이 끝나는 순간 선입력 버퍼를 비우고(T-10과 같은 처리) sim을 재개한다.

자동 일시정지를 거부할 근거로 「§14.3의 실측 중에 예상치 못한 정지를 끼워 넣어 측정을 흐린다」를 들 수 있지만 **그 근거는 성립하지 않는다.** §14.3의 실측은 헤드리스에서 돌고([09](09_검증_전략.md) §4) 거기엔 `requestAnimationFrame`도 탭도 없다 — 브라우저 플레이의 자동 일시정지가 헤드리스 측정을 흐릴 경로가 없다. 그리고 [09](09_검증_전략.md) §6 E-02가 이 동작을 §7.3 완료 게이트의 합격 기준으로 못 박았으므로, 안 하면 게이트가 영구 빨간불이다.

탭을 벗어난 동안 흐른 실시간은 sim에 전달되지 않는다. `loop.ts`의 `realDt` 상한 0.25초([02_아키텍처.md](02_아키텍처.md) §1)가 이미 이것을 막지만, 일시정지가 그보다 먼저 걸린다.
