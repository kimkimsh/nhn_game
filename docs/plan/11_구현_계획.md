# 11. 구현 계획

병렬 에이전트 구현을 전제로 짠 작업 분해. **분할의 유일한 기준은 파일 소유권이다** — 두 작업이 같은 파일을 건드리면 병렬로 돌릴 수 없다. 리서치가 이유를 적었다: "Two teammates editing the same file leads to overwrites. Break the work so each teammate owns a different set of files"(`docs/research/claude_research/06_7일_스코프와_AI_에이전트_프로세스.md:324-329`).

전제: [03_파일_구조.md](03_파일_구조.md)의 트리가 확정이라는 것. 파일 경로가 흔들리면 소유권 분리가 성립하지 않는다.

---

## 1. 단계 지도

```
P-probe 프로브        직렬 1개      30줄 probe.html.  호출당 µs와 Mpx/s를 P0보다 먼저 잰다
P0  뼈대              직렬 1개      빈 캔버스가 60fps로 돈다
P2a 설정 데이터 (선행)  1 + 병렬 4개  P2-0 → P2-1 · P2-3 · P2-12a · P2-12b
P1  성능 스파이크      직렬 1개      ★ 게이트 — 786개를 그리며 p99 ≤ 16.67ms인가
P2b 설정 데이터 (나머지) 병렬 10개    P2-2 · P2-4 ~ P2-11 · P2-13.  P1과 동시에 돈다
P3  코어 + 최소 루프    일부 병렬     ★ 게이트 — 패리해서 반사탄이 적을 죽인다
P4  렌더 이식          병렬 14개     목업의 그림이 실게임에 들어온다
P5  전투 시스템 전체    병렬 9개      적·웨이브·보스·장판·카드·점수·진행 테스트
P6  화면 + 오디오 + 치트 병렬 9개
P7  밸런싱과 검증       직렬          실측 → 수치 조정 → 완료 판정
```

**P2가 P1 앞뒤로 갈라진 이유** ([12_통합_계약.md](12_통합_계약.md) §2). P1의 소유 파일이 P2의 산출물을 읽는다 — 탄환 `shape`·`radiusU`(P2-3), 글로우 색 목록(P2-12a), 폰트 리터럴(P2-12b), 스트레스 씬 개수(P2-1). `config/` 아래는 로직이 없어서 값을 옮겨 적는 일이고, 그래서 이 넷을 앞으로 옮겨도 성능 스파이크가 지연되지 않는다. 나머지 열 개는 P1과 병렬로 돈다.

각 단계의 게이트를 통과하지 못하면 다음 단계를 시작하지 않는다. 특히 **P1과 P3의 게이트는 협상 대상이 아니다.**

### 1.1 P-probe — P0보다 먼저 (직렬, 작업 1개)

[12_통합_계약.md](12_통합_계약.md) E-18의 확정이다. [06](06_렌더링과_게임필.md) §3.7.1이 사양을 갖는다.

| 항목 | 내용 |
|---|---|
| 소유 파일 | `probe.html` **한 장뿐** |
| 의존 | 없음. `npm install`도 하지 않는다 |
| 산출 | 숫자 두 개 — `lighter` `drawImage` 호출당 µs, 전면 `fillRect`의 Mpx/s |

재는 것은 이렇다.

```
① 1080×1920 캔버스에 85×85 스프라이트를 lighter로 10,000회 drawImage → 총 시간 ÷ 10,000 = t
② 같은 캔버스에 fillRect(0, 0, 1080, 1920)을 60회 → 60 × 2.07M px ÷ 총 시간 = Mpx/s
```

**이 30줄이 P1 전체보다 먼저 R-02를 닫는다.** P1은 P0과 P2a 네 작업이 선행이고 스프라이트 30장 + 글로우 13색 + 스트레스 씬 + 오버레이를 다 만들어야 첫 숫자가 나오는데, D-02를 뒤집을 수 있는 상수는 한 줄로 잴 수 있다. `16.67ms ÷ 2,500 = 6.7µs`가 [06](06_렌더링과_게임필.md) §3.5의 환산식이고, 측정된 `t`가 그 **미측정 상한 2,500을 직접 대체한다** — 실제 상한은 `16,670 / t`다. 판정표는 [06](06_렌더링과_게임필.md) §3.7.1에 있다.

**얻는 것은 P1의 성격이 바뀌는 것이다.** 이걸 먼저 하면 P1이 "될까?"가 아니라 **"예측한 값이 나오는가?"**를 재는 시험이 되고, 실패했을 때 원인이 굽기인지 fill인지 상태 변경인지를 이미 알고 시작한다.

**게이트는 없다.** 숫자를 얻는 것이 산출물이고, 그 숫자가 P1의 해석 기준이 된다.

## 2. P0 — 뼈대 (직렬, 작업 1개)

| 항목 | 내용 |

| 소유 파일 | `package.json` · `tsconfig.json` · `vite.config.ts` · `eslint.config.js` · `index.html` · `README.md` · `src/main.ts` · `src/boot/canvas.ts` |
| 의존 | 없음 |
| 산출 | `npm run dev`가 뜨고, 검은 1080×1920 캔버스가 화면 비율에 맞게 렌더된다 |

해야 할 것:

- TypeScript strict. `vite`, `vitest`, `typescript`, `eslint` 외 의존성 0개.
- `vite.config.ts`에 단일 파일 빌드 설정 ([01_설계_결정.md](01_설계_결정.md) D-03).
- `eslint.config.js`에 [03_파일_구조.md](03_파일_구조.md) §5의 계층 의존 규칙을 `no-restricted-imports`로 구현. **이걸 P0에 넣는 이유는, 나중에 넣으면 이미 위반한 코드가 쌓여 있기 때문이다.**

- `npm run verify` 스크립트 껍데기 (typecheck + test).

**게이트:** 빈 캔버스가 60fps. `npm run lint`와 `npm run typecheck`가 통과.

## 3. P1 — 성능 스파이크 (직렬, 작업 1개) ★

**이 단계가 [01_설계_결정.md](01_설계_결정.md) D-02(Canvas 2D)를 검증하거나 뒤집는다.** 리서치 코퍼스에 "탄환 N개 @ 60fps" 실측이 없으므로([01](01_설계_결정.md) R-02), 게임을 만들기 전에 잰다. **§1.1의 프로브가 이미 호출당 µs를 줬으므로, 이 단계는 그 예측이 프레임 전체에서도 맞는지를 재는 것이다.**

| 항목 | 내용 |
|---|---|
| 소유 파일 | `src/boot/sprite-bake.ts` · `src/render/sprites.ts` · `src/render/primitives.ts` · `src/dev/overlay.ts` · 임시 스트레스 씬 |
| 의존 | P-probe · P0 · **P2a** — `config/bullets.ts`(shape · radiusU) · `config/palette.ts`(글로우 색) · `config/ui.ts`(폰트 리터럴) · `config/playfield.ts`(스트레스 씬 개수) |
| 산출 | 786개를 그리면서 프레임 타임을 재는 화면 |

스트레스 씬의 동시 적 탄환 280은 `config/difficulty.ts`의 S5 상한인데 그 파일은 P2-5(P2b) 소유다. **P1이 읽는 값은 그 한 칸뿐이므로 스펙 §14.1에서 직접 읽고**, P2-5가 나온 뒤 참조를 그쪽으로 옮긴다. 이 한 값 때문에 P2-5 전체를 앞으로 당기지 않는다.

해야 할 것:

- 목업 `engine.js:96-160`의 `glowSprite` / `hexA` / `glow` / `hatch` / `poly` / `label`을 `render/primitives.ts`로 이식.
- **탄환 스프라이트 30장 + 글로우 13색**을 부팅 시 오프스크린에 굽는다 ([12_통합_계약.md](12_통합_계약.md) §1 C-04 · [06](06_렌더링과_게임필.md) §3.1). 유도는 이렇다 — 12종 중 P9 화염 장판과 P12 관통 대창은 `drawBullet`의 shape 분기에 case가 없고(engine.js:202-269) §6.1상 반사탄도 되지 않으므로 탄환 스프라이트가 아니다 → **패리 가능 10종.** 상태는 소유자 2가 아니라 **3**이다 — 반사탄은 자해 유예 0.15초 동안 적색 rim이 없어서 적 탄환·유예 중 반사탄·유예 후 반사탄이 서로 다른 그림이다([06](06_렌더링과_게임필.md) §5.3). `10 × 3 = 30`. 이 단계에서는 목업 `drawBullet`(engine.js:172-284)의 shape 분기를 굽기 함수 안으로 옮기는 것이 전부다.
- **탄환 층을 두 패스로 그린다** — 글로우 520장을 `lighter`로 전부, 모드를 한 번 바꾸고 본체 520장을 `source-over`로 전부([06](06_렌더링과_게임필.md) §3.1 · [12](12_통합_계약.md) E-14). 발마다 왕복하면 합성 모드 전환이 프레임당 1,040회이고, GPU 래스터라이저는 모드가 바뀔 때마다 배치를 flush한다. 스트레스 씬이 이걸 안 지키면 재는 것이 실게임의 프레임이 아니다.
- 스트레스 씬: 잡몹 20 + 탄환 280 + 반사탄 240 + 장판 6 + 파티클 240 = **786.** 씬은 [06](06_렌더링과_게임필.md) §3.7.2가 정본이고, **§6의 연쇄 20링크가 도는 구간을 반드시 포함한다.**
- `dev/overlay.ts`: fps, 프레임 타임 p50/p95/p99, 엔티티 수, draw call 수, 합성 모드 전환 수.

**게이트 — [06](06_렌더링과_게임필.md) §3.7.2가 정본이다**([12_통합_계약.md](12_통합_계약.md) E-16)**. 세 줄 다 만족해야 한다:**

1. 786개(엔티티 546 + 파티클 240)에서 프레임 타임 **p99 ≤ 16.67ms** (Chrome 기준). 연쇄 20링크 구간을 포함한 600프레임에서 잰다
2. 배경 정적 레이어 굽기를 적용한 뒤 위 조건 유지
3. Firefox에서도 **p99 ≤ 16.67ms**

**이 세 줄은 이 문서가 원래 적었던 것과 다르다.** p95 ≤ 16.6ms · 엔티티 750~950 · 파티클 400 · "게임 규칙은 없다"였고, 넷 다 [06](06_렌더링과_게임필.md) §3.7과 어긋났다. p95는 600프레임에서 **30프레임 실패를 허용**하고 p99는 6프레임만 허용하는데, 06이 p99를 고른 이유("한 프레임이 밀리면 그게 패리 실패로 나타난다")가 p95를 그대로 무효로 만든다. 파티클 400은 [12](12_통합_계약.md) §7.4가 240으로 확정하기 전의 값이고, 연쇄가 없는 씬은 최악 프레임이 아니다. **Firefox의 20ms(50fps)도 지웠다** — 그것을 통과선으로 두면 D-02 검증이 60fps를 한 번도 안 묻는 셈이 된다.

**실패 시.** 프레임워크로 갈아타지 않는다. 순서는 [02_아키텍처.md](02_아키텍처.md) §5.5 — 스펙 §14.3 T-07에 따라 **동시 적 탄환 상한을 먼저 내린다.** 그 다음이 청해파문 스트립 굽기, 그 다음이 글로우 스프라이트 반경이고, 그 뒤에야 D-02를 재검토한다([06](06_렌더링과_게임필.md) §3.6). **소형탄 글로우의 상수항 26은 손잡이가 아니다** — 낮추면 소형 고속탄의 가독성이 먼저 깨지고, 그건 §17 항목이다([12](12_통합_계약.md) E-17).

## 4. P2 — 설정 데이터 (15개, P2a / P2b로 갈린다)

`config/` 아래는 로직이 없으므로 파일마다 완전히 독립이다. **단, `ids.ts`와 `types.ts`는 나머지 전부가 의존하므로 먼저 직렬로 만든다.**

**P2a는 P1 앞에서, P2b는 P1과 나란히 돈다** ([12_통합_계약.md](12_통합_계약.md) §2). 가르는 기준은 하나 — P1의 스프라이트 굽기와 스트레스 씬이 그 값을 읽는가.

| 묶음 | 작업 | 언제 |
|---|---|---|
| **P2a** | P2-0 (선행) → P2-1 · P2-3 · P2-12a · P2-12b | P0 직후, P1 앞 |
| **P2b** | P2-2 · P2-4 ~ P2-11 · P2-13 | P1과 병렬 |

`types.ts`는 나머지 11개 작업의 계약이므로 여기서 모든 테이블 타입을 정의한다 — `BulletDef`, `EnemyDef`, `StageDef`, `WaveDef`, `BossDef`, `BossPattern`, `CardDef`, `CardEffect`, `StageScaling`, `ParryConfig`, `ParryBand`, `BossPartDef`, `BossCommon`.

**여기에 피격 크기가 함께 들어간다** ([12](12_통합_계약.md) §10 E-04). `EnemyDef.hitRadiusU` · `BossDef.hitBox: {wU, hU}` · `BossPartDef.hitBox`가 없으면 P3-B의 `collision.ts`가 `render/enemy.ts`의 `w`를 읽어야 하고, 그건 [03](03_파일_구조.md) §5의 계층 규칙 위반이다. **이 셋이 없으면 P3-B를 시작할 수 없다.**

**P2-12를 둘로 쪼갠 이유** ([12](12_통합_계약.md) §3). 합치면 `ui.ts` 158 + `feel.ts` 40 + `palette.ts`로 350개에 가까운 값을 한 작업이 갖는다. 병렬 묶음 안에서 혼자 크면 그 하나가 묶음 전체의 실제 소요 시간이 된다 — 분할의 기준이 파일 소유권인 것과 같은 이유로, 분량도 갈라야 병렬이 병렬로 작동한다.

**`config/audio.ts`는 지금까지 소유자가 없었다** ([12](12_통합_계약.md) §3). [07](07_오디오_설계.md) §5가 leaf 숫자 약 218개를 확정해 두었는데 P2 표 어디에도 그 파일이 없었고, P6-5~P6-7이 그 값을 쓰는 코드만 갖고 있었다. **P2-13이 값을 갖고, P6-5~P6-7은 읽는다.**

`core/`는 게임 규칙을 모르므로 서로 의존하지 않는다. **각각의 단위 테스트는 P3-C3의 `tests/core.test.ts` 한 파일로 모인다**([09](09_검증_전략.md) §3.7) — 예산이 6개 파일이던 때는 낼 곳이 없었다.

특히 주의할 것:
- `loop.ts` — [02_아키텍처.md](02_아키텍처.md) §1의 그림 그대로. `MAX_STEPS = 5`, 입력은 히트스톱 중에도 접수. 5스텝을 넘는 지연은 **버린다** — spiral of death 방어이고, [09](09_검증_전략.md) §3.6이 그 버리기 경로를 별도 케이스로 검증한다.
- **`clock.ts` — 히트스톱 식을 고쳐서 낸다**([12](12_통합_계약.md) E-02). `simDt = hitstopRemaining > 0 ? 0 : realDt`는 프레임 중간에 히트스톱이 끝나도 그 프레임 전체의 sim 시간을 버려서 NOT BAD 0.02초가 실제로는 33.3ms(**+67%**)가 되고, 설계된 체감 비율 `1 : 2.5 : 3.75`가 `1 : 1.5 : 2.5`로 뭉개진다. 세 줄이다.
  ```ts
  const freeze = Math.min(realDt, hitstopRemaining);
  hitstopRemaining -= freeze;
  simDt = realDt - freeze;
  ```
  그리고 **누적 상한 0.32초/초의 "최근 1초"가 sim 초임을 시그니처와 주석에 못 박는다.** 실시간 창으로 밀면 1주기가 `0.24 + 0.075 = 0.315`초라 초당 3.175회가 되어 상한이 사실상 안 걸린다. `4.16회/초`가 플레이어 체감값이 **아니라는** 사실도 같은 자리에 적는다.
- `sweep.ts` — 선분 대 원. 느린 물체에서도 올바르게 퇴화해야 조건 분기가 필요 없다. **피격 판정은 상대 변위로 한다** — `Δ = 탄환 이동 − 플레이어 이동` 선분 대 정지 원([12](12_통합_계약.md) E-07). 그리고 B3 선체·포문이 사각형이므로 **선분–AABB를 같은 파일에 둔다**(E-04).

**P3-A2(`input.ts`)는 이벤트 타임스탬프를 보관한다**([12](12_통합_계약.md) E-01). `input.beginFrame()`이 rAF 프레임당 1회라서, 1/120 스텝을 돌려도 플레이어가 등급을 고를 수 있는 해상도는 press edge가 확정되는 프레임 간격 — 60Hz에서 `1018 × 1/60 = 16.97u`다. **그걸 고치지 않으면 1/120은 프레임당 sim 비용만 2배다.** `KeyboardEvent.timeStamp`·`PointerEvent.timeStamp`를 그대로 들고 있다가 `screens/play.ts`가 그 타임스탬프가 속한 sim 스텝에서 press를 소비한다. `performance.now()`와 같은 타임베이스라 변환이 없고 약 15줄이다. **선입력 버퍼는 `simDt`로 감산한다**(E-03) — 실시간으로 깎으면 GREAT 직후 버퍼 0.12초 중 0.083초가 사라지는데(**69%**) 쿨다운은 얼어 있어 끝나지 않는다. 실시간에 남는 것은 press edge 검출뿐이다.

**ⓒ가 P5-3의 짝이다.** [12](12_통합_계약.md) §4.1이 `default: { const _never: never = pattern; throw … }`를 계약에 넣었지만 **그것이 실제로 던지는지를 보는 것이 없었다** — 안 던지는 구현도 컴파일되고 나머지 테스트를 전부 통과한다. ⓓ는 [05](05_시스템_설계.md) §8.3이 목업의 실제 버그로 지목한 자리이고(선체 히트박스가 포문 넷을 덮어 반사탄이 포문에 도달할 방법이 없다), ⓔ는 목업 HUD에 클램프가 아예 없는 자리다(engine.js:1729).

**P5-3이 가장 큰 덩어리다.** 보스 5기 × 페이즈 2~4 × 패턴 2~3 = 약 38개 패턴이지만, `config/bosses/`가 이미 데이터로 갖고 있으므로 `boss-runner.ts`는 **8종의 프리미티브**를 해석하는 코드다 — `volley` · `spread` · `ring` · `arc` · `charge` · `mortar` · `barrage` · **`parallel`**([12](12_통합_계약.md) §10 E-08~E-10). `summon`은 두 번째 사용처인 §10.4 화공선이 `EnemyId`에 없어 표현 불가라 삭제됐고(B1 연막 돌격은 `sim/boss.ts`의 페이즈 진입 훅), `lance`는 §9.7의 S5 W4 배경 함대가 웨이브 위협이라 `sim/lance.ts`로 나갔다. 대신 `parallel`이 들어왔다 — 스펙이 동시 실행을 네 곳에서 요구하는데(§10.6 전탄 발사 · §10.5 초토화 · §10.6 화공 총공세 · §10.4 최후 포격) 기존 union으로는 표현할 수 없었다. 프리미티브 하나가 안 되면 그 프리미티브를 쓰는 패턴만 안 된다 — 잘라내기 쉬운 구조다.

해석기에는 `default` 분기의 exhaustiveness 검사를 함께 넣는다([12](12_통합_계약.md) §4.1). 없으면 union에 kind를 추가하고 해석기를 안 고쳐도 컴파일이 통과하고, 보스가 그 패턴 차례에 아무것도 하지 않는다 — 타입 오류 0개, 테스트 통과, 게임만 조용히 고장.

**P5-5의 작업 지시에 `EffectiveStats`의 시그니처를 그대로 적는다** ([12](12_통합_계약.md) §8-17 · §10 E-05). `clamps`의 네 필드(`step` · `rule` · `field` · `after`)뿐 아니라 **런타임 파생 네 개**도 함께 적는다 — `reflectDamageMulFor(combo)`(R05는 콤보 종속) · `cooldownSecFor(outcome)`(N13은 쿨다운을 둘로 만든다) · `r10ActiveMinGapSec` · `shieldCharges`(E03은 스테이지마다 재충전). 네 카드가 「카드 변경 시에만 재계산」 모델을 깨므로, 정적 스냅샷만 넘기면 P5-5가 처음부터 틀린 타입을 만든다. §10.2가 요구하는 「계약 먼저」인데 이 하나만 문서 링크로 남아 있었고, 소비자가 셋(P6-8 치트 메뉴 · P6-3 카드 화면 · P5-8 테스트)이라 형태가 어긋나면 세 작업이 동시에 깨진다.

```ts
type Clamp = {
  step: number;                    // §11.6 보정 순서의 몇 단계가 잘랐나 (1~8)
  rule: string;                    // 'INV-1' · 'INV-2' · 개별 상한 ID
  field: keyof EffectiveStats;     // 잘린 필드 이름
  after: number;                   // 자른 뒤의 값
};
```

**게이트:** 치트 모드 없이 스테이지 1을 시작해 보스 1을 죽이고 카드를 고르고 스테이지 2로 넘어간다.

## 10. 병렬 실행 규칙

### 10.1 소유권

**한 작업이 만든 파일은 그 작업만 쓴다.** 다른 작업이 그 파일을 고쳐야 하면 그건 분할이 틀린 것이므로, 병렬로 돌리지 말고 합친다.

읽기는 자유다. `sim/parry.ts`를 만드는 작업이 `config/parry.ts`를 읽는 것은 문제없다 — 그 파일을 쓰지만 않으면 된다.

### 10.2 계약 먼저

병렬 작업이 서로의 함수를 부를 때, **호출 대상의 시그니처를 작업 지시에 적어서 넘긴다.** 각 작업은 자기 파일만 보므로, 이웃 파일의 이름과 타입은 지시에서만 알 수 있다.

이게 [01_설계_결정.md](01_설계_결정.md) D-01(TypeScript)의 실질적 이유다. 시그니처가 틀리면 `npm run typecheck`가 잡는다.

### 10.3 검증 게이트

각 작업의 완료 조건은 "코드를 썼다"가 아니라 다음 셋이다.

1. `npm run typecheck` 통과
2. 그 작업이 만든 테스트가 통과
3. `npm run lint` 통과 (계층 의존 규칙 포함)

**단계 게이트에서만 전체 스위트를 돌린다.** 작업 중에는 방금 바꾼 것을 덮는 테스트만 돌린다 — `vitest run -t "케이스 이름"`. 전체 스위트를 중간에 돌리면 필요한 결과 하나가 수백 개 사이에 묻힌다.

필터를 골라서 실패하는 테스트를 우연히 제외하는 것은, 테스트를 건너뛴 것과 같다.

### 10.4 재생성 금지

리서치가 같은 사양으로 10회 생성했을 때의 편차를 기록했다 — 코드량 492~652줄, 비용 $0.18~0.28(`docs/research/claude_research/06_7일_스코프와_AI_에이전트_프로세스.md:224-230`). 결론은 이렇다: **핵심 시스템은 한 번 생성하고 고정한 뒤 수정만 한다.** 마음에 안 들어서 통째로 다시 만들면 이미 그 시스템에 맞춰 짠 이웃 작업들이 전부 어긋난다.

반대로 파티클·SFX처럼 교체 가능한 부품은 여러 후보를 병렬로 만들어 고르는 편이 낫다.

| 4 | 시각 회귀 하네스 (P4-14 · 그것을 돌리는 P7-11) | 목업 대조가 수동이 된다 |
| 5 | 스테이지 5 관통 대창 (P12) | S5의 패리 불가 요소가 장판만 남는다. §10 E-10으로 `sim/lance.ts` 한 파일이 됐으므로 삭제가 한 곳에서 끝난다 |

**자르지 않는 것:** 치트 모드, 헤드리스 밸런스 시뮬, `sim/guards.ts`. 셋 다 자르면 나머지 전부의 품질이 측정 불가가 된다.
