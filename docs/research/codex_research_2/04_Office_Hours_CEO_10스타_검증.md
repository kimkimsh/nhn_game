# Office Hours + CEO 10스타 검증

사용한 검토 모드:

- `office-hours`: Builder Mode
- `plan-ceo-review`: Scope Expansion

사용자가 “개발 리소스를 신경 쓰지 말고 순수 재미와 참신함, 사전심사 1등을 목표로 하라”고 명시했으므로 범위 축소안은 선택하지 않았다. 다만 **제작량을 무시하는 것과 전달력을 무시하는 것은 다르다.** 설명해야만 재미있는 거대 기획은 10스타가 아니므로 제외했다.

## 1. 문제 재정의

표면 질문은 “일주일 동안 만들 게임 주제는 무엇인가?”다. 실제 문제는 다음과 같다.

> 연속해서 많은 제출물을 보는 심사자가 실제 플레이 첫 10초에 규칙을 이해하고, “처음 보는 조작인데 당장 해보고 싶다”고 느끼며, 30~60초 동안 같은 규칙이 계속 더 큰 사고를 만드는 주제를 찾는다.

목표 사용자는 장기 플레이 유저보다 먼저 **사전심사 담당자**다. 따라서 세계관의 깊이, 콘텐츠 양, 장기 성장보다 첫 조작의 명확성과 결과의 연쇄가 우선한다.

## 2. 전제 반박

### 전제 A: 참신한 소재가 참신한 게임을 만든다

반박: 메일함, 수술실, 한글 같은 소재가 새로워도 플레이어가 하는 일이 평범한 슈팅, 정렬, 단어 퍼즐이면 영상에서 익숙하게 보인다. 참신함은 배경보다 핵심 동사에서 나와야 한다.

### 전제 B: 복잡한 시스템일수록 AI 제작 역량을 잘 보여준다

반박: 복잡한 기능 수는 AI 활용 문서에는 유리해 보여도 게임의 재미를 희석할 수 있다. AI 역량은 하나의 불가능해 보이는 규칙을 안정적으로 구현하고, 대량의 반증·테스트 흔적을 남기는 방식으로도 더 강하게 보일 수 있다.

### 전제 C: 개발 리소스를 무시하면 설명 비용도 무시할 수 있다

반박: 개발량은 AI 에이전트로 압축할 수 있지만 심사자의 이해 시간은 압축할 수 없다. 30초 설명이 필요한 규칙은 아무리 거대해도 사전 제출에 불리하다.

### 전제 D: AI 대회이므로 게임 주제도 AI여야 한다

반박: 공개된 제출 항목은 AI 활용 기술 문서를 요구하지만 런타임 AI를 명시하지 않는다. 억지 AI NPC보다 제작 과정에서 AI를 깊고 검증 가능하게 사용하고, 게임은 순수하게 재미를 겨냥하는 편이 사용자의 의도와 맞다.

### 전제 E: 1등 주제를 찾으면 1등이 보장된다

반박: 공개 배점과 경쟁작이 없으므로 보장은 불가능하다. 할 수 있는 일은 흔한 핵심 동사를 제거하고, 재미·독창성·영상 전달력이 동시에 높은 선택지를 만드는 것이다.

## 3. 검토한 세 가지 전략

### 전략 A — 안전한 완성도 우선

검증된 아케이드 장르에 작은 반전을 붙이고 시각 완성도를 높인다.

- 장점: 실패 확률이 낮고 설명이 쉽다.
- 약점: 사용자가 기존 제안을 싫어한 이유를 반복하며, 1등을 노리는 기억점이 약하다.
- 결정: 사용자의 명시적 목표와 맞지 않아 제외.

### 전략 B — 퍼즐 발명 우선

언어, 시간, 레이어, 화면 UI 같은 추상 규칙을 하나 발명하고 정교한 레벨로 증명한다.

- 장점: 기획서에서 지적으로 참신해 보인다.
- 약점: 기존 20개와 가까워지기 쉽고, 실제 영상에서 수동적이거나 설명 의존적으로 보일 수 있다.
- 결정: 일부 원칙만 사용하고 주 전략에서는 제외.

### 전략 C — 익숙한 시각 언어를 빼앗는 시스템 액션

경고 장판, 검열 띠, 피해 숫자, 그림자, 포장 봉투처럼 누구나 이미 아는 것을 플레이어의 직접 조작 대상으로 바꾼다.

- 장점: 설명 전에도 그림이 읽히며, 관습의 배반과 손맛이 동시에 생긴다.
- 약점: 첫 훅만 있고 깊이가 없으면 짧은 밈 게임으로 끝난다.
- 결정: **채택.** 모든 최종안에 중첩, 쟁탈, 상태 보존, 보스 피니시 중 하나를 넣어 깊이를 확보했다.

## 4. 10스타 상태

평범한 5스타 제출물은 “아이디어가 기발하고 한 판 플레이된다”에서 끝난다. 10스타 제출물은 다음 다섯 장면이 하나의 규칙으로 이어진다.

1. **3초 역전:** 피하던 것, 보던 것, 가리던 것을 직접 잡는다.
2. **10초 손맛:** 잡고 옮기고 놓은 결과가 크고 명확하게 터진다.
3. **30초 연쇄:** 같은 행동이 둘 이상의 대상과 만나 예상 밖의 콤보가 된다.
4. **45초 피니시:** 보스의 가장 큰 공격이나 몸을 자기 파괴에 쓴다.
5. **제목 회수:** 게임 제목을 보면 방금 한 행동이 다시 떠오른다.

다섯 최종안은 이 구조를 만족하도록 고쳤다. 단순 참신성 후보였던 운동량 전송, 스테이플러 연결, 거대 보스 절단은 선행작과 첫인상이 겹쳐 제거했다.

# CEO 11개 관점 리뷰

## Section 1. Architecture Review — 재미 구조

다섯 게임의 공통 구조는 “관찰 → 탈취/변형 → 재배치 → 원래 시스템이 실행 → 연쇄 결과”다.

```text
익숙한 위험·표시·현상
          │
          ▼
플레이어가 직접 붙잡음
          │
          ▼
위치·방향·타이밍을 바꿈
          │
          ▼
원래의 공격·피해·물리가 실행됨
          │
          ▼
적끼리 충돌 / 보스 자폭 / 다음 재료 생성
          └──────────────────────────┐
                                     └── 다음 판단
```

중요한 결정은 플레이어에게 별도 무기를 주지 않는 것이다. 검, 총, 스킬 트리가 추가되면 훅이 보조 능력으로 밀려난다. 각 게임의 이름이 가리키는 도구가 처음부터 끝까지 주 공격, 방어, 이동을 담당해야 한다.

## Section 2. Error & Rescue Map — 기획 실패와 구제

| 실패 이름 | 발생 조건 | 심사자가 느끼는 것 | 구제 원칙 |
|---|---|---|---|
| 설명 의존 실패 | 첫 장면 전에 튜토리얼 문장이 길다 | “무슨 게임인지 모르겠다” | 첫 입력이 곧 규칙 시연 |
| 스킨 반전 실패 | 소재만 특이하고 행동은 평범하다 | “결국 흔한 장르” | 조종 대상 자체를 변경 |
| 한 번 웃고 끝 실패 | 첫 반전 뒤 새 판단이 없다 | “아이디어 데모” | 중첩·쟁탈·상태 보존 추가 |
| 혼돈 불독성 실패 | 연쇄가 커질수록 원인이 안 보인다 | “랜덤 물리” | 원인 색·궤적·짧은 히트 스톱 |
| 선행작 충돌 실패 | 핵심 문장이 기존 게임과 같다 | “어디서 본 것” | 소재 변경이 아닌 후보 폐기 |
| 피니시 단절 실패 | 보스전에서 갑자기 다른 규칙 사용 | “기믹 모음” | 첫 규칙을 가장 큰 규모로 회수 |

## Section 3. Security & Threat Model — 오프라인·권리

게임 자체는 오프라인 싱글이므로 계정, 서버, 사용자 생성 콘텐츠, 외부 API를 필요로 하지 않는다. 주요 위험은 보안보다 제출 권리와 제작 증명이다.

- 외부 네트워크가 끊겨도 전체 플레이가 가능해야 한다.
- AI 생성물, 폰트, 사운드, 라이브러리의 이용 조건을 기록해야 한다.
- 실제 플레이 영상과 빌드가 일치해야 한다.
- 프롬프트와 커밋 기록에서 타인의 게임을 복제하도록 지시한 흔적이 없어야 한다.
- 검색 결과 부재를 “세계 최초”라고 홍보하지 않는다.

## Section 4. Data Flow & Interaction Edge Cases — 입력과 결과

```text
입력
 │
 ├─ 대상이 없음 ───────────────► 실패 피드백만, 상태 변화 없음
 │
 ├─ 둘 이상의 대상이 겹침 ────► 우선순위가 화면에서 보임
 │
 └─ 유효 대상
        │
        ▼
   잡기/고정/포장
        │
        ├─ 취소 ───────────────► 원상 복귀
        ├─ 플레이어 피격 ──────► 잡은 상태의 규칙을 명시
        └─ 실행
              │
              ▼
       결과 예고 → 충돌 → 연쇄 → 점수/보스 상태
```

필수 상호작용 예외는 대상 중첩, 화면 밖 이동, 장면 전환 중 조작, 보스 무적 상태, 동시에 두 결과가 발생하는 경우다. 무엇이 선택됐고 왜 실패했는지 시각적으로 남겨야 한다.

## Section 5. Code Quality Review — 규칙 순도

구현 계획이 아니라 주제 리뷰 단계에서도 구조 순도가 중요하다.

- 핵심 규칙은 하나의 문장으로 유지한다.
- 개별 적이 예외 규칙을 갖기보다 같은 규칙에 다른 물성을 제공한다.
- 보스는 새 미니게임을 꺼내지 않고 기존 규칙의 크기·속도·동시성을 키운다.
- 점수, 업그레이드, 스토리는 핵심 동작을 가리지 않을 때만 존재한다.
- 다섯 게임의 기능을 서로 섞어 “모든 것을 조작하는 게임”으로 만들지 않는다.

## Section 6. Test Review — 재미 검증

주제 선정 후 첫 프로토타입은 다음 테스트를 통과해야 한다.

| 테스트 | 통과 기준 |
|---|---|
| 3초 무자막 테스트 | 처음 보는 사람이 조종 대상을 가리킬 수 있음 |
| 10초 욕구 테스트 | “내가 해보고 싶다”는 반응이 나옴 |
| 30초 변주 테스트 | 같은 입력에서 최소 세 종류의 의미 있는 결과가 보임 |
| 무음 영상 테스트 | 소리 없이도 원인과 결과를 설명할 수 있음 |
| 실패 재미 테스트 | 실패 장면도 다시 시도하고 싶을 만큼 읽히고 웃김 |
| 제목 회상 테스트 | 영상을 본 뒤 제목과 핵심 행동을 함께 기억함 |
| 선행작 반박 테스트 | “그 게임과 뭐가 다른가?”에 동사로 답할 수 있음 |

## Section 7. Performance Review — 화면 복잡도

개발 리소스는 선정 점수에서 제외했지만, 성능이 아니라 **인지 성능**은 재미와 직결된다.

- 연쇄 반응이 커져도 핵심 대상의 실루엣이 사라지지 않아야 한다.
- 충돌 직전과 결과 순간은 짧은 시간 압축으로 구분한다.
- 파티클보다 궤적, 외곽선, 크기 변화가 우선이다.
- 화면 밖에서 결정적인 결과가 나지 않도록 카메라가 원인을 따라간다.
- 물리 개체 수가 많아져도 결과가 무작위처럼 보이지 않아야 한다.

## Section 8. Observability & Debuggability Review — 원인 추적

AI 에이전트가 빠르게 확장할수록 “왜 이런 결과가 났는지”를 추적할 수 있어야 한다.

- 조작 대상의 현재 상태와 다음 상태를 시각화하는 디버그 보기
- 충돌 소유자, 공격 출처, 상태 보존 값을 확인하는 이벤트 기록
- 실패 직전 몇 초를 즉시 재생하는 리플레이
- 동일 입력과 시드로 물리 결과를 재현하는 테스트 장면
- 영상 후보 장면을 자동 표식하는 콤보·피니시 로그

## Section 9. Deployment & Rollout Review — 제출 경험

```text
저장소 커밋
   ├─ 실행 빌드 ──► 새 브라우저에서 완주 검증
   ├─ 플레이 로그 ─► 대표 장면 선택
   ├─ 실제 플레이 ─► 30~60초 영상
   └─ AI 기록 ─────► 기술 문서와 출처표
```

첫 실행은 로고보다 플레이가 먼저여야 한다. 별도 로그인, 네트워크, 긴 설정 화면을 두지 않는다. 실제 게임의 첫 보스 또는 첫 연쇄가 영상의 대표 장면과 동일해야 한다.

## Section 10. Long-Term Trajectory Review — 한 규칙의 확장성

각 주제는 새 기능을 붙이지 않고도 다음 방향으로 커질 수 있다.

- 장판 배달부: 장판의 형태와 서로의 반응
- 검은띠 방송사고: 카메라 구도와 공간 마스크의 관계
- 데미지 반송센터: 숫자의 무게, 목적지, 소유권 쟁탈
- 그림자 압정: 광원 수, 그림자 겹침, 장력 관계
- 진공포장 기사: 내용물 상태와 동시 개봉 조합

이 확장 축이 있다는 것이 단발성 밈과 시스템 게임의 차이다.

## Section 11. Design & UX Review — 시각 위계

첫 번째로 보여야 하는 것은 플레이어가 만질 대상, 두 번째는 그 대상의 목적지, 세 번째는 결과다.

| 주제 | 1순위 시각 요소 | 2순위 | 3순위 |
|---|---|---|---|
| 장판 배달부 | 잡을 수 있는 장판 테두리 | 남은 확정 시간 | 공격 결과 |
| 검은띠 방송사고 | 검열 영역 경계 | 사라질 충돌 단면 | 복구 위험 |
| 데미지 반송센터 | 날아가는 숫자 | 내 체력 바까지 궤적 | 반송 목적지 |
| 그림자 압정 | 고정점과 장력 | 광원 이동 | 발사 충돌 |
| 진공포장 기사 | 투명 패키지 내용물 | 타이머·방향 | 개봉 연쇄 |

색만으로 상태를 구분하지 않고 형태, 패턴, 움직임을 함께 쓴다. 튜토리얼 문장은 핵심 행동 뒤에 보조로 나타나야 한다.

## GSTACK REVIEW REPORT

### Critical

- 공식 배점표가 없으므로 1등을 보장한다는 표현은 사용할 수 없다.
- 각 게임에 일반 공격을 추가하면 핵심 훅이 보조 기믹으로 밀려난다.

### Important

- 최종 선택 뒤에는 3초·10초·30초 무자막 플레이테스트를 가장 먼저 해야 한다.
- 선행작 역검색 결과와 인간의 채택·폐기 판단을 AI 활용 기술 문서에 포함하면 제작 역량 증명이 강해진다.

### Accepted expansion

- 단순 반전에서 멈추지 않고 중첩, 쟁탈, 상태 보존, 보스 피니시까지 같은 규칙으로 확장한다.
- 실제 플레이와 심사 영상의 대표 장면을 동일하게 설계한다.

### Not in scope

- 런타임 생성형 AI 강제
- 온라인 멀티플레이
- 장기 성장 메타와 라이브 서비스
- 기존 20개 핵심 동사의 재포장
