## 3. 근거 1 — LLM 정확도는 '학습 데이터 밀도 × API 안정성'으로 결정된다

### 3.1 1차원리: 엔진 선택이 모델 선택보다 크다

Chier Hu의 1차원리 분석은 이렇게 정리한다.

> "LLMs manipulate text, and the engines they help most are the ones that *are* text."

그리고 상위 모델들이 SWE-bench 76~81%로 몰려 있는 상황에서

> "model choice barely matters for game-dev outcomes compared to engine choice, verification-loop quality, and human discipline."

티어 분류:

| 티어 | 대상 | 근거 |
|---|---|---|
| 1 (구조적 최적) | Godot, 웹 프레임워크(Three.js, Phaser, Babylon.js, Kaboom.js, PixiJS) | 전체 상태가 사람이 읽는 텍스트, JS가 학습 코퍼스 최상위, 단일 파일 배포 |
| 2 (양호) | Unity/C#, Pygame/Python | 코퍼스는 크지만 Unity는 에디터 의존 |
| 3 (보통) | LÖVE/Lua, Unreal C++ | 코퍼스가 "comparatively starved" |
| 4 (심각한 제약) | Unreal Blueprints, **Bevy/Rust** | Blueprint는 "binary visual format the LLM cannot read or write", Bevy는 "thin, fast-changing corpus" |

출처: [AI Coding Tools for Video Game Development — A First-Principles Analysis](https://chierhu.medium.com/ai-coding-tools-for-video-game-development-a-first-principles-analysis-of-what-actually-works-90dfa10edd13)

읽는 법에 주의가 필요하다.

- **Three.js 1,319만은 게임 코드 학습량이 아니다.** 데이터 시각화·제품 3D 뷰어·웹사이트 인터랙션 사용이 대부분이다(추정 — 용도별 분해 자료는 확인하지 못했다).
- **Kaplay는 Phaser 대비 다운로드 40배, 스타 23배 차이.** API가 짧고 예뻐서 매력적이지만, 모델이 본 예제 수가 그만큼 적다. 게다가 Kaboom.js가 Replit에 의해 방치된 뒤 갈라져 나온 후속이라, 모델이 구 Kaboom API를 섞어 쓸 위험이 Phaser의 v3/v4 문제와 똑같이 재현된다. 출처: [KAPLAY 공식](https://kaplayjs.com/), [Gamedev.js Kaplay](https://gamedevjs.com/tools/kaplay/)
- **PixiJS 86만**은 대부분 렌더러 용도다. Pixi를 쓰면 게임 루프·입력·충돌·씬 관리를 전부 직접 짜야 하므로, 바닐라 Canvas 대비 실제로 얻는 건 스프라이트 배칭 성능뿐이다.

### 3.3 **가장 중요한 함정 — Phaser 4가 npm의 `latest`를 가져갔다**

이번 조사에서 나온 단일 최대 리스크다.

| 항목 | 값 |
|---|---|
| npm dist-tag `latest` | **4.2.1** (2026-07-09 릴리스) |
| Phaser 4.0.0 최초 출시 | **2026-04-10** |
| 마지막 3.x | **3.90.0** (2025-05-23) |

출처: [registry.npmjs.org/phaser](https://registry.npmjs.org/phaser), [Phaser Releases](https://github.com/phaserjs/phaser/releases)

v3 → v4 파괴적 변경(공식 마이그레이션 스킬, 29단계 체크리스트):

- 렌더러 전면 개편 — 커스텀 파이프라인은 렌더노드로 재작성
- `Geom.Point` 제거 → `Vector2`
- `Mesh`, `Plane`, `BitmapMask` 게임오브젝트 제거
- `setTintFill()` → `setTint().setTintMode()`
- FX/Mask가 단일 Filter 시스템으로 통합
- `Phaser.Struct.Set`/`Map` → 네이티브 JS로 교체
- 텍스처 Y축이 GL 기준으로 반전(Y=0이 하단)
- **`Math.TAU` 값이 v3의 `PI/2`에서 v4의 `PI*2`로 변경** — 이름은 그대로다

출처: [v3-to-v4-migration SKILL.md](https://github.com/phaserjs/phaser/blob/master/skills/v3-to-v4-migration/SKILL.md), [Phaser 3 vs Phaser 4 (2026-05-13)](https://phaser.io/news/2026/05/phaser-3-vs-phaser-4), [Migrating from Phaser 3 to Phaser 4](https://phaser.io/news/2026/04/migrating-from-phaser-3-to-phaser-4-what-you-need-to-know)

`Math.TAU`가 왜 최악이냐면, **예외도 안 나고 콘솔 에러도 없고 화면 각도만 조용히 틀어진다.** 에이전트는 이걸 절대 못 잡는다. 사람이 눈으로 보고 "왜 이상하지"부터 시작해야 한다.

그리고 이게 실재하는 문제라는 3자 증거가 있다. 서드파티 Claude Code 플러그인 `phaser4-gamedev`의 저자는 제작 이유를 이렇게 썼다.

> "AI models lack deep knowledge of Phaser 4's API, leading to incorrect code generation."

이 플러그인은 **저장 전에 폐기된 Phaser 3 API를 차단하는 PreToolUse 훅**을 넣었다. 훅으로 막아야 할 만큼 모델의 기본 출력이 v3라는 뜻이다. 출처: [Yakoub-ai/phaser4-gamedev](https://github.com/Yakoub-ai/phaser4-gamedev)

반대 방향 주장도 있다. Phaser 공식 블로그는 "Every major model already knows the Phaser API well"이고 v4가 그 지식을 보존했다고 적었다. 다만 이건 **벤더 자체 주장이고 독립 검증 수치가 없다.** 서드파티 훅의 존재가 더 신뢰할 만한 신호로 본다.

**대응**: Phaser를 쓸 경우 `package.json`에 `"phaser": "3.90.0"`을 캐럿 없이 정확 핀하고 CLAUDE.md에 버전을 박는다. 그리고 공식 `/skills`(28종, v4 겨냥)를 붙이지 않는다. 섞으면 최악이다. 출처: [phaserjs/phaser /skills](https://github.com/phaserjs/phaser/tree/master/skills)

### 3.4 바닐라 Canvas 2D에는 이 문제가 존재하지 않는다

`CanvasRenderingContext2D`, `requestAnimationFrame`, `AudioContext`는 십수 년간 API가 바뀌지 않았고, 모든 학습 코퍼스에 프레임워크와 무관하게 존재한다. **버전 모호성이 구조적으로 0이다.** 이게 이번 추천의 1번 근거다.

## 4. 근거 2 — GitHub Pages 즉시 실행 가능성

### 4.1 GitHub Pages 실제 제한

| 항목 | 값 |
|---|---|
| 저장소 권장 크기 | 1 GB |
| 게시 사이트 최대 | 1 GB |
| 대역폭 | 월 100 GB (소프트) |
| 빌드 횟수 | 시간당 10회 (소프트) — **커스텀 GitHub Actions 워크플로 사용 시 미적용** |
| 배포 타임아웃 | 10분 |
| **커스텀 HTTP 헤더** | **설정 불가** |

출처: [GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)

"Actions 워크플로면 시간당 제한 미적용"이 실무적으로 크다. 7일 내내 커밋할 때마다 자동 배포해도 안 걸린다. 심사용 링크를 **1일차에 만들어 두고 마지막 날까지 갱신**하는 운용이 가능하다.

### 4.2 Godot의 헤더 문제 — 정확히 정리

여기는 검색 결과가 서로 어긋나서 공식 문서로 확인했다.

- **스레드 사용 내보내기**: `Cross-Origin-Opener-Policy: same-origin`과 `Cross-Origin-Embedder-Policy: require-corp`가 필요하다. GitHub Pages는 커스텀 헤더를 설정할 수 없으므로 **실행되지 않는다.**
- **Godot 4.3부터 단일 스레드 내보내기가 기본값이자 권장 방식**이 되어 특수 서버 헤더가 불필요하다. 즉 GitHub Pages에서 돌긴 돈다.
- 단일 스레드의 대가(공식 문서 명시): 스레드 사용 불가, 멀티스레드 대비 **성능 저하**, **오디오 지연 증가**, 기본 Sample 재생 모드에서 **오디오 이펙트 미지원**.
- 우회책 `coi-serviceworker`는 사용자의 **첫 로드 때 페이지를 한 번 리로드**시킨다.

출처: [Godot — Exporting for the Web](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html), [Deploying Godot 4 HTML exports (rafa.ee)](https://www.rafa.ee/articles/deploying-godot-4-html-exports/), [godot-ci #116](https://github.com/abarichello/godot-ci/issues/116), [godot-coi-serviceworker](https://github.com/nisovin/godot-coi-serviceworker)

심사자가 링크를 눌렀을 때 흰 화면이 뜨거나 페이지가 한 번 새로고침되는 건, 30~60초 영상과 함께 첫인상을 결정하는 지점에서 감수할 이유가 없는 리스크다.

### 4.3 Unity WebGL — 두 축 모두에서 걸린다

- GitHub은 100MB 초과 파일 푸시를 차단하고, Unity WebGL 산출물이 이를 넘는 보고가 있다(119MB 캐시 파일 사례).
- Git LFS로 우회한 경우 **"Unity 로딩 아이콘 이후 WebGL 프로젝트가 멈춘다"**는 보고가 있다.
- GitHub Pages 게시 사이트 1GB 상한과 10분 배포 타임아웃도 함께 걸린다.

출처: [Unity Discussions — Issue pushing to GitHub after WebGL build](https://discussions.unity.com/t/issue-pushing-to-github-after-webgl-build/801839), [GitHub community discussion #180231](https://github.com/orgs/community/discussions/180231)

### 4.4 LÖVE — Godot과 동일한 문제

`love.js`(LÖVE 11.5 대응) 표준 빌드는 SharedArrayBuffer 헤더를 요구하고, 회피용 호환 모드는 pthreads를 안 써서 **오디오가 "dodgy"**해지고 **스레드·코루틴이 비활성화**된다. 출처: [Davidobot/love.js](https://github.com/Davidobot/love.js)

### 4.5 웹 스택 — 이 항목 자체가 없다

Vite 공식 배포 가이드: 저장소 하위 경로 배포 시 `base: '/<REPO>/'` 설정, Settings → Pages에서 소스를 GitHub Actions로 지정, checkout → setup-node(npm 캐시) → `npm ci` → `npm run build` → configure-pages → `dist` 업로드 → deploy. 출처: [Vite Static Deploy](https://vite.dev/guide/static-deploy.html)

바닐라 단일 파일이면 빌드조차 필요 없다. `index.html`을 브랜치에 올리는 것으로 끝이다.

> `base` 경로 누락은 GitHub Pages 하위 경로 배포에서 가장 흔한 실수다. CLAUDE.md에 명시해야 한다.

## 5. 근거 3 — 에디터 GUI 의존성

에이전트는 GUI를 조작하지 못한다. 이 축에서 후보들이 명확히 갈린다.

| 스택 | GUI 필요 여부 | 근거 |
|---|---|---|
| Canvas / Phaser / Three.js / PixiJS | **불필요** | 전 산출물이 텍스트 소스 |
| Godot | 부분적으로 필요 | `.tscn`은 텍스트지만 씬 조립·노드 연결·리소스 임포트는 실질적으로 에디터 작업 |
| Unity | **필수** | "you can't run the game without loading the editor first", "editor-dependency is genuinely hostile to terminal-first agentic workflows" |
| Unreal | **치명적** | `.uasset` 바이너리. "inside Unreal Engine everything is serialized binary data… when I fire up Claude Code to have him review my blueprints, he can't" |

출처: [First-Principles Analysis](https://chierhu.medium.com/ai-coding-tools-for-video-game-development-a-first-principles-analysis-of-what-actually-works-90dfa10edd13), [Claude Code for Game Development](https://chierhu.medium.com/claude-code-for-game-development-7a88fcd19992)

Unity 관련 "40~60% 시간 단축" 마케팅 주장은 통제된 검증이 없다고 위 조사가 지적한다. Claude는 Unity 작업을 "코딩 중심에서 디자인 중심으로 옮길" 뿐 자동화하지 못한다는 게 조사의 결론이다.

## 6. 근거 4 — 에이전트 자동 디버깅 루프

### 6.1 핵심 실패 유형: "테스트는 통과하는데 게임이 안 된다"

이 조사에서 가장 반복적으로 나온 지적이다. 조사는 이를 **runtime blindness**로 부른다.

yurukusa의 기록:

> "The tests passed. The code compiled. The game launched. And the game was unplayable."

구체 수치: **60초 동안 누적 데미지 0**, 재미 구간이 10~30초인데 **레벨업이 3.9초마다** 발생. 출처: [Claude Code for Game Development](https://chierhu.medium.com/claude-code-for-game-development-7a88fcd19992)

Godot에서도 마찬가지다.

> "it reads the scene file, it does not run the scene… it cannot press play and read a live debugger error."

### 6.2 Godot의 `--headless`는 렌더링을 하지 않는다

공식 CLI 문서 정의:

> `--headless: Enable headless mode (--display-driver headless --audio-driver Dummy). Useful for servers and with --script.`

디스플레이 드라이버가 headless, 오디오가 더미다. 문서에 headless 모드 스크린샷 취득 방법에 대한 언급은 없다. 출처: [Godot Command line tutorial](https://docs.godotengine.org/en/stable/tutorials/editor/command_line_tutorial.html)

### 6.3 브라우저 게임만 루프가 닫힌다

Playwright CLI는 GUI 없이 에이전트에 텍스트 인터페이스를 제공하고, 구조화된 JSON 출력과 스크린샷을 지원한다. "test → 실패 식별 → 코드 수정 → 재테스트"를 자율 루프로 돌릴 수 있다. 캔버스 요소는 접근성 스냅샷에 안 잡히므로 **스크린샷 기반 시각 검증이 필수**라는 점도 명시돼 있다. 출처: [Playwright CLI with AI Agents](https://www.mindstudio.ai/blog/playwright-cli-ai-agents-automated-qa-testing), [Playwright](https://playwright.dev/)

`godogen` 프로젝트는 이걸 실제로 구현했다.

> "the agent judges results from the running game (a live URL or a recorded clip), not from a clean compile, so visible defects drive the next iteration."

지원 3종(Godot 4 / Bevy / Babylon.js) 중 **라이브 URL로 서빙되는 건 Babylon.js뿐**이다. 출처: [htdt/godogen](https://github.com/htdt/godogen)

**우리 환경에는 playwright MCP와 chrome-devtools MCP가 이미 붙어 있다.** 브라우저 게임을 고르면 추가 설정 0으로 이 루프가 즉시 작동한다. 7일 예산에서 이게 가장 큰 배율 요인이다.

### 6.4 게임플레이 수치 평가기를 직접 붙여야 한다

조사가 권하는 대응: 단위 테스트만 믿지 말고 **난이도·페이싱 지표를 재는 게임플레이 평가기**, **자동 플레이테스트 봇**, **스크린샷/비전 검증**을 붙일 것. 컨텍스트는 약 40분 후 붕괴하므로 서브에이전트·라인 범위 참조·`.claudeignore`로 관리할 것.

실무 번역: 게임 상태를 `window.__game`에 노출하고, Playwright가 헤드리스로 30초 시뮬레이션을 돌린 뒤 "누적 데미지", "첫 레벨업까지 걸린 시간", "초당 스폰 수" 같은 숫자를 뽑아 임계값으로 검사하게 만든다. 이러면 위의 실패 유형을 에이전트가 스스로 잡는다.

## 10. 최종 권고 스택과 7일 운용 방법

### 10.1 구성

```
언어      TypeScript (strict)
렌더      HTML5 Canvas 2D  (ctx.drawImage / fillRect, requestAnimationFrame)
오디오    Web Audio API (절차적 생성 — 에셋 라이선스 문제 회피)
빌드      Vite (base: '/<REPO>/')
배포      GitHub Actions → GitHub Pages
검증      Playwright MCP + Chrome DevTools MCP (스크린샷 + 콘솔 + 수치 평가)
외부 의존 없음 (또는 있어도 정확 핀 고정)
```

### 10.2 1일차에 반드시 세워야 할 것

1. **배포 파이프라인 먼저.** 게임 코드보다 GitHub Actions → Pages 배포를 먼저 뚫는다. 심사 링크가 1일차부터 살아 있어야 한다. Actions 워크플로면 시간당 빌드 제한도 안 걸린다.
2. **고정 타임스텝 + 결정론적 시드.** 에이전트가 같은 입력으로 같은 결과를 재현할 수 있어야 검증 루프가 성립한다.
3. **`window.__game` 상태 노출.** Playwright가 읽을 수 있는 형태로 HP, 스코어, 스폰 카운트, 경과 시간, 레벨을 노출한다.
4. **CLAUDE.md에 박을 것**: Canvas 2D API만 사용 / 외부 라이브러리 추가 금지(추가 시 정확 핀) / `base` 경로 / 좌표계 규약 / 프레임 예산.

### 10.3 디버깅 루프 설계 (runtime blindness 대응)

에이전트가 스스로 돌릴 수 있는 3단 검사:

| 단계 | 검사 | 실패 판정 |
|---|---|---|
| 1. 스모크 | 헤드리스로 페이지 로드 → 콘솔 에러 0, 5초 후 캔버스가 단색이 아님 | 콘솔 에러 존재 또는 흰 화면 |
| 2. 수치 평가 | 봇 입력으로 60초 시뮬레이션 → `window.__game`에서 누적 데미지, 첫 레벨업 시각, 초당 스폰 수 추출 | 누적 데미지 0, 첫 레벨업 < 10초 또는 > 30초 등 임계값 위반 |
| 3. 시각 회귀 | 주요 상태(타이틀/플레이/게임오버) 스크린샷 저장, 이전 대비 비교 | 사람이 눈으로 최종 판정 |

2단계가 핵심이다. yurukusa가 겪은 "60초간 데미지 0, 레벨업 3.9초마다"는 정확히 이 검사로 잡힌다. 이건 프레임워크가 안 해 주는 부분이라 우리가 직접 설계해 넣어야 하고, **브라우저 스택에서만 저렴하게 만들 수 있다.**

### 10.4 인간(개발자 1명)의 시간 배분

조사가 일관되게 지적하는 병목은 코드가 아니라 게임 디자인이다. 7일 중 코드 작성은 에이전트에 완전히 위임하고, 사람은 다음에 시간을 쓴다.

- 플레이테스트와 수치 튜닝 (충돌 판정 관대함, 스폰 레이트, 난이도 곡선)
- 30~60초 영상에서 무엇이 보여야 하는지 역산한 연출
- AI 활용 기술 PDF에 들어갈 프롬프트·채택/폐기 판단 기록

컨텍스트가 약 40분 후 붕괴한다는 지적을 고려해, 세션을 기능 단위로 끊고 `.claudeignore`와 라인 범위 참조를 쓴다.

### 10.5 NAN 심사 관점의 부수 효과

바닐라 Canvas를 고르면 **AI 활용 기술 PDF의 서사가 강해진다.** 게임 루프, 충돌 시스템, 파티클, 절차적 오디오 합성까지 에이전트가 전부 작성한 기록이 커밋 히스토리로 남는다. "프레임워크 컴포넌트를 조립했다"보다 검증 가능한 AI 활용 증거다. (이건 공식 배점표가 아니라 제출 요건에서 도출한 추정이다.)
