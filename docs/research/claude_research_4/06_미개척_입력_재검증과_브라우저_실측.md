# 미개척 입력축 재검증과 브라우저 실측 가능성

조사자: claude / 4차 라운드 / 2026-07-31
대상: 3차 리서치가 "비어 있다"고 지목한 입력축 5개의 재검증 + 브라우저에서 실제로 측정 가능한지

---

## 결론 먼저 (5줄)

1. **3차 리서치의 "선행작 0" 판정은 5축 중 4축에서 틀렸다.** 각속도 4건, 휠 관성 4건, 저크(흔들기) 8건 이상 + OS 기본기능 3종, dwell 7건을 URL로 확보했다. 남은 진짜 빈 축은 **커서 선속도를 소모성 자원으로 쓰는 것** 하나뿐이고, 이것도 반쪽짜리다.
2. **브라우저에서 픽셀·속도 기반 지표는 사람마다 다른 게임이 된다.** MDN이 명시적으로 경고한다 — `movementX`의 단위가 브라우저·OS마다 physical/logical/CSS 픽셀로 갈린다. 여기에 OS 포인터 가속이 얹히고, 마우스 폴링레이트가 125Hz~1000Hz로 8배 차이 난다. 속도 임계값을 내 PC에서 튜닝하면 심사자 PC에서는 다른 난이도가 된다.
3. **그 오염을 제거하는 유일한 API(`unadjustedMovement`)는 pointer lock을 요구하고, pointer lock은 Chrome이 "Press Esc to show your cursor" 회색 버블을 화면 한가운데 띄운다.** 30~60초 심사 영상에 브라우저 시스템 UI가 박히므로 **pointer lock은 사용 불가**. 따라서 OS 가속 오염은 제거 불가능한 전제다.
4. **그래서 살아남는 것은 각도 기반 지표뿐이다.** 각도는 확대·축소에 불변이므로 DPI·가속·폴링레이트에 거의 영향받지 않는다. 실제로 업계 표준 흔들기 판정 라이브러리(mouse-shake.js)가 픽셀이 아니라 **도(degree) 합**으로 판정하는 이유가 정확히 이것이다. 원문 알고리즘 전문을 아래에 실었다.
5. **진짜로 비어 있는 축은 "연속 곡률"이다.** 원을 그려서 주문 시전하는 제스처 인식은 포화지만, "지금 이 순간 얼마나 급하게 꺾고 있는가"를 연속 스칼라로 읽어 게임 상태에 매 프레임 먹이는 설계는 선행작 0이다. 그리고 곡률은 각도 기반이라 위 3번 문제를 통과한다. **주제 선정은 이 하나로 좁혀라.**

> **게임 컨셉에 어떻게 쓰는가**: 각속도를 코어 동사로 삼는 안은 이번 라운드에서 전부 폐기하라. 남길 수 있는 건 "각속도"가 아니라 "각속도를 어디에 주입하는가"인데, 요요·팽이·태엽은 이미 다 점유됐다.

# 2부. 브라우저 실측 가능성 — 무엇을 믿을 수 있고 무엇을 못 믿는가

여기가 이번 조사의 진짜 수확이다. **결론: 절대 픽셀값은 못 믿는다. 각도는 믿을 수 있다.**

## 2-1. pointermove의 실제 발화 레이트 — rAF에 정렬되어 있다

Chrome은 **버전 60부터** 연속 입력 이벤트를 프레임에 정렬시킨다.

> 원문: *"the input pipeline will delay dispatching continuous events and dispatch them right before the `requestAnimationFrame()` callback occurs."*
> 대상 이벤트: `wheel`, `mousewheel`, `touchmove`, `pointermove`, `mousemove`
> 배경 수치 원문: *"touch-screens deliver input at 60-120Hz and mice deliver input typically at 100Hz"* / *"the typical refresh rate of a monitor is 60Hz."*
> 출처: https://developer.chrome.com/blog/aligning-input-events

즉 **`pointermove` 핸들러는 초당 60번(모니터 주사율) 호출된다.** 마우스가 1000Hz로 보고해도 마찬가지다. 소박한 `pointermove` 카운터로 속도·각속도를 재면 **원래 궤적의 6% 표본만 보고 있는 것**이다.

> **게임 컨셉에 어떻게 쓰는가**: 60Hz(16.7ms 간격) 표본만으로도 "원을 그린다"(각속도, 주기 300~800ms)는 충분히 읽힌다. 하지만 "채찍처럼 순간적으로 꺾었다"(저크, 지속 20~50ms)는 표본 3개 안에서 벌어지므로 놓치거나 뭉개진다. **저크를 코어로 쓰려면 아래 getCoalescedEvents가 필수다.**

## 2-2. getCoalescedEvents() — 잃어버린 표본을 되찾는 유일한 수단

> MDN 원문: *"Instead of a stream of many `pointermove` events, user agents coalesce multiple updates into a single event. This helps with performance as the user agent has less event handling to perform, but **there is a reduction in the granularity and accuracy when tracking, especially with fast and large movements.**"*
> *"The `getCoalescedEvents()` method lets applications access all un-coalesced position changes for precise handling of pointer movement data where necessary."*
> 출처: https://developer.mozilla.org/en-US/docs/Web/API/PointerEvent/getCoalescedEvents

**지원 현황 (caniuse 실측, https://caniuse.com/mdn-api_pointerevent_getcoalescedevents):**

| 브라우저 | 지원 | 최소 버전 |
|---|---|---|
| Chrome | ✅ | 58+ |
| Edge | ✅ | 79+ |
| Firefox | ✅ | 59+ |
| Safari (macOS/iOS) | ✅ | 18.2+ |
| Opera | ✅ | 45+ |
| **글로벌 커버리지** | **92.8%** | |

**주의 — MDN과 caniuse가 어긋난다.** MDN 페이지에는 *"This feature is not Baseline because it does not work in some of the most widely-used browsers."* 라는 배지가 붙어 있는데, caniuse 표에는 Safari 18.2+가 지원으로 찍혀 있다. Safari 18.2는 2024년 말 릴리스이므로 MDN 배지 문구가 갱신되지 않은 것으로 보인다 **(추정)**. 실무 판단: **써도 된다. 단 `if (e.getCoalescedEvents)` 가드는 반드시 넣는다.**

`pointerrawupdate`도 있지만 MDN이 성능 경고를 붙여놨다:
> *"because listening to `pointerrawupdate` events can affect performance, you should add these listeners only if your JavaScript needs high-frequency events and can handle them as quickly as they are dispatched. For most use cases, other pointer event types should suffice."*
> 출처: https://developer.mozilla.org/en-US/docs/Web/API/Element/pointerrawupdate_event

> **게임 컨셉에 어떻게 쓰는가**: 실측 스택은 이렇게 고정한다 — `pointermove` 한 번 받고, 그 안에서 `getCoalescedEvents()`로 원시 표본 배열을 꺼내 전부 누적하고, 물리 갱신은 rAF에서 한 번만 한다. `pointerrawupdate`는 쓰지 않는다(지원 좁고 성능 위험).

## 2-3. 마우스 폴링레이트 — 사람마다 8배 차이 난다

| 폴링레이트 | 보고 간격 | 60Hz 프레임당 표본 수 |
|---|---|---|
| 125 Hz (일반 사무용 USB 마우스 기본값) | 8 ms | 약 2개 |
| 500 Hz | 2 ms | 약 8개 |
| 1000 Hz (게이밍 마우스 표준) | 1 ms | 약 16개 |
| 8000 Hz | 0.125 ms | 약 133개 |

출처: https://capytoolkit.com/tools/hardware/input-lag/usb-polling-rate-explained/ (원문: *"125 Hz: one report every 8 ms / 500 Hz: one report every 2 ms / 1000 Hz: one report every 1 ms / 8000 Hz: one report every 0.125 ms"*)

즉 `getCoalescedEvents()`를 써도 **심사자가 사무용 마우스를 쓰면 프레임당 2표본, 게이밍 마우스면 16표본**이다. 세 점이 있어야 계산되는 저크·곡률은 사무용 마우스에서 **프레임당 0회 갱신**될 수도 있다.

> **게임 컨셉에 어떻게 쓰는가**: 저크·곡률 판정은 **프레임 단위가 아니라 시간창(sliding time window) 단위**로 하라. mouse-shake.js가 500ms 창을 쓰는 이유가 이것이다. 창을 300~500ms로 잡으면 125Hz 마우스에서도 표본 40개 이상이 확보된다.

## 2-4. **OS 포인터 가속 — 제거 불가능하다 (이번 조사 최대의 제약)**

Chrome 공식 문서가 인정한다:
> *"The existing Pointer Lock API returns the mouse movement that the platforms give Chrome, and **by default all platforms include some form of mouse acceleration** in the movement information they give Chrome."*
> 출처: https://groups.google.com/a/chromium.org/g/blink-dev/c/cQn7OwcMQ64/m/OWmA9KMKBQAJ

web.dev 원문:
> 운영체제는 마우스 가속을 기본으로 켜두며, 이 때문에 *"the same physical distance that you move the mouse"* 를 빠르게 움직이면 커서가 더 멀리 간다.
> 출처: https://web.dev/articles/disable-mouse-acceleration

해제 API는 존재한다:
```javascript
myTargetElement.requestPointerLock({ unadjustedMovement: true });
```
그런데 **세 겹의 제약이 걸린다.**

1. **pointer lock이 필수다.** web.dev 원문: *"The `unadjustedMovement` option requires pointer lock to be active on the target element."*
2. **Chromium 계열만 지원한다.** *"Chromium-based browsers (e.g. Chrome, Edge, etc.) are the only ones to support disabling OS-level adjustment for mouse acceleration."* Firefox·Safari 미지원. Linux 미지원.
3. **★ pointer lock은 화면에 브라우저 시스템 UI를 띄운다.** Chromium 이슈 트래커와 Deno 이슈에 원문이 남아 있다:
   - *"A web page can enter pointer lock without showing the 'Press Esc' bubble (which is considered a security surface)."* — https://issues.chromium.org/issues/40522116 (버블이 없는 건 보안 버그로 취급된다 = 정상 동작은 버블이 뜬다)
   - *"On every lock, Chromium's exclusive-access bubble ('Press Esc to show your cursor') appears over the app. In a shipped native application this reads as a browser artifact."* — https://github.com/denoland/deno/issues/36131
   - Babylon.js 포럼: *"JavaScript cannot engage pointer lock without the browser explicitly notifying the user."* — https://forum.babylonjs.com/t/to-show-your-cursor-press-esc/61901

**따라서 판정은 이렇다.** 30~60초 심사 영상에 "Press Esc to show your cursor"라는 회색 시스템 버블이 화면 상단 중앙에 박힌다. 편집·자막 트릭이 금지된 규정에서 이건 잘라낼 수도 없다. **pointer lock 사용 금지 → unadjustedMovement 사용 불가 → OS 포인터 가속은 영구 전제.**

> **게임 컨셉에 어떻게 쓰는가**: 커서를 숨기고 자체 아바타를 그리는 설계(FPS식 상대 이동)는 전부 폐기하라. 코어 동사는 **OS가 그려주는 진짜 커서가 화면에서 실제로 지나간 경로**만 가지고 성립해야 한다.

## 2-5. **movementX의 단위가 브라우저마다 다르다 — 픽셀 임계값을 못 쓰는 결정적 이유**

MDN이 경고 박스로 명시한다:
> *"Browsers use different units for `movementX` and `screenX` than what the specification defines. Depending on the browser and operating system, the `movementX` units may be a physical pixel, a logical pixel, or a CSS pixel. **You may want to avoid the movement properties**, and instead calculate the delta between the current client values (`screenX`, `screenY`) and the previous client values."*
> 정의 원문: `currentEvent.movementX = currentEvent.screenX - previousEvent.screenX`
> 출처: https://developer.mozilla.org/en-US/docs/Web/API/MouseEvent/movementX / 근본 이슈 https://github.com/w3c/pointerlock/issues/42

이걸 2-4의 OS 가속, 2-3의 폴링레이트 차이와 곱하면 이렇게 된다.

> **같은 물리적 손동작이, 심사자 PC에서 내 PC 대비 2~4배 다른 픽셀값으로 들어온다. (추정 — 배율은 측정하지 않았고 문헌상 요인 세 개의 곱으로 추산한 값이다.)**

**그런데 각도는 이 오염을 통과한다.** 가속·DPI·CSS픽셀 스케일은 전부 **크기 스케일링**이고, 세 점이 이루는 각은 스케일 불변이다. 이것이 왜 mouse-shake.js가 픽셀 임계값이 아니라 `shakeDeg: 500`(도 단위 합)을 쓰는지에 대한 설명이다.

| 지표 | 스케일 불변? | 심사자 PC에서 안전한가 |
|---|---|---|
| 커서 속도 (px/s) | ❌ | 위험 — 자동 캘리브레이션 필수 |
| 이동 거리 (px) | ❌ | 위험 |
| **회전각·각속도 (deg/s)** | ✅ | **안전** |
| **꺾임각 합 (deg)** | ✅ | **안전** |
| **곡률의 부호·상대 크기** | ✅ (부호는 완전 불변, 크기는 준-불변) | **안전** |
| 곡률 절대값 (1/px) | ❌ | 위험 |
| 정지 시간 (ms) | ✅ (시간축이라 무관) | 안전 |

> **게임 컨셉에 어떻게 쓰는가**: 코어 동사를 정할 때 "몇 픽셀"이 아니라 "몇 도"로 말할 수 있는 동사를 골라라. "빠르게 휘두르면"은 위험하고, "90도 이상 꺾으면"은 안전하다.

## 2-6. 화면 가장자리 압력 — 브라우저에서 **측정 불가**

3차·4차 아이디어로 나온 "커서를 화면 가장자리에 밀어붙이는 압력(넘어간 픽셀량)"은 **측정 자체가 불가능하다.**

- OS가 커서를 화면 경계에서 클램프한다. 좌표가 더 이상 변하지 않으므로 `mousemove`/`pointermove` 자체가 발화하지 않는다. `movementX = screenX - 이전 screenX = 0`. **(추정 — 문헌으로 직접 확인하지 못했고, movementX 정의식에서 연역했다.)**
- 유일한 우회로인 `unadjustedMovement`는 2-4에서 확인했듯 pointer lock을 요구하고 pointer lock은 버블을 띄운다.
- **다만 "브라우저 창 밖"까지는 측정된다.** 드래그(버튼을 누른 채) 중에는 `setPointerCapture()`가 걸려 뷰포트 밖 좌표가 계속 들어오고, `clientX`가 음수 또는 `innerWidth` 초과로 나온다. javascript.info가 이를 전제로 설명한다: *"if clientX/clientY are out of the window, then elementFromPoint returns null"* — https://javascript.info/mouse-drag-and-drop , Win32 근거 https://learn.microsoft.com/en-us/windows/win32/learnwin32/mouse-movement (*"After calling SetCapture, the window will continue to receive WM_MOUSEMOVE messages for as long as the user holds at least one mouse button down, even if the mouse moves outside the window."*)

> **게임 컨셉에 어떻게 쓰는가**: "화면 밖으로 밀어내기"는 죽었고, **"브라우저 창 밖으로 끌어내기"는 살아 있다** — 단, 버튼을 누른 드래그 중에만. 게임판이 창 전체를 덮지 않게 설계하면(창 안에 여백을 둠) 여백까지 끌어낼 수 있다. 다만 이는 금지목록의 "UI 메타(창이 게임판)"와 아슬아슬하게 인접하므로 신중해야 한다.

## 2-7. 마우스 하드웨어의 각도 스내핑 — 곡률 축의 유일한 오염원

일부 마우스는 펌웨어에서 궤적을 직선으로 펴는 보정을 한다.
> 원문: 각도 스내핑은 *"an accessibility feature that corrects the mouse movement trajectory through algorithms, making the cursor move on the screen in a straighter direction or aligned with a specific angle."* / *"reduces jagged edges and sharp lines, making curve paths smoother"*
> 기본값: *"most gaming mice disable this feature by default to cater to gamers"* — 디자이너용 마우스에서는 *"usually enabled by default"*
> 출처: https://akkogear.eu/blogs/news/mouse-angle-snapping-guide

> **게임 컨셉에 어떻게 쓰는가**: 곡률 기반 설계의 유일한 하드웨어 리스크. 다만 게이밍 마우스에서는 기본 꺼짐이고 사무용 마우스에는 대개 이 기능 자체가 없다. **곡률의 "부호"(왼쪽으로 도나 오른쪽으로 도나)는 스내핑에도 살아남으므로, 부호를 코어로 쓰면 리스크가 0에 수렴한다.**

# 3부. 저크 판정 알고리즘 — 원문 전문

3차 리서치가 "포럼에 30줄로 공개돼 있다"고 지목한 것의 실체는 **`mouse-shake.js` (David Godzsak, 2015, MIT)** 로 판단된다. 전체 107줄, 핵심 판정 로직은 정확히 30줄 남짓이다.

- 저장소: https://github.com/davidgodzsak/mouse-shake.js/
- 원문 파일: https://raw.githubusercontent.com/davidgodzsak/mouse-shake.js/master/src/mouse-shake.js

## 3-1. 상수 (원문 그대로)

```javascript
var stuff={                  //units
    moves:[],                  //set of Stamps
    deg:0,                     //degrees
    tick:new Date().getTime(), //time
    x:0,                       //coordinate x
    y:0,                       //coorddinate y
    refresh:80,                //milisecs
    shakeDeg:500,              //degrees
    lifeTime:500,              //milisecs
    l:false                    //mousemove indicator
};
```

| 상수 | 값 | 의미 |
|---|---|---|
| `refresh` | 80 ms | 판정 루프 주기 = **12.5Hz 다운샘플링** |
| `lifeTime` | 500 ms | 슬라이딩 시간창 |
| `shakeDeg` | 500 deg | 창 안의 꺾임각 총합 임계값 |

## 3-2. 꺾임각 계산 — 코사인 제2법칙 (원문 그대로)

```javascript
//get gamma in triangles using law of cosines
function gamma(st,nd,rd){
    //pythagoras
    var a=Math.sqrt(Math.pow(st.x-nd.x,2)+Math.pow(st.y-nd.y,2));
    var b=Math.sqrt(Math.pow(nd.x-rd.x,2)+Math.pow(nd.y-rd.y,2));
    var c=Math.sqrt(Math.pow(rd.x-st.x,2)+Math.pow(rd.y-st.y,2));
    var gam;

    if((a*b)==0){
        gam=0;
    }else{
        //law of cosines
        gam=180-Math.acos((Math.pow(a,2)+Math.pow(b,2)-Math.pow(c,2))/(2*a*b))*180/Math.PI;
    };
    return gam;
};
```

세 점 `st → nd → rd` 에 대해, `nd`에서의 **외각(꺾인 정도)** 을 도 단위로 반환한다. 직진이면 0°, 완전히 되돌아오면 180°.

## 3-3. 판정 루프 — 코어 30줄 (원문 그대로)

```javascript
//update mouse position
document.addEventListener('mousemove',function(e){
    stuff.x=e.pageX;
    stuff.y=e.pageY;
    stuff.l=true;
});

//detects shake event
detect=setInterval(function(){

        //add new Stamps
        if(stuff.l){
            var now=new Date().getTime();
            var a=new Stamp(stuff.x,stuff.y,now);
            stuff.moves.push(a);
            stuff.l=false;  //mousemove indicator off
        };

        //delete old Stamps   -----------------might need some improvement.
        for(var i=0;i<stuff.moves.length;++i){
            if(now-stuff.moves[i].time>stuff.lifeTime){
                stuff.moves.splice(i, 1);
            };
        };

        //reset degrees so we can add them again
        stuff.deg=0;
        //add up gammas (deg=sum(gamma))
        if(stuff.moves.length>2){
            for(var i=2;i<stuff.moves.length;++i){
                stuff.deg+=gamma(stuff.moves[i],stuff.moves[i-1],stuff.moves[i-2]);
            };
        };

        //if degree exceeds shakeDeg shake event happens
        if(stuff.deg>stuff.shakeDeg){
            document.dispatchEvent(mouseshake);
            stuff.deg=0;
            stuff.moves=[];
        };
},stuff.refresh);
```

## 3-4. 이 알고리즘에 대한 실전 평가 (이 조사의 판단)

**좋은 점 — 그리고 이게 2부의 결론과 정확히 맞물린다.**
- 판정이 **전부 각도**다. 픽셀 임계값이 하나도 없다. → OS 가속·DPI·CSS픽셀 스케일에 불변.
- 80ms 다운샘플링이 **의도적 저역통과 필터** 역할을 한다. 폴링레이트 차이(125Hz vs 1000Hz)를 12.5Hz로 눌러버리므로 하드웨어 차이가 소거된다.
- 500ms 창 / 500도 임계값 = 평균적으로 **0.5초 안에 큰 꺾임 4~5회**. 사람이 "흔들었다"고 느끼는 것과 잘 맞는다.

**게임에 그대로 쓰면 안 되는 점.**
- **불리언 이벤트다.** `mouseshake`가 발화하거나 안 하거나뿐이다. 게임에는 "얼마나 세게 흔드는가"의 **연속값**이 필요하다. → `stuff.deg`를 이벤트로 만들지 말고 **매 프레임 노출되는 아날로그 게이지**로 바꿔야 한다.
- **발화 후 `moves=[]`로 전부 리셋한다.** 게임에서는 이게 "때렸는데 다음 0.5초가 먹통"으로 느껴진다. → 리셋 대신 **감쇠(decay)**: `deg *= 0.85` 같은 식.
- `now`가 `if(stuff.l)` 블록 안에서만 정의되는 **명백한 스코프 버그**가 있다(마우스가 멈추면 `now`가 undefined가 되어 오래된 stamp가 안 지워진다). 그대로 복붙하면 안 된다.
- `splice`를 순방향 루프에서 하므로 **인덱스 밀림 버그**도 있다. 원저자도 주석에 `might need some improvement`라고 적어놨다.
- `mousemove`만 듣는다. 2-2에서 봤듯 **`pointermove` + `getCoalescedEvents()`로 갈아타야** 빠른 채찍질을 놓치지 않는다.

**우리가 쓸 형태 (권장 파라미터, 이 조사의 제안 — 미검증):**

| 파라미터 | mouse-shake.js | 게임용 권장 | 이유 |
|---|---|---|---|
| 샘플 주기 | 80 ms (setInterval) | rAF 안에서 coalesced 표본 전량, 단 **8ms 이하 표본은 병합** | 1000Hz 마우스의 노이즈 제거 + 125Hz와 동일 조건화 |
| 시간창 | 500 ms | **300 ms** | 15~18초 웃음 사이클 안에 반응이 3~5번 들어가야 함 |
| 임계값 | 500 deg (불리언) | **연속 게이지 0~1로 정규화, 360deg=1.0** | 손맛은 아날로그에서 나온다 |
| 리셋 | 전체 초기화 | **프레임당 15% 감쇠** | 먹통 구간 제거 |

> **게임 컨셉에 어떻게 쓰는가**: 이 30줄은 "저크 게임"의 진입장벽이 사실상 0이라는 증거다. 즉 **저크를 코어 동사로 쓰는 것 자체는 차별점이 되지 않는다.** 차별점은 그 아날로그 값을 무엇에 연결하느냐뿐이다.

# 4부. 신규 발굴 축 — 아무도 안 쓴 입력

각 항목에 대해 itch.io 자체 검색 엔진(`itch.io/search?q=`)으로 직접 조회했다. 못 찾은 것은 **던진 검색어를 그대로 남겼다.**

## 4-1. ⭐ 연속 곡률 (curvature) — **진짜로 비어 있다. 이번 라운드의 본선 후보**

**정의**: 제스처 인식("원을 그리면 주문 시전")이 아니라, **매 프레임 "지금 커서가 얼마나 급하게, 어느 쪽으로 휘고 있는가"를 스칼라로 읽어 게임 상태에 연속적으로 먹이는 것.**

**검색 결과 — 게임 선행작 0건.**
- `https://itch.io/search?q=draw+circles+with+your+mouse+to` → 전부 **제스처 인식** (Blood Summoner's Despair "draw spell circles", Polygon Protector "Draw Perfect Circles to defend your castle", Demon Chalk, Summon, Circle Painter). **금지목록의 "폐곡선 포획(라소·Qix)"에 해당하는 것도 섞여 있다** (Cinch "Draw circles. Cut everything inside.", VOIDBOUND "Draw circles around your enemies").

  - https://medium.com/@silenttiger/how-to-draw-smooth-mouse-track-b46f9490a92e (원문: *"Mouse trajectory obtained through mousemove events is a discrete coordinate point, not a real trajectory curve"*)
  - https://github.com/sarperavci/human_mouse , https://ijirt.org/publishedpaper/IJIRT183343_PAPER.pdf
- `https://itch.io/search?q=whip+your+mouse` → 마우스 채찍질이 코어인 게임 0건 (전부 게임 내 무기로서의 채찍)

**왜 이게 좋은가 — 2부 전부를 통과하는 유일한 축이다.**

| 관문 | 곡률의 성적 |

| pointer lock 불필요 | **불필요 — 진짜 커서 그대로 사용** |
| 각도 스내핑 | 부호만 쓰면 리스크 0 |
| 무음 30초 가독성 | **상 — 궤적을 화면에 잔상으로 그리면 "휜 정도"가 그대로 보인다** |

**곡률과 이미 나온 45개 주제와의 충돌 검사**: "다트판 던지기", "칸 긋기", "그림자 압정 새총" 등 궤적을 쓰는 것은 있으나, **궤적의 휨 자체가 매 프레임 자원인 것은 없다.**

> **게임 컨셉에 어떻게 쓰는가**: 커서가 지나간 길이 화면에 **물리적 실체**(줄·철사·스파게티·머리카락)로 남고, 그 실체의 **곡률**이 곧 힘·장력·자름·감김을 결정하게 하라. 왼쪽으로 휘면 감기고 오른쪽으로 휘면 풀리는 식으로 **부호**를 반대 효과에 배정하면 하드웨어 리스크가 사라지고 관객이 무음으로도 즉시 읽는다.

## 4-2. 화면 가장자리 압력 — **선행작 0이지만 브라우저가 막는다**

- 검색어: `game "push the cursor off the screen edge" mechanic screen border cursor pressure novel input` → 게임 0건 (전부 커서가 화면 밖으로 나가는 **버그 문의**)

- **2-6에서 확인했듯 화면(스크린) 경계 너머는 측정 불가.** 창(window) 경계 너머는 드래그 중에만 측정 가능.

> **게임 컨셉에 어떻게 쓰는가**: 단독 코어로는 못 쓴다. 곡률 게임의 **보조 양념**(창 밖으로 끌어내면 뭔가 떨어진다)으로만 쓸 수 있고, 그마저 금지목록의 UI 메타와 인접하므로 권장하지 않는다.

## 4-3. 두 클릭 사이 간격의 리듬 — 선행작 0이지만 **무음에서 죽는다**

- `https://itch.io/search?q=double+click+rhythm+timing` → 클릭 **간격**을 측정하는 게임 0건. 나온 것은 전부 "박자에 맞춰 클릭"(Double Kick Heroes 등)으로, 이건 게임이 박자를 주고 플레이어가 따라가는 정반대 구조.

**치명적 결함**: 클릭 간격은 **화면에 아무 것도 안 보인다.** 심사자는 "왜 저기서 실패했지?"를 이해할 수 없다. 무음 30초 규칙 단독 탈락.

> **게임 컨셉에 어떻게 쓰는가**: 쓰지 마라. 굳이 쓴다면 간격을 **화면에 물리적 길이**(늘어나는 고무줄)로 실시간 시각화해야 하는데, 그러면 그건 이미 "홀드 시간 충전"(금지목록)이다.

## 4-4. 마우스 정지 시간의 분포 — 선행작 극소, 무음에서 죽는다

**추가 측정 문제**: 미세 떨림의 진폭은 1~3픽셀 수준인데, 여기에 OS 가속(2-4)과 폴링레이트 차이(2-3)가 그대로 얹히므로 **신호 대 잡음비가 사용자마다 다르다.** 곡률과 달리 각도로 정규화할 수도 없다(작은 이동에서는 각도가 노이즈로 폭발한다).

> **게임 컨셉에 어떻게 쓰는가**: 쓰지 마라. 선행작 포화 + 측정 불안정 이중 탈락.

# 5부. 무음 30초 가독성 판정 — 축별

판정 기준: **소리 없이 30초를 보는 관객이 (a) 플레이어의 손이 무엇을 하고 있는지, (b) 왜 지금 이 결과가 나왔는지를 자막 없이 아는가.**

| 축 | 손동작이 화면에 보이는가 | 인과가 읽히는가 | 판정 |
|---|---|---|---|
| 각속도 | ✅ 커서가 큰 원을 그림 | ✅ 빨리 돌수록 대상이 빨리 돎 | **통과** (그러나 선행작 4건) |
| 저크·흔들기 | ✅ 커서가 격렬히 진동 | ✅ 흔들수록 부서짐 | **통과** (그러나 선행작 8건 + OS 기능) |
| **연속 곡률** | ✅ 궤적을 그리면 휜 정도가 그대로 보임 | ✅ 급하게 꺾을수록 줄이 조여짐 | **통과 ⭐** |
| 선속도 | △ 잔상·트레일로만 | △ "왜 지금 터졌지?" | 조건부 (트레일 필수) |
| 휠 각속도 | ❌ 손가락이 화면 밖 | △ | **탈락** |
| hover dwell | ❌ 커서가 멈춰 있음 | ❌ | **탈락** |
| 정지 시간 | ❌ 화면 정지 | ❌ | **탈락** |
| 클릭 간격 | ❌ 클릭은 점 하나 | ❌ | **탈락** |
| 미세 떨림 | △ 확대해야 보임 | △ | 조건부 |

**여기서 나오는 일반 법칙 (이 조사의 결론)**:

> **무음 30초에서 살아남는 입력은 "커서가 화면에서 실제로 넓게 움직이는" 것뿐이다.**
> 각속도·저크·곡률이 통과하는 이유는 전부 같다 — 셋 다 커서가 크게, 빠르게, 계속 움직인다.
> dwell·정지·클릭간격·휠이 탈락하는 이유도 전부 같다 — 넷 다 커서가 화면에서 안 움직인다.

그리고 이 법칙은 1~3차 교훈 #1("참신함 점수와 손의 재미가 역상관한다")의 **물리적 원인**을 설명한다. 영리한 규칙일수록 플레이어가 멈춰서 생각하고, 멈추면 커서가 안 움직이고, 커서가 안 움직이면 화면이 죽는다. **역상관의 원인은 "규칙의 영리함"이 아니라 "커서 이동량"이다.** 커서를 계속 크게 움직이게 만드는 영리한 규칙이라면 역상관은 깨진다.

# 6부. 주제 선정에 주는 최종 지시

1. **5축 중 4축(각속도·휠·저크·dwell)을 코어 동사로 쓰는 안은 전부 폐기하라.** URL로 선행작을 확보했고, 그 중 둘은 2026년 6월 출품작이다.
2. **선속도는 자동 캘리브레이션을 붙이는 조건에서만 살려라.** 안 붙이면 심사자 PC에서 다른 게임이 된다.
3. **연속 곡률 하나로 좁혀라.** 선행작 0, 스케일 불변, pointer lock 불필요, 무음 가독성 상 — 이 네 관문을 동시에 통과하는 유일한 축이다.
4. **곡률을 쓸 때는 "곡률의 부호"를 반대되는 두 효과에 배정하라.** 부호는 OS 가속·DPI·각도 스내핑에 완전 불변이고, 관객에게도 "왼쪽으로 감았다 / 오른쪽으로 풀었다"로 즉시 읽힌다.
5. **판정 로직은 mouse-shake.js를 각도 합에서 연속 게이지로 개조해 재사용하라.** 300ms 창 + 프레임당 15% 감쇠 + `pointermove` × `getCoalescedEvents()`.
6. **pointer lock을 쓰는 어떤 안도 즉시 탈락시켜라.** 심사 영상에 "Press Esc to show your cursor" 시스템 버블이 박힌다.

# 조사 한계 (확인하지 못한 것)

정직하게 적는다.

1. **실측을 하지 않았다.** 이 문서의 브라우저 관련 판정은 전부 MDN·W3C 스펙·Chrome 공식 블로그·caniuse **문헌 근거**이지, 이 PC에서 코드를 돌려 측정한 값이 아니다. 특히 다음은 반드시 실기로 확인해야 한다.
   - `getCoalescedEvents()`가 실제로 몇 개의 표본을 반환하는지 (문헌상 폴링레이트/주사율 비율이지만 브라우저 구현 차이가 있을 수 있음)
   - 화면 경계에서 정말로 이벤트가 멈추는지 (2-6은 `movementX` 정의식에서 연역한 **추정**)
   - OS 가속이 실제로 속도값을 몇 배 왜곡하는지 (2-5의 "2~4배"는 **추정**이며 요인 세 개의 곱으로 추산했다)
2. **"Press Esc" 버블의 정확한 렌더링 위치·지속시간·화면 점유 면적을 확인하지 못했다.** Chromium 이슈와 Deno 이슈에서 존재는 확인했으나, 최신 Chrome에서 몇 초 뒤 사라지는지는 미확인. **버블이 2초 만에 사라진다면 pointer lock 금지 판정이 완화될 수 있다.**
3. **검색 예산이 중간에 소진됐다.** WebSearch 200회 한도 초과, Exa 크레딧 초과, Firecrawl 무료 티어 한도 초과. 이후는 itch.io 자체 검색 엔진과 MDN/caniuse 직접 fetch만으로 진행했다. **따라서 Steam·Newgrounds·게임잼 아카이브(Ludum Dare, GMTK) 사이트 내 검색은 충분히 못 했다.** 특히 다음은 미확인:
   - Steam에서 마우스 회전/흔들기를 코어로 쓰는 상용작
   - Ludum Dare / GMTK Jam 아카이브의 곡률 기반 작품
   - Newgrounds Flash 시대의 흔들기 게임 계보
4. **itch.io 검색 결과가 잘려서 나왔다.** 각 쿼리마다 "1000+ projects" 중 첫 페이지만 봤다. 곡률 선행작 0건 판정은 **첫 페이지 기준**이며, 깊은 페이지에 존재할 가능성을 배제하지 못한다.
5. **`mouse-shake.js`가 3차 리서치가 말한 "포럼의 30줄"과 동일한 것인지 확정하지 못했다.** ReactFX 이슈 #52(https://github.com/TomasMikula/ReactFX/issues/52)는 실제로 확인해보니 **알고리즘도 코드도 없는 단순 질문 글**이었다. macOS 흔들기 판정의 실제 알고리즘(총 경로장 대 순변위 비율 + 시간창 내 급반전 횟수)은 검색 요약문에만 등장했고 **Apple 공식 문서 원문을 찾지 못했다.**
6. **하드웨어 각도 스내핑의 시장 보급률을 확인하지 못했다.** Akko 제조사 블로그 1건에만 의존했고, 이는 이해관계자 소스다.
7. **선행작을 직접 플레이해보지 않았다.** Attack on the Town, Interdimensional Spinning Championship, Hover Defense, MX Master Runner 모두 **페이지 설명문만 읽었다.** 실제 손맛과 판정 알고리즘은 다를 수 있다. 특히 Attack on the Town이 진짜 저크를 판정하는지, 단순 이동거리 누적인지는 미확인.
